# A daily Lighthouse chore — Spec

Status: v0.5 (2026-10-25: the day's findings a run produces are still the agent's `summarize`, but the 14-day trend, the first page's `a11y` and `security` views and the finished `lighthouse` summary are the store's own computation from the computer's raw result, not the agent's; item `summaries-move-to-store`, [last-local-state.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/last-local-state.md) section 3.4). Previously v0.4, backlog id daily-lighthouse. On for this repo since 2026-10-06 (`lighthouse: { enabled: true, pages: ["/"] }` in the project's settings, on `https://staging.retaskable.com`). Trimmed for the agent: when the chore is due, the trend and views, the switch and the screens are the store's, the hub's or the app's. Section 2's **[Decided]** lines are what the human asked for; the **[Proposal]** lines fill the gaps and are the human's call. Adds a scheduled chore to the agent's chores ([agent.md](agent.md) section 6.7).

Theme: Orchestration

Kind: new

## 1. What it is

A Lighthouse run on staging on 2026-10-04 found a slow first load on phones and a few clean-ups ([expo-web-speed.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/expo-web-speed.md), [lighthouse-tidy.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/lighthouse-tidy.md)). Nobody would have noticed without running it by hand. This step has the agent run Lighthouse on the project's staging site once a day, and turn anything new it finds into a spec draft in the Inbox, the same way the `specs` chore does.

**What it costs.** Lighthouse itself is free: it is a command run on the agent's own machine, about a minute of CPU for each page and form factor, with no model involved. A model runs only when there is something new to write up: one spec-draft session on the chore tier (Sonnet, section 7.1 of agent.md), typically well under a dollar. A day with nothing new costs nothing.

## 2. Decisions

- **[Decided]** Lighthouse runs as a daily chore, if that's possible and not too costly (it is; see section 1).
- **[Decided]** What it finds becomes specs to fix it.
- **[Proposal]** **What is measured**: each page in the project's `lighthouse.pages` (paths, default `["/"]`), on the staging deploy's `url` ([environments.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/environments.md), `deploy.staging.url`), with Lighthouse's mobile and desktop presets. No staging url: the chore doesn't run, and says why. For this repo: `["/"]` (the app is served from the root).
- **[Proposal]** **When**: the agent asks the store whether the chore is due (store op `jobs_due`) and runs it when the store says so, with a lane free and usage allowing. The store decides the day, the hour (`lighthouse.hour`, default 06:00, in the project's time zone), whether the project is paused and whether today's result is already in; a store that can't be reached means not due (the agent fails closed). The computer holds no schedule of its own. It doesn't take a lane from roadmap work, and it doesn't count as the one chore in flight: it holds no lane, since it builds nothing.
- **[Proposal]** **One run a day per repo**, not per agent: it first takes the store's chore lock `lighthouse-<yyyy-mm-dd>` (store op `chore_lock`, [backlog.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/backlog.md) section 15); if another agent has it, this one skips the day.
- **[Proposal]** **What counts as a finding**: a failing audit (score under 0.9, not informative, not manual, not "not applicable"), or a category score under `lighthouse.minScore` (default 90). Findings about other origins' scripts (any URL not on the staging host) are dropped: we can't fix them. So are `is-crawlable` and the SEO score, which staging fails on purpose (section 5).
- **[Proposal]** **New only**: each finding has a key (`<page> <preset> <audit id>`, or `<page> <preset> score <category>`). A finding whose key is known isn't written up again while its draft is open, merged, or was rejected less than 30 days ago. So the same 401 isn't a new draft every morning, and a rejected one comes back once a month at most. The keys, each with the id of the draft it went into, are kept in the store (written by the computer that made the draft); the agent asks the store for them and for each draft's status, so a second computer finds the draft open, merged or rejected when it was, and the 30 days count from the store's time.
- **[Proposal]** **One draft per day at most**, holding all of that day's new findings, so related ones land in one spec. It is a spec draft like any other (agent.md section 6.5): the drafter writes a new spec, or extends one, and it goes to the Inbox for approval. The `specs` chore's limit of 2 open drafts applies to these too, counted by the store across the team's computers (the store's open chore drafts, as `chore_next` counts them).
- **[Proposal]** **Nothing new**: no session, nothing in the Inbox.
- **[Proposal]** **Lighthouse and Chrome**: run with `npx --yes lighthouse@<pinned major>` and the machine's Chrome or Chromium (`CHROME_PATH` if set, else Lighthouse's own lookup). If none is found, the chore says once in the Inbox "Lighthouse needs Chrome on this computer" and stops trying until the agent restarts.
- **[Proposal]** `lighthouse: { enabled, pages, hour, minScore }` is a project setting kept in the store, off by default ([project-settings-on-server.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/project-settings-on-server.md)); the switch and the pages are on the Chores screen of the Expo app. The agent reads the setting; it keeps no copy of its own.

## 3. Behavior

- **Plain code runs it** (`agent/src/lighthouse.ts`): for each page and preset, `npx --yes lighthouse@12 <url> --output=json --output-path=<tmp> --chrome-flags=--headless=new --quiet` (`--preset=desktop` for desktop), with a 3-minute timeout each, outside any session, as the orchestrator's own command (like the checks). It reads the JSON into the run's raw result: the four category scores, LCP, FCP, TBT, CLS, and the findings as above, each with its title, display value and up to 3 offending items (URL or selector). The full reports are kept in `.retaskable/projects/<id>/lighthouse/<date>/` only until they are uploaded. Each day's raw report moves to the backlog store instead ([last-local-state.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/last-local-state.md) section 3.9): uploaded once the run finishes (each page and preset's file) and the local file deleted as soon as the store confirms it, kept there for 14 days, read back from there after a restart (`savedRuns`/`latestSaved` in `lighthouseChore.ts`), and read by any project member, so one computer's Lighthouse history isn't lost when it's offline or its disk is pruned.
- **When it runs** (`agent/src/orchestrator.ts`, where chores are picked): beside the rotation, not one of `tidy → tests → bugs → specs` and not moving the rotation. The orchestrator's `step` calls `maybeRun` after the items advance, so never while paused; it needs the store's `jobs_due` (`askDue`) to name `lighthouse`, `Orchestrator.canPlan()`, `Orchestrator.laneFree()` (any lane, the chore lane included) and no run already under way. With the shared backlog's chore locks, `ChoreLocks.take(lighthouseLock(day))`; `{ by }` ends the day with the note "<login>'s agent runs Lighthouse today", and a store that can't be reached takes nothing, so nothing runs and a later tick asks again; then `drop` lets go of the day before's lock. Each page and preset runs in turn (`<staging url><page>`), its report in `lighthouse/<day>/`, then reports older than 14 days are pruned. A run's failures are counted in its note ("1 of 2 runs failed: …").
- **The write-up**: new findings render `prompts/lighthouse.md`: the pages, scores, each new finding with its items, the repo's specs index, and the instruction to write one spec (or extend an existing one) that says what's wrong, with the numbers, what to change, and how to check it's fixed with Lighthouse. That starts a spec draft (section 6.5), tagged `[Lighthouse]` and noting which finding keys it covers; each key is recorded with that draft's id in the store. `newFindings` keeps each key once and only if `isNewFinding`. With fewer than 2 open chore drafts (the store's count), `lighthouseRequest` starts the draft; past the limit nothing is recorded, so the findings come back the next day, and the note says so. The drafter runs a `[Lighthouse]` draft on the chore tier (`choreModel`), others on the top tier as before.
- (`agent/src/lighthouse.ts`, tested in `lighthouse.test.ts`): `lighthouseTarget(cfg)` (null when off, `{ note }` without a staging url), `runLighthouse` (npx through the shell on Windows, args quoted; Chrome missing is told apart by Lighthouse's own words), `summarize` (an audit's items are its `url`, `source.url` or `node.selector`; a finding whose named URLs are all on other origins is dropped; an informative audit that names a `High` severity problem is a finding all the same, its items the problems in its own words (`severeItems`: the security headers `csp-xss`, `has-hsts`, `origin-isolation` and `trusted-types-xss` always score 1 and report what is missing this way; the human: "we should automatically make chores to fix it"); with `staging`, which the chore always passes, `is-crawlable` and the `seo` score aren't findings, though the scores keep it), `isNewFinding` (a discarded draft's 30 days count from its last timeline entry; a failed or missing draft's findings are new again), `lighthouseLock(day)`, `reportFile`/`pruneReports`.
- **What goes up**: the run's raw result is sent as a `fact_set` on `lighthouse_raw`: just that run's per-page, per-preset scores, Core Web Vitals and findings, plus `newFindings`, `drafted?`, `note?` and each security check's `fixQueued` (decided here, from this computer's own knowledge of open `[Lighthouse]` drafts). The store folds it into the 14-day trend and the first page's `a11y` and `security` views (`shared/factSummaries.ts`'s `lighthouseSummary`) and answers the finished `lighthouse` summary in the same call. The agent builds no day list, no `a11y` view and no security view; the page's `State.lighthouse` is gone, and the day's "already run" check is the store's. Chrome missing: the chore puts the line "Lighthouse needs Chrome on this computer. Install Google Chrome, then restart Retaskable, and the daily check runs again." at the top of the Inbox, and the project isn't tried again until the agent restarts (kept in memory only).
- **The Chores screen and the Agents line** (the Lighthouse section's switch, pages field, Save, and the "Lighthouse at 06:12" line) are the Expo app's. A switch or pages change is a project setting the owner saves through the hub and the store ([cloud.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/cloud.md) section 6.1, [project-settings-on-server.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/project-settings-on-server.md) section 3.6); the agent never takes one on its own port. Pages are paths of letters, digits and `._~-/` only, at most 20, checked where they are saved.
- **Tests**: the findings from a saved Lighthouse JSON (failing audits, other-origin findings dropped, scores); the new-only rule (known keys, open, merged and rejected drafts, the 30 days); a due day, a day the store says is not due, the store lock taken by another agent; no Chrome.
- **Spec words** (done in slice 2): [agent.md](agent.md) section 6.7 has the Lighthouse chore before the main sync; [environments.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/environments.md) says it uses the staging url.

**The latest saved day written up again** (2026-10-18, the human: "do the auto chore creation"). A rule added after a day's run (the security headers' `High` problems, `severeItems`) finds things that run didn't, which would otherwise wait for the next day. So once per project while the agent runs, and not while it's paused or over its limit, `maybeRun` reads the newest saved day's reports again (`latestSaved`, every page and preset) with today's rules, and writes up the findings that aren't known (`newFindings`), exactly as a run does: one `[Lighthouse]` draft, only under the limit of open chore drafts, its keys recorded with the draft. Nothing runs, and nothing happens when every finding is known.

## 4. Acceptance

- With the setting on and a staging url, the agent runs Lighthouse when the store says it is due, and `.retaskable/projects/<id>/lighthouse/<date>/` has a report per page and preset until it is uploaded.
- On a day with new findings, one spec draft appears in the Inbox naming them, with their scores and items. The next day, with the same findings and that draft still open, there is no new draft.
- With two agents linked to the same repo, only one runs it that day.
- With no Chrome on the machine, the Inbox says so once.
- The store's `lighthouse` row, not the agent, holds the 14-day trend and the first page's `a11y` and `security` views; a fresh `fact_set` on `lighthouse_raw` with a new day's result extends the trend without the agent sending the days before it.
- `npm test` passes.

## 5. Staging's own no-index

Built (item `seo-blocked-staging`).

The 2026-10-06 run on `/` scored **SEO 63** on mobile and on desktop. Both come from "Page is blocked from indexing": staging's `robots.txt` is `Disallow: /`, on purpose ([lighthouse-tidy.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/lighthouse-tidy.md) section 2). Staging should never be indexed, so this can't be fixed from this project without reversing that decision. Writing it up each time it's new only repeats a known, intended state.

Decisions:

- **[Proposal]** A finding the environment blocks on purpose isn't written up. On the staging host, `is-crawlable` and the SEO score are dropped from the findings, the way other-origin findings are dropped. The saved reports keep them.
- **[Proposal]** Before that rule goes in, check the saved report for any other failing SEO audit. If the report shows another failing SEO audit, that one stays a finding, and its write-up names it. Checked: in the 2026-10-06 reports (mobile and desktop) every other SEO audit scores 1; `is-crawlable` alone has weight 4.04 of the category's 11.04, which is the 63.
- **[Proposal]** The chore runs no SEO check on production (`lighthouse.pages` runs on staging only). Adding a production run is a separate decision; this spec doesn't add it.

Behavior: `summarize` in `agent/src/lighthouse.ts` takes `staging`; with it, a failing `is-crawlable` and an `seo` score under `minScore` aren't findings, as other-origin findings aren't. Any other failing SEO audit still is. The scores keep the SEO score, the saved report is untouched, and the keys are unchanged. The chore (`lighthouseChore.ts`) passes `staging: true`, since it runs only on the staging url. Tests: in `lighthouse.test.ts`, a staging run with `is-crawlable` failing gives no finding and keeps the SEO score; with another failing SEO audit it gives that one; the same report without `staging` is unchanged. In `lighthouseChore.test.ts`, a day whose only failure is staging's no-index starts no draft.

Acceptance:

- On the next daily run on staging, no `is-crawlable` or `score seo` finding is written up, and the Inbox has no draft for them.
- A run with another failing SEO audit still writes that audit up.
- The saved report in `lighthouse/<day>/` still lists the SEO score and `is-crawlable`.
- `npm test` passes.
