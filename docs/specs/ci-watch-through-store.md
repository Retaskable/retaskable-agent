## 1. What it is

The CI watcher looks at a project's open pull requests, the ones with no board item as well, and gets a red, conflicted or stuck one looked at. The computer reads GitHub, sends the raw facts of each head to the store (`ci_result`) and runs the one instruction that comes back. It keeps no verdict, attempt count or "tried" memory of its own: the store decides the condition, counts attempts and says what to do next. The old `ci_watch_detect`, `ci_watch_attempt`, `ci_watch_verdict` and `ci_watch_needs_person` ops are gone from the store (`ci_release` stays), so no computer calls them. A computer that can't reach the store watches nothing (fail closed).

Beside that, this piece copies four rules about being gentle with GitHub, the push rules for another person's or the user's own pull request, the Fix button's agent side, and Run now for the daily chores through the store.

## 2. Decisions

- **[Decided]** The store's `ci_result` decides the verdicts. The computer keeps only what is a fact: when it first saw a head pending (`pendingSince`) and which fixes are running here.
- **[Decided]** A watch reads its checks at most every 45 seconds, not every 15. A failed read waits its minute for real: the orchestrator honours the run's `resumeAfter`.
- **[Decided]** After a GitHub "rate limit exceeded" answer, the computer makes no `gh` call for 5 minutes, then tries one. A failed call is not remembered as no access: only a `404` is, and that is the store's.
- **[Decided]** The signed-in login is kept only when read successfully and not empty; a failed or empty read counts as "not the own account" for that pass and is read again on the next.
- **[Decided]** A merge of main into a conflicted pull request is tried again only after `origin/main` has moved.
- **[Decided]** The Fix button on another person's red pull request waits for the watcher's first attempt, unless the watcher may not push there.
- **[Decided]** Run now goes through the store: the store takes the button's request (`job_run`) and hands the computer the chore as a task; the computer has no `chore_run` handler.
- **[Proposal]** The Rust names: `Client::ci_result` in `src/backlog/`, `src/ci_watch.rs` keeping the reads (`read_checks`, `red_entry`) and losing `decide`, the rate-limit gate in `src/gh_limit.rs` (called from `ci_watch::gh_out`), the pull-request watcher in `src/orchestrator/ci_pulls.rs`.

## 3. Behavior, in build order

1. **`ci_result`** (`src/backlog/`, an agent op, tests against the fake store that `src/backlog/runs/tests.rs` uses). Arguments `{ pr, sha, title, branch, mayPush, button?, conflicting, checks: { state: pass | fail | pending, what, logs, endedAt? }, pendingSince?, redNow?, baseHead?, did? }`: `what` the failed checks named with log excerpts, `logs` their logs (at most 10, each cut to 4000), `redNow` how many pull requests failed in this pass, `baseHead` the fetched base's sha (sent only for a conflicted head the computer may push to), `did` what it ran last: `{ kind: "judge", verdict | null, report }`, `{ kind: "fix" | "mergeMain", pushed }` or `{ kind: "rerun", rerun, ok }`. It answers `{ ok, refused?, condition, notTheChange, found, attempts, needsPerson, next, logs, bells }`. The computer writes `logs` with `log_add` kind `ci` and shows `bells` as notifications, word for word. `next` is null or one of `{ do: "judge" }`, `{ do: "judge", report: true }`, `{ do: "fix" }`, `{ do: "mergeMain" }`, `{ do: "rerun", rerun: "force" | "stuck", hung }`.
2. **The pass** (`src/orchestrator/ci_pulls.rs`): on the computer the store names as the project's runner, at most every 2 minutes, read the open pull requests (a `retaskable/` branch that is a board item's is skipped), and for each head send `ci_result`, run `next` and send again with `did`, at most 4 steps per head per pass. The instructions: `judge` runs one read-only session on the failing logs that returns a verdict (`change`, `expectation`, `not-change`); with `report: true` it counts no attempt and pushes nothing. `fix` runs a session in a throwaway worktree on the branch, commits and pushes plainly. `mergeMain` merges `origin/main` in a throwaway worktree and pushes plainly (never a rebase or a force-push). `rerun` with `force` restarts the failed checks, with `stuck` frees the head's leases (`ci_release`) and starts the check again. A pull request the computer pushes to itself is reported as `did.pushed`.
3. **Who may be pushed to** (`may_push_to`, pure): a `retaskable/` branch, a `claude/` branch, a pull request opened by the account `gh` is signed in as (compared without case; never on GitLab), or an author on the project's `ciWatchAllow` list. The login comes from `gh api user` and is kept only after a successful non-empty read; after a failed read the next pass reads it again. For any other pull request the watcher only reports: the store answers `judge` with `report: true` once per head.
4. **Conflicts:** `baseHead` is the sha of `origin/main` after a fetch, sent for a conflicted head the computer may push to. The store answers `mergeMain` once per head until `baseHead` moves; the computer sends no retry of its own. A merge that itself conflicts pushes nothing and goes back as `did: { kind: "mergeMain", pushed: false }`.
5. **The Fix button** (`ci_fix { pr, sha }` command in `src/commands.rs`): refuse unless this computer is the runner, the pull request is open at exactly that head, and no fix for it at that head is already running ("A fix is already running"); then send `ci_result` with `button: true`. The store refuses unless its record is red at that head, does not need a person and the checks fail now; a refusal's `refused` goes back as the command's answer. Otherwise run the instructions once, without waiting, and answer "Trying a fix for pull request #N.". The `ciWatchAllow` rule does not apply; the store's limit of 3 attempts does. The app shows the button only after one attempt, or at once for a pull request the watcher may not push to (the store's and the app's side).
6. **The `watch` run's reads** (`src/orchestrator/watch_run/`): every 45 seconds, not 15. A `gh` error still waits a minute, and the run's `resumeAfter` is honoured. The five-errors-in-a-row and pending-past-`ciMaxMinutes` ends are as [pieces.md](pieces.md) says. What the checks mean is still decided in `ci_watch::decide`, for a piece's run; the pull-request watcher takes its verdicts from the store.
7. **The rate-limit gate** (`src/gh_limit.rs`, checked in `ci_watch::gh_out` and the other `gh` callers that go through `host_call`): when a `gh` call's output says "rate limit exceeded", record the time; until 5 minutes have passed every `gh` call fails at once with an error naming the wait and starts no process; then one call is let through, and if it too is limited the 5 minutes start over. The watch run treats such an error as a `gh` error that waits.
8. **Run now through the store** (item `chore-run-now`'s way): the app's button reaches the store's `job_run { kind }`; the store applies its own refusals (paused, one running, one in the last 10 minutes, nothing configured) and gives the computer the chore as a task at its next `health`. The computer runs the same function as the scheduled run, told it's by hand, and a refusal only it can know (no Chrome, no token) comes back with the task's end as `refused` with words; a refusal is stored as `{ key, day }`, is ignored on a later day and is cleared by the kind's next `job_run`. The agent adds no `chore_run` handler and keeps no in-memory 10-minute gap. A computer that sends no `can` is never handed the task.
9. **Tests:** `ci_result`'s facts and the instructions run, against the fake store (each condition; the 4-step cap; a stale head; report-only; `mayPush` for each rule; the login retried after a failed read; a conflict tried again only after `baseHead` moves; the button's refusals and its one run); the gate (limited, waiting, one let through, limited again); a watch's 45-second reads and a `resumeAfter` honoured; Run now's task refused with words.

## 4. Acceptance

- No `ci_watch_*` op is called; every verdict, attempt count and "tried" memory is the store's.
- A pull request nobody owns on the board is judged, reported and, where allowed, fixed, with no condition held on the computer.
- No watch reads more often than every 45 seconds; after a "rate limit exceeded" no `gh` process starts for 5 minutes, and a rate-limited answer is never remembered as no access.
- A failed login read is read again on the next pass.
- A conflicting merge of main is not tried again on the same head until `origin/main` moves.
- A Fix press is refused for a stale head, a closed or unwatched pull request, a non-runner or a fix already running, and runs once otherwise.
- Run now starts only from a store task; there is no `chore_run` handler.
- `cargo fmt`, `cargo clippy --all-targets -- -D warnings` and `cargo test` pass.
