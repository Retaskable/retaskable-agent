## 1. What it is

The CI watcher looks at a project's open pull requests, the ones with no board item as well, and gets a red, conflicted or stuck one looked at. The computer reads GitHub, sends the raw facts of each head to the store (`ci_result`) and runs the one instruction that comes back. It keeps no verdict, attempt count or "tried" memory of its own: the store decides the condition, counts attempts and says what to do next. The old `ci_watch_detect`, `ci_watch_attempt`, `ci_watch_verdict` and `ci_watch_needs_person` ops are gone from the store (`ci_release` stays), so no computer calls them. A computer that can't reach the store watches nothing (fail closed).

Beside that, this piece copies four rules about being gentle with GitHub, the push rules for another person's or the user's own pull request, the Fix button's agent side, and Run now for the daily chores through the store.

## 2. Decisions

- **[Decided]** The store's `ci_result` decides the verdicts. The computer keeps only what is a fact: when it first saw a head pending (`pendingSince`) and which fixes are running here.
- **[Decided]** A watch reads its checks at most every 45 seconds, not every 15. A failed read waits its minute for real: the orchestrator honours the run's `resumeAfter`.
- **[Decided]** After a GitHub "rate limit exceeded" answer, the computer makes no `gh` call for 5 minutes, then tries one. A failed call is not remembered as no access: only a `404` is, and that is the store's.
- **[Decided]** The signed-in login is kept only when read successfully and not empty; a failed or empty read counts as "not the own account" for that pass and is read again on the next.
- **[Decided]** A merge of main into a conflicted pull request is tried again only after `origin/main` has moved.
- **[Decided]** The Fix button on another person's red pull request waits for the watcher's first attempt, unless the watcher may not push there.
- **[Decided]** Run now goes through the store: the store takes the button's request (`job_run`) and hands the computer the chore as a task; the computer has no `chore_run` handler.
- **[Decided]** Only the computer the store names as the project's rollout runner watches (the TS agent's `rolloutRun.runner`): a project with no store rollout has no watcher. The rollout loop keeps a per-project flag (`rollout::Runners`), true while the store's last `rollout_poll` answer carried an epoch.
- **[Decided]** The checks, the open-pull-request list and the rerun sit behind a small host trait (`ci_pass::CiHost`: `open_pulls`, `checks`, `rerun`), so GitLab slots in as a second implementation chosen in `ci_pass::host_for` (`glab`, its pipelines for the checks, a pipeline retry for the rerun) with nothing else changing.
- **[Proposal]** The Rust names: `Client::ci_result` in `src/backlog/`, `src/ci_watch.rs` keeping the reads (`read_checks`, `red_entry`) and losing `decide`, the rate-limit gate in `src/gh_limit.rs` (called from `ci_watch::gh_out`), the pass in `src/ci_pass.rs` with the host in `src/ci_pass/host.rs` and its schedule in `src/orchestrator/driver/ci_pass.rs`.

## 3. Behavior, in build order

1. **`ci_result`** (`src/backlog/`, an agent op, tests against the fake store that `src/backlog/runs/tests.rs` uses). Arguments `{ pr, sha, title, branch, mayPush, button?, conflicting, checks: { state: pass | fail | pending, what, logs, endedAt? }, pendingSince?, redNow?, baseHead?, did? }`: `what` the failed checks named with log excerpts, `logs` their logs (at most 10, each cut to 4000), `redNow` how many pull requests failed in this pass, `baseHead` the fetched base's sha (sent only for a conflicted head the computer may push to), `did` what it ran last: `{ kind: "judge", verdict | null, report }`, `{ kind: "fix" | "mergeMain", pushed }` or `{ kind: "rerun", rerun, ok }`. It answers `{ ok, refused?, condition, notTheChange, found, attempts, needsPerson, next, logs, bells }`. The computer writes `logs` with `log_add` kind `ci` and shows `bells` as notifications, word for word. `next` is null or one of `{ do: "judge" }`, `{ do: "judge", report: true }`, `{ do: "fix" }`, `{ do: "mergeMain" }`, `{ do: "rerun", rerun: "force" | "stuck", hung }`.
2. **The pass** (`src/ci_pass.rs`): on the computer the store names as the project's runner, at most every 2 minutes, read the open pull requests (a `retaskable/` branch that is a board item's is skipped), and for each head send `ci_result`, run `next` and send again with `did`, at most 4 steps per head per pass. The instructions: `judge` runs one read-only session on the failing logs that returns a verdict (`change`, `expectation`, `not-change`); with `report: true` it counts no attempt and pushes nothing. `fix` runs a session in a throwaway worktree on the branch, commits and pushes plainly. `mergeMain` merges `origin/main` in a throwaway worktree and pushes plainly (never a rebase or a force-push). `rerun` with `force` restarts the failed checks, with `stuck` frees the head's leases (`ci_release`) and starts the check again. A pull request the computer pushes to itself is reported as `did.pushed`.
3. **Who may be pushed to** (`may_push_to`, pure): a `retaskable/` branch, a `claude/` branch, a pull request opened by the account `gh` is signed in as (compared without case; never on GitLab), or an author on the project's `ciWatchAllow` list. The login comes from `gh api user` and is kept only after a successful non-empty read; after a failed read the next pass reads it again. For any other pull request the watcher only reports: the store answers `judge` with `report: true` once per head.
4. **Conflicts:** `baseHead` is the sha of `origin/main` after a fetch, sent for a conflicted head the computer may push to. The store answers `mergeMain` once per head until `baseHead` moves; the computer sends no retry of its own. A merge that itself conflicts pushes nothing and goes back as `did: { kind: "mergeMain", pushed: false }`.
5. **The Fix button** (`fix_requested { pr, sha }` intent row, the TS `ci_fix`: `src/intents/fix_requested.rs`, `src/ci_pass/press.rs`, `src/orchestrator/driver/fix_requests.rs`; the row's rules are in [agent/06.6-ask-claude.md](agent/06.6-ask-claude.md)). `Pass::press` refuses, in this order and in these words: a fix already under way on that head in `Fixing` (`A fix is already running for pull request #N.`, before anything else), this computer not the runner (`This computer isn't the one watching this project's pull requests.`), the pull request not open at exactly that head (`Pull request #N is no longer open at that commit.`; the open pull requests are listed afresh); then, for a pull request in this repository, it sends `ci_result` with `button: true`, `redNow: 0` and `mayPush` true. The store refuses unless its record is red at that head, does not need a person and the checks fail now; its `refused` is the answer, `Pull request #N isn't one the watcher can fix.` when it gives none. Otherwise `press` answers "Trying a fix for pull request #N." at once and `Press::begin` carries the instructions out in a background task, holding the head until it ends, its failures logged; the store logs the entries with `fixButton: true`. The `ciWatchAllow` rule does not apply; the store's limit of 3 attempts does. The app shows the button only after one attempt, or at once for a pull request the watcher may not push to (the store's and the app's side). A press whose store call, list or read of the checks breaks ends `failed`, the rest `refused`.

**A fork's pull request is refused up front** (the fork rule above wins over TS, which sends `mayPush: true` for every press): right after the open-at-that-head check, before the checks are read and before the store is asked, with `Pull request #N comes from a fork, so this computer won't push a fix to it.` No attempt is counted and nothing runs.
6. **The `watch` run's reads** (`src/orchestrator/watch_run/`): every 45 seconds, not 15. A `gh` error still waits a minute, and the run's `resumeAfter` is honoured. The five-errors-in-a-row and pending-past-`ciMaxMinutes` ends are as [pieces.md](pieces.md) says. What the checks mean is still decided in `ci_watch::decide`, for a piece's run; the pull-request watcher takes its verdicts from the store.
7. **The rate-limit gate** (`src/gh_limit.rs`, checked in `ci_watch::gh_out` and the other `gh` callers that go through `host_call`): when a `gh` call's output says "rate limit exceeded", record the time; until 5 minutes have passed every `gh` call fails at once with an error naming the wait and starts no process; then one call is let through, and if it too is limited the 5 minutes start over. The watch run treats such an error as a `gh` error that waits.
8. **Run now through the store** (item `chore-run-now`'s way): the app's button reaches the store's `job_run { kind }`; the store applies its own refusals (paused, one running, one in the last 10 minutes, nothing configured) and gives the computer the chore as a task at its next `health`. The computer runs the same function as the scheduled run, told it's by hand, and a refusal only it can know (no Chrome, no token) comes back with the task's end as `refused` with words; a refusal is stored as `{ key, day }`, is ignored on a later day and is cleared by the kind's next `job_run`. The agent adds no `chore_run` handler and keeps no in-memory 10-minute gap. A computer that sends no `can` is never handed the task.
9. **Tests:** `ci_result`'s facts and the instructions run, against the fake store (each condition; the 4-step cap; a stale head; report-only; `mayPush` for each rule; the login retried after a failed read; a conflict tried again only after `baseHead` moves; the button's refusals and its one run); the gate (limited, waiting, one let through, limited again); a watch's 45-second reads and a `resumeAfter` honoured; Run now's task refused with words.

## 4. Acceptance

- No `ci_watch_*` op is called; every verdict, attempt count and "tried" memory is the store's.
- A pull request nobody owns on the board is judged, reported and, where allowed, fixed, with no condition held on the computer.
- No watch reads more often than every 45 seconds; after a "rate limit exceeded" no `gh` process starts for 5 minutes, and a rate-limited answer is never remembered as no access.
- A failed login read is read again on the next pass.
- A conflicting merge of main is not tried again on the same head until `origin/main` moves.
- A Fix press is refused for a stale head, a closed or unwatched pull request, a non-runner or a fix already running, and runs once otherwise.
- Run now starts only from a store task; there is no `chore_run` handler.
- `cargo fmt`, `cargo clippy --all-targets -- -D warnings` and `cargo test` pass.

## 5. What is built

Built, in this order:

1. `ci_result` and `log_add` (`src/backlog/ci_result.rs`), the commit checks and the failure note (`src/ci_checks.rs`), the open pull requests and `may_push_to` (`src/ci_pulls.rs`), `ciWatchAllow`, and the read-only judge session (`src/ci_judge.rs`).
2. **The pass, report only** (`src/ci_pass.rs`, `src/ci_pass/host.rs`, `src/orchestrator/driver/ci_pass.rs`, `src/orchestrator/ci_watch_host.rs`). On the rollout runner, at most every 2 minutes, from the project loop in `claim` mode, with the backlog linked and the repo's id known: list the open pull requests (a `retaskable/` branch that is a board item's is skipped; one whose checks can't be read is skipped), send each head's facts with `mayPush` always false, write the store's `logs` with `log_add` kind `ci`, show its `bells`, and run `next` up to 4 times per head: `judge` (the scouts' tier, `budget.scoutUsd`, the project's sandbox setting, the base checkout) and `rerun` (`force` or `stuck`: `gh run cancel` for a hung head's pending runs, then `gh run rerun <id> --failed` for the runs behind its cancelled checks only, as the TS agent's `rerunCancelledRuns` does; with `requireCi` and `ciWhenReady`, the `ci-ready` label taken off and put back instead). Each answer goes back as `did`.

Suspected TS bug, copied faithfully: a plain failed run is never rerun, so a `force` rerun of an ordinary red answers `ok: false`. It is to be fixed in Retaskable.com first and then copied here.

3. **`mayPush`, `baseHead` and `mergeMain`** (`src/ci_pass.rs`, `src/ci_pass/host.rs`, `src/merge_update.rs`). `mayPush` is `may_push_to` with the signed-in login (`gh api user --jq .login`, read on a blocking thread only for a pull request that lists an author, kept in `ci_pulls::LoginCache` once non-empty, so a failed read is no own account for that pass and is read again) and the project's `ciWatchAllow`. `baseHead` is sent only for a conflicting head with `mayPush`: the base fetched fresh, then `git rev-parse origin/<base>`. `mergeMain` is `merge_update::update_from_base` in the throwaway worktree `<worktreesDir>/merge-ci-<pr>`: detached at `origin/<branch>`, `git merge --no-edit origin/<base>`, on a conflict `git merge --abort` and nothing pushed, else `git push origin HEAD:refs/heads/<branch>`, never forced and never a rebase; the worktree is removed afterwards either way. `did` is `{ kind: "mergeMain", pushed }`: true for a merge that went, false for a conflict or any failure (the TS agent's `"needs-claude"`). A head that has a judge, fix or merge in flight is held in `ci_pass::Fixing` (the TS `fixing:<pr>@<sha>` key, `withFixing`), shared by the pass and the Fix button, let go after the carry-out, a failed one too, and a pass leaves a head held alone. Beyond the TS agent: a `mergeMain` the store asks for on a head the computer may not push to is not run (the store never asks, so this is only a second lock).

A fork's pull request (`isCrossRepository`) is listed and judged like any other, but `mayPush` is always false for it, whoever opened it and whatever its branch is called: no `baseHead` is sent and no `mergeMain` or `fix` can run on it, so the watcher only reports. This is a deliberate divergence from the TS agent, which pushes to `origin` by the pull request's branch name: for a fork that name can be an unrelated branch of `origin`, which would then have main merged into it. TS is to follow (a Retaskable.com issue); `may_push_to` itself is unchanged.

4. **`fix`** (`src/ci_fix.rs`, `src/ci_pass.rs`, `src/orchestrator/ci_watch_host.rs`, `prompts/ci-fix.md`). Run only where `mayPush` is true (a second lock beyond the store, as for `mergeMain`; never for a fork), under the same `fixing:` key. `ci_fix::FixTree` is the throwaway worktree `<worktreesDir>/merge-fix-<pr>` (the TS `mergeDir(cfg, "fix-<id>")`), detached at `origin/<branch>` after a fresh fetch and removed when dropped, whatever happened. The session is the implementer lane's own spec builder (`implementer::session_spec`, `Start::Continuing` with the TS prompt word for word): the implementer's schema (`IMPLEMENTER_SCHEMA`), write (not read-only), `budget.implementerUsd`, `machine.maxTurns` (300 by default) as `--max-turns`, cwd the worktree, the implementer role's engine and the project's sandbox setting, so Claude runs with `--permission-mode auto` and Codex in its own sandbox exactly as in a lane. Afterwards: a failed session, a dirty worktree (`git status --porcelain -uall` not empty) or an unmoved `HEAD` pushes nothing; otherwise `git push origin HEAD:refs/heads/<branch>`, never forced, so a branch that moved meanwhile refuses it. `did` is `{ kind: "fix", pushed }`, false for every case above and for a refused push or any failure. Differs from the TS agent: the model is sonnet (the floor tier `local` when Claude is at its limit and the local model is up) because this agent works no usage tier out, where TS reads `o.tier().tier`; there is no `canPlan` gate on the session.

Not built yet: the GitLab host, and a bell with a title and a body of its own (the agent has none: the store's bell lines are logged for now).
