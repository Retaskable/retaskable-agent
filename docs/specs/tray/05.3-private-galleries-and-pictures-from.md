### 5.3 Galleries and pictures on the computer

The agent's side of section 5's rows 5 and 7: shooting a gallery, and the pictures a message carries. What stays as decided: the cloud never holds a private gallery's pictures except as the store keeps them for the owner's project ([last-local-state.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/last-local-state.md) section 3.8), and pictures sent with a message are never stored in D1 or R2. The pages that show them, the picture queue and the hub's rate limits are the app's and the cloud's.

#### 5.3.1 A gallery on the machine

- Its config is `{ name, command, outDir }` in `galleries` (`shared/configTypes.ts`); its pictures are JPEGs (sharp, quality 82, at most 1920 px wide) in `.retaskable/projects/<project>/galleries/<slug>/` beside `index.json` (`{ name, shotAt, sha, images: [{ file, title, group? }] }`).
- The snapshot carries each gallery's `GalleryInfo` (name, status, `shotAt`, `sha`, `count`, error). That is derived, not the pictures.
  - **In this Rust agent**, `galleries::GalleryInfo` and `galleries::info(data_dir, project, gallery)` build it fresh each time: `status` from the in-memory [`status`] a shoot leaves behind, and `shotAt`/`sha`/`count` from the last shoot's `index.json` on disk, left out before the gallery's first shoot. The old set's `shotAt`/`sha`/`count` stay in a `failed` gallery's info alongside its error, the same as the picture folder itself keeps the old set until a new shoot's conversion fully replaces it. `connector::AgentView::snapshot` sends one of these per project gallery (agent/09-web-ui.md section 9.2); the command that produced a `failed` status's error is named inside that error text (`galleries::run_shoot`'s own wording), not a separate field, since `GalleryInfo` names none.
- A shoot's pictures go up to the backlog store (last-local-state.md section 3.8), and the store serves them (`gallery_index`, `gallery_image` read them from there), so a gallery shows with the machine offline. The agent asks the store for nothing here; it uploads the shoot's result.
- **In this Rust agent**, that upload doesn't exist (item **galleries-in-store**): `src/backlog.rs` only reads from the store, so every `gallery_index`/`gallery_image` answer goes through 5.3.2's machine-reading path below, not this one.

#### 5.3.2 Reading a gallery from the machine

- Where a gallery is still read from the machine (`/demo`, a gallery not yet uploaded), the agent answers two read commands at once with no one at the machine asked: `gallery_index { gallery }` answers the gallery's `index.json`; `gallery_image { gallery, file }` answers `{ file, shotAt, type: "image/jpeg", data }`, `data` the picture as base64. `gallery` is `/^[\w-]+$/`, `file` is `PICTURE_FILE` (`shared/galleries.ts`, `/^[\w.-]{1,100}\.jpg$/i`), and the agent reads only a file named in that gallery's `index.json`, so nothing else on disk can be asked for. `remote.enabled` off refuses them as any command.
- **One picture per answer, never over 768 KiB of base64** (`MAX_PICTURE_BASE64`). A picture whose base64 is bigger is sent smaller instead: the agent re-encodes it with sharp at 1280 px wide, then 960, quality 75, keeps the first that fits, and caches it in memory (at most 50 pictures, the oldest dropped). One that still doesn't fit is a `nack`: "Too big to send from the machine." The file on disk never changes. The cap is checked at both ends (the hub refuses any agent message over 1 MiB).
- **Passed through, never kept.** The answer goes as the command's `ack` and nowhere else. `remote.log` records a picture's answer by its size, not its bytes.
- An unknown picture is "No picture <file> in that gallery."
- **In this Rust agent**, `gallery_index` and `gallery_image` are built as plain functions in `src/galleries.rs`, but neither answers a hub command yet: `src/commands.rs` dispatches a few other commands (Restart, Pause, Resume), but not these two, so `remote.enabled` and the 1 MiB hub-side cap are checked for no command yet either.

#### 5.3.3 Shoot

- **`shoot { gallery }`** runs `galleries.shoot` on the base branch, for up to 30 minutes (`SHOOT_TIMEOUT_MS`), with the command read from the config at that moment, never from the site. It runs at once since 2026-10-22; the `ack` comes once the shoot has started.
- **Checks.** As any command ([cloud.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/cloud.md) section 6.2), then `shootRefusal`: "No command set for this gallery." for a blank `command`, an unsafe `outDir`, "Already shooting." and "The base checkout is busy: try again when the current session is done." An unknown gallery is "No gallery called <slug>."
- **Progress** is the gallery's `status` in the snapshot (`shooting`, `converting`, then `idle` with a new `shotAt` and `count`, or `failed` with its error).
- **In this Rust agent**, `shoot { gallery }` is dispatched from the hub: `src/commands.rs`'s Shoot finds the gallery by its slug among the project's own `galleries` (`GalleryConfig::slug`), runs the command/outDir/already-shooting/unknown-gallery checks above, then spawns `galleries::shoot` on its own thread and acks at once, once it's started. The base-checkout half of `shootRefusal` ("busy: try again...") isn't checked yet either, since the lock it refuses on is still a later piece (`src/lanes.rs`'s `base_checkout_path`; docs/specs/agent/06.8-galleries-the-game-photographs-itself.md). Each step `galleries::set_status` records (`shooting`, `converting`, then `idle`/`failed`) resends the project's snapshot at once, the same way a lane-size or pause change does (agent/09-web-ui.md section 9.2): it carries every project's change count over a `tokio::sync::watch` that `connector::connected` subscribes to (`galleries::subscribe_status_changes`), comparing its own project's count against what it last saw so a change on one project can't make the watch's single slot hide a same-tick change on another, so the site sees progress without waiting for a reconnect.

#### 5.3.4 Pictures in what you send

- **Inline in the command.** Every command whose local route took `images` (`answer`, `playtest`, `continue`, `retry`, `ask`, `draft_spec`, `draft_answer`, `draft_revise`, `gallery_feedback`) may carry `pictures: [{ type, data }]`: `type` one of `image/png`, `image/jpeg`, `image/gif`, `image/webp`; `data` base64. On a shared backlog the pictures go to the store first and the command carries `pictureIds` instead (last-local-state.md section 3.3). The limits are in `shared/sentPictures.ts`: at most 4 pictures to a message, 1 MiB each decoded, 4 MiB in all.
- **At the agent.** Before it runs one of those commands, `withPictures` saves the pictures with `attachments.saveAll`: the type and size checks (PNG, JPEG, GIF or WebP, at most 10 MB), a fresh `<uuid>.<ext>` under `.retaskable/attachments/`, pruned after 30 days. All are checked before any is written; one that fails fails the whole command (`nack` with the reason) and nothing is saved. Their paths are then added to the text the session reads (`withImages`), to the notes, the question or the request, or to the last answer.
- **Never kept in the cloud.** `remote.log` records the pictures as `{ count, bytes }` only.
- **Tested** in `agent/src/galleryImages.test.ts` and `agent/src/commands.test.ts` (a picture for a file not in `index.json`, or with `..` or a slash in it, is refused; a picture over 768 KiB of base64 arrives re-encoded under it and the file on disk is unchanged; both pictures' paths reach the session; `remote.log` holds no bytes; one bad picture saves none).
