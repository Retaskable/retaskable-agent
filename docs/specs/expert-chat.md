# Expert Chat — the Rust port

Status: v0.1, draft (2026-10-30). Ports Retaskable.com's [expert-chat.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/expert-chat.md) sections 2, 3 and 8 (build order step 12, "The Rust port") to this agent, and carries over [personal-chat.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/personal-chat.md)'s note that the conversation is, as of this port, still the item's own history — personal-chat's own move of it to a person's chat store (its section 3.6) is a later step on the TypeScript side this port doesn't follow yet. Builds on [agent/05-item-lifecycle.md](agent/05-item-lifecycle.md), [agent/06-sessions.md](agent/06-sessions.md), [agent/07.4-stopping-and-restarting.md](agent/07.4-stopping-and-restarting.md), [agent/07.5-what-a-claim-and-a-give-back-send.md](agent/07.5-what-a-claim-and-a-give-back-send.md), [pieces.md](pieces.md) and [engines.md](engines.md).

Theme: Chat

Kind: new

An expert session is a person-driven coding session: it holds a lane and a branch the way an implementer's slice does, but across as many messages as the person sends, stops and restarts mid-step on the person's word, answers in-line questions, and can start its own helpers. It finishes the way any item's work does — ships through checks and review, goes back to the backlog, is parked, or is thrown away. Retaskable.com's own agent built this first and dogfooded it for a week before this port, so the decisions below are already **[Decided]** there; this spec only decides how they land in this agent's own types.

## Decisions

- **Expert sessions don't go through pieces.** [pieces.md](pieces.md) replaces claiming a whole item for its life — the lease, parking, take-over and resuming a session by id — with short, disposable runs on pieces any computer can pick up. An expert session is the opposite of disposable: one person holds it, by design, across many messages, and nothing about it is safe to hand to a different computer mid-conversation. **[Proposal]** it keeps using the item-lifecycle and lane-pool primitives directly (`src/item_lifecycle.rs`, `src/lane_pool.rs`, `src/lanes.rs`), the way the TypeScript agent's own `session.ts` does, rather than `run_take` / `run_beat` / `run_done`. A project running `pieces: "on"` for its roadmap work still takes expert sessions the old way, since an expert session was never a piece to begin with.
- **The state machine gains no new box.** `ItemState` (`item_lifecycle.rs`) models the automated build/check/review/merge path; an expert session only ever sits in `Queued` (parked) or `Implementing` (live), the two boxes expert-chat.md section 3.1 describes. **[Proposal]** the finer detail TypeScript tags onto the item (`expert_working` / `expert_asking` / `expert_idle` / `expert_parked`) is carried on the item's own run record as its own field, not as new `ItemState` variants — those four values describe a person's conversation, not a step in the pipeline, and the pipeline's own transitions (`implementer_finished`, `ci_finished`, ...) never fire for one.
- Everything else TypeScript decided 2026-10-30 carries over unchanged: starts free / takes over (parks the lowest-priority item in the lane first, waits up to `TAKE_WAIT_MS` 120s) / adds a lane; counts toward the daily budget but a running turn is never stopped by it, only warned at 80% and 100%; `expert_say` and `expert_stop` are the only two offered on MCP; only the computer's own linked person can drive one, and only on their own computer; idle for `expertIdleMinutes` (default 30) lets go of the lane on its own; helpers run the engine's own Fast tier automatically; the name stays "Expert", the item's `kind` is `expert`.

## Behavior, in build order

### 1. The item and its lane (`expert-item-lane`)

Beside `kind`, the item carries `expert: { startedBy, detail }` (`startedBy` a person id; `detail` one of `working` / `asking` / `idle` / `parked`) — `backlog.rs`'s `Item` has no such field yet and needs one, passed through the way `kind` already is (serde already leaves other unknown fields alone, so this is additive). Placing an expert's lane ports `session.ts`'s `placeExpert` / `takeLane` onto `lane_pool.rs`: free lane first (last one freed, first taken, `LanePool::free_lane`), else take over one (`LanePool::holder` finds the lowest-priority item holding a lane, that item is parked, then up to `TAKE_WAIT_MS` is spent waiting for it to actually let go; a lane that's `Merging` or already another expert's is refused), else add one (`LaneScaling`'s `scaled_out`, one added lane per computer, and the lane that would otherwise be freed next sits out while the added one is held). An idle session — no turn running, not asking — past `expertIdleMinutes` lets go of its lane on its own, the same way parking does. **Superseded (2026-10-31, by Retaskable.com's expert-chat.md section 3.2):** a session takes the added lane, lane `lanes + 1`, and nothing is taken over or sits out; see "Lane: the added lane" under Built so far.

### 2. Turns (`expert-turns`)

One `claude -p` (or `cursor-agent -p`, or a Codex thread) run per message, resumed on whichever engine the session started on. Ports `turns.ts`'s `turn` / `settle` onto this agent's engines layer: a fresh session for the first message, `--resume <id>` (or the engine's own equivalent) after, `role: "implementer"`'s tier and budget but `maxTurns` raised the way TypeScript's own default (300) is, and a structured result shaped like `EXPERT_SCHEMA` — `summary` required, an optional `question` with up to 4 options, an optional list of up to 4 helper tasks — read back the way `engines::json_result` already reads an implementer's. A turn ending with a question sets `expert.detail = asking`; one ending without sets `idle` and keeps `summary` as the session's last line; a run that failed or was stopped sets its own detail rather than `ItemState::NeedsHuman` — a person is already there watching, so nothing needs a human pulled in on top.

### 3. The commands (`expert-commands`)

`src/commands.rs`'s dispatcher gets five new match arms, each checked the way `refusal()` already checks every command — replay, expiry, setup-done — plus a check of its own: `expert_start` refuses off the driving person's own computer, and the other four refuse anyone but the session's own `startedBy` (`driverRefusal`). These are never routed through the MCP server's generic command path, which keeps exposing only `expert_say` / `expert_stop`.

- `expert_start { where, detail, laneItemId?, continue? }`: adds an item via the backlog store with `via: "expert"`, claiming it in the same step `claim_next` already claims one — **a new store op**, since `backlog.rs`'s `Client` has no "add an item" call yet — retries the id with a numeric suffix on a collision up to 20 tries, places its lane (piece 1), and starts the first turn (piece 2). `continue` starts that first turn from a Claude Code session already on disk instead of fresh; this piece's acceptance covers only the fresh-start path, since reading another session's transcript for a handover is its own, later unit of work.
- `expert_say { text }`: stops a running turn first, places the lane if the session is parked, then starts a turn.
- `expert_stop {}`: stops the running turn only; the session stays live and idle.
- `expert_helper { task, lane? }`: starts a helper (piece 5).
- `expert_end { outcome }`: `park` and `discard` are buildable now against `lane_pool.rs`'s `release` and `lanes.rs`'s `kill_processes_in` — park stops any helpers, lets go of the lane, and sets `expert.detail = parked` with `ItemState::Queued`; discard does the same and skips the item instead of requeuing it. `ship` and hand to backlog are built, below.

### 4. Steering, Claude only (`expert-steering`)

TypeScript's own build order builds this last (step 11) because it needs turns working first: a long-lived `claude -p --input-format stream-json --output-format stream-json --replay-user-messages` with stdin left open, so a message sent mid-turn is a stream-json line in rather than a stop-and-resume. **[Proposal]** this agent's engines layer has no long-lived, stdin-fed session shape yet (`runner.rs`'s `spawn_and_read` reads a finished process's output; it doesn't feed one lines while it runs), so this piece builds that shape for Claude specifically, falling back to stop-and-resume (prefixed "stopped you mid-step", matching `turns.ts`'s `MID_STEP`) for Cursor, pi and Codex, exactly as TypeScript's own fallback does.

### 5. Helpers (`expert-helpers`)

Ports `helpers.ts`: a helper is a `role: "scout"` session on the engine's Fast tier, either read-only in the expert session's own lane (`read` mode) or on its own lane branched from the session's last commit (`lane` mode, via `lane_pool.rs`'s `free_lane` — never a take-over or an added lane; it waits). Capped at `expertHelpers` (default 2) running at once; a helper can't start one of its own. Its result (`{ result: string }`) is delivered as a message to the session — at once if it's idle, held until the next person message if it's mid-turn — and stops with the session, on `expert_stop`, `expert_end`, or a restart.

### 6. The right panel's data (`expert-work-panel`)

Read from git after every turn, kept nowhere: files changed since the branch's merge-base (uncommitted ones included), the first 100 plus a count of the rest; the last 30 commits, each with whether it's pushed (left off a commit with nowhere to push). `src/lanes.rs` already knows the lane's path and its base; this piece adds the `git diff --name-status` / `git log` calls and shapes the result the way the website's panel expects it.

### 7. The bell question (`expert-bell-question`)

A turn's `question` becomes an `expert.ask` row the same way any other item's row reaches the shared inbox — sent to the session's own driver only, since nobody else on the project can answer it.

## Built so far

The session itself, one slice (`src/expert/`, `src/commands/expert.rs`, `src/orchestrator/driver/experts.rs`, `src/orchestrator/expert_host.rs`, `prompts/expert.md`). It sits on the queue of [expert-queue-on-server.md](expert-queue-on-server.md).

- **Start, say, stop, end.** `expert_start` adds the item to the store (`add` with `via: "expert"`, claimed by this agent in the same step, the id `expert-<slug>`, the next number on a `conflict`), answers with `{ itemId }` and runs the first turn. Each message is one resumed `claude -p` turn. A message sent during a turn waits in the store queue and runs as the next turn, in order; `now` (and `expert_stop`) cuts the turn. A stop keeps the queue, and the next turn is told it was cut. Only the person who started a session drives it.
- **Lane: the added lane.** Every session works in the **added lane**, lane `lanes + 1` (`LanePool::added_lane`), made on demand as any lane is and kept between sessions so its build stays warm. It runs beside every other lane: `free_lane` doesn't count it and no lane sits out for it, so one more session runs at once than `lanes`. The computer has one, so one session at a time holds it, across every project here. While another holds it a start adds the item and leaves it parked, saying why in its history ("Another expert session has this computer's added lane: park or finish it first. The session is parked and your request wasn't sent: send it again to try."), a message to a parked session is refused with the first sentence, and the first message after the lane is free takes it on a fresh branch from the base (a session that has been parked before takes it again on its pushed branch). Shipping a parked session takes the added lane the same way. The snapshot's `addedLane` (`lanes + 1`) is there while no session or run holds it, which the Start sheet reads to warn that tokens go faster, else to say another session has it; the held lane is listed in `lanes` with its session, as any lane past `lanes` is. Its turns count against `slots` and are never held back by a pause. **There is no take-over:** the Retaskable.com spec decided on 2026-10-31 that nothing is taken over (a session takes no lane from an item and parks none), so the take-over of the first draft of this port (parking the lowest-priority item, waiting `TAKE_WAIT_MS`) is not built, and the `LaneScaling` "sits out" it described is not either. **Differs from the TypeScript agent:** the lane is taken before the first message is queued rather than after (the first message is simply not sent when the lane is held), and the organisation lane slot of pricing.md section 3.0.1 isn't taken here, as no other start in this agent takes one.
- **Park.** `expert_end` with `park`, or 30 minutes idle, commits what the lane left, pushes the branch and frees the lane; the lease is kept. The next message takes a lane again on `origin/<branch>` and starts a new Claude session there (the conversation is not resumed). A push that fails keeps the lane.
- **Discard.** `expert_end` with `discard` clears the queue, `release`s and `skip`s the item, cuts what the lane runs, frees it and deletes the pushed branch.
- **Beat.** Once a minute each lease is beaten (`report` with no note) and the queue is read back with `pull()`, so the site's edits, cancels and messages from another page reach the session. The store socket's `facts_changed` naming `expert_queue` (or nothing), and its reopening, make the beat due at once ([backlog-socket.md](backlog-socket.md)); with the socket down it is the minute's beat alone.
- **Continue.** `expert_start { request, continue: <session id> }` carries on a Claude Code session of this computer (3.10). The id is checked (`[\w-]{1,100}`), then found under Claude's `projects` folder (`CLAUDE_CONFIG_DIR`, else `~/.claude`) before anything is added: a session that's gone, or with none of the person's messages, is a nack ("That Claude Code session isn't on this computer any more." / "… has none of your messages to continue from."). The item is titled after the session. When its folder is a checkout of this project (the same git directory, or the same origin) on a branch other than the base, the session's branch is fetched from it, pushed, and the lane starts there as a parked session's does (history: "Carries on from <branch> in <folder>"); else it starts from the base and says why ("Starts from <base>: its folder isn't a checkout of this project"). The session's id, title and branch go to the store (`expert_continues_set`, no path). The first turn that answers opens with the handover (up to 40,000 characters of the conversation, newest kept, each tool call a line and no output; the folder and branch; `git status --short` there; then the person's message), the chat showing only their words; a file that has gone is the message alone. A Claude Code session is carried on once: continuing it again sends the message to the person's open session. `claude_sessions` (read, the computer's owner only at the hub) lists the recent sessions, 20 at most, newest first, each with `id`, `title` (Claude's own, else the first message cut as a request is), `folder`, `branch`, `at` and `uncommitted`, leaving out any in a project's lanes. **Differs from the TypeScript agent:** a branch name read from Claude's file is checked before it is put in a refspec (no space, `:`, `~`, `^`, `?`, `*`, `[`, `\\`, `..` or leading `-`), and the handover is sent on the first turn only, not again on the first turn after a park (a parked session starts a new Claude session here, from its pushed work, rather than resuming).
- **Pictures.** `expert_say` takes `pictureIds` (at most four, each the store's id: 36 characters and `png`, `jpg`, `gif` or `webp`; anything else is a nack, "No attached image <id>."). The ids go in the queue row, so the site shows the pictures and an edit of them is read; when the message's turn starts they are fetched from the store into a folder made for that turn, listed after the message ("Attached images (look at each with your Read tool before acting on this):" and a path each) and removed when the turn ends. A picture the store won't give drops the message (the row is read) with a history line, "Couldn't read the attached pictures. Your message wasn't sent: send it again to try." **Differs from the TypeScript agent**, which adds the paths to the text before it is queued (so a path of the computer is written to the store, and the row has no ids) and lets a run's end remove a picture a queued message still needs.
- **Snapshot.** Each session is an item of the project's live view with `expert: { detail, queue, ask? }`, `detail` being `expert_working`, `expert_asking`, `expert_idle` or `expert_parked`, `queue` the waiting messages (`text`, `at` as an ISO time) and `ask` the open question with its options. Expert items are filtered out of the backlog read, so the loop never plans or claims one.
- **Tier.** Claude only, on Sonnet, no dollar cap, `maxTurns` 300, in the engine's sandbox.

- **Ship it** (`expert_end { outcome: "ship" }`, `driver/experts/ship.rs`; the TS `shipExpert` through `changeOpened`). In `claim` mode: a parked session takes a lane again (set up from its pushed branch; no lane free is a nack). The store first hears `report { status: "in_review", detail: "expert_shipped", branch, prUrl? }` for the item (the fields the TS agent's `hostedWork.changed` sends for a checking item, with `expert_shipped` as the detail), so the marker is in the store before anything is pushed. Then the lane's uncommitted work is committed, the lane moves to the item's own branch `retaskable/<id>-<slug>-s<slice>` (the name the item loop derives for any item, so its checks, review and merge find the change; the TS agent keeps the session's branch name), the branch is pushed and its change opened (`<id>: <title>`, described by the session's request then "Driven by <login> in a Retaskable expert session."), and the session's own remote branch is deleted. A change that can't be opened answers "Couldn't push <branch> or open its pull request: <why>", rolls the marker back (`status: "claimed"`) and leaves the session as it was. Once open, the store gets the change's address with the same marker, "Shipped by the person" goes in the history, the session's queued messages and continuation note are cleared, and the session ends: the item loop takes the item over in `checking` on the same lane under the same lease (`ProjectLoop::adopt_shipped`), so checks, review and merge are the loop's own and a restart takes it back from the saved record. `read.rs` lets an expert item with `detail: expert_shipped` through (`expert::held_by_experts`); every other expert item stays the experts module's. **`runs` mode** (`driver/experts/ship_runs.rs`; [expert-ship-as-a-piece.md](expert-ship-as-a-piece.md)): no item loop holds an item, so the store carries the change as a piece. The lane is taken, committed and pushed as the same `retaskable/<id>-<slug>-s0` branch and the change opened exactly as above (a piece's runs check out `branch` as the store has it, so any name works; this one is also what the CI watcher skips for an item), but no `in_review` / `expert_shipped` marker is sent. The change is then listed as owed in the state file (`state.expert_ship_owed`: lease, branch, address, number, head, title), and `expert_ship { id, token: <the session's lease>, branch, prUrl, prNumber, head, title }` is sent. Taken (the store answers `{ piece: "<id>#1", pieces }`): the session's queued messages and continuation note are cleared, the session is forgotten and its lane freed, and the item loop never sees it. The store writes the history line "Shipped by <login>: <prUrl>" itself and ends the lease, so none is written here. Refused (`forbidden`, `conflict`, `stale_lease`, `not_found`, `bad_request`; nothing changed): the entry is dropped and the answer says in words that the pull request is open but the store wouldn't take it as the item's piece and why; the session stays as it was. Not answered (store unreachable, 5xx, lost reply): the session lets go all the same, the entry stays, and the same call is sent every pass and after a restart until the store answers (`expert_ship` is idempotent for a lease and a change); a refusal after a restart has no session to tell, so it is logged as an error with the open change's address.
- **Hand it to the backlog** (`expert_end { outcome: "backlog" }`, `driver/experts/backlog.rs`; the TS `endExpert` and `handBack`). The session is parked as `park` does (its branch pushed, its lane freed; a push that fails keeps the lane and answers with why), then `draft_queue { request, titles: [title], revises: <item>, requestedBy, assignee }` queues a plan asked by the person who drove it; the request is `expert::handoff_request`: the title, "This comes from an expert session <login> drove; plan what's left of it as a change to this item. Its work so far is pushed on `<branch>`: build on that branch rather than start again.", then the conversation oldest first (the person's messages as "The person: …" and each turn's answer line, kept in memory for the session), cut from the oldest end to the store's 20,000 characters. The session is then `expert_handed` with `plan` in the snapshot and "Handed to the backlog: plan <id> revises it" in its history. A message is nacked "It's handed to the backlog: plan <id> revises it. Park it from Finish to drive it again.", a message the site wrote to the store's queue is not run, and Park takes it back. A plan the store won't queue leaves the session parked with the reason. When the plan merges (`driver/revise.rs`, in both `claim` and `runs` mode) this computer, before it sends the store's `revise`, gives the lease back (`report` "Handed to the backlog by <login>", then `release`; a `stale_lease` counts as given back) and forgets the session and its queued rows, so the store's change finds the item waiting, puts it in the queue and drops its `expert`: any computer builds it. A release the store won't take holds the revision for the next pass. A restart drops the handed session with every other (its lease lapses, and the revision then applies when the slice in hand ends). **Differs from the TypeScript agent:** the revision is kept in the state file and sent again until the store answers (see 06.5), and the session's queued messages are cleared when it is given back. `draft_queue`'s answer is read as the store sends it, `{ draft: { id } }`; the Rust client read a bare `{ id }`.

- **Session history** (`session_history { itemId, before?, limit? }`, `expert/history.rs`). Any member of the project may ask; the answer is `{ turns: [{ at, events, said? }], more }` read from the session's run files on this computer (`<session id>.jsonl`, a `retaskable_meta` line starting each turn) and summarized as live steps are: the newest turns that started before `before`, up to `limit` steps (at most 200, the oldest kept turn cut to fit), the running turn left to `watch`. A session that continues a Claude Code session starts with that conversation (each message of the person's a turn with `said`, a background task's notice a step), for the person who started it only. Nothing is kept: the hub passes the answer on. An item that isn't a session of this computer (one already shipped included, since its session is forgotten when its change is open) is a nack, "That's not an expert session.". **Differs from the TypeScript agent:** steps carry `at`, `kind` and `text` only (this agent's `SessionEvent` has no `diff`, `todos` or subagent fields yet), so there is nothing for `fitEvents` to trim.

- **Work summary** (`expert.work` in the snapshot, `expert/work.rs`, `driver/experts/work.rs`). After every turn, whatever way it ended, the session's branch is read from its lane's git: the files changed since the branch left `origin/<base>` (uncommitted ones included; the first 100 with `more` for the rest, each `{ path, added, removed }`) and the last 30 commits, newest first, each `{ sha, subject, pushed }` (a commit is unpushed when it is among the newest `origin/<branch>..HEAD`, all of them before the branch's first push). `prs` lists the pull requests of the session's branch and of each lane helper's (`<branch>-h<n>`), found with `gh pr list --head <branch> --state all`, newest first, ten at most, each `{ number, title, url, state: open|merged|closed, checks: none|running|passed|failed, autoMerge, branch, helper? }`; none is left off. The read is a task of its own, taken in on a later pass. A lane git that can't be read keeps the last files and commits, and a host that can't be read keeps the last pull requests. While a pull request is open and no turn runs, the pull requests alone are read again every beat, so checks finishing, auto-merge, a merge or a close show up without a new turn. A parked session keeps what it last showed. **Differs from the TypeScript agent:** the pull requests are read with `gh` only (a GitLab project shows none until its merge requests are read here), and there is no "nowhere to push" mode to leave `pushed` off for, since every project has its shared backlog.

- **Helpers** (`expert_helper { itemId, task, mode: "read" | "lane" }`, and a turn's `helpers: [{ task, lane? }]`, at most four a turn; `expert/helpers.rs`, `driver/experts/helpers.rs`). Only the person who started the session may ask for one, and a parked session refuses ("This session is parked: a helper needs its lane. Send a message first."). At most two run (or wait for a lane) at once per session ("2 helpers are running for this session already: wait for one to finish."); the model's turn starts its helpers once its summary is in the history, and one refused says so there ("A helper wasn't started: ..."). Each is a Claude `scout` on the lighter tier (`haiku`), no dollar cap, `maxTurns` 300, with `{ result }` as its structured output and the prompts `prompts/helper.md` / `prompts/helper-lane.md`. A `read` helper runs read-only in the session's own lane beside its turn. A `lane` helper waits for a free lane of the pool (a take-over or an added lane are never used for it; the history says "Helper <n> is waiting for a free lane" once), and works there on `<the session's branch>-h<n>`, made from the session's last commit as this checkout has it (nothing of it pushed), where it commits and never pushes; its lane is `<item>/helper-<n>` in the pool, so it is one lane of its own. The history says "Helper <n> started: <task>", and at its end `Helper <n> ("<task>") finished: <result>` (or "didn't finish: <why>", or "was stopped"; a lane helper's lines end with the branch its commits are on, kept whole when the line is cut to 600 characters), the lines the app reads. Its result goes to the session as a message: a turn of its own at once when the session is idle in its lane, else ahead of the person's next message (held in memory, given once); it never interrupts a turn or a question waiting for its answer. Helpers stop with the session on `expert_end` (any outcome) and on a park, idle ones too; `expert_stop` stops the turn only. The answer to `expert_helper` is `{ helper: "helper-<n>" }`, `n` counted from 1 for the session's life here. **Differs from the TypeScript agent:** `n` is counted in memory, not from the history's lines (a restart drops the session anyway, so there is no "Retaskable restarted" line to write for a helper it cut off); `expertHelpers` isn't a setting here yet (two, as its default); the `specs` a turn can ask for (draft specs) aren't ported, so the expert prompt leaves that rule out.
- **Usage-limit waiting** (`driver/experts/limit.rs`; `turns.ts`'s `settle` tail). A turn that ends at Claude's usage limit (the host answers `TurnEnd::Limited`; the history still says "The turn failed: <why>") with messages queued holds them, kept in the store's queue: the history says "At the usage limit: sends at HH:MM" (the computer's time, 24-hour) and they go when the limit lifts, which is the reset the usage reading gave (`EngineLimits`), never sooner than ten minutes (the hit may have been another limit), as the TypeScript agent's `limitResume`. Another message from the person (or Send now) tries the oldest at once, and nothing is held when nothing is queued. A session that isn't at the limit never waits; a turn started at the limit runs and ends at it. **Differs from the TypeScript agent:** the time is written 24-hour rather than in the locale's style, and only Claude is held (a turn on another engine isn't built here).

Not built, and nacked or ignored: engines other than Claude, and readopting a live turn after a restart (a session is held in memory; a restart drops it and its lease lapses).

## On restarts

An expert turn runs under `role: "implementer"` (piece 2), so it falls under [agent/07.4-stopping-and-restarting.md](agent/07.4-stopping-and-restarting.md)'s "detached implementers" rule rather than "every other session is cut": its process is readopted after a restart — attached if still alive, resumed by session id if it finished while the agent was down, or its left-behind result answered — the same as a roadmap implementer's. **[Proposal]** a helper (piece 5), being `role: "scout"`, is cut like any other non-implementer session and is not resumed; its result, if any, is lost, the same as a scout's would be.

## Acceptance

Same bar TypeScript set for itself: a week of Retaskable's own work done in expert sessions, run through this agent instead of the TypeScript one, finishing by park or discard, with no loss of the person's place in a conversation across a restart.
