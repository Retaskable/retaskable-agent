# Project kits and designs from the kit's pieces — Spec

Status: v0.1, draft (2026-11-19). Copies the TypeScript agent's `kitDiscovery.ts`, `kitStore.ts`, `draftDesign.ts` and the kit parts of `designBoard.ts` (Retaskable.com #4002 and #4029; `docs/specs/project-kits.md`, `designs-from-ui-pieces.md`, `add-and-design-review.md` sections 6 and 7, deleted with that agent in #4161). The card, the stored review's shape for the phone and the site's words stay Retaskable.com's.

Theme: Orchestration

Kind: new

## 1. What it is

"Approve this change?" works for any project because this computer reads a small **kit** of the project's UI pieces, and the design step draws with it. **No model writes a graphic**: the drafter gives a plan's picture as a layout of the kit's pieces (`design`), and the app draws it. The agent finds the kit with plain code, optionally tidied by one read-only session, and keeps it as the project fact `project_kit`.

## 2. Decisions

- **[Decided]** **The kit** (`kit::Kit`, `readKit`): `tier` (`library`, `catalogue` or `wireframe`), `genre` (`app`, `game`, `data`), `fingerprint` (8 to 64 hex), `pieces` (at most 60: `id` letters, digits and a dash from a letter, up to 41; `name` one line up to 40; `kind` from the closed set `text, heading, button, input, list, table, image, canvas, header, tabBar, sheet, dialog, card, toggle, badge, chip, nav, player, enemy, healthBar, score, menu, dialogBox`; at most 8 `options` of up to 24), `tokens` (`colors` at most 12 as name to `#rrggbb`, `spacing` at most 8 numbers 0 to 128, `radius` at most 6 of 0 to 64, `fonts` at most 3), `pages` (at most 30: `id`, `name`, `kind` of `screen`, `route` or `scene`). A kit that is not the library has pieces; piece ids differ; page ids differ. At most **24 KB** of JSON; `cap_kit` drops pages, options, then trailing pieces until it fits; `read_kit` refuses a bigger or invalid one (nothing is shown rather than something wrong).
- **[Decided]** **The wireframe kit** (`wireframe_kit(genre)`): text, heading, button, input, list, table, image area, canvas area, header, tab bar, sheet, dialog, card, and for `game` also player, enemy, health bar, score, menu and dialog box. The tokens, pages and fingerprint the code found ride along.
- **[Decided]** **Discovery is read-only and never runs the project's code** (`kit::discovery`, from the project's repo path): no dev server, no Storybook, no import, no install, no git. It lists folders (depth 4, 4,000 entries; `node_modules`, `.git`, build folders and links skipped) and reads at most 240 small text files of at most 64 KB. Plain code detects, in order: Retaskable's own project (`app/src/ui/whiteboardDesign.ts` beside `shared/designLayout.ts`): tier `library`, nothing stored; the signals (package.json dependency names, never versions: react-native, expo, react, vue, svelte, next, tailwind, game and grid libraries; `.storybook`; Tailwind config; Godot, Unity and Unreal markers; Python requirements); pieces from `*.stories.*` titles and `argTypes`, then component folders' file names and, for lower-case files, their `export` names; tokens from `tokens`, `theme`, `colors`, `palette` and variables files and the Tailwind config; pages from `screens/pages/routes/views` folders, framework `app/` routes, Godot `.tscn`, Unity `.unity`, Unreal `.umap` and top-level `.html`, by name only; and a fingerprint (16 hex) of the inputs.
- **[Decided]** **The tier by code**: `library` for Retaskable's own project; `catalogue` when at least 3 pieces were found, or any under a Storybook; else `wireframe` (genre `game` for a game marker or library, `data` for a grid library, else `app`). For `catalogue` an optional read-only session (the design board's kind, `prompts/kit-summary.md`, structured `{ pieces }`) tidies the found names into the closed kit; it is validated by `read_kit`, and **an invalid or missing answer falls back to `wireframe`** keeping the tokens and pages. Without a session the code's own pieces stand.
- **[Decided]** **The fact.** The kit is kept as `fact_set { kind: "project_kit", data: kit }` and read with `facts_get { kinds: ["project_kit"] }`; the store checks the shape. It is written only for a catalogue or wireframe. When the stored kit's fingerprint and tier match a fresh scan, the stored kit is used and no session runs; this computer trusts its last look for ten minutes (in memory) before scanning again. Any failure is the wireframe kit: a design review is never blocked by it.
- **[Decided]** **The design step uses the active kit.** For the library tier nothing changes. Otherwise the layout's closed set of element ids is the kit's piece ids and its pages are the kit's page names, each with one region `content`; `prompts/design-board.md` gets `{{kitNote}}` ("This project is not Retaskable's own: draw with ITS kit below...") and lists the kit's pieces (`id`: name (kind; options)) and pages. On the idea's board a kit piece is drawn by the board's own element for its kind (button, textField, header, bottomBar, listGroup, card, switchRow, badge, chip, segmented) and any other kind as a new-piece placeholder named for it, on a new screen.
- **[Decided]** **The stored review carries the kit's pieces it uses**, not the kit: `review.kit { tier, accent?, pieces (at most 12: id, name, kind), pageName? }`, so a phone draws the card with no computer on. `accent` is a colour named primary, brand or accent (never a muted, surface, edge, text or other variant). The review's cap is 8 KB (it was 6).
- **[Decided]** **The drafter gives the plan's picture as a `design`** (an optional field of its structured answer: the same layout `check_layout` accepts and one plain `sentence`). The drafter prompt ends with **The design kit**: the active kit's pieces and pages, and step 4 says it never writes an SVG, an image or a drawing (`*.preview.svg` is refused). Plain code checks the design (`keep_plan_design`): an invalid one is dropped with a timeline line, never repaired by a model; a sentence that fails its check falls back to the standard one with **no** second model call. A kept design is the plan's `designReview`; the plan's `preview` fact is true when one was kept (or the plan already held one, when it is sent back with no new design). A new `*.preview.svg` the drafter wrote is left out of the plan's files and logged as "a drawing is not a design here". The store reads `preview` with the feature kind to put a plan on its drafting table and, with the idea's `visible` ([idea-sort.md](idea-sort.md)), to send it to a design review.

## 3. Tests

The kit's schema (closed kinds, caps, the library with no pieces, duplicate ids, the byte cap, `cap_kit`), the wireframe kits, the prompt's lines, the review subset and the accent; discovery on fixture folders made in a temp directory for each tier (a Storybook, a component folder, a lower-case library, a game, a grid library, Retaskable's own, an empty folder), tokens, pages, the fingerprint staying put across a version change and moving with a new piece, and nothing run; the kit's fact (stored kit used on a matching fingerprint, a changed one re-read and written, a failed store falling back to the wireframe, the session used only on a changed fingerprint); the layout checked against the kit's ids; the board's layout of kit pieces; the review's `kit`; a drafter design kept, invalid dropped with no second call, a drawing left out, `preview` true only with a kept design.

## 4. Acceptance

- A project with its own components gets designs drawn with them; one with none gets the plain wireframe kit; Retaskable's own project keeps its library.
- Nothing the project owns is run, and the session sees only names and token lines.
- The drafter's prompt has no instruction to draw.
