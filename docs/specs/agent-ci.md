# Agent-run CI — Spec

Status: v0.1, a draft, backlog id `agent-ci`. Builds on [agent.md](agent.md) sections 4.1 and 5 (`awaiting_ci`), [agent-settings.md](agent-settings.md) section 3, [agent-telemetry.md](agent-telemetry.md) section 3, [pieces.md](pieces.md) section 3.2 (`watch`) and [docker.md](docker.md). Copies, for the Rust agent, what Retaskable.com's [ci-when-ready.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/ci-when-ready.md) section 10 says about CI run on the agent computers (since 2026-11-02, off Woodpecker).

Theme: Orchestration

Kind: new

## 1. What it is

In Retaskable.com, `.agent-ci/runner.mjs` polls GitHub and checks each ready pull request, merged with current main, in a Docker container at low priority. It posts the commit statuses the orchestrator waits on, comments the tail of a failed log on the pull request, squash-merges `automerge` pull requests on green, and holds a person's merge while an agent pull request that is up to date with main is still being checked. This spec has the Rust agent do the same, on its own slot, so a computer whose every lane is busy building still runs the CI those lanes wait on.

**CI is its own binary.** It is not a task inside the agent: `retaskable-ci` (`src/bin/ci.rs`) is a separate process with its own link to the backlog store, shaped like the Chat Agent's ([chat-agent-process.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/chat-agent-process.md)); Retaskable.com's [ci-agent-process.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/ci-agent-process.md) is the contract. The agent (`src/main.rs`) starts no CI loop, reads no CI settings and shows no CI on the Now tab or in the tick. Sections 3.1 to 3.6 describe what the loop does; section 3.7 is how the process gets its repos, its link and its settings.

The Rust agent's own repo already carries the project side of it: `.agent-ci/image` (one line, the Docker image: `rust:1-bookworm`) and `.agent-ci/checks.sh` (run as `bash .agent-ci/checks.sh <pull_request|push>`, the same checks as the repo's workflow).

## 2. Decisions

- **[Decided]** CI is its own process, `retaskable-ci`, with its own slots (`AGENT_CI_SLOTS`), never a lane and never a session slot. It doesn't count toward `lanes` or `concurrency`, and shares nothing with the agent but the computer.
- **[Decided]** It runs at low CPU priority.
- **[Decided]** The code host token never shares a container with the code under test. Only a separate fetch container sees it, and only for the clone and fetch; the warm and check containers get none.
- **[Decided]** Several computers may run CI for one repo; they never run the same commit twice, and claim a commit with a pending status.
- **[Decided]** A failure reaches the fix session as a comment with the failing lines and the last lines of the failed log (at most 200 lines and 60000 characters, `logExcerpt.mjs`'s). (2026-11-15) When the failing lines don't all fit, a failed test's own line (`not ok`, `✖`) is kept first, then the lines around it, then other error lines, so printed `Error:` lines never push out which test failed.
- **[Decided]** Windows, Linux and macOS are all supported, and Docker is required.
- **[Proposal]** Run the loop natively in Rust rather than supervising the project's `runner.mjs`. Reasons: `runner.mjs` is Retaskable.com's own file (this repo has only `image` and `checks.sh`, so there is nothing to supervise here); supervising it needs Node on every computer, which a Windows install of this agent doesn't have; and a child process the agent can't see into is harder to stop on restart (agent.md section 7.4) and to hold to the token rule below. The contract stays the project's: its `.agent-ci/image` and `.agent-ci/checks.sh`, so a project's CI is the same whichever agent runs it. A project that has only `runner.mjs` and no `image` gets no agent CI from this agent (section 3.1).
- **[Decided]** `AGENT_CI_SLOTS` defaults to 2, a whole number; 0 runs nothing. `AGENT_CI_CPUS` (default 8, capped at the CPUs Docker reports) is each check's `--cpus`.
- **[Proposal]** A claim is stale 15 minutes after its last refresh (section 3.4).
- **[Proposal]** Where this spec says the statuses' names and wording are "the TypeScript runner's", the build copies them from `.agent-ci/runner.mjs` in Retaskable.com rather than inventing new ones, so the orchestrator's wait is unchanged.

## 3. Behavior

### 3.1 Discovery and the slot

- **Discovery.** For each repo in `AGENT_CI_REPO` (GitHub, `gh`; section 3.7), the loop looks in the repo's own mirror's `origin/<baseBranch>` for `.agent-ci/image` and `.agent-ci/checks.sh`. Both present: the project has agent CI. One missing: it doesn't, and the loop says why once in its log. It reads them from main, not from a pull request, so a pull request can't change what runs its own CI.
- **The slot.** `src/agent_ci/` holds the loop (`mod.rs`), the claims (`claim.rs`), the container runner (`container.rs`), the three steps (`steps.rs`, `exec.rs`), the host's reads for a check (`inputs.rs`), the ETag cache (`etag.rs`) and the code host side, statuses and the failure comment (`report.rs`, `log_excerpt.rs`). It is the whole of `retaskable-ci run`, with `AGENT_CI_SLOTS` permits. A permit is held from the claim to the last status posted. **[Decided]** The permits are shared fairly across the repos in `AGENT_CI_REPO`: when several repos have checks waiting, a pass of the loop deals them out one at a time, repo by repo, and the repo it starts with rotates each pass, so a repo with a steady flow of pull requests can't keep a free permit from another's (2026-11-16: 67 checks started for one repo and 5 for the other in two hours, the first repo's keys all being tried first). Every repo with waiting work gets a permit whenever at least as many are free as repos wait; a lone repo still uses them all. A head's one check at a time, the claims and the other limits are unchanged. Lanes, sessions and `concurrency` neither take nor wait for one.
- **As built.** `discovery.rs` (the `git show` of the two files and the fetch of `origin/<baseBranch>`) and `prs.rs` (`gh pr list` and the check keys) sit beside `mod.rs`. A poll probes Docker again each time, so a Docker started later resumes without a restart; `AGENT_CI_SLOTS` 0 probes nothing and says so. There is no backlog-loop gate: the loop depends on no orchestrator, so it runs whether or not an agent is up. The reason a repo has no CI is logged once (again if it changes). There is no Now-tab header and no `ci` in the tick: what the Now tab showed is log lines now (`checking <pr or push>`, `passed in <n>s`, `failed in <n>s`). Only GitHub (`gh`) is read yet.
- **As built, one check.** After each poll `CiLoop::start` takes a permit (`try_acquire_owned`; none free waits for the next poll) for each key this loop hasn't started, and `check.rs` runs it with the permit held to the last status: pending (`agent-ci <computer>: running`) on the pull request's head, then the three containers (section 3.2, `exec.rs`), then success or failure (a non-zero exit, the ceiling or an error, each said as an `error:` line in the log) and on failure the comment, whose link the failure status carries. A started key is not run again by this loop. `started` and `finished` `ci` events (written under `<data>/ci/projects/<owner>-<repo>/events`) carry `item` (`PR #<n>`), `key` (`<head7>-<main7>`), `pr` and `ms`. At start, `recover` removes this computer's leftover step containers of each repo by name prefix with `docker rm -f`.
- **One check of a head at a time** (2026-11-15). A pull request's key is its head and main's sha, so a new main makes a new key for a head still being checked against the old one. `start` leaves it for the next poll after that check ends (`head_running`): the steps' containers are named by the head (`steps::Plan::name`) and each step removes a container of its own name first, so a second check of the head removed the running one's containers and both failed (Retaskable.com #3835, twice, right after another change merged).
- **Low priority.** The loop's children (`git`, `docker`) start at below-normal priority, as the agent's own sessions do (agent.md section 4), and the container gets `--cpu-shares 128` so it yields to the computer's own apps and to the agent's sessions.
- **What is checked.** Each poll (every `pollIntervalSec`) lists the project's open pull requests that are ready (`ci-ready` label when `ciWhenReady` is on, as in agent.md section 5; otherwise every non-draft one) and, per pull request, the head sha and current main's sha. The commit to check is the pull request's head merged with main. The key of a check is the pair (head sha, main sha); a new main sha makes it a new check. A pull request that conflicts with main fails the check with that as its reason, without a container.
- **A person's merge.** While an agent pull request that is up to date with main is queued or being checked, a person's pull request waits: the loop leaves its merge-hold status pending (the TypeScript runner's) until the agent's is checked, then releases it.

### 3.2 One check, and the token

Each check is three `docker run --rm` steps in turn, named `agent-ci-<computer>-<repo>--<sha8>-<event>-<fetch|warm|check>` (slugs of lower-case letters, digits and dashes), all labelled `com.docker.compose.project=retaskable-ci`, all writing one log, and sharing one 45 minute wall-clock ceiling (**[Proposal]**: the runner has none). Names are why a restart can find a cut check: at start, and before each check, this computer's containers of the repo (`docker ps -aq --filter name=^agent-ci-<computer>-<repo>--`) are removed with `docker rm -f`.

1. **Fetch (container, token).** Runs with the token only: `gh auth token`, passed as `-e T` with the value in the docker process's environment, never in its arguments. Its volume `agent-ci-mirror-<repo>` is a bare mirror that survives between checks; the step clones it if empty, then fetches `refs/heads/main` and the check's ref (`refs/pull/<n>/head` or `refs/heads/main`) to `refs/ci/<sha>` in up to 5 tries 3 seconds apart. It prints `AGENT_CI_IMAGE <name>` from `.agent-ci/image` at that ref. The name must match `^[a-z0-9][a-z0-9._/:@-]*$` and be at most 200 characters, else the check fails with `.agent-ci/image is not an image name: <first 80>`; no line means `mcr.microsoft.com/playwright:v1.63.0-noble`.
2. **Warm (container, no token).** Only when main has `.agent-ci/warm.sh` and the image is that default: clones the mirror to `/w`, checks out main and runs `bash .agent-ci/warm.sh` with `CI=true`, the shared npm cache and the deps volume writable, the mirror read-only. Its failure is ignored.
3. **Check (container, no token).** The mirror read-only, the npm cache, the deps volume read-only and the cargo registry mounted; `--cpus`, `--shm-size 1g`; the environment is `CI`, the npm cache settings, `CI_PIPELINE_EVENT`, `CI_PIPELINE_FILES` (the pull request's changed files as JSON, read on the host), `CI_COMMIT_TARGET_BRANCH=main`, `SHA`, and `CI_CARD_LINE` (the pull request body's `Release flag:` line for a `retaskable/` branch, with `CI_CARD_UNREADABLE=1` when the body can't be read). It clones the mirror, fetches `refs/ci/<sha>`, checks out `FETCH_HEAD`, merges `origin/main` for a pull request (a conflict fails the check, saying so) and runs `bash .agent-ci/checks.sh <pull_request|push>`. The containers have no `gh`, `glab`, token, SSH agent or Docker socket; they may reach the network, since checks install their own tools.

The log is kept on this computer under the project's `ci-logs` folder (`<sha12>-<event>.log`) for 7 days. The exit code and the log's tail go back through the code host's CLI, never from a container (section 3.5).

A push to main runs the same steps with `push`, on main alone, for the baseline the orchestrator reads (agent.md section 6.7, fix main). As built, each poll lists main's check beside the pull requests' (`CheckKey::push`, pr 0, key = main's short sha alone). It is claimed, held under a permit and reported like any key, but under the `ci/agent/push/ci` context on main's commit, with `checks.sh push` on a fetch of main alone, and a failure's comment goes on main's commit (`commits/<sha>/comments`), since there is no pull request. A main sha already run (here or on another computer) isn't run again; a new sha is a new run.

### 3.3 Statuses, merging and the hold

The loop posts the commit statuses the orchestrator waits on, with the TypeScript runner's contexts and descriptions (`agent-ci <computer>: running`, `passed in N.Nm`, `failed in N.Nm <tail>`, cut to 140 characters): pending when claimed, success or failure when done. A green pull request labelled `automerge`, or one a person asked to merge on the site (the store's `ci_merge_requests`), is squash-merged by the loop, pinned to the checked head (GitHub refuses if the branch moved). There is no store lock: the merge queue is GitHub's. **The hold** (`automerge.rs`): a pull request whose branch isn't `retaskable/` waits, by not merging yet, while an agent pull request that is open, ready, 0 behind main (`compare`; an unreadable answer is not up to date) and has a pending `ci/agent/pr/ci` status is being checked, for at most 25 minutes from the first wait. There is no `ci/agent/turn` status. A host that can't be read holds no one.

- **As built.** `automerge.rs`: `Automerge::run` reads the pull request (`GET pulls/<n>`); only an open one at the checked head, labelled `automerge` or asked for in the store, goes on. Then the hold above, then `PUT pulls/<n>/merge` with `merge_method=squash` and `sha=<head>`, then one try of `ci_merged {sha, context: ci/agent/pr/ci, pr}`. A failed merge is logged and tells the store nothing. A green check calls it, and so does each poll for every ready pull request that asks and whose newest `ci/agent/pr/ci` status is success (a late label, a person's Merge, a wait that ended). Each poll also reads `ci_merge_requests` and, once per closed pull request whose head repo is this one, sends `ci_pr_closed {pr, merged}` (told again if the store refused). Only GitHub is merged yet.

### 3.4 Several computers, one repo

The store's lease is the claim, as in `runner.mjs`: `ci_claim {sha, context, event, pr?, branch?, title?, author?, computer, slots}` answers won, held (with the holder) or finished, and the check runs only on won. A held key is looked at again next poll; a finished one is done. A commit whose newest status of the context is another CI's success, or an `agent-ci` status that isn't pending, isn't claimed at all (`wants_run`, a port of `claim.mjs`). A running check sends `ci_heartbeat {sha, context, slots}` every 5 minutes, posting its pending status again then; when it ends it sends `ci_finish {sha, context, event, pr, result, minutes, computer, branch?, title?, author?}` (3 tries, 5 s apart). `once <sha>` claims with `force`. `slots` is `AGENT_CI_SLOTS` (none at 0), which the store keeps on the lease so the Agents tab can show "CI · 2 of 4 running" (Retaskable.com ci-when-ready/10, "Leases"). All ops go to `<store>/v1/repos/<GitHub repo id>/ops` as `{op, args}` with the binary's own `ci` token; with the store unreachable or unlinked nothing new runs.

**As built.** `store.rs` is the ops (`CiStore`, `StoreOps`: one retry on 401 with a fresh token) and the claim's wire shapes; `claim.rs` is `wants_run`, `newest` and `refreshing`. The old status-based claim (`decide`, key suffixes in descriptions, `stale_taken_over`) is gone. A loser forgets the key, so the next poll looks again; a host or store that can't be read runs nothing and also looks again. Deviations from `runner.mjs`: the poll is 10 s not 30 s, the three steps share one 45 minute ceiling, and the ETag cache for the host's GETs (`etag.rs`, as `etagCache.mjs`) is used for status reads only.

### 3.5 Failures reach the fix session

A failed check comments on the pull request (or main's commit for a push run), once, through the code host's CLI, with `agent-ci <computer> failed on <sha8>. The failing lines and last lines of its log:` and a fenced excerpt: `log_excerpt.rs` is `logExcerpt.mjs`'s port (the failing lines with 4 after each, the last 60, 200 lines at most, 60000 characters at most, gaps marked `... (N lines left out)`). The failure status links to the comment's `html_url`, and its description ends with the log's last line that matches `not ok|error|fail|✖`. The fix session reads the pull request's comments as it already does for a red CI (agent.md section 5, `awaiting_ci`: a failure goes back to `implementing` with the failed checks' names and links), so nothing in the orchestrator changes. The full log is kept on this computer for 7 days; the comment is what survives. `ci_finish` carries the comment's link.

What the computer reports:

- **Events.** The `ci` event (agent-telemetry.md section 3) gains `claimed`, `started`, `finished` and states, with the item or pull request, the key and `ms`.
- **To the backlog.** Nothing about a check is sent by this slice: the log and code stay here (README.md's rule: the server never sees the user's code). The statuses on the code host are what the store's own CI reading uses. The store lease and history ops are a later slice.
- **Settings page.** None: the agent's settings page, tick and `MACHINE_KEYS` no longer know CI (`ciSlots` and the Now-tab CI header are gone). Slots and CPUs are the process's environment (section 3.7).

### 3.6 Platforms and Docker

- **Docker is required.** The loop uses the `docker` CLI on PATH. On Windows that's Docker Desktop in Linux-containers mode (the image is Linux, as the project's `checks.sh` is bash); on macOS Docker Desktop, Colima or OrbStack; on Linux Docker Engine. The first-run check (first-run-check.md) gains a Docker line: `docker version` answers and `docker run` of the project's image works (pulled once).
- **As built.** `src/agent_ci/docker.rs` probes `docker version` (program injectable) and answers `ok`, `missing` (not found, no permission, or inside the agent's own image, detected by `/.dockerenv`) or `stopped` (the daemon doesn't answer), each with its reason; `probe_image` runs `docker run --rm <image> true`. The Docker line shows in the setup check. `src/agent_ci/priority.rs` starts the loop's `git` and `docker` children at below-normal priority: `BELOW_NORMAL_PRIORITY_CLASS` on Windows, `nice -n 10` elsewhere.
- **As built, the run.** `container::run` runs one `Step` (`docker run --rm ...` from `steps.rs`) through the low-priority helper, with the child's environment cleared to `PATH`, the home/profile/system variables and `DOCKER_*` that docker itself needs, plus `T` for the fetch step alone. Output streams to the check's log file (`start_log`); the result is the exit code or the ceiling, which kills the run and `docker rm -f`s it. `remove_leftovers(prefix)` removes a cut check's containers. Logs older than 7 days are pruned at the start of each run.
- **Without Docker** (missing, stopped, no permission, or the image can't be pulled): `ciSlots` is treated as 0 and the settings page and `ci.docker` say why ("Docker isn't running: this computer won't run CI"). It never runs `checks.sh` on the host as a fallback: that would put the code under test beside the token and the user's files. Other computers carry on; if none can, the orchestrator's wait ends at `ciMaxMinutes` as it does for any CI that never starts. The loop starts checking again, with no restart, when Docker answers.
- **Windows paths.** Nothing is mounted from the host: the mirror, npm cache, deps and cargo registry are named Docker volumes, so no host path reaches `docker -v`. Line endings of `checks.sh` are as committed.
- **Inside the agent's own Docker image** ([docker.md](docker.md)): nested `docker run` needs the host's socket, which that image must not get (the token rule). So an agent running in Docker runs no CI (`docker: "missing"`), and the computer's other, non-Docker agent does.

### 3.7 The process: link, repos and settings

`retaskable-ci` has three commands. `link` links it to the shared backlog store, once. `run` is the loop. `once <sha>...` polls once, checks only the pull requests or main whose head starts with one of the shas, waits for them and exits.

- **Link, role `ci`.** `link` runs the store's device flow (`src/link/`, the same one the Chat Agent uses) asking for `role: "ci"`, backlog target only; it never links to retaskable.com's Worker. Its refresh token is kept apart from the Coding Agent's: OS credential service `retaskable-ci` (file override `RETASKABLE_CI_CREDENTIALS_FILE`), and its own data subfolder `<data dir>/ci`, so linking it never replaces the agent's link on the same computer. The loop warns when it isn't linked, and the store ops of section 3.4 are its store calls.
- **Repos.** `AGENT_CI_REPO`, comma-separated, each `owner/repo` or `owner/repo@branch` for a base other than `main`. There is no config file and no project list.
- **Its own mirror.** There is no project checkout, so each repo has a bare git directory, `<data dir>/ci/mirrors/<owner>-<repo>.git`, made on first use with `git init --bare` and `origin` set to `https://github.com/<owner>/<repo>.git`. Each poll fetches the base branch into `refs/remotes/origin/<base>` (`mirror.rs`); discovery reads `.agent-ci/image` and `checks.sh` from there with `git show`, `gh` runs with the mirror as its directory, and a check's fetch step clones from it, fetching the head from the remote itself. The fetch uses the computer's own git credentials, as the fetch step always did.
- **Settings.** `AGENT_CI_SLOTS` (default 2, 0 = nothing), `AGENT_CI_CPUS` (default 8, capped at the NCPU `docker info` reports; each check runs with `--cpus`), `AGENT_CI_NAME` (default the host name; the `<computer>` in each status), and `RETASKABLE_DATA_DIR` for the data folder.
- **Which pull requests.** Not drafts, not forks, and a `retaskable/` branch only once it has `ci-ready`; this replaces the per-project `ciWhenReady` switch with the runner's own rule.

### 3.8 Published binaries

`.github/workflows/sidecars.yml` builds `retaskable-ci` and `retaskable-chat-agent` for win32, linux and darwin on x64 and arm64, and uploads them to a GitHub release (published, a pushed `v*` tag, or run by hand for a tag). Assets: `<bin>-<win32|linux|darwin>-<x64|arm64>` (`.exe` on win32) and `<asset>.sha256` holding the hex digest, the names Retaskable.com's `agent/src/chatAgent.ts` downloads from `releases/latest/download`. The R2 release flow (`.woodpecker/release.yaml`) makes no GitHub release; a pushed `v*` tag makes one.

## 4. Slices

1. **Slot, discovery and settings.** `ciSlots` in `config/machine.rs` and its environment variable; `src/agent_ci/mod.rs`'s loop with discovery; the Docker check (first-run line, `ci.docker`); the Now tab and tick fields. No container run.
2. **One check.** Fetch, run and report for one claimed pull request: `steps.rs` (the three containers' arguments and scripts), `exec.rs`, `container.rs`, `inputs.rs`, `log_excerpt.rs` and `report.rs`, the statuses and the failure comment (sections 3.2, 3.3 and 3.5).
3. **Claims across computers.** `claim.rs`: pending claims, refresh, stale takeover, `ci` events (section 3.4).
4. **Merging and the hold.** `automerge` squash-merge and the person's-merge hold (section 3.3), the push-to-main run.

## 5. Acceptance

- With every lane building, a ready pull request still gets checked: `ciSlots: 1` runs one container beside any number of busy lanes.
- `ciSlots: 0`, or no Docker, runs no check, runs nothing on the host, and says why on the settings page.
- A fake container run (a `docker` stub on PATH) sees the token only in the fetch container's environment (`T`), never in any argument, warm or check container.
- Two loops sharing one stubbed host, given one commit key, run it once; a claim left 15 minutes old is taken over; a finished key is never rerun.
- A red check leaves one comment of at most 200 log lines on the pull request or main's commit, linked from its status; a green `automerge` pull request is squash-merged; main moving after the check checks it again.
- A person's pull request waits while an up-to-date agent one is being checked and is released after.
- The Rust agent's own pull request is checked by `.agent-ci/checks.sh` and reports the same statuses a TypeScript-run one does.
- `cargo fmt`, `cargo clippy --all-targets -- -D warnings` and `cargo test` pass, with the Docker-dependent tests skipped when `docker` is absent.

## 6. In Docker

- **[Decided]** (2026-11-16, the owner: "the CI runner in Rust should be in the agent repo") The runner's container lives here, in `docker/ci/` (`Dockerfile`, `compose.yaml`, `README.md`), beside `docker/agent/`, instead of in Retaskable.com's `docker/ci`. It replaces that copy: the same image (a `rust:1-bookworm` build stage; `debian:bookworm-slim` with `docker`, `git` and `gh`, no Node), the same Compose project, service and container (`retaskable-ci`, `ci`, `retaskable-ci`) and the same `data` volume (`RETASKABLE_DATA_DIR=/data`, the link's token file `RETASKABLE_CI_CREDENTIALS_FILE=/data/ci-credentials.json`), so a computer that switches keeps its link and mirrors.
- **[Decided]** The image is built from the checkout it is in (context: the repo root; `.dockerignore` keeps `target/`, `.git` and any `.env` out), not by fetching a pinned commit. Approving a version is still rebuilding from that commit: `git checkout <commit>`, then `GH_TOKEN=$(gh auth token) AGENT_CI_NAME=<computer> CI_RUST_COMMIT=$(git rev-parse HEAD) docker compose -f docker/ci/compose.yaml up -d --build`. `CI_RUST_COMMIT` now only labels the image (`org.retaskable.ci-rust-commit`, `unknown` when unset).
- **[Decided]** `AGENT_CI_REPO` defaults to `Retaskable/Retaskable.com,Retaskable/retaskable-agent` and can be set; `AGENT_CI_SLOTS` 4 and `AGENT_CI_CPUS` 8 as before. Only this container has the Docker socket.
