# First-run check — Spec

Status: v0.2, draft (2026-10-11; 2026-10-30: section 3.3's trial plan fleshed out — every new line there is a **[Proposal]**). From an audit of Retaskable on 2026-10-11 (a new user gets a three-step Getting started guide that checks nothing: a missing or signed-out `claude` only shows up as a failed session later, and installers are left for later in tray.md section 8). Section 2's **[Decided]** lines are what the human asked for; the **[Proposal]** lines fill the gaps and are the human's call. Changes Getting started ([cloud.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/cloud.md) section 4.2, build order getting-started), the agent's `hello` ([cloud.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/cloud.md) section 5.3) and its engine probe ([engines.md](engines.md)).

The TypeScript agent in Retaskable.com is the ground truth for behaviour (`agent/src/…` paths below). This Rust agent ports the same behaviour as its pieces land: section 3.1's checks (minus `node`, which only matters to the TypeScript runtime) live in `src/setup_check.rs`, run from `src/runtime.rs` at start and from a `check` subcommand — this item's own, standalone part. The rest of section 3.1 isn't a further slice of this item: the cloud connector (`src/connector/`) sends `hello.checks`, and the read-only `setup_check` command lands with command handling ([11-build-milestones.md](agent/11-build-milestones.md) milestone 5). The trial plan (3.3) is its own backlog item, `trial-plan-draft`, waiting on the cloud link, an implementer session and command handling to reach this agent — not on a drafts module, which it doesn't depend on.

Theme: Website, Setup

Kind: new

## 1. What it is

Today a new user reads three steps on retaskable.com (run the agent, link it, approve the code) and then reloads the page. Nothing checks that Claude Code is installed, that it's signed in, that `gh` is signed in, or that a change can actually go all the way through. When something's missing they find out from a failed session, often much later.

This replaces Getting started with **one page of five steps**. Each step is checked automatically and turns green by itself. A step that fails says, in plain words, what to do.

## 2. Decisions

- **[Decided]** A new user is walked through: installing the agent; checking `claude` (or `cursor-agent`) is installed and signed in; linking the computer; linking a project; and a trial change. The human asked for this on 2026-10-11 after the audit. The agent's part is the checks (section 3.1) and the trial plan (section 3.3).
- **[Decided]** Each step is checked automatically, with a plain fix when it fails.
- **[Proposal]** The agent runs the checks itself, at start and on request, and reports them in its `hello`. retaskable.com never reaches into the machine: the agent's port stays `127.0.0.1` only (CLAUDE.md).
- **[Proposal]** Before the computer is linked, the site can't see the machine. So the agent also prints the same checks in its terminal at start (`npm start`) and in `npm run check`, and the page's step 2 says "Checked once this computer is linked" until then.
- **[Proposal]** **Claude Code or Cursor**: step 2 passes when either engine is ready. Claude Code is the default; Cursor's line shows only when Claude Code isn't ready or the project uses Cursor (engines.md).
- **[Proposal]** **The trial change** is a small plan: "Add a line to the README saying this project uses Retaskable." It never approves itself, so nothing merges until the person presses **Approve plan**. The step passes once the plan's pull request is open, which proves Claude ran, signed in, on their repo, and `gh` could push.
- The page that shows the steps (`/start`), when the home opens it and when the profile menu hides **Setup** are the app's, not the agent's. The agent only supplies the checks.
- **[Proposal]** One new read-only cloud command, `setup_check`, for **Check again**. It runs only the fixed probes and takes no arguments (built, in [cloud.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/cloud.md) section 6.1's table).

## 3. Behavior

TypeScript paths are Retaskable.com's; Rust paths appear as this agent ports each piece.

### 3.1 The checks, on the agent (slice 1, built)

- `agent/src/setupCheck.ts`, `runSetupChecks(): Promise<SetupChecks>`, each check `{ ok: boolean | null, detail, fix? }` (`null`: couldn't tell). Runs with `run` (`agent/src/proc.ts`), 20 s each, never through a shell:
  - `node`: `process.versions.node` is 22 or later. Fix: "Install Node 22 or later from nodejs.org, then run `npm start` again."
  - `git`: `git --version`. Fix: "Install git from git-scm.com." While Retaskable's own copy of git is in use (a folder project on a computer with none, [code-storage.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/code-storage.md) section 3.2.1), it says "Retaskable's own copy: git version …".
  - `ghInstalled` (since install-tools, [setup-in-app.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/setup-in-app.md) section 5.4): `gh --version` answers, shown as its first line ("gh version 2.103.0 (…)"); a missing one says "The GitHub CLI isn't installed" with `ghMissing`'s fix. Optional in `SetupChecks`, so an older agent's checks still parse; the terminal's lines don't show it.
  - `gh`: `gh auth status` exits 0. Fix: "Run `gh auth login` in a terminal on this computer." A missing `gh` says "The GitHub CLI isn't installed", fix "Install the GitHub CLI from cli.github.com, then run `gh auth login`."
  - `claude`: `probeEngines` (`agent/src/engines/probe.ts`, which now takes the `run` to use) as today, shown as "Claude Code 2.1.4". Fix: "Install Claude Code: `npm install -g @anthropic-ai/claude-code`."
  - `claudeSignedIn`: `ANTHROPIC_API_KEY` set in the agent's environment passes without asking; otherwise `claude auth status`, which answers JSON with `loggedIn`. It fails only on an answer that says it's signed out (`loggedIn: false`, or "not logged in"); it passes on exit 0 with `loggedIn: true` (or no JSON and no "unknown"/"usage"). Anything else (an older Claude Code that doesn't know the command, a timeout) is `null`, "Couldn't tell whether Claude Code is signed in; the trial change will show it". `null` too, "Checked once Claude Code is installed", while `claude` is missing. The account's email and the rest of the JSON stay on the machine. Fix: "Run `claude` in a terminal on this computer and sign in."
  - `cursor`: the probe's Cursor answer (installed, then `cursor-agent status`). Fix: "Run `cursor-agent login`.", or when it isn't installed "Install Cursor's agent from cursor.com/cli, then run `cursor-agent login`."
  - `pi` and `codex` (optional, like `ghInstalled`): `pi --version` or `codex --version`, only when the binary answered, so an engine nobody installed adds nothing. They feed the computer's own Now tab (agent-settings.md section 4.5) and don't count toward `setupChecksPass`. **[Proposal]** A probe that says why an engine failed, and a line for each, is planned in [engines.md](engines.md) section 9.1.
- `SetupChecks` and `SetupCheck` in `shared/types.ts`; the words in `shared/setupCheckText.ts`, so the agent's terminal and the page say the same: the fixes (`SETUP_FIXES`), `claudeReady` (installed and not known signed out), `engineReady` (Claude Code or Cursor), `showCursor` (Claude Code not ready), `setupChecksPass` (Node, git, a signed-in gh and an engine) and the lines (`setupCheckLines`, `setupCheckReport`): "✓ detail", "✗ detail: fix" (the fix's first letter lowered), "? detail" for `null`.
- **At start**, `agent/src/index.ts` runs them once the port is up and prints "Setup check:" and one line each ("✓ Claude Code 2.1.4", "✗ gh isn't signed in: run `gh auth login` …"), Cursor's only when Claude Code isn't ready. `npm run check` (`retaskable check`, `agent/src/cli.ts`) prints the same and exits 1 unless `setupChecksPass`.
- **In `hello`**: an optional `checks: SetupChecks` (`shared/cloud.ts`; older agents send none, and none goes before the first run). A missing git, GitHub CLI or Claude Code has an **Install** button on the page ([setup-in-app.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/setup-in-app.md) section 5), and the agent's start puts a GitHub CLI it fetched and `~/.local/bin` on its own PATH, so the checks find them. `SetupCheckRunner` (`agent/src/setupCheck.ts`) keeps the latest, runs one at a time, and runs again every 10 minutes (whether or not a site is linked: it's a few quick commands); a changed result marks every connection changed (`clouds.changed(null)`), so `hello` goes again within a second.
- **`setup_check`** (read-only, `{}`): runs them now and answers `SetupChecks` as its `ack`; a changed result goes up in `hello` too. It's taken before Setup (the checks are the machine's), refused on a view-only agent like every command, and any argument is refused.
- In this Rust agent: `src/setup_check.rs` has `SetupCheck` / `SetupChecks` and `run_setup_checks`, with the same checks minus `node` (a compiled binary has no Node runtime version to check). `src/runtime.rs` runs them once the port is up and prints the same "Setup check:" lines, and a `check` subcommand prints them and exits 1 unless they pass, matching `npm run check`. `AgentView::hello` sends `checks` (with a stand-in `node`, since the hub's schema asks for one this agent doesn't have) once the first run has finished, and the connector sends `hello` again when the runner's result changes; `src/setup_check/runner.rs` has `SetupCheckRunner` (latest, one run at a time, `subscribe()` ticking on a changed result, a 10-minute re-run started by `runtime::spawn_setup_checks`; it's a field of `AgentView`) and `SetupChecks::to_json()` gives the `shared/types.ts` shape with a stand-in `node`, the `setup_check` command isn't ported yet (item `setup-check-command`). The trial plan (3.3) needs the cloud link and an implementer session before it can be ported, not a drafts module.
- **[Proposal] Sending the checks and answering `setup_check` (item `setup-check-command`).** Both halves of the paragraph above that were left to command handling:
  - **`hello.checks`.** `AgentView::hello` (`src/view.rs`) carries the latest `SetupChecks` as `checks`, once the first run has finished (none before it, as the TypeScript agent does). The hub's schema asks for a `node` check this agent has no use for, so the Rust `hello` sends `node: { ok: true, detail: "Not needed: this agent is a compiled program" }` — the human's call; the alternative is making `node` optional in the hub's schema.
  - **The runner.** A `SetupCheckRunner` keeps the latest result, runs the checks once at start (as `runtime.rs` does now) and again every 10 minutes, one run at a time, whether or not a site is linked. A changed result marks every connection changed so `hello` goes again within a second; an unchanged one sends nothing. The settings page and the orchestrator read the runner's latest instead of running their own.
  - **`setup_check`.** `src/commands.rs` gets an arm for it: `{}` only (any argument is a nack), runs the fixed probes now (no shell, 20 s each) and acks with `SetupChecks` as the `answer`; a changed result goes up in `hello` too. It is already in `BEFORE_SETUP`, so it needs no project, and it stops falling through to "Not a command this agent takes yet".
  - **Tested** with stubbed probes: the `ack` carries the checks, an argument is a nack, it works with no project, a changed result resends `hello` and an unchanged one doesn't, and the 10-minute re-run is driven by a fake clock.

### 3.2 The page

The page of steps (`/start`, nine steps since setup-steps), its badges, its "Check again" and "I'm done here", and its home redirect are the Expo app's. It shows the agent's check lines from `hello.checks` as they come, and sends `setup_check` for **Check again** (the command [cloud.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/cloud.md) section 6.1 lists). The agent does not draw or serve any of it.

### 3.3 The trial plan

- **[Decided]** The content never changes: "Add a line to the README saying this project uses Retaskable." The step passes once the plan's pull request is open — proof that Claude ran, signed in, on the person's repo, and `gh` could push — never once it merges, and it never approves itself.
- A trial draft is an ordinary draft the agent writes, marked `trial: true` by the `draft_spec` command. The agent's `approvesItself` (`agent/src/drafts.ts`) answers false for it, so it always waits for **Approve plan** ([simple-flow.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/simple-flow.md) section 2). Allowing one trial at a time per project is the store's to decide.
- **[Proposal]** **When it fires.** The agent queues it itself, once, the first time a project is configured with a repo: no person asks for it, and it isn't held back by section 3.1's checks passing first, since a drafter session that can't start, sign in or push is itself the proof something's missing — the same gap one of those checks already names, just found by actually trying. It's sent the way a chat message is (section 6.6): `draft_spec { titles: ["Say hello to this repo"], text: "Add a line to the README saying this project uses Retaskable.", trial: true, audience: null, revises: null }`. Whether this project has already had its trial sent is kept on the project's own state (`trialDraftSent` in `state.json`), set the moment the `draft_spec` call is made, so a restart before it's answered never sends a second one. A project configured with no repo yet (local-only) sends none, and never did before this change either.
- **[Proposal]** **Its place in the queue.** It takes the project's normal spec-queue order (section 6.5), the same as a chat message would: nothing special jumps it ahead. In practice it's always the first draft a brand new project runs, since nothing else exists yet to be ahead of it.
- **[Proposal]** **Nothing to spec.** The request names one line of text, not a behavior, so the drafter's fix/tweak/feature split (section 6.5) has nothing to classify: it's none of the three. The drafter edits `README.md` directly in its worktree — adding the line under an existing `## Retaskable` heading, a new one at the end when there isn't one, or a new file when the repo has none — and opens the PR with that one change. No spec is written and no backlog item is added (`itemId` and `itemIds` stay empty on this draft).
- **[Proposal]** **If it fails.** A drafter session that can't start, can't push, or answers `failed` for any other reason clears `trialDraftSent` rather than leaving it set, so the next restart queues a fresh one instead of the step staying silently stuck. The failure's reason reaches the person on the draft exactly as any other draft's would; section 3.1's own checks are usually why.
- **[Proposal]** **Discard and retry.** Discarding the trial's PR (section 6.5's **Discard**) is read the same way as the trial never having been sent: `trialDraftSent` clears, the step goes back to not started, and the next restart queues a new one.
- **[Proposal]** **Budget and tier.** It runs on `<midTier>` under `budget.drafterUsd`, exactly as any other spec draft (section 6.5) — no separate budget, since it is, deliberately, the smallest draft the pipeline ever runs.
- This Rust agent has no `drafts` module or `draft_spec` command yet, so the trial plan isn't ported here. It's its own backlog item, `trial-plan-draft`, not a slice of this item; it waits on a drafts module this port hasn't built.
- **[Proposal] When it runs.** Once this computer has finished linking a project for the first time — section 3.1's checks pass, and the project's config is saved with its repo known — and that project has never had a trial plan, the agent queues one. It takes a free lane the moment one opens, ahead of chores (section 6.7) but never ahead of roadmap work already running, so a brand-new project with nothing else queued gets it at the very next tick. A project whose backlog already holds items (an existing repo linked here a second time) skips it outright: real work proves the same things. The "never had one" flag lives with the project's own state, not the machine's, so re-linking the same project here or on another computer never starts a second one.
- **[Proposal] The loop's part.** `claim` mode runs the check each pass for live projects (`orchestrator/driver/trial.rs`), after asks and drafts and before items are planned, behind the `trial-plan-draft` release flag. It asks `trial_plan::should_start` with the pass's backlog item count, the latest setup checks and the project's `trialPlan` record: `Skip` saves `skipped`; `Start` needs an unpaused project, a free session slot and a free non-chore lane (never one roadmap work holds), takes the lane as `Holder::Trial`, saves `running`, then runs the session. When it ends, `Opened` saves `open` with the PR's URL and logs `trial_opened`; `Dropped` (or any error) saves `failed` and logs `trial_dropped` with the reason; the lane is released either way. A restart that finds `running` with no session takes it as dropped.
- **[Proposal] In this Rust agent, no drafts module, no store draft.** `trial-plan-draft` depends on the cloud link, an implementer session and command handling, not on `spec-drafts` — so this agent never asks the store for a draft and the store never hears about a trial plan at all. It runs the fixed change straight through one implementer session ([06.2-implementer.md](agent/06.2-implementer.md)), the same claim, lane, worktree and branch a chore gets (agent.md section 6.7), with the instruction above standing in for an item's `remaining` text: add the one line to the repo's top-level README (creating it if there is none), nothing else. The session's answer is read the same `IMPLEMENTER_RESULT_SCHEMA` way; `pr_opened` is all the step needs. A `needs_clarification`, `failed`, or anything else drops it exactly as a chore that can't do its job is dropped (agent.md section 6.7's last bullet): no retry, the fifth step stays unchecked, and why is in the project's event log, never on a backlog card, since the trial plan is never a backlog item here.
- **[Proposal] Reporting it.** The project's own status (agent.md section 9.2) carries one more field, `trial: { state: "not_started" | "running" | "open" | "failed", prUrl? }`: `running` while its session holds a lane, `open` with the PR's URL once `pr_opened` lands, `failed` when it was dropped. Which words `/start` puts on each state is the app's; the agent only reports the state. In this Rust agent `AgentView::snapshot` (`src/view.rs`) reads the record from the project's `state.json` (a skipped record reports as `not_started`, `prUrl` only when `open`), leaves `trial` out before Setup, and the cloud link resends the snapshot when `Store::set_trial` saves a record that changes it.
- **[Proposal] Approving it, on this Rust agent.** With no drafts module to hold an **Approve plan** button, merging the open PR on the code host — exactly as the person can with any PR today — is enough: the step already reads **Done** from the PR being open, so nothing here needs to notice the merge either. Closing the PR by hand is the same as **Discard**; the agent doesn't reopen it, and (per the bullet above) doesn't start a second trial plan for the same project either way.

## 5. Acceptance

- On a fresh machine with Claude Code installed but not signed in, `npm start` prints "✗ Claude Code isn't signed in: run `claude` …", and after linking, `/start`'s step 2 says the same, then turns **Done** within a minute of signing in and pressing **Check again**.
- With `gh` signed out, step 1 shows the `gh auth login` fix.
- The trial plan doesn't merge on its own: on the TypeScript agent nothing merges until **Approve plan** is pressed; on this Rust agent the open PR sits until the person merges or closes it by hand.
- TypeScript: `npm run test:changed` and `npm run lint` pass. Rust: `cargo test setup_check` and `retaskable check` on this machine print the same lines and exit code `npm run check` would.
