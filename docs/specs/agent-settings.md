# Agent settings — Spec

Status: v0.2, decided (2026-10-22), trimmed for the agent. Builds on [tray.md](tray.md) (decision 8, the deliberate exception to "no website of its own"), [agent.md](agent.md) section 8 (the port), [computer-tags.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/computer-tags.md) (tags) and [engines.md](engines.md) (Cursor's models).

Theme: Orchestration

Kind: new

## 1. What it is

A computer running Retaskable has settings of its own, apart from any project's. Until now they were spread over the config file, requests someone at the computer allowed, and three screens on the site. This splits them in two, by who should change them:

- **On the site, by the agent's owner** (the person who linked the computer): what costs money or decides how hard the computer works.
- **At the computer only**: what points it somewhere, or what only makes sense where it runs. Setup asks, an environment variable can set it, and a small page the tray opens changes it.

A project's own settings stay in Project settings on retaskable.com, as before.

## 2. Decisions

- **[Decided]** (2026-10-22) The split below. Nothing in the computer-only half can be changed from the site, so a stolen site session can't point a computer at another cloud, another model server, or open it to the network.
- **[Decided]** (2026-10-22) The human: "could we use a tiny webserver?", then "that way you could navigate to your local ip with the agent running and change the settings remotely from within the network". So the computer-only settings get a page of their own, served by the agent (tray.md decision 8): on `127.0.0.1` by default, on the local network only when the person turns that on at the computer and sets a password.
- **[Decided]** The page changes settings only. It never runs a command, and it never shows or changes a project's settings or the owner's.
- **[Decided]** (2026-10-22) The human: daily budget, sessions at once and model thresholds are agent settings changed on the site, "only changeable by the owner of the agent" (the person who linked it). Everything else about a computer (links, port, local model, how often it checks, tags, Cursor settings, network access) is set only at the computer, never from the site.
- **[Decided]** (2026-10-22) The owner's settings need no fresh sign-in: they run no code. They cost money, so they stay the owner's alone.
- **[Decided]** (2026-11-09, [pools-on-server.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/pools-on-server.md)) The owner's three settings moved from the computer to the server: they are kept in the project's store, in the pool record of each computer that has reported to it, and written by `pool_settings`, not by the `agent_settings` command, which is gone. The computer does not read them back; the store applies them when it sends work (the number of sessions at once, the daily budget, the tier thresholds). Settings start from the defaults (1 session, no daily cap, auto on with 1 to 8 at 75%, Opus above 50%, wait below 5%); nothing is read from an old `config.json`. There is no per-model sessions setting and no Sonnet threshold any more. The keys stay in `config.json` and the agent's own scheduling still reads them until the agent's own pool is deleted (not built), so the numbers on the computer no longer show anywhere.

| Setting | Where it's changed | Kept in |
|---|---|---|
| Link to retaskable.com | the tray's **Link to**, `retaskable link`, or the settings page's **Link** button (section 4.6) | the credential store |
| Link to the shared backlog | by itself once linked, or the tray's **Waiting for you** | the credential store |
| Port | setup, `RETASKABLE_PORT`, the settings page | `config.json` `port` |
| Local model: on or off, the model, its address | setup, `RETASKABLE_LOCAL_MODEL`, `RETASKABLE_LOCAL_URL`, the settings page | `config.json` `local` |
| How often it checks for work | setup, `RETASKABLE_POLL_SEC`, the settings page | `config.json` `pollIntervalSec` |
| Tags | setup, `RETASKABLE_TAGS`, the settings page | `machine.json` `tags` |
| Engine (the one company everything runs on: Claude Code, Codex, Cursor, pi or the local model) | `RETASKABLE_ENGINE`, the settings page | `config.json` `engine` |
| Models (the model for each tier: Smart, Fast, Cheap) | setup, the settings page | `config.json` `models.smart`, `models.fast`, `models.cheap` |
| Network access to the settings page, and its password | setup, `RETASKABLE_NETWORK_PASSWORD`, the settings page | `machine.json` `network` (the password as a scrypt hash) |
| Daily budget | Settings → Agents on the site, by the agent's owner only (`pool_settings`) | the project's store, in that computer's pool record (`dailyUsd`) |
| Sessions at once (`limit`) | Settings → Agents on the site, by the agent's owner only (`pool_settings`) | the project's store (`limit`) |
| Model thresholds (`opusAbovePct`, `pauseBelowPct`) | Settings → Agents on the site, by the agent's owner only (`pool_settings`) | the project's store (`models`) |

### 2.1 The owner's settings: `pool_settings` (changed 2026-11-09)

- **The op** (`shared/backlogPoolOps.ts`, [pools-on-server.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/pools-on-server.md) section 5.4): `pool_settings { agent, limit?, dailyUsd?, autoConcurrency?, models? }`, checked in the ranges of `shared/pools.ts`, saved in the project's store at once. `pool_get` reads them with `allowed` and the reason to wait. The store takes `pool_settings` only from the computer's owner, who is the login of its first `health`; so it is refused until the computer has reported once to that project, and the Agents tab shows the defaults read-only until then.
- **The site** sends it through the shown project's store (a computer that serves several projects has one pool per store, so the tab shows the shown project's). Only the keys that changed are sent. The old `agent_settings` command, its schema, the hello capability and the agent's write (`saveAgentSettings`) are gone, and the hub refuses an old page's `agent_settings` with "...saved in the project, not on the computer", the owner too. This Rust agent matches: no `agent_settings` capability in the hello, no command, no `site_settings` module (`src/commands.rs` answers it as it does any unknown command).
- **The old ways stay gone.** The hub still refuses `computer_tags` and a `settings_request` naming one of these settings or one set at the computer (`pollIntervalSec`, `local`, `cursorModels`, `lanes`), in plain words (`retiredRefusal`).
- **A one-time note**, a dismissible banner kept on the device (`retaskable.poolSettingsNote`), says the settings moved and start from the defaults.

The Agents page on the site (one card per computer, which settings are editable by the owner or read-only with how to change them at the computer, the Sample's made-up computer) is the app's: [expo.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/expo.md). The agent sends what it needs in its hello's `computer` (`ComputerView`, `shared/computerView.ts`; `src/computer_view.rs`): `lanes`, `laneScaling?`, `choreLane?`, `concurrency`, `modelConcurrency?`, `pollIntervalSec`, `port`, `models`, `local` (`server` is its host and port only), `dailyUsd`, `cursorModels`, `engines`, `cloud` and `backlog` (origins only), `tags` (`found`, `added`, `removed`), `network` (whether the settings page is open on the network) and `secrets`: only each environment variable's name and whether it is set, never a value, then each link (`kind: "link"`, `state` `linked`, `not linked` or `waiting`: each cloud by its host, then `backlog store <host>`). The values are read from `config.json`, `machine.json` and the environment on every hello, so one the settings page saves reaches the site with the hello it sends on a save. In this Rust agent: `lanesAuto`, `usesEngines` and `releases` are left out (each optional, "none from an older agent"): the lane count doesn't follow the Claude plan, there is no `work` setting, and the release gate (the hub's `owner_role`, the login's admin check and the rollout tools) isn't ported; `local.server` is the configured address even while the model is off. `src/view/hub_tests.rs` checks the whole shape against the hub contract. The hello has no `settings` any more: the owner's settings are the store's pool settings.

## 3. The computer-only settings

`agent/src/machineSettings.ts` reads, checks and saves them.

### 3.1 Their values

- **Port**: a whole number from 1024 to 65535. Changes once the agent restarts.
- **Lanes**: a whole number from 1 to 64, 2 until set: how many items the computer works on at once, across all its projects (the projects share them: lane k is one lane, and a project can't start work in one another holds). `MACHINE_KEYS` has it, at the top of `config.json`. A config whose projects still have their own `lanes` (or `migrated.lanes`) reads the computer's as the largest of them; those keys are then ignored, noted once on startup (`retiredKeysNote`) and dropped by the next save. The engine of each lane is `engines.lanes` below, and the page shows that many selects.
- **CI slots** (**[Proposal]**, [agent-ci.md](agent-ci.md)): a whole number from 0 to 8, 1 until set: how many pull requests' CI the computer runs at once in Docker, apart from the lanes. `MACHINE_KEYS` has it.
- **Local model**: on or off; its model's name (up to 100 letters, digits and `. _ : / -`); its address, `http` or `https`, with no user or password in it.
- **How often it checks**: 2 to 3600 seconds.
- **Tags**: [computer-tags.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/computer-tags.md)'s rules. A list typed in is saved as your changes to the found tags (`added`, `removed`), as before. Which work a computer with these tags takes is the store's to decide.
- **Engine and models** (**[Decided 2026-11-20]**, the owner, from using the page: "Who does what" with an engine for every kind of work and every lane was too much, and nobody mixes companies). One section, **Engine and models**: the **company** (`engine`: `claude`, `codex`, `cursor`, `pi` or `local`) and the **model for each of three tiers**, `models.smart`, `models.fast` and `models.cheap`. **Only one company at a time; no mixing.** The store names a tier only ([agent/07.1-model-tiers.md](agent/07.1-model-tiers.md)); this computer turns the tier into a model and a program from these two settings and reports them (`tiers` in the hello). **Smart** is the strongest: the planner, the final review, drafts, triage and escalations (the store's `opus`). **Fast** is the normal building model: implementers, asks and chores (`sonnet`). **Cheap** is for quick looks and judges: scouts, release notes, classifiers (`haiku`). An empty model is the company's default (`src/tier_models.rs`): Claude Code `opus` / `sonnet` / `haiku`; Cursor `auto`, its own pick; Codex, pi and the local model, empty, which sends no model flag so the program's own default runs (the local model's name is under **Local model**). A model's name is letters, digits and `. _ : / -`, not starting with `-` (so `--force` can't be slipped in). Environment: `RETASKABLE_ENGINE` (one name); the older `RETASKABLE_ENGINES` and `RETASKABLE_CURSOR_MODELS` are still read.
  - **The older keys are migrated, never written back** (`config::engine_choice`, `config::tier_models`). A config with no `engine` but an `engineChoice` reads as the one company the building work ran on: its `roles.implementer`, else its `default`, else the first lane that named an engine, else none (Claude Code); roles and lanes are then ignored. A config with no `models.smart/fast/cheap` but a `cursor.models` reads `top` as Smart, `implementer` as Fast and `scout` as Cheap. The old `RETASKABLE_ENGINES` is collapsed the same way. The first save of **Engine and models** writes `engine` and `models.*` and deletes `engineChoice` and `cursor.models`. A project's own older `engines.default` still counts while the computer has chosen none (it is its own key and has no per-lane part). Every place that picked an engine per kind of work or per lane (`engine_for`, the lanes' chips, `used_for`, the hello's `engines`) now reads the one company; `engines.roles` in the hello is all `default`.
  - **The tier is turned into a model where the session starts.** Claude Code `--model` and pi `--model` take the model of the tier the session's name stands for (`opus` Smart, `sonnet` Fast, `haiku` Cheap; `tier_models::session_model`), Codex `--model` likewise (only when set, and not on a resume), and a Cursor session takes it by its role (`place`: Smart for the planner, reviewer, drafter and triager; Fast for the implementer; Cheap for scouts, the writer and the assistant). Only the chosen company's program is changed: a helper that always runs Claude Code (a judge, a classifier) keeps its own `haiku`.
  - **What is shown follows the company.** The **Local model** panel is shown only while `local` is the company (or while the local model is on as the floor behind Claude Code, so it can still be turned off); the old **Cursor's models** panel is gone (its three names are the tier models); **Cursor may also run** is shown only while Cursor is the company. A field an environment variable sets is greyed out, with why (3.2).
- **Cursor may also run** (per project, shown while Cursor is the company): a text box for the typed `engines.allow` entries (commas or new lines), a refused entry's reason beside it, the `allowlist_in_force` line (red when sessions won't start) and, when there are any, "Already allowed, from your checks: Shell(npm), Shell(cargo)". It saves through `POST /api/settings` (`cursorAllow`).
- **Network access**: on or off. On needs a password of at least 8 characters, kept as `scrypt$N$r$p$salt$hash` and checked in constant time. Turning it off keeps the hash, so turning it on again needs no new one. Changes once the agent restarts.

### 3.2 Environment variables

For a computer with no screen, each can be set by a variable, read through `envVar` (so the product's old variable names count too):

| Variable | Sets |
|---|---|
| `RETASKABLE_PORT` | the port |
| `RETASKABLE_LOCAL_MODEL` | the local model on, with this model; `off`, `false`, `0` or `no` turns it off |
| `RETASKABLE_LOCAL_URL` | the local model's address |
| `RETASKABLE_LANES` | the lanes, a whole number from 1 to 64 |
| `RETASKABLE_CI_SLOTS` | the CI slots, a whole number from 0 to 8 |
| `RETASKABLE_POLL_SEC` | how often it checks |
| `RETASKABLE_TAGS` | the tags, comma between, instead of the found ones and your changes |
| `RETASKABLE_CURSOR_MODELS` | one model for every tier (`gpt-5`), or each by name (`top=gpt-5,implementer=sonnet,scout=gpt-5-mini`) |
| `RETASKABLE_NETWORK_PASSWORD` | network access on, with this password |
| `RETASKABLE_SECRETS_KEY_FILE` | a file holding the key for saved secrets, as base64 (section 3.3) |
| `RETASKABLE_SECRETS_KEY` | the key for saved secrets, as base64 (section 3.3) |
| `RETASKABLE_SETTINGS_PUBLISHED_LOCAL` | `1`: the port is published on the host's `127.0.0.1` only (Docker), so a request whose Host is `127.0.0.1`, `localhost` or `[::1]` counts as this computer for saving secrets (section 4.3) though it reaches the agent from Docker's gateway. Not a setting the page shows. |
| `RETASKABLE_TRUST_DOCKER_HOST` | `1` (Linux only), in a container whose port is published on the host's `127.0.0.1` only: the page listens on `0.0.0.0` inside the container, and the container's default gateway (read at start from `/proc/net/route`, logged) counts as this computer, as loopback does (section 4.4). Not a setting the page shows. |
| `RETASKABLE_START_PAUSED` | `1`: each project this computer hasn't paused this way before starts with this computer's own pause on, until someone resumes it (section 3.4). |

- **A variable wins over the file.** The agent runs on the file's settings with the variables' over them (`withEnvSettings`, in `Pool.configure`); the file keeps its own, so a save never writes a variable's value into it. A value that doesn't read (a port that isn't a number) is left out.
- **It says so.** The settings page shows such a setting greyed out, "Set by RETASKABLE_POLL_SEC: change it there.", and refuses a change to it; setup says it instead of asking. Each is in `AGENT_ENV_VARS`, so the hello's `computer.secrets` lists it as set, by name only, never its value. In this Rust agent `AGENT_ENV_VARS` (`hello_settings.rs`) also has `RETASKABLE_LANES`; a save on the settings page sends a fresh hello on every project's connection. The hello sends no `settings` object (the hub dropped it; it was the retired `agent_settings` channel's, section 2.1), and `capabilities` is `[]`: the `agent_settings` capability, the `agent_settings` command and `site_settings` (its save) are gone, as in the TypeScript agent, so the command answers like any other this agent doesn't take ("Not a command this agent takes yet"). The TypeScript hello lists `chat_context` (its `ask` takes the hub's `context`) and `peer_code` (a peer-code project); this coding agent takes neither (its `ask` is the Chat Agent's, and it has no peer code), so it lists none.

### 3.3 Secrets (encrypted in the config; a deliberate divergence from the TypeScript agent)

The TypeScript agent keeps each saved secret as its own OS credential entry (service `retaskable-secret`), or in a 0600 `credentials.json` where there's no OS store. **This Rust agent does not: the user chose to keep them as ciphertext in the config.** Everything the page and the environment do is the same; only where a saved value rests differs.

- **Which**: any variable a person adds (next bullet), and the program's known ones: `GH_TOKEN` (gh, and git over https), `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_API_KEY`, `GITLAB_TOKEN`, `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN` (`SECRETS`, `src/secrets/mod.rs`).
- **Any name** (**[Decided 2026-11-16, the owner]**). The person can add variables of any name, not only each program's known secrets, in all three programs. `src/secrets/names.rs` is the authority and the page only mirrors it (`secretRules` in `GET /api/settings` and in each program, so the rules live in one place). A name is `^[A-Za-z_][A-Za-z0-9_]*$`, at most 128 characters, and not (compared without regard to case, as Windows does): a **system variable** every tool depends on (`PATH`, `PATHEXT`, `HOME`, `USER`, `USERNAME`, `LOGNAME`, `SHELL`, `USERPROFILE`, `APPDATA`, `LOCALAPPDATA`, `PROGRAMDATA`, `PROGRAMFILES`, `SYSTEMROOT`, `WINDIR`, `COMSPEC`, `TMPDIR`, `TEMP`, `TMP`, `PWD`, `OLDPWD`, `SHLVL`, `IFS`, `XDG_RUNTIME_DIR`, `MSYSTEM`), one that **changes what the tools load or run** (`LD_*`, `DYLD_*`, `GIT_*`, `DOCKER_*`, `BASH_FUNC_*`, `NODE_OPTIONS`, `NODE_PATH`, `BASH_ENV`, `ENV`, `PS4`, `PROMPT_COMMAND`, `EDITOR`, `VISUAL`, `PAGER`, `BROWSER`, `PYTHONPATH`, `PYTHONSTARTUP`, `PYTHONHOME`, `RUBYOPT`, `RUBYLIB`, `PERL5OPT`, `PERL5LIB`, `JAVA_TOOL_OPTIONS`, `_JAVA_OPTIONS`, `JDK_JAVA_OPTIONS`, `RUSTC_WRAPPER`, `RUSTC_WORKSPACE_WRAPPER`), one **the agent sets itself on what it starts** (`T`, `REF`, `SHA`, `CI`, `CI_*`, `NPM_CONFIG_*` and the CI containers' other variables; for sessions `CF_API_TOKEN`, `CLAUDE_CONFIG_DIR`, `ENABLE_CLAUDEAI_MCP_SERVERS`, `ANTHROPIC_BASE_URL`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_SMALL_FAST_MODEL`, `ANTHROPIC_DEFAULT_*`, `CLAUDE_CODE_SUBAGENT_MODEL`, `CLAUDE_CODE_AUTO_COMPACT_WINDOW`, `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`) or anything in the **`RETASKABLE_*`** namespace. A program's own known names are always allowed (another program's known name is just a custom one there). Its value is trimmed, 1 to 8192 bytes, spaces allowed, no NUL or other control character (a line break can't be written in the advanced text box). At most 64 custom variables per program. A name that differs only by case from a known one, another in the same save or one already saved is refused as the same variable. A custom variable is **sealed exactly like a known secret** (the same `secrets` map of the program's file, the same data key and cipher, its name as associated data), **applied the same way** (a saved one wins over the environment and is put in the process environment, `apply`, `refresh`, `commit`) and **Reset** is the same: deleting one puts back the environment's value the variable had (noted at start, or when the variable was first added), or removes it. **Who inherits them:** everything the program starts with the process environment: `gh`, `git`, and the Claude, Codex, Cursor and Pi sessions. **Not the CI check containers**: `docker` is run with its environment cleared to what docker itself needs and each container gets only the `-e` list the runner writes, which is the rule today for `GH_TOKEN` (repo code in a check is untrusted); a custom variable never reaches one. A name in a hand-edited file that the rules refuse is ignored with a warning. The site is told the names of the known secrets only, never of a custom variable.
- **A saved secret wins over the environment.** **[Decided 2026-11-16, the owner: "i said i wanted the config/web secrets to override the env not the other way around"]** This is for secrets only, and in all three programs; ordinary settings keep the environment winning and locked (above, and agent-ci.md section 3.7). It diverges from the TypeScript agent (Retaskable.com #3859, #3850), which layers the environment first; the encrypted config is Rust-only, so nothing else follows it. At start, before anything is spawned (`Secrets::apply`, called in `main` before the first project starts), a variable with a non-empty value is noted with its value as the one the process started with (an empty one, compose's unset `${X:-}`, is none). A secret that is saved is decrypted and put in the agent's own environment, **replacing** the variable's value, and every session, check and script it starts inherits it. One that was never saved keeps the environment's value. **Deleting a saved one** (the page's Reset, `secret reset`, or a `null` save) puts the started-with environment value back, or removes the variable when the environment had none; this applies live. Nothing is ever locked because the environment sets it. `RETASKABLE_SAVED_SECRETS` names the ones the agent put there (names only), so a restarted agent, which inherits that environment, doesn't mistake the saved value it finds there for the environment's (after such a restart the original environment value is unknown, so a later delete leaves the variable unset unless the environment changed it). **A saved secret that won't open** (no key, the wrong key) fails closed: the variable is removed from the process, never left at the environment's value, a warning is logged, and the page shows **Unreadable**; Reset (delete) is how to get back to the environment's value.
- **Saved** in `config.json`, in a `secrets` object, `{ "<NAME>": "<ciphertext>" }`: the same file as the rest of the computer's settings, so one place to back up or move, and `save_machine_settings` keeps `secrets` (and any key it doesn't know) through every other save. A sibling `secrets.json` was the other choice; it would add a second file to keep in step with the first and nothing the config's patching doesn't already give.
- **The cipher**: XChaCha20-Poly1305 (the RustCrypto `chacha20poly1305` crate, `src/secrets/cipher.rs`) under a 256-bit data key, a fresh random 24-byte nonce for every seal (so saving the same value twice stores different text), and the secret's NAME as associated data (so a ciphertext copied under another name doesn't open). Stored as `v1:<base64 of nonce, then ciphertext and tag>`; the version prefix lets another cipher live beside it.
- **The key**: one random data key per data folder, never in the config (`src/secrets/key.rs`):
  1. `RETASKABLE_SECRETS_KEY_FILE`: a file holding the key as base64 (32 bytes). On Unix it must be readable by this user only (0600); one that isn't is refused. If the file isn't there yet, the first save creates it with a fresh key (0600).
  2. `RETASKABLE_SECRETS_KEY`: the key as base64. Read once at start and then removed from the agent's own environment, so no session inherits it. (A copy of the agent that restarts itself without its supervisor would not have it; a supervisor such as Docker or systemd brings its own back. The file does not depend on this.)
  3. The OS credential store (Windows Credential Manager, macOS Keychain, the Secret Service), service `retaskable-secrets-key`, account a hash of the data folder's absolute path. Made on the first save, not at start.
  4. None of these (no OS store, no variable): secrets can't be saved, and the page says so, naming both variables.
- **Plainly, on a computer with no OS store (Docker), the key sits beside the config** (a file in the volume, or the container's environment). Anyone who can read the data folder and the key can read the secrets; the protection there is file permissions, not the cipher. What the encryption buys everywhere is that the config on its own (a backup, a copied folder, a screen share, an accidental commit) holds no usable secret. It is not a boundary against a process running as the same user: the sessions get the same tokens in their environment (but not `CLOUDFLARE_API_TOKEN`, which sessions never get) and could read the key where the user can.
- **Fail closed.** A missing or wrong key, a changed ciphertext, one under another name, a format this build doesn't know, or an OS store that won't answer: that secret reads as **Unreadable: save it again**. It is not put in the environment, there is no plaintext fallback, and nothing crashes. Saving it again makes it readable under the key now in use.
- **From a terminal.** `retaskable secret set <NAME>` (and `retaskable-ci secret set <NAME>` for the CI runner's `GH_TOKEN`) saves one without the page, for a container with no browser to hand: the value is asked for with no echo at a terminal, or read as the first line of stdin when piped, and never taken from an argument (a value given as one is refused). The NAME is one of that program's own (`SECRETS`, `CI_SECRETS`) or any other name the rules above allow (`secret set MY_KEY`, `secret reset MY_KEY`; `secret list` shows custom ones too); the value is sealed under the key above exactly as a page save is, so with `RETASKABLE_SECRETS_KEY_FILE` the first save makes the key file (0600), and with no key anywhere, or a key file others can read, nothing is saved and no value is asked for. `secret list` prints each name, its source (`saved` or `unset`, or `unreadable`) and fingerprint, never a value. Neither touches the process environment or runs `gh`: the CI runner takes a saved value up live (`refresh`), the code agent at its next start (`apply` then also runs `gh auth setup-git` for a saved `GH_TOKEN`, so a container's start script needs no token of its own). `src/secrets/cli.rs`.
- **Moving from the TypeScript agent.** At start, for each name the config has no entry for but the TypeScript agent's store does (service `retaskable-secret`, account the name, in the OS store or in `credentials.json`, or the file `RETASKABLE_CREDENTIALS_FILE` names), the value is encrypted into the config and then the old entry is deleted, with one line in the log naming the secrets (never a value). The link tokens beside them in `credentials.json` stay. An entry the config already has wins and the old one is left alone; without a key to seal with, the old one stays where it is and the log says why.
- **The page shows** each as **Saved on this computer** (it wins over the environment's value), **From the environment** (nothing saved), **Not set**, or **Unreadable: save it again**, and a set one's fingerprint: the first 8 hex characters of its SHA-256 (`sha256 1a2b3c4d`). Never the value: the page never has it, and no response, log line or error carries one. A field takes a new one (written only, cleared on every render, empty keeps the saved one), whether or not the environment sets it. Each row carries `envSet` (the program's environment set it when it started). A saved or unreadable one has a **Reset** button, shown only then: "Use the environment's value" when `envSet`, "Clear" otherwise. It deletes the saved value at once (a `{ "secrets": { "NAME": null } }` save, so the same session, CSRF, Origin, Host and this-computer checks as any save, and no new route), and the process goes back to the original environment value. `retaskable secret reset <NAME>` does the same from a terminal.
- **The secrets card is an environment-variable editor** (**[Decided 2026-11-16, the owner]**, `assets/settings-secrets.js`, `RT.secrets.editor`, one script for the code agent's page, the CI runner's trimmed page and every program's tab). - **Only from this computer** (section 4.3).
- **The other two programs' secrets** (**[Decided 2026-11-16]**, `Owner`, `src/secrets/mod.rs`). ### 3.4 Starting paused

## 4. The settings page

### 4.1 What it is

- `GET /settings` on the agent's port: `agent/settings.html`, plain HTML with a little inline JS and no app code, nothing loaded from elsewhere (inlined in a release build by `scripts/bundle.ts`). Its CSP allows only its own nonce'd script and style and calls to itself; it can't be framed or cached.
- `GET /api/settings` gives the settings, which a variable sets, and whether a restart is waiting (the saved port or network access differs from what the agent runs on). `POST /api/settings` saves a change through `saveSettings` (the config file through `saveConfigFile`, tags and network access in machine.json), then `pool.configure`, then a new hello. The port and network access say "Saved. The port and network access change once Retaskable restarts." with **Restart now**, which is `POST /api/settings/restart`, the same `requestRestart` as the site's Restart.
- `/api/health` is unchanged. Every other path is still a 404. The port never takes a command.

### 4.2 Signing in on this computer

- `SettingsServer::settings_link()` makes the address the tray's **Settings…** (and the terminal menu's) opens, and the first run below opens, `http://127.0.0.1:<port>/settings#<token>`: a random token, made for that click, good once within 5 minutes. A token in the fragment never reaches a server log or a `Referer`.
- The page takes it out of the address and posts it to `/api/settings/session`, which answers with a session cookie (`HttpOnly`, `SameSite=Strict`, 8 hours) and a CSRF token. A tray token is taken only from the computer itself (a loopback address); one from another address is refused and not used up.

### 4.3 What every request must have

- **Its Host is this computer's own**: `127.0.0.1`, `localhost` or `[::1]` at the port it answered on, and while network access is on, the computer's own network addresses. Any other (a DNS name pointed at 127.0.0.1) is refused: no DNS rebinding.
- **A POST's Origin is its own** (`http://<the Host>`), and its body is JSON of at most 16 KB, so another page can't post a form to it.
- **A change has the session's CSRF token** in `X-CSRF-Token`, compared in constant time.
- **This computer** is a request from a loopback address, or, with `RETASKABLE_TRUST_DOCKER_HOST=1` (section 4.4), from the container's default gateway. A one-time link is taken only from it, a password signs in from it where the program allows that (the CI runner's does with network access off), and the next point is about it.
- **Secrets are saved only from this computer** (section 3.3): a request from it, or, with `RETASKABLE_SETTINGS_PUBLISHED_LOCAL=1`, one whose Host is `127.0.0.1`, `localhost` or `[::1]`. Any other answers 403 "Secrets can be saved only on this computer." and nothing of it is saved (not even a clear); `GET /api/settings` says which with `canSaveSecrets`.
- **From another computer**, only while network access is on, and signed in only with the password; a tray token doesn't work there.
- **Wrong tries wait.** Five wrong tokens or passwords from one address within a minute and it waits a minute, then two, then four, up to an hour; even the right password waits.

### 4.4 Network access

Off by default. When it was on with a password as the agent started (or `RETASKABLE_NETWORK_PASSWORD` is set), the port listens on every address (`0.0.0.0`) instead of `127.0.0.1`, and the console says the page is open on the network. Turned off while running, other computers are refused at once; the binding changes at the restart. The page is plain `http` on the local network: a password typed there crosses it unencrypted, as on any router's own page, so it's a password for this page only. The port binds `127.0.0.1` unless the person at the computer turns this on, and never takes a command either way.

**In a Docker container (`RETASKABLE_TRUST_DOCKER_HOST=1`, Linux only; docker.md section 7).** A port Docker publishes on the host's `127.0.0.1` reaches the container from its default gateway, not from loopback, and the page must listen on `0.0.0.0` inside the container for the publish to reach it at all. With the variable set the page binds `0.0.0.0` (code agent and CI runner alike, `page_host::docker_trust::bind_ip`), reads the default route's gateway from `/proc/net/route` once at start and logs it, and counts a request whose peer address is that gateway as this computer, for the one-time link, the password-optional sign-in and saving secrets. Every other peer is treated exactly as with the variable unset: with network access off it is refused with the same 404. The Host and Origin checks are unchanged (`localhost:<port>` or `127.0.0.1:<port>`, which is what the host's browser sends). With the variable set but no default route readable, nothing is trusted and the log says so. The compose file must publish the port on `127.0.0.1` only: that is what keeps the gateway meaning "the host itself", and a port published on every address would let another computer's request look like the host's. Without the variable nothing changes (`127.0.0.1`).

A release build opens the page once by itself, on its first run with no config file yet (`settingsOpened` in machine.json, set when it opens, even if no browser could be started). A checkout build never opens it.

A folder that exists with something in it, one inside the data folder or inside a project's worktrees folder is refused.
- **The entry** has `id` (the folder's name in kebab case, `-2`, `-3` when taken), `repoPath`, `githubRepo` (GitHub's own spelling), `backlogPath`, `baseBranch` (**always** GitHub's default branch for the repo, the owner's decision: never empty, so the agent never reads `origin/`), `worktreesDir` (`<folder's parent>/.retaskable-worktrees/<folder name>`, `defaultWorktreesDir`), `projectType`, `requireCi` (the repo has workflows), `checks` and `playCommand` (the scan), and `deploy.mergesTo` `production` (a new project starts Production only). It is written into `projects[]` with the file's other settings kept, atomically (`write_json_atomic`). A file in the old one-project format (no `version`) is refused in words rather than rewritten.
- **A project with no `baseBranch`** in a hand-edited `config.json` takes its repo's default branch once at start (`gh repo view`, or the plain remote's `HEAD`, else `refs/remotes/origin/HEAD`; `config::resolve_base_branches`) and says so in the log; one that can't be found stays empty, with a warning.
- **It starts paused, and applying it takes a restart.** The agent builds each part (the orchestrator, the connectors, the store sockets, the lane pollers) from the project list once, at start, and can't take one more live; so an add ends by restarting the agent through the same exit as the page's **Restart** button, and the page says so, and that a restart signs the page out (open **Settings** from the tray again). The new project's id is first written to the `hold` list of `start-paused.json` (3.4), so the next start pauses it with this computer's own pause whether `RETASKABLE_START_PAUSED` is set or not, takes it off the list and records it, and a later restart after a resume doesn't pause it again. If the hold can't be written nothing is added. The page tells the person that **Resume** is on this page (the project's row) and on retaskable.com, for when it is ready.
- **Pause / Resume** (**[Decided 2026-11-16]**, the owner: a project that started paused had no way to be resumed from here). Each project row shows this computer's pause reason (e.g. "Paused at its first start (RETASKABLE_START_PAUSED): resume it when it's ready") with a **Resume** button, or a **Pause** button when it isn't paused. It is this computer only, and it is a setting, not a command: `POST /api/projects/{id}/paused` with `{ paused: true|false }` (the same session, CSRF, Origin, Host and this-computer checks as an add: 401, then 403 from another computer; an unknown id is 404). It is named for the setting it changes, as no route is named for a command (`no_route_is_named_like_a_command`). It runs the very functions the site's `pause` and `resume` with `computer: true` run (`commands::pause_computer`, `resume_computer`, so `PauseState::set`: `paused.json`, and the snapshot the hub is sent on a change), with the reason "Paused from the settings page" (the site's is "Paused from retaskable.com by <who>", the chat's "Paused from the chat"), and applies live, with no restart. `GET /api/projects` rows carry `paused` (the reason, or null) and `storePaused` (true, false, or null when not known, with `storePausedReason`): a pause the store holds for every computer on retaskable.com is shown read-only ("Paused for every computer on retaskable.com"), and resuming this computer leaves it alone. `canPause` is `canAdd`'s: this computer only.
- **No token is ever shown.** Every message the page is sent or the log holds goes through `add_project::redact` first: a token's own shape (`ghp_…`, `github_pat_…`, `x-access-token:…`) and the value of each token variable this process holds.
- **Remove project** is not here: the TypeScript agent removes a project only from retaskable.com's **Unlink** (`unlink_project`, projects.md section 6.6), a command this agent's port never takes.

## 5. Setup

A setting a variable sets is said, not asked. Without a terminal nothing is asked. It saves as the page does (the same `Saver` in `src/settings_server/save.rs`, so the same validation and refusals, asked again) and says "Saved. If Retaskable is running, restart it to use them." A running agent's own saves of machine.json keep the tags and network access setup wrote meanwhile.
