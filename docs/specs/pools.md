# Pools: run what the server sends — Spec

Status: v0.5, built in part (2026-11-17). Backlog: `pool-tasks`. Copies the TypeScript agent's pool work (`poolTasks.ts`, `poolReport.ts`, `fixTasks.ts`, `jobTasks.ts`), which Retaskable.com's [pools-on-server.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/pools-on-server.md) and chores-on-server.md stay the source for. Builds on [agent.md](agent.md), [pieces.md](pieces.md) and [agent/07.5-what-a-claim-and-a-give-back-send.md](agent/07.5-what-a-claim-and-a-give-back-send.md).

Theme: Orchestration

Kind: change

## 1. What this is

The store stops answering `claim_next`, `lane_take` and `agent_settings` once the agent release ships. Work comes as **tasks**: the computer reports `health` with `obeys: true` and the answer lists what to run. A task is an item's whole chain on this computer. Pieces still come by `run_take` (pieces.md), side by side with the tasks: a runs-mode computer reports `health` and takes tasks too (section 3e).

## 2. Decided

- The computer starts nothing the store did not send; with the store unreachable it starts nothing (fail closed, no fallback).
- A finishing write (`task_end`) is kept in the state file until the store answers, also across a restart (the owner's outage rule: finish what it is doing, take nothing new).
- The tier is the store's (`smart` or `fast`); the model is the computer's: `smart` is the item flow's `opus` tier, `fast` is `sonnet` (`Tier::item_tier`).

## 3. As built (claim mode)

- **Ops** (`src/backlog/pool.rs`, tests with a copy of the store's argument rules in `pool/contract.rs`): `health`, `task_end` (answer `{ held }`; `false` drops the end), `claim { id, agent }` by name (the store answers its own lease token), `chore_trigger` (`behind_main` for a person's Sync now only; the contract still knows `red_main`, `playtest_fix` and `staging_smoke`, which this agent sends no more: the store derives a red main from `health.main` and makes the smoke fix from the smoke task's result) and `chore_nofix`, `chores_get` (`noFixSha`).
- **Report** (`src/orchestrator/driver/pool.rs`): once a minute per project, at once on `work_available`, paused or not: `{ obeys, can: [], project, agent (machine, environment, baseBranch, tags, week), running: [{ id }], usage (the open five-hour window), limits (engine to epoch ms), spend, refused?, paused, draining, main? }` (`main`, the base branch's facts, below). `can` is the facts about what a job needs here (`jobs::job_can`: `chrome` until a run found none, `repo` and `engine` for a project with a folder, `scanToken` when the probes are on and the staging origin has a saved test token, and the `issues:<tracker>` facts below); empty when no job host is wired. `refused` is `signed out` when no lane on another engine can start, or the port guard's words.
- **Receiving** (`src/pool_tasks.rs`): a task id is taken once per run of the agent (a restart reports the tasks it still runs, kept as `state.pool_tasks`, so they are not taken again). Nothing is received while paused (own or store pause, or the store's unknown), stopping, with no session slot, no lane that may start, or a full model cap.
  - the kind of a task is its `run` (section 3g), never its subject; an item (`run: item`, `subject` is the item's id): claimed by name, `take_lease`, then the existing flow starts it. `conflict`, `not_found` and `held_by_owner` end the task not ok; any other error forgets it, and the store sends it again;
  - every chore (`run: chore` with its `kind`: `fix_main`, `tidy`, `tests`, `bugs`; `run: fix` named by `fix.kind`; `run: sync`): a local item (section 3d); a chore kind it doesn't know ends not ok with `No chore called <kind> here.`; every job: ended at once, not ok, with `This computer doesn't run <kind> jobs.`
- **Ending**: the task is open while its item is queued, implementing, checking or reviewing; ok once the item is handed on (awaiting CI, merging, awaiting merge, awaiting playtest, merged, done); not ok when it needs clarification or a person, or has left the loop. The end is written to `state.task_ends_owed` before it is sent, sent again every minute until answered; a coded refusal drops it; one older than a day is dropped.
- **`stop`** in the answer closes a parked chore (section 3g); for any other task it is logged only.

## 3a. The item flow as built (claim mode)

A step is a future the loop runs as the item's own task (`steps::Running`); it reads the lane and the code host, never the store, and hands back the run, a flow record, notes for the item's history and, when the item goes back to its implementer, a message. The loop (`driver/flow.rs`) applies that, queues the resume, and tells the store. State transitions stay `item_lifecycle`'s plain code.

- **`checking`** (`flow/checks.rs`): the lane's processes are stopped, the project's checks run with the baseline comparison (a failure main has too is `preexisting`), the evidence (marks, diff stat) is kept for the review. A blocking failure goes back to the implementer's session, resumed with `The project's checks failed on your branch:` and each failing check's output tail, up to `maxCheckRounds`, then a person; a pass goes to `reviewing`. The change the session opened is found by its branch (`gh pr list --head`) and kept.
- **`reviewing`** (`flow/review.rs`): an approval that still covers the head is reused (same head, a rebase whose own changes read the same, a conflict's resolution of at most 12 lines: `piece_approval::reuse`, the same rule a piece's run applies). Otherwise the scouts and the reviewer read the lane (`piece_review::run_lane_review`, shared with the runs) and the comment goes on the change. Approved: the head is the approved one; a diff that raises the tier (`piece_tier::held`) or a try-out the project's `playtests` asks for goes to `awaiting_playtest` (the held reasons in the try-out's words), `after_merge` keeps the try-out for after the merge (`flow.pendingPlaytest`), else to the merge (or CI with `ciWhenReady`). Requested changes go back (`The reviewer requested changes (round N):` ...) up to `maxReviewRounds`; a person's steps or a decision go to `needs_human` with the TypeScript reasons. A usage limit leaves the item in `reviewing` and the step is asked again later (`flow.retryAfterMs`).
- **Sending back**: the message is kept in the item's record (`flow.followUp`) and the session is resumed with it (`Launch::Resume`, `StartRequest.follow_up` with `resume`); one that cannot be resumed (grown, another engine) gets the message in a fresh session's prompt. The record (`RunRecord.flow`: change, rounds, approved head, last review, try-out) is in the state file, so a restart carries on mid-chain.
- **What the store hears**: `report { id, token, status, detail, branch, prUrl, note?, claudeOnIt? }` whenever an item's status, state, branch or change moved (`claimed`, `building`, `in_review`, `merging`, `needs_person`), kept and sent again until answered (`backlog/progress.rs`, TypeScript `HostedWork.changed`, `hostedWork.ts:603`). A refusal is a `store_error`; `stale_lease` ends it.
- **A chore item** (local, no store item) takes the same steps: a step takes no store, and the loop leaves `report`, `park`, `complete` out for an item it holds no lease for (`progress_of` returns nothing without one); the PR is found by branch.

## 3b. The item flow's merge, CI and parking as built (claim mode)

- **CI** (`awaiting_ci`): the change is found by its branch when the record has none. CI is not waited for where no workflow runs for the base (`ci_coverage`) or the host is not GitHub. With `ciWhenReady` the `ci-ready` label goes on beside the checks (`start`, after the host shows the push as the head and the change is 20 seconds old) and only a check that ended after it counts. Pass, red (each failed check's log in the send-back, a check round), a cancelled run run again (`maxCiReruns`, default 3), a pending check past `ciMaxMinutes` cancelled to be run again and then a person, nothing reported past `ciGraceMinutes` carry on. The poll is every 15 seconds (`flow.retryAfterMs`).
- **A state that works in a lane** entered from one that holds none (CI passed, a send-back from `awaiting_ci` or `merging`) waits for a lane in the loop (`lane_resumes.rs`, `advance`); a step puts the item's pushed branch on it (`flow/lane.rs`).
- **Parking** (`parkFor`): `awaiting_ci` (`ci`), `awaiting_playtest` (`tryout`) with a change on the host and no lane, and `awaiting_merge` where a person lands it (`merge`). Details go first, the park is kept owed until the store takes it and recorded in the state file (`parked`) with the item's record. The step keeps polling the host while parked. When the state moves on the lease is claimed back by name (`claim`) before anything is written for it; a refusal for good (another computer has it) drops the run. A restart takes a parked item up again in its state, or drops it when the store no longer lists it waiting. `needs_human` is not parked, as in TypeScript, because a session worked on it; the no-session case TypeScript parks (`help`) is not built.
- **Merge**: the store's turn comes first (`merge_enqueue` with `holdsBranch`, `merge_next`, then a `merge_beat` each pass before the step runs; a store that cannot be asked is a wait). The step merges with the project's method, hands to GitHub's auto-merge (`--auto`) or a person (`awaiting_merge`, `land`), brings a conflicting change or one GitHub cannot work out for 5 minutes up to date (clean: back to `awaiting_ci`; conflict: the implementer, `maxConflictRounds`), sends a head pushed since the approval through CI again, retries a merge GitHub is not ready for (`maxMergeRetries`). The loop sends `merge_result` (kept and sent again) and, once merged, `complete { built, remaining, mergeCommit, onDefaultBranch, playtest }` through the outbox (`outbox.rs`), claiming the lease back first. An item with no lease (a synthetic chore) takes the steps and leaves `report`, `park` and `complete` out; its turn is queued as a chore entry.
- **Divergences from TypeScript**: the beat before `gh pr merge` is the loop's, just before the step starts, not inside it; an update from the base always sends the change through CI and the checks again (the review reuses the approval when the changes read the same), where TypeScript keeps the approval through CI; the CI `since` filter only drops a failure that ended before the label (a pass from before the label is not told apart); `ciInfra` reruns (a run lost to the machine) and the "CI looks broken" health note are not ported; the 20-second settle for a new change is a sleep in the step; a `gh` error is retried each poll without a count; the CI-coverage read in `watch_run` passes `origin/<base>` where `ci_coverage` wants the plain branch name (suspected flaw, `watch_run/mod.rs`, left alone).

## 3c. Try-outs and reopen as built (claim mode)

TypeScript: `review.ts:219` (`pendingPlaytest`), `steps.ts:553` (`implPlaytest`), `merge.ts:333` (`landed`), `storeTryouts.ts` (`send`, `problem`), `reopen.ts`, `orchestratorActions.ts` (`playtestHere`, `deferredPlaytest`).

- **Details** (`backlog/decisions.rs`): `playtest` and `pendingPlaytest` (`{ what, steps }`, cut to the store's 2000 characters and 50 steps) sit beside the 26 decision fields (`TRYOUT_FIELDS`), filled from the item's record (`FlowRecord.playtest`, `pending_playtest`) each time a step ends (`sync_tryouts`) and written with the pass's `details_report`, or before a park lets go of the lease. `implPlaytest` is not written: the implementer's suggested try-out is read from its own answer file when the slice merges and goes in `complete` as the store's `implPlaytest`. A synthetic chore item has no details and writes nothing.
- **After the merge** (`driver/item_merge.rs`, `outbox.rs`): the deferred try-out (the record's `pending_playtest`, else the details') is listed in the completion outbox with the completion, so an outage or a restart keeps both; the record and the details are cleared in the same `details_report` that precedes `complete`. Once `complete` is taken, `tryout_add { itemId, mergedAt, title, what, steps, prUrl, sha (the merge commit), servedAt (staging's url), machine }` is sent and kept until the store answers; a `bad_request` or `forbidden` drops it, any other failure keeps it. The key `<id>@<mergedAt>` is then kept with the session and lane that built the slice (`state.tryouts_built`, the last 200). Divergence: TypeScript clears the store's copy first and sends from memory only, so a restart between them loses the try-out.
- **A person's answer to the try-out of an item held here** (`driver/item_commands.rs`): a pass moves the item to the merge (or CI); a problem sends the implementer back with the notes and, where the record kept it, what they were asked to check. An item parked for its try-out is claimed back by name first (`claim_one`): a refusal for good drops the answer, a store that can't be asked leaves it waiting. An item with no lane takes one and starts a new session on its pushed branch with the picking-up prompt. The answer ends the try-out in the record and the details. An answer for a merged slice's try-out goes to the store (`tryout_result`, `playtest_owed.rs`).
- **Reopen** (`driver/reopening.rs`, `src/reopen.rs`): the store's `tryout_problem` push is kept for the project's loop (`WorkSignals::problem`). A key this computer has in `tryouts_built` is taken (`tryout_taken`, which answers the rest of the row), then `reopen { id, notes, by, what, steps, agent, key, title, prUrl }` asks the store, which decides both ways (section 3g): it reopens the item and hands it back under a lease, and it starts like a claimed item, or it keeps the item (a chore's own try-out, an item being built) and makes the playtest fix itself, answering `fix: queued | open | taken`, and the fix comes back as a task. The agent has no rule for which item may reopen and sends no `chore_trigger playtest_fix`. A key with no record here is left to the store (the item reopens itself after 2 minutes). Divergence: the reopened item starts a new session from the item's own remaining work (the person's notes and the try-out's steps), not the builder's session resumed with `resumeForReopen`: a session belongs to the lane it ran in and the item takes whichever lane is free. The stats correction TypeScript writes on a problem is not ported.
- **Tested**: `src/orchestrator/driver/tests/item_flow/{tryouts,reopen,chain}.rs`: the details, the try-out after the completion and through an outage and a restart, a problem on a parked and a lane-less item, the reopen and its fallback, and one test of the whole chain (task, claim, checks, review, CI, parking, merge, completion, try-out, task end).

## 3d. Chore tasks as local items, and the triggers (built)

The agent never schedules a chore: the store sends it as a task, and the agent reports what only a computer can see as facts (`health.main`, the main look below), sending `chore_trigger` only for a person's Sync now. TypeScript: `chores.ts` (`addTaskChore`, `reportRedMain`), `fixTasks.ts`, `mainSync.ts` (`startSync`), `orchestratorSync.ts` (`syncTask`, `maybeSyncMain`), `steps.ts`, `stepsCi.ts`, `merge.ts`, `review.ts`.

- **The item** (`src/chore_items.rs`, `driver/chores.rs`): the task's id, no store item, no lease. Kept in `state.chores` with its run record, so a restart takes it back in its state (`driver/readopt.rs`). The loop writes nothing to the store for it except the merge turn (`merge_enqueue chore:true`) and `task_end`; a merged chore stays `done` until its task has ended, then is forgotten.
- **The session** is briefed with the store's own words (`prompts/chore.md`, the main sync's `prompts/sync-main.md`), on the chore tier (a playtest fix keeps the item's tier). Titles: `<label>: <fix title or subject>`, `Fix main: main's checks failing`, `<label>: finding something worth doing`. A `fix_main` from `chore:fix_main` keeps main's commit as `red_sha`.
- **Differences from a roadmap item** (as TypeScript): a fix main is not forgiven what main fails too (no baseline comparison); a main sync skips the code gates and the review (checks go to the merge), adds no `ci-ready` label step and merges with a merge commit; a chore's review is told it is a chore.
- **A chore that stops** (needs a person or clarification, gave up, nothing left) is parked and reported, not decided on: section 3g.
- **`chore:sync_main:<branch>`** (`sync_task`): merges main into a branch off the base in the sync worktree (plain code); clean: the change is open and the item waits for CI; conflict: queued for a session on the sync's branch. Nothing to do any more (caught up, a sync open here, no default branch) ends the task ok.
- **The main look** (`src/main_look.rs`, `driver/main_facts.rs`; Store PR B, pools-on-server.md section 15): this computer decides nothing about main being red or behind and sends no `chore_trigger red_main` or `behind_main` (except a person's Sync now, `driver/main_sync.rs`). After each good fetch (`report`) it keeps the base branch's head, the tree of `.github/workflows` there (null when none) and how far the default branch is ahead (`behind: { branch, head, count }`, left out when the base is the default branch); `health` carries them as `main` with the baseline `{ sha, failed }`, the CI `{ sha, state, failed }` and the CI coverage key `{ base, tree }` it holds, and `busy: true` while the base checkout is in use (`base_hold`, a baseline running included). Nothing is sent before the first fetch, and every part is checked against the store's shape first (`MainLook::facts`; `contract::main_facts` is the test copy): a part that does not fit is left out, because the store refuses the whole `health` for one malformed `main`. The store's `main` job (`job.kind` `main`, `args { want, sha }`; no session, no slot, one at a time with the other jobs, started whatever else holds this computer back) is run by `main_look::main_job`: if `sha` is no longer the base head it ends ok with `{ sha }`; `coverage` reads the workflows, writes the `ci_coverage` fact (GitHub projects only; another host holds the key and writes no row, so the store stops asking) and answers `{ sha }`; `ci` reads the host's CI (refused where the host cannot say; a cancelled run is no failure; a failure naming no check is `none`) and answers `{ sha, ci }`; `baseline` runs the approved checks in the base checkout (`busy: true` when it is taken; failed with a note when it cannot run; refused when no check is approved here, which is not a green main) and answers `{ sha, baseline }`. When anything failed the answer carries `brief`, at most 20 000 characters of the failing checks' last lines and the CI logs. The results are also kept as the `baseline` and `main_ci` facts. **The integration-branch rebase** (`src/main_rebase.rs`; Store PR C, pools-on-server.md section 17): a project saved with the `integration` pattern (`github.pattern`) catches its base branch up with main by a rebase, not a sync pull request. It reports `main.rebase: { branch, head, base, count, waiting }` in place of `behind` (`waiting` names the items, pieces and drafts cut from the base branch that have not gone in yet, read live for each `health` and each job: `ProjectLoop::waiting_on_base`), and the store asks for it with `main` job `want: "rebase"` (`args { sha, main, mainSha }`). The job answers the bare `{ sha }` when the base head is no longer `sha` or main no longer `mainSha`, `busy: true` when anything waits or the checkout is in use, else rebases `origin/<base>` onto `origin/<main>` in `<worktrees_dir>/rebase-main` and pushes with `--force-with-lease` on the head it read: `{ sha, rebase: {} }` when pushed or already up to date, `{ sha, rebase: { conflict: [files] } }` (nothing pushed) or `{ sha, rebase: { error } }`. This agent had no rebase of its own to delete; the `sync_main` task of such a project ends ok at once. Sync now on such a project is a direct call (it rebases at once, refusing for nothing behind, something waiting or a busy checkout, and saying a conflict's files) and sends the store nothing; the team-branch strip's `rebase` field is not ported. A fix main that ends without a merge still sends `chore_nofix` and shows "Fixing main found nothing to fix at <sha>" until main moves.
- **Facts**: the baseline, main's CI and the CI coverage are kept as the store's `baseline`, `main_ci` and `ci_coverage` facts through `kept_facts` (`keep_result`).
- **Gone**: `add via:"chore"` (`add_fix_main`, `add_sync_main`), the `fix_main` and `sync_main` locks the agent took for them, and the sync's own add/lock/drop.
- **Divergences**: a playtest fix starts a fresh session (the builder's is not resumed, as for a reopen); `extraSlot` (a rollback's revert) takes a normal lane and slot; a chore's own try-out is not sent after its merge (no completion for a lease-less item); the lane preference of a chore (`choreLane`) and the order (fix before items before chores) are not applied; `afterMainSync` (sending open changes that now conflict back to rebase) is not ported; the chore's title is not rewritten from the session's description.

## 3e. The runs-mode hybrid (built)

A runs-mode computer with a session runner (`Machine::claims`) reports `health { obeys: true }` and takes the items and chore tasks the store sends, beside the pieces it takes by `run_take`. Lanes and session slots are shared; the passes that are not about an item run once. What was hard-wired to claim mode follows `takes_tasks` (merge rows naming an item, expert ships, a Cursor limit's give-back, owed releases); a Play names the item idle in the lane, else the piece whose run last took it. Tested: `tests/item_flow/chores.rs` (`a_runs_mode_computer_takes_...`).

## 3f. Jobs (built)

A task with a `job` (`lighthouse`, `probes`, `a11y`, `vet`, `deprecations`, `triage`, `release_notes`; `smoke` is the exception below) runs a fixed command and ends with its raw result; the store owns the day, the lock, the schedule and what the result means (jobs-on-server.md). TypeScript: `jobTasks.ts`, `poolTasks.ts` (`TaskRuns.runJob`). Rust: `src/jobs/` (the entries), `jobs/run.rs` (the kind picks the entry and the computer's settings fill its input), `jobs/host.rs` (the seam for the tools and the session), `orchestrator/driver/job_tasks.rs` (the queue), `orchestrator/job_host.rs` (the real host).

- **The staging smoke** (`job.kind` `smoke`, `args { sha, url, command }`; [06.3](agent/06.3-review.md), TypeScript `runSmokeTask`) is the one job that is not queued: `orchestrator/driver/smoke_task.rs` runs it on its own blocking thread (`smoke::run_with`) with no slot and no lane, because it waits up to 20 minutes for staging to serve the commit. It is in `health.running` until it ends, never run twice (the task id is seen once), refused in words when the url, the command or the commit isn't what the project's own settings allow, and ended `ok: true` with `result { sha, outcome, tail? }`. It is not held back by a pause (a stopping agent calls its wait off and tells nothing). `can` holds `repo` when the project has a checkout here (`jobs::job_can`), which is what the store looks for.
- **One at a time per project**, off the loop (a spawned task; blocking work is `spawn_blocking`). Not started while the project is paused or the agent is stopping. A job is in `health.running` while it waits or runs. Not kept across a restart: its lease runs out and the store sends it again.
- **Session jobs** (`vet`, `triage`, `release_notes`) wait for one of the computer's session slots and hold it while they run (`Machine::sessions`); the others take no slot and no lane. The session is read-only and ephemeral, in the base checkout when there is one, listed on the Agents tab as `_vet`, `_triage`, `_release`: triage on the triager's engine at the chore tier (the top tier for a check) with `budget.reviewerUsd`; vet and release notes on the writer's engine at the scouts' tier (haiku, or the local model while it is free) with `budget.scoutUsd` and `budget.releaseNotesUsd`.
- **The end** is `task_end { id, ok, result?, known?, refused?, note?, noRetry?, limitHit? }` (`jobs::end_body`, `TaskEnd::from_job_body`), kept in the state file until the store answers like any end (section 2). A kind this computer doesn't run, or no job host, is a refusal in words. A secret is never in a result.
- **Settings**: the `scan` section of the project's config (`probes`, `a11y`, `pages`, `signedInPaths`), `lighthouse.*` and the deploy urls; a task's url must be the staging origin the settings name. The staging test token is a saved secret per origin, `SCAN_TOKEN_<HOST>` (the host upper-cased, other characters `_`, a port appended), read at the run and never logged (the TypeScript agent keeps it in the credential store under `retaskable-scan-token`; this is an agent-side choice).
- **Lighthouse** runs `npx lighthouse` and uploads each report to the store (`POST /v1/repos/<id>/lighthouse/<day>/<file>`), deleting the file once the store's sha-256 matches. **Probes** use `reqwest` and a `rustls` handshake (`jobs/probes_tls.rs`; TLS 1.0 and 1.1 are `unknown`). The **sweep** drives a Node `playwright-core` script (`assets/a11y-browser.cjs`, `jobs/a11y_browser.rs`; Node modules are installed on demand under `a11y-tools/` in the data folder; no Chromium is the no-Chrome refusal). **Vet** asks the project's hub through the cloud link (`suggestions_ask`, `suggestion_verdict`, `BugLink::ask`). **Triage** sends a Retaskable bug it names to the hub scrubbed.
- **Gone from the agent** (it started these on its own): the daily deprecations check and its `jobs_due` asker, the triage pass with its second look and bug sender (`claudeOnIt` is now true while a triage job for the item waits or runs), the vet pass (`src/vet`), the Lighthouse write-up and its prompts.
- **Issues** (`src/issues/`; Store PR C, pools-on-server.md section 16, issue-import.md section 3.7): the store decides when the tracker is read, what comes in, how many wait and which plans' issues are finished; this agent keeps no timer, no `issue-import` `chore_lock`, no list of what was imported, no cap, no timeline note and no `issue_import` fact (the store writes the error). Two light jobs (no session, no slot, started whatever else holds the computer back): `issues` (`args { source, label?, milestone?, team?, project?, site? }`) lists the tracker's open issues and answers `{ issues: [{ ref, title, body (cut to 8000), author, trusted }] (at most 100), milestoneMissing? }`, or ends `ok: false` with the first line of the tracker's own words; `issues_finish` (`args.finish`, at most 20 entries `{ id, ref, comment?, close? }`) does each entry's comment and then its close on the issue's own tracker and answers `{ done: [{ id, commented?, closed?, error? }] }`, always `ok: true`, skipping a malformed entry. `can` carries `issues:github` when the project is on GitHub with a repo (this computer's own `gh`), and `issues:linear` or `issues:jira` when that tracker's key is saved here (a secret); a key is never sent. Show matches (`issues_preview`) stays, tagging each issue with the store's own skip rule (`issues::import::comes`, `issueComes`). The settings page's `issueImport` row field is gone: there is no local check to show an error for.
- **Change actions** (`change_actions`, 2026-11-19, pieces/15 and ci-when-ready/12.19 in Retaskable.com): the store queues the closing of a pull request nobody owns (replaced by a newer change, or of a skipped item) and a forced rerun of a piece's CI, and sends them as a job (`args { actions: [{ id, kind: "close" | "rerun", pr, url?, sha?, comment? }] }`, at most 10) to a computer whose `can` has `changes`. No session, no slot. Only a `retaskable/` branch is touched; a merged or already closed pull request is `skipped`; a `rerun` for a head that moved is `skipped`; a close never deletes the branch. The answer is `{ done: [{ id, ok, skipped?, error? }] }`. The agent decides nothing about which pull request.

## 5. Tests

## 3g. The store decides (built, Store PR A: Retaskable.com pools-on-server.md section 14)

The agent is a dumb client: the store decides what work exists, when, and who does it; the agent reports facts and runs what it is sent. Each part below is built.

- **`run`** (`pool_tasks::classify`, `backlog::pool::TaskInput`): a task says what it is. `item` claims the item `subject` names; `chore` is a rotation chore or a fix main (`kind`: `tidy`, `tests`, `bugs`, `fix_main`); `fix` is a playtest fix or a smoke fix (`fix.kind`, `fix.key`); `sync` is a main sync (`sync { branch, main }`, which `sync_task` uses as the branches); `job` runs the job in `job`. An unknown `run` (or a `chore` with no `kind`, a `fix` with no `fix.kind`, a `job` with no `job`) ends not ok with `This agent doesn't know what a <run> task is.` Nothing is read from `subject` for any of this. A task with **no** `run` (a store older than `run`) is read from its subject as before (`from_subject`), except `chore:specs`: the store queues the specs draft itself now, so the agent has no `specs_task` and no `draft_queue` for it, and an older store's `chore:specs` ends not ok.
- **Own failure** (`Machine::own_failure`, `settle::hand_back`): an own failure before any session ran is reported as `ownFailure { at, why }` (epoch ms, why cut to 300) in every project's `health`, the computer-wide fact in each, until a session starts well (`settle` clears it on a session that answered, needs a person or hit a limit); it is not saved, so a restart clears it. The agent has no `CLAIM_PAUSE` and no `paused after an own failure` refusal: the store answers `wait` and sends no task for `ownFailurePauseMinutes`.
- **Wait** (`pool::Wait`, `ProjectLoop::pool_pass`, `runs.rs`): each `health` answer's `wait` is kept (`Clear`, `Held(words)`, or `Unknown` before the first answer and after one that could not be had). While it is not `Clear` the agent starts nothing it would take itself: no task of the answer (it comes again once the store stops holding it; smoke tasks and jobs are the store's own and are not held) and, on a computer that takes tasks, no piece by `run_take` (`store_lets_runs_start`). A store that can't be read leaves it `Unknown`, so nothing starts (fail closed). What the agent still keeps of its own are the facts of the computer: a local pause (reported as `paused`, held as before), an engine that hit its usage limit or is signed out (`StartGate`), a full lane, session slot or model cap. A computer that takes no tasks reports no `health`, so `run_take` is not gated for it.
- **A chore that stopped** (`driver/chore_stop.rs`): a chore item in `needs_human` or `needs_clarification` is parked. Its task stays open and `health` reports it `running: [{ id, state: "needs_human", why }]` (`why` is the item's reason, `it stopped` when it has none); the agent closes nothing and ends nothing itself. The store decides: a playtest fix and a main sync become an item waiting for a person, every other chore is dropped, and either way it answers `stop: [id]`. On that, the agent closes the chore's change (`SessionStarter::abandon`), tells the store when a fix main stopped at a known commit (`chore_nofix`), frees the lane, forgets the item and ends the task not ok. A `stop` for a task that is not parked is only logged. A chore parked across a restart is still parked after it (its item is in `state.chores`). `drop_stopped_chores` is gone.
- **Tuning** (`src/store_tuning.rs`, `HealthAnswer::tuning`): every number the agent used to hold comes in `health`'s answer as `tuning`: `maxReasks`, `maxMergeRetries`, `maxCiReruns`, `ciMaxMinutes`, `ciGraceMinutes`, `sessionQuietMinutes`, `cursorLimitWaitMinutes`, `weekCutoffPct`, `ownFailureRetries`, `baselineWaitSeconds`, `baselineGiveUpMinutes`, `mainCiReadSeconds`, `deployWaitMinutes`, `draftMergeTries`, `draftHandBacks`. The agent holds no default for any of them. An answer without the whole set (an older store) leaves them unknown, and then **nothing that needs one starts** (fail closed): no task, no resume, no step, no piece. The last answer's numbers are kept while the store can't be read (the owner's outage rule: finish what is in hand). They are laid over each project's config (`TuningConfig::store`, `ProjectLoop::take_store_tuning`, re-applied every pass over `file_project`) and, the two about limits, over the computer's `EngineLimits::take_numbers`. Who reads what:
  - `maxReasks`: `ItemRun::implementer_finished` (unknown: the item goes to a person). `ownFailureRetries`: `settle` (unknown: none is retried).
  - `cursorLimitWaitMinutes`: the wait after an engine's usage limit that gave no reset time (`record_session_end`, `settle`; unknown: nothing is recorded). `weekCutoffPct`: the weekly cutoff of `EngineLimits::cut_off_for_week`, used for engine fall-over only (the store's `wait` decides whether work starts; unknown: only a rejected window cuts off; the saved reading is read once the number is known).
  - `draftMergeTries`, `draftHandBacks`: `driver/land.rs` (unknown: the press is let go and answered "try again in a minute").
  - `deployWaitMinutes`: the landed look at production (`driver/report.rs`; unknown: production is not looked at) and the staging smoke (`Timing::waiting`; unknown: the task is let go and comes again).
  - `baselineWaitSeconds`, `baselineGiveUpMinutes`: `baseline_wait::Waits`, used by the checks step (unknown: the step waits) and a piece's checks (unknown: no comparison, the failure counts against the change).
  - `mainCiReadSeconds`: `fix_main::read_main_ci` (unknown: main's CI is not read).
  - `maxMergeRetries`, `maxCiReruns`, `ciMaxMinutes`, `ciGraceMinutes`: the item flow's CI and merge steps (unknown: CI is not read, a merge is not retried), a piece's CI watch and merge run, and the CI watcher's pass. `sessionQuietMinutes`: the session watchdog (`cursor_guard::watch_for`).
  - **Round caps** (`maxReviewRounds`, `maxCheckRounds`, `maxConflictRounds`) are the project's settings, laid with the other defaults from `settings_get`'s `effective` (section 3h): the agent holds no 3, 5 and 3 of its own and a file's value is never read.
- **Reopen or fix** (`Client::reopen`, `driver/reopening.rs`): a problem with a try-out this computer built is taken (`tryout_taken`) and `reopen` is sent with the try-out's `key`, `title` and `prUrl`. `ReopenAnswer` is `Reopened` (the item under a lease), `Fix(Queued | Open | Taken)` (the store kept the item and made the playtest fix for this computer: it arrives as a `run: fix` task, section 3d, and nothing more is sent) or `Kept` (an older store that did neither: logged). `Trigger::PlaytestFix`, `chore_trigger playtest_fix` and the `may_reopen` pre-filter are gone; a problem the store can't be asked about is not retried.

## 3h. The store decides the rest (built, Store PR D: Retaskable.com pools-on-server.md section 18)

The agent is still a dumb client. Two things stay its own: the model and engine a session runs on (the store names a tier, `smart` or `fast`; the agent maps it from its settings and reports the map in `hello.computer.tiers`, `computer_view::tiers`, beside `models`, `engines` and `cursorModels`) and updating itself. Everything below is built.

- **Playtest grouping** (`jobs/playtest_group.rs`, `playtest_groups.rs`): a `playtest_group` job (`can: engine`, one read-only Sonnet planner session, no lane, `JobRole::Group`) over `args.entries`, answered `{ groups: [{ title, why, keys }] }` as the session gave them. The store decides when, holds the `tryout-groups` lock and makes the groups fit its queue. `should_group`, `MIN_TO_GROUP`, `REGROUP_EVERY_MS`, `signature`, the lock, `clean_groups` and the minute round (`playtest_rounds`) are gone; `tryouts_list`'s `groups` (the groups view) stays.
- **Plans** (`driver/drafts.rs`, `backlog/drafts.rs`): the `draft_report` that makes a plan ready carries `plan { risk, pieces, people, paths, build, title, itemKinds, preview, first }` (the store works out the tier and the drafting table from `pieces`, `people` and `paths`) (a release note carries none). The store answers `{ approve, needsDesign, table, tier, reasons }` (`PlanDecision`): Approve is queued only on `approve`, the designs are drawn only on `needsDesign`, and no decision leaves the plan for a person. `approves_itself` and `needs_design_of` are gone. An item the plan adds takes `checking: manual` with the reasons (at most 200 characters) when the tier isn't `routine` and the drafter gave it no call, and a store that sent no tier is read as `needsyou`: it rides in the item the drafter returned (`items`, kept in `plan_items.pending.json` and sent as `add { via: "draft" }` when the plan merges, 06.5), and `plan_checking.json` and `apply_checking` carry it only for an entry with no `items`, to the Items header that adds it. `itemKinds`, `paths` and each piece's `checking` in the facts come from those `items`.
- **Sorting an idea** (`ideas/bug_sort.rs`): the classifier's raw `{ kind, confidence }` goes to `idea_classify`; the store holds `ideaBugConfidencePct`, moves a bug at or above it and answers `{ moved, threshold }`; the claimed plan is rewritten as a fix only when `moved`. `should_sort` and the 0.8 are gone.
- **Held for a person** (`orchestrator/piece_tier.rs`): a build or fix run's `pr_opened` carries `diff { files: [{ path, added, removed, addedText? }], newDependencies, size? }` (or `{ unreadable: true }`) once its review approved. The store runs the tier rule with the risk profile. `escalate_tier`, `piece_tier::held` and `change_tier.rs` are gone; the claim-mode review raises no tier either. `piece_approval::reuse` stays.
- **Numbers** (`store_tuning.rs`, `store_effective.rs`): `health`'s `tuning` gains `maxSilenceResumes`, `maxCursorLimits`, `silenceResumeSeconds`, `signedOutRetrySeconds`, `mergeUnknownMinutes`, `mergeRetrySeconds`, `ghErrorsMax` and `reviewLimitWaitMinutes` (`settle`, `flow/merge`, `merge_run`, `ci_watch`, `flow/review`, `experts/limit`; unknown: nothing is retried or waited for). `settings_get`'s `effective` carries the round caps, `maxSlicesPerItem`, the scout diff lines, the code gates, `cursorMaxMinutes` and `expertHelpers`, laid over the project each pass (`StoreEffective::lay`); a file's value for any of them is never read, and **nothing starts until `effective` has been read** (`has_store_numbers`; a `settings_get` with no saved record answers `{ effective }` alone, with no `version`, and that is all it needs; `SettingsAnswer`).
  - **Cadences** (2026-11-19, `store_tuning::Cadences`): `reportSeconds`, `watchSeconds`, `ciWatchSeconds` and `mergePollSeconds` replace the agent's own 60, 45, 120 and 15 seconds (`driver/pool.rs`, `watch_run`, `driver/ci_pass.rs`, `merge_run`). They are read tolerantly: a missing key is its default (60, 45, 120, 15) and a value outside the store's range (10 to 600, 15 to 600, 30 to 900, 5 to 300) is the default too, so an older store still sends a whole set of the others.
- **Run ceilings** (`RunRequest::ceiling`): `run_take`'s `ceilingMs` bounds only the CI watch's own loop. The agent holds no ceiling (`runs::ceiling`, `CEILING_MARGIN`, `end_past_ceilings` and the locks' own ceilings are gone): the store loses a run or lock past its deadline and a beat's `stop` ends it.
- **Order** (`TaskInput::order`, `ItemRun::order`, `orchestrator::decide`): a project's tasks start in the store's `order`; the rush phase and a do-next item's exemption from the session slots are gone. Sharing the free lanes between projects (`round_robin`) stays.
- **The Chat Agent** (`chat/numbers.rs`): `settings_get`'s `effective.tuning.chatConfidencePct`, `chatMaxAsks` and `codeQuestionWaitMinutes` are read for each ask; without them nothing is sorted, filed or answered. The 0.8, `MAX_ASKS` and `CODE_QUESTION_WAIT` are gone.
- **The CI runner** (`agent_ci/automerge.rs`, section 3.3 of agent-ci.md): each `ci_merge_requests` poll sends `prs: [{ pr, sha, labels, approvals }]` and `turn: [pr]`; only a request with `merge: true` is merged, pinned to its `sha`.
