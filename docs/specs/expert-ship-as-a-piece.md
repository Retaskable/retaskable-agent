# Ship an expert session as a piece (2026-11-16)

Status: copied from Retaskable.com's [expert-chat/14-ship-as-a-piece-2026-11-16.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/expert-chat/14-ship-as-a-piece-2026-11-16.md) (store PR #3918, `expert_ship`); the Rust agent's side of it is in [expert-chat.md](expert-chat.md) under "Ship it".

## 14. Ship as a piece

On a project whose computers take runs ([pieces.md](pieces.md)), an expert session's shipped change is carried by runs, not by the one computer that held the session. Section 3.8's ship opened the change and left the item `in_review`, driven by the item loop of that computer alone: if the computer goes away, nothing watches the change or merges it.

- **[Decided]** (2026-11-16, the owner) "Store adopts the PR as a piece": the store takes the session's open change as a piece already at the change stage, skipping the planner, so runs mode's ordinary watch, fix and merge runs carry it on any computer.
- **The op.** `expert_ship { id, token, branch, prUrl, prNumber, head?, title?, what? }`, sent by the agent holding the session's lease, after it has pushed the branch and opened the change through the code host (section 3.8 of [expert-chat.md](expert-chat.md)). `id` and `token` are the item and its lease; `branch`, `prUrl` and `prNumber` name the open change (`prUrl` is a GitHub `/pull/<n>` or GitLab `/merge_requests/<n>` address over https, and `prNumber` is that `<n>`); `head`, when sent, must be a commit id (it is checked and not kept: the watch run reads the change's current head itself); `title` and `what` are the piece's words, defaulting to the item's title and "The change from the expert session: <title>".
- **[Decided] What it does** (2026-11-16, the owner), in one step:
  1. The item gets one piece, `n` 1, already `in_ci` (as if planned with one piece and built): `needs` empty, `next` null, `branch`, `prUrl` and `prNumber` as sent, `doneWhen` "The change is merged.", no run. A `watch` run is due on it at once, then the usual `green`, `red` (a `fix` run), `merge` ([pieces/03-behavior.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/pieces/03-behavior.md) sections 3.2 and 3.3), and the item is built when it merges.
  2. The item goes `building` with `branch` and `prUrl` set (the CI watcher skips a `retaskable/` branch an item has, [ci-when-ready/12-the-ci-watcher-2026-11-06.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/ci-when-ready/12-the-ci-watcher-2026-11-06.md)), its lease, `claimedBy`, `owner` and wait ended, so `run_take` may take its runs (`open`, `backlogPieceOps.ts`).
  3. `expert` is dropped, with the history line "Shipped by <login>: <prUrl>". `claim_next` never handed an `expert` item out; it has pieces now, so it never hands it out as a whole item either.
  4. The item has no flag of its own, since nothing planned it: it gets `noFlag` "Built in an expert session, outside the plan" unless it already has a flag.
  5. `workAvailable` is set, so every computer asks for runs.
- **Rules.** Only an agent may send it. `not_found` for no such item; `conflict` when the item isn't an expert session or already has pieces or a plan; `forbidden` when its `expert` login isn't the caller's; `stale_lease` when `token` isn't the item's current lease; `bad_request` for a missing or over-long `branch`, a `prUrl` that isn't a change address, a `prNumber` that isn't its number, or a `head` that isn't a commit; `conflict` when another item or piece already has that `prUrl` or branch. The store has no "runs mode" setting (every project works in pieces, [pieces/06-moving-over.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/pieces/06-moving-over.md) step 8), so whether runs are taken is the agent's call: an agent that does not take runs ships as section 3.8 says and never sends this. Nothing is changed by a refusal.
- **Idempotent per lease.** The item keeps `expertShipped { lease, prUrl, at }`. A repeat with the same token and the same `prUrl` (the first answer was lost, or the agent restarted between the op and what it does next) answers the same and changes nothing; the same token with another `prUrl` is `conflict`. Answers `{ piece: "<id>#1", pieces }`.
- **After it.** The change and its branch are kept. The agent that held the session lets the session go and clears its queue (`expert_queue_clear`) as for any ended session; the person's messages to it are refused as section 3.8 says. A review or check that asks for changes is a `fix` run on the piece's branch, on any computer, with a fresh session, as for any piece.
- **[Decided] A lapsed lease** (2026-11-16, the owner; issue Retaskable/Retaskable.com#3917). When the store frees an `expert` item whose lease ran out (`expireLeases`) and the item has a change open (`prUrl`), `expert` is dropped with the history line "Its expert session's computer went away; it is anyone's now", and the change and branch are kept. Before, the item sat in `todo` with `expert` set for ever, since `claim_next` skips such items and only a card revision cleared it. A session with no change yet keeps `expert` (its work is on the person's computer, and the person may bring it back); that case stays open.
- **[Proposal] Follow-up: the agents.** The Rust agent's expert ship sends `expert_ship` when it takes runs, in place of reporting `in_review` / `expert_shipped`; it keeps the claim-mode report for a project it runs as claims. The TypeScript agent's ship (`agent/src/expert/commands.ts` `shipExpert`) is claim-only and single-computer; it should send the op the same way, but it is not changed here.
- **Tests.** `shared/backlogExpertShip.test.ts`: the piece it makes, idempotence, each refusal, the end-to-end (watch red, fix, watch green, merge, item built, no plan taken), and the lapse.
