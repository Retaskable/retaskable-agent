## 14. The Codex engine

Built, slice 1 (2026-10-29, the human: "add support for Codex"). [Codex](https://developers.openai.com/codex) (`codex`, OpenAI's Codex CLI) is a fourth engine beside Claude Code, Cursor and pi, picked per computer and per role like the others (section 3.1: `claude`, `cursor`, `pi`, `codex` or `local`). It is `agent/src/engines/codex.ts`, tested in `codex.test.ts` with a stubbed `codex`.

- **Running it.** `codex exec --json --sandbox <mode> --ignore-user-config -`, with the prompt on stdin. The binary is `RETASKABLE_CODEX`, else `codex` on the PATH. Sign-in is Codex's own (`codex login`, ChatGPT or an API key); Retaskable never holds the key.
- **Never the person's own Codex config.** `--ignore-user-config` leaves out `~/.codex/config.toml`: its model, plugins, MCP servers and computer use. It's the same reason every Claude session runs with `--setting-sources project` (section 3.4). Sign-in still comes from `CODEX_HOME`.
- **The sandbox, not an allowlist.** A read-only session (planner, reviewer, scout) runs in `--sandbox read-only`. A writing session runs in `workspace-write`, with the network on (`sandbox_workspace_write.network_access=true`, for installs and tests) and the repo's git folder added (`--add-dir`, from `git rev-parse --git-common-dir`, so a worktree's session can commit). On Windows, Codex refuses to run anything that writes without its own sandbox, so every session passes `windows.sandbox="elevated"`. Its commands run as a separate sandbox user, so git calls the lane's folder "dubious ownership". Each session therefore sets `safe.directory` to its own folder through the sandbox's environment (`shell_environment_policy.set`, `GIT_CONFIG_COUNT`/`KEY_0`/`VALUE_0`), never `*` (`windowsSandbox`). Never `--dangerously-bypass-approvals-and-sandbox`, the same as `--dangerously-skip-permissions` for Claude and `--force` for Cursor.
- **The model.** Codex's own default: no `-m`, because the role's model is a Claude tier name (`sonnet`), which Codex doesn't know. Per-tier Codex model names, as Cursor has (section 3.4), are a later slice.
- **The result.** As for Cursor and pi (section 5): the prompt asks for one fenced `json` block at the end of the final message, and at `turn.completed` the reader checks the last `agent_message` against the result schema. A miss is `invalid_result`. The retry resumes Codex's own thread (`codex exec resume <thread_id>`, with the sandbox as `-c sandbox_mode=…`, since `exec resume` has no `--sandbox`), learnt from `thread.started`. The thread is kept in memory, by the runner's session id. `--output-schema` isn't used, because OpenAI's strict schemas need every property required, and the result schemas don't.
- **A process that lingers.** A Codex process can stay alive after `turn.completed` while a sandboxed command it started still hangs. So its engine is `endsOnResult`: the runner ends the process tree 5 seconds after a result, and the result stands.
- **No resume across sessions.** The thread id lives only in the agent process that ran it. So, as for pi, an implementer follow-up on Codex, or on a build that began on Codex, starts a fresh session on the same branch (section 3.3). It never falls over to another engine when it hits a limit (section 3.5).
- **Limits and failures.** `turn.failed` reports Codex's `error.message`. When it, or the stderr of a process that exited without a result, says "usage limit", "rate limit" or `429`, the result sets `limitHit`. A top-level `error` event can be a reconnect notice, so only `turn.failed` ends the turn.
- **Cost.** Codex reports tokens (`turn.completed`'s `usage`, on `SessionResult.tokens`) but no dollars. So a Codex session counts as unknown cost (section 7), with no budget cap. The pool adds each session's tokens to the day's total in machine.json (`codexTokens`), which only the computer's own Now tab shows (agent-settings.md section 4.5). Like pi, it has its own start rules (section 3.2: only pause, a pending restart and its own usage limit hold it, never Claude Code's window, sign-in or `laneScaling`) and the slot kind that counts toward `concurrency` only (`Slots` kind `cursor`).
- **Transcript.** `agent_message` text, a command as it starts, a `file_change`'s paths ("Edited a.ts"), MCP calls and web searches show as events (section 8). `turn.completed` shows as "Finished", and `turn.failed` as "Failed: …".
- **What you see.** Codex is in every engine choice, a lane's own included (section 3.1): the computer's settings page, `npm run link`, `RETASKABLE_ENGINES` and the site's labels. A Codex session's panel shows the **Codex** chip.
- **Checked on Windows** (2026-10-29, codex-cli 0.165.0, signed in with ChatGPT). With these flags, a `workspace-write` run wrote a file and committed it in a scratch repo. Codex denies writes to `.git` inside a writable root, but `--add-dir` on the git folder grants them back. Without `safe.directory` the commit fails as "dubious ownership".
- **The first run in a new folder is slow.** It needs no admin prompt. But the first time the sandbox sees a writable folder, `codex-windows-sandbox-setup` grants the sandbox users read access across the whole user profile. That took about 12 minutes here (`~/.codex/.sandbox/sandbox.<date>.log`), and commands wait behind it, so a lane's first Codex session can look stuck. A lane's folder is reused, so it happens once per folder. Later runs started at once.
- **Not yet checked:** a full Retaskable session (planner, implementer, review) on Codex, and macOS and Linux.
- **In this Rust agent**, `src/engines/codex.rs` is `codex.ts` (its tests are `codex.rs`'s own, with the same cases), the runner's `end_after_result` ends a lingering process (`Engine::ends_on_result`), and `choose.rs`, `config/machine.rs` and the settings page accept `codex` wherever they accept an engine. There is no pool yet, so the start rules and the limit hold (sections 3.2 and 3.5) and `codexTokens` wait for it.
