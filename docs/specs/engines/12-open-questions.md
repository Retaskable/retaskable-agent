## 12. Open questions

- **Settled by the build, not by deciding it.** All four questions below were open while slice 2 was still ahead of us. Slices 1 through 4 are all Built now (section 10), and the answer slice 2 landed on for each is folded into the sections it touches; this entry keeps the open part honest rather than pretending the question is still live where it isn't.

- **[Proposal] Native Windows: answered empirically, not by a check that gates anything.** No probe in `probe.ts` or `Setup` ever asks "does `cursor-agent` run natively here" and greys Cursor out on a "no" — `resolveCursor` (`agent/src/engines/cursor.ts`) just looks for `cursor-agent.exe`/`cursor-agent.cmd` on `PATH` (or `RETASKABLE_CURSOR`, or `~/.local/bin`) on `win32` the same way it looks for the POSIX binary elsewhere, and every lane it runs in is a junction under a possibly-deep worktree path (`agent/src/git.ts` section around line 154, `fs.symlinkSync(target, link, "junction")`), the same lane a Claude Code session in the same role would get. Cursor's sessions have been running in that shape since slice 2, on the Windows-first computers this repo already runs on (the global `CLAUDE.md`'s own first rule), with no Windows-specific skip in `cursor.test.ts` or `cursorRun.test.ts`. So the practical answer is yes, well enough that nobody built a fallback for "no" — but it was never turned into a decision line or a probe result, so a machine where it genuinely doesn't work (a very long lane path past Windows' historical 260-character limit, hit before `git` itself would hit it) fails the same way any other spawn error does: the session's result carries that error, the implementer retries once, then `needs_human` (section 4's "a session whose binary won't start fails with that spawn error rather than falling back to Claude Code"). **Remaining gap:** nothing distinguishes "cursor-agent isn't installed" from "cursor-agent is installed but chokes on this lane's path" in what a person sees — both show as the session's spawn error. Worth a `needs_human` reason that names the path length specifically (`err.code === "ENAMETOOLONG"` or Windows' own `ERROR_FILENAME_EXCED_RANGE`) if this ever actually bites someone, rather than guessing now.

- **[Proposal] `Shell(...)` argument matching: still genuinely unknown, because it's a fact about Cursor's own CLI, not ours.** Section 6.4 line 28 and section 6.2's last line both already say Shell entries match the program's first word only and that whether Cursor can match arguments too is still open; nothing in `agent/src/engines/cursor.ts` or `shared/cursorAllow.ts` parses or forwards anything beyond the program name, so our code can't answer this — only Cursor's own CLI behavior can, and that's not something to guess at in a spec. What's changed since this question was written is how much rides on the answer staying "no": `Shell(git)` already lets `git push --force` through (section 6.2), and with the implementer now resuming real Cursor chats across retries and lane changes (section 3.3, Built), that's not a one-off risk — it's every implementer session on Cursor, for as long as this project runs it. The guard today is entirely the prompt (`cursorPrompt`, section 4) and the implementer's own "never push to the base branch" rule, same as under Claude Code's auto mode; there's no second, code-level check behind it the way the allowlist is a second check behind the prompt for which programs run at all. **A concrete way to settle it** rather than leaving it open forever: write `.cursor/cli.json` with `{"deny": ["Shell(git push --force)"]}` in a scratch repo and run `cursor-agent -p` asking it to force-push; if Cursor refuses, section 6.2's deny list grows to cover `git push --force`, `git reset --hard` run against a shared branch, and similar; if it doesn't, the answer is confirmed no and this line can finally close as "no, by test" instead of "unknown."

- **[Proposal] Resuming a chat from another folder: unknown, but low-stakes because the fallback already covers it.** `create-chat` (`agent/src/engines/cursor.ts`) makes a chat id before the first run and `--resume <chatId>` is passed with the lane's own worktree as `cwd` every time after (section 3.3); nothing in the code ever resumes a chat id from a `cwd` other than the one it was created in, so this was never exercised, let alone tested, in either direction. The reason it's stayed open this long without costing anything: slice 3's actual behavior for "the item moved to another lane" already assumes the answer is no and starts a fresh chat on the new lane's branch or PR either way (section 3.3's `cursorFollowUp`, same as a Claude Code session whose transcript file can't be found, agent.md section 4.1) — so even if Cursor can resume cross-folder, Retaskable doesn't currently try it, and even if it can't, nothing breaks. The only thing a "yes" would unlock is dropping that "start fresh, lose the chat's context" cost when a lane changes; not worth spending a slice to find out until lane-hopping an implementer mid-build is common enough that losing the chat's context is noticeably worse than the alternative.

- **Not actually open: no cross-engine fallback, and it's Built, not pending.** Section 3.2 and section 4 spell out the real shape now: Claude Code waiting for its usage limit holds only Claude Code sessions (`waiting_for_limit`, `canStartOn` ignores it for other engines); Cursor hitting its own limit sets `Pool.limitedUntil.cursor` and holds only Cursor (`engineMayStart`; pi and Codex likewise); new work is claimed only by a lane whose own engine can start (`laneMayStart`); and neither engine is ever substituted for the other mid-session — a Cursor spawn error goes to `needs_human`, not to a Claude Code retry, and vice versa. That's "neither falls back to the other," built and tested (`agent/src/engines/limits.test.ts`, `agent/src/hostedWork.test.ts`), not a question still waiting on an answer. **[Proposal] The real open question going forward** is narrower: should a *role* (not a session mid-flight) ever be allowed to fall back automatically — e.g. an implementer role pinned to Cursor quietly borrowing a free Claude Code lane while Cursor is limited, rather than sitting at `needs_human` or waiting the 30 minutes — and if so, whose budget and daily cap would that borrowed work count against. Nothing proposes an answer here; it's flagged because a shared backlog with mixed-engine computers (section 3.1) makes "my Cursor is down but someone else's Claude Code lane is idle" a real, not hypothetical, shape, and it's worth deciding on purpose rather than by whichever computer happens to pick up the item next.
