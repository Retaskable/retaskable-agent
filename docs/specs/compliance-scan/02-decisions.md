## 2. Decisions

- **[Decided]** A bigger compliance and accessibility scan than the daily Lighthouse run (the human, 2026-10-18).
- **[Decided]** Built here, in TypeScript, not on smart-coder's `sc-comply` ("ignore smart coder then, maybe reuse the rules if it makes sense"). `sc-comply` audits a source tree from Rust, with no HTTP client, browser, WCAG or ASVS content. What carries over is its shape: the status order and a rule's fields (section 3.1).
- **[Decided]** **Tools, "whichever makes more sense architecturally"**: `playwright-core` and `axe-core` are the agent's own dependencies, pinned. The release bundle has no `node_modules` ([installers.md](../installers.md) section 3.1), so esbuild bundles them into the agent's one file, `axe-core`'s script as text it injects into the page. `playwright-core` downloads no browser: it drives the computer's Chrome (`CHROME_PATH`, or the lookup Lighthouse uses), as Lighthouse does. Lighthouse itself stays on `npx`, being a whole tool of its own rather than a library our code calls. `app/scripts/shoot-ui.mts` already uses Playwright, so the repo keeps one browser library. Without Chrome the scan shows Lighthouse's Inbox line and isn't tried again until the agent restarts.
- **[Decided]** **Daily**, "if it's a minute doing it daily won't hurt": the probes and the sweep each run once a day, after `lighthouse.hour`, the sweep kept to about a minute by what it checks where (section 3.3). Each run's time is shown on the Chores screen. One run a day per repo: the store's chore locks `probes-<day>` and `a11y-<day>` (store op `chore_lock`), as `lighthouse-<day>` (daily-lighthouse.md section 2); the store says when each is due (`jobs_due`).
- **[Decided]** **Signed-in screens, "yes, or mock it like we do with the screenshots"**:
  - The sweep reaches signed-in screens through the Sample (`?sample` on any path, routes.ts), the mock `npm run shoot:ui` photographs ([ui-shots.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/ui-shots.md)). No credentials.
  - Signed-in API answers (14.3.2's `no-store`, cookies set after sign-in) are probed only when the project gives a **staging test token**, kept on the computer like its other secrets (by name only on the site, tray.md section 5.4) and sent only on `GET`s to the paths in `scan.signedInPaths`. Without one, those rows are "Not checked automatically".
- **[Decided]** **Requirements no probe can answer** "usually need a certified team": each is marked **Needs an assessor** by the store and the app. No attestation feature for now.
- **[Decided]** **Run now**, "on the chore page for all three": a button beside Lighthouse, the probes and the sweep (section 3.5; the button is the app's, the agent runs the chore).
- **[Decided]** **No ZAP** for now.
- **[Decided]** **ASVS 5.0.0** ("if it's better do it"). 5.0 (2025) replaces 4.0.3, which the tab cites today: 17 chapters, 345 requirements, 70 at Level 1, every id renumbered. The ids in section 3.2 are from OWASP's `v5.0.0_release` tag (`5.0/en/`) and its mapping to 4.0.3 (`5.0/mappings/mapping_v5.0.0_to_v4.0.3.yml`), read on 2026-10-18.
- **[Proposal]** **A chore like Lighthouse's** (`agent/src/scanChore.ts` beside `agent/src/lighthouseChore.ts`): the orchestrator's own command, outside any session, holding no lane, after the items advance, never while paused or over the limit.
- **[Proposal]** **Staging only**. The scan never runs against `deploy.production.url`, and refuses to when the staging url equals it.
- **[Proposal]** **Read-only**: only `GET`, `HEAD` and `OPTIONS`, no form submitted. On retaskable.com, `/demo` is looked at and never pressed (a visitor's first press makes a cloud copy, [demo.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/demo.md)).
- **[Proposal]** **Findings, new only, one draft**: Lighthouse's rules (daily-lighthouse.md section 2): a key per finding, written up once while its draft is open, merged or discarded under 30 days ago; at most one `[Scan]` draft a run; the limit of 2 open chore drafts covers it (the count and each finding's draft status come from the store, which counts `[Scan]` drafts).
- **[Proposal]** `scan: { probes, a11y, pages, signedInPaths }` is a project setting kept in the store (`probes` and `a11y` switches, off by default; `pages` defaults to `lighthouse.pages`); the switches are on the Chores screen of the Expo app and saved through the hub like Lighthouse's. The agent reads it. On for this repo once built.
