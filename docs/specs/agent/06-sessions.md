## 6. Sessions

A **session** is one `claude -p` or `cursor-agent -p` invocation doing a single role's job, always under `--permission-mode auto` (never `--dangerously-skip-permissions` or `bypassPermissions`, section 2). [engines.md](../engines.md) is the engine-neutral shape every session shares, whichever tool runs it: what it's asked to do and what it reports back, in or out of a sandbox (section 4.2). This section is the orchestrator's own view of the roster: which roles exist, what each one costs, and where every session sits relative to a lane, a budget, and the usage limit.

**The roster.**

| Role | Tier (section 7.1) | Budget | Prompt | Read-only | Runs in |
|---|---|---|---|---|---|
| Implementer | `<tier>` (Sonnet on a first try, 7.1) | `budget.implementerUsd` | `prompts/implementer.md` | No | The item's lane (4.1) |
| Chore implementer | Sonnet, or local when its slot is free (6.7) | `budget.implementerUsd` | `prompts/chore.md` | No | The chore's lane if one is set, else any free lane (4.1, 6.7) |
| Scout (one per concern, or more on a big diff) | `<scoutTier>` | `budget.scoutUsd` | `prompts/scout.md` + `prompts/scouts.json` | Yes | The item's lane, held through `reviewing` (4.1, 6.3) |
| Final reviewer | `<topTier>` (opus unless the usage limit is at `local`, 7.1) | `budget.reviewerUsd` | `prompts/reviewer.md` | Yes | The item's lane (4.1, 6.3) |
| Triager | `<midTier>` (never opus) | `budget.reviewerUsd` | not named (`agent/src/triage.ts`) | Yes | The item's lane if it kept one, else the base checkout (6.9) |
| Drafter | `<midTier>` | `budget.drafterUsd` | `prompts/drafter.md` | No (writes specs, never code) | Its own docs-only worktree, `<worktreesDir>/draft-<id>` (6.5) |
| Assistant (Ask Claude) | the implementer's tier | `budget.askUsd` | `prompts/assistant.md` | Yes | The base checkout (6.6) |
| Release notes | scouts' tier, or local when it's free | `budget.releaseNotesUsd` | `prompts/release-notes.md` | Yes | Not stated; **[Proposal]** the base checkout, like the assistant and a lane-less triager, since it only reads `git log` and `gh pr list` (9.3) |
| Ideas | scouts' tier | `budget.scoutUsd` | `prompts/ideas.md` | Yes | Not stated; **[Proposal]** the base checkout, for the same reason (9.3) |
| Vetting suggestions | scouts' tier | not named; **[Proposal]** `budget.scoutUsd`, since it's the same size job | `prompts/vet-suggestions.md` | Yes | No lane; it judges what the hub hands it, not the working tree (6.7) |
| Playtest grouping | Sonnet | not named; **[Proposal]** `budget.scoutUsd`, same reason | `prompts/playtest-groups.md` | Yes | No lane, even while it runs (6.4) |

Rows marked read-only are launched with `--disallowedTools "Edit Write NotebookEdit"` (Cursor: `--mode ask` and a read-only allowlist) — the `readonly` flag on a session's spec ([engines.md](../engines.md); `engines::engine::SessionSpec::readonly` in this port), set by the role, not chosen per session.

**What every session gets, whichever role.** `--strict-mcp-config`, and the project's own `.mcp.json` back in when it has one, so no session loads MCP servers from the user's own Claude Code config; `ENABLE_CLAUDEAI_MCP_SERVERS=false`; `CLAUDE_CODE_AUTO_COMPACT_WINDOW=200000`; `CLAUDE_CODE_SUBAGENT_MODEL` (`sonnet`, or `haiku` in a Haiku session) (6.2). A Cloudflare token that isn't one, so no session can reach the account however it's spelled, and no session ever deploys (4.2). The agent's own below-normal process priority (4). `RETASKABLE_LANE=<k>` for a session with a lane, and nothing for one without (4.1, 4.2). Outside Claude's own sandbox on macOS and Linux when it's available (never on native Windows); the orchestrator's own commands — checks, CI polling, Play — are never sandboxed (4.2).

**Fresh every time, or resumed.** An implementer, a chore implementer, and a drafter keep their session (or Cursor chat) id and resume it for every follow-up — an answer, a CI failure, review feedback, a rebase (6.2: "A spec draft keeps its chat id the same way"). A scout and the final reviewer never do: "a new round starts from stage 1, and every session is fresh, so it has no memory of writing the code" (6.3) — matched in this port's own types, where a session that will never be resumed skips transcript persistence entirely (`SessionStart::Ephemeral` in `engines::engine`, with a scout as the worked example). **[Proposal]** The triager, release notes, ideas, vetting suggestions and playtest grouping are the same: each looks at one snapshot of the state and is done, so each is `Ephemeral` too, with nothing to `--resume` later.

**Interactive sessions jump the queue, not the slot.** A human or the roadmap is waiting on an ask, a spec draft, or a chat reply, so these don't queue behind `concurrency` the way a roadmap implementer does — they still count toward it once they're running (6.6). Release notes is the same, "interactive like an ask" (9.3), even though nobody is watching it run. A scout and the final reviewer queue *ahead* of implementers waiting for a slot instead, so finished work clears before more is written (6.3). The triager "waits for a slot like any other session" (6.9) — it gets no priority either way.

**The engine choice is per kind of work, not per role.** Setup and the settings page pick an engine (Claude Code, Cursor, pi, or local) per **kind of work** — `planner`, `implementer`, `review`, `drafter`, `chat`, `writer` (agent-settings.md section 3.1, decided 2026-10-22) — a coarser grouping than the roster above: a scout and the final reviewer are both `review`, and the implementer and the chore implementer are both `implementer`. The assistant is `chat`; the drafter is `drafter`.

**[Proposal]** This is where section 6.1's note that "chat, triage, release notes and playtest grouping['s] engine and budget still go under the `planner` role" is now only half right. It predates the `writer` kind (agent-settings.md section 3.1, decided 2026-10-22) and the snapshot's `writer` role (section 9.2), which release notes and ideas sessions already report (section 9.3: "a read-only release notes session (role `writer`, …)" and "a read-only `writer` session"). Only the triager and playtest grouping are still actually `planner`'s, for lack of anywhere else to put them; chat has its own kind too. The drafter's reported role isn't named anywhere — section 9.2's list ("planner, implementer, scout, reviewer or writer") has no `drafter` value, and section 6.1 doesn't mention it either. Until that's settled: a drafter session should report role `drafter`, the same way `writer` was split out, rather than disappearing into `planner`'s catch-all — a person watching the sessions list has no other way to tell "drafting a spec" apart from "sorting playtests" or "looking into a stuck item".
