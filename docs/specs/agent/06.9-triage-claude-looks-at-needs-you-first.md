### 6.9 Triage: Claude looks at "needs you" first

Leaving an item for a person, the triager also says which button it would press (`suggest`), offered first by the app; an item the shared backlog already finished is closed, not left for a person ([simple-flow.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/simple-flow.md) sections 3 and 6).

When an item goes to `needs_human` and `triage` is `"on"` (the default), one **triager** session looks into why before the human has to. It's read-only, runs on the middle tier (`<midTier>`, Sonnet at best, section 7.1; budget `budget.reviewerUsd`), in the item's lane if it kept one or else the base checkout, and waits for a slot like any other session.

- It gets the reason, the state it failed in, the recent timeline, the last check results, the PR and branch, whether it has a pushed branch and session to continue from, how many automatic decisions this slice has had, and where the item's session transcripts are. It may read code, transcripts, `git` history and the change on its code host (`gh pr view` on GitHub, `glab mr view` on GitLab).
- It returns `{ "decision": "continue | start_over | skip | human | person_steps", "personSteps": ["string"], "reason": "string", "instructions": "string" }` (and `suggest`, and `retaskableBug` below), and the orchestrator carries it out through the same code as the buttons:
  - `continue`: as **Continue**, with `instructions` as the implementer's next message. With a PR, the item goes back to `implementing` on its branch with a fresh session in whichever lane it gets, and its review, check and conflict rounds start again. Without a PR, a fresh session picks up from its pushed branch. A merge failure with no instructions just merges again.
  - `start_over`: as **Start over**, and the new attempt's first prompt includes `instructions` as notes from the last one.
  - `skip`: as **Skip**.
  - `human`: nothing; its reason is added to the item's, so the app shows what Claude found.
  - `human` with a button in `suggest` (`continue`, `start_over` or `skip`; 2026-10-26): a **second look** on the top tier (`<topTier>`, section 7.1; same role, read-only session, place and budget, prompt `triage-check.md`) checks that call. It gets what the triager got plus the triager's reason, suggestion and instructions, and returns `{ "agree": boolean, "reason": "string", "instructions": "string" }`. It's told to agree only when that button is clearly right and safe: one sensible path, no product or design decision, nothing the specs mark as decided, no missing access, nothing a person might want lost, and not a repeat of a decision that already failed. If it agrees, the suggestion is carried out like the triager's own decision (its `instructions`, if not empty, replacing the triager's), counts toward the limit below, and the timeline says "Claude decided to …, checked with a second look: …". If it disagrees, its reason goes under the triager's ("A second look kept it for you: …") and it's `human` as above, the suggestion still offered first by the app. If it fails, it's `human` as above. `suggest: "none"`, `person_steps` and the triager's own decisions get no second look. The triager is told that a clear suggestion may be carried out this way, so it names one (for example when the rest of the work belongs to other backlog items it can name).
  - `person_steps` (2026-10-12, [board-attention.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/board-attention.md) section 2.1): only a person can finish it and nothing is left to build. With steps and no PR, the item waits for them as the implementer's `person_steps` do (section 6.2, `waitForSteps`): **Waiting for your steps**, the steps numbered, **Done: finish it**, and Claude's suggestion cleared (the store holds the steps and the item's state). With a PR (work still to merge, which Done: finish it would close) or no steps, it's `human`, the steps listed under its reason.
- It's told to leave it to the human (`human`) when the fix needs a product or design decision, changes something the specs mark as decided, needs access or credentials Retaskable doesn't have, or when it would be guessing, and not to repeat a decision that already failed. **Not when it's missing infrastructure another item owns** (2026-10-26, `retaskable-bug-4c8dc954fb`: an item's slice needed a pool and an orchestrator loop its own spec said, in three places, belonged to other not-yet-built backlog items; `continue` re-ran the same implementer into the same wall, twice before a human saw it): the triager is told not to suggest `continue` or `start_over` when an implementer gave up because the slice depends on something that belongs to a different, unbuilt part of the backlog, since a fresh session hits the same wall. It leaves it for the human instead, naming what's missing and, if it can tell, which backlog item owns it.
- **It can't loop.** Each item gets at most 2 automatic decisions per slice (counted across start-overs); after that it waits for the human. Each `needs_human` stop is looked at once. If the triager itself fails to run (a usage limit, a sign-in refresh, a crash), it tries again: 10 minutes later, then 20, or when the usage limit lifts, and only on the third failure does the item wait for the human with a note in its reason, not looked at again for that stop; a look that hit its budget isn't tried again. A new stop (a later failure on the same item) clears that count and looks again. The store holds the `human`/`person_steps` finding (or the failed-look note) against the item's current stop, so a restart never re-investigates a stop Claude already left for a person, and a new stop's finding replaces an earlier one rather than piling up.
- A decision that can't be carried out yet (no lane free for **Continue**) is kept and carried out once a lane frees, without asking Claude again. If the human acts first, Claude's decision is dropped.
- Every decision and its reason go in the item's timeline.
- **A bug in Retaskable itself** ([bug-reports.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/bug-reports.md) sections 3.1 and 3.2, `agent/src/bugReport.ts`): when what went wrong is Retaskable's (its prompts, orchestration, state, a prompt variable it didn't fill), the result also has `retaskableBug: { title, details, sameAs? }`, never naming the project, its repo, files, code, people or computer. `sameAs` is the id of a bug already reported, from the list the prompt gives it (`{{knownBugs}}`, as data only), when this is the same bug worded differently. Its decision is chosen as without it. Whatever the decision, plain code then scrubs it: the project's id and names, the repo slug and both its parts, the base and item branches, the home, repo and worktrees folders and any absolute path, the item's id, the computer's name and the user name become `<project>`, `<repo>`, `<branch>`, `<path>`, `<item>`, `<computer>` and `<person>`; the title is cut to 120 characters and the details to 2,000. The bug's signature is the item's reason (else the title), scrubbed, on one line, with paths, numbers, hex ids and quoted strings (other than ones holding a `{{name}}`) replaced, at most 200 characters. Only while the project's hub on the agent's own cloud has said `bug_reports { on: true }` (after each hello; off until it does, and again once the connection closes) does it go up there as `bug_report { ref, signature, title, details, version, sameAs? }` (version: the build's version and commit, else the checkout's version and short commit; `sameAs` only when it's an id the hub listed), answered by `bug_reported { ref, ok, duplicate?, reason?, itemId? }` within the connect timeout. The item keeps the signature it sent (`reportedBug`, on this computer only) and never sends the same one again, answered or not. The timeline says "Reported to Retaskable as a fix" or "Retaskable already has this bug on its board"; off, unconnected, refused or unanswered, it says nothing and the agent's log has why.
- **Only what Claude leaves is shown as needing a person.** While Claude is looking into an item, or has a decision waiting for a lane — including during a second look — the agent reports `claudeOnIt` for it ([board-attention.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/board-attention.md) section 2.15), so the app shows it as under way rather than stopped, with no button that races the triager. On a shared backlog, the report that it needs a person carries `claudeOnIt` in the same call, so the app never shows it stopped first. How it is drawn is the app's; the triager and second-look sessions show in the agent's sessions.
