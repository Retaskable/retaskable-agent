## 4. Architecture

```
Retaskable.com/
  agent/         Node + TypeScript: orchestrator loop, the tray (or its menu in the terminal), a health check on node:http (no framework)
  app/           the Expo app, the only UI ([expo.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/expo.md); `?sample` runs it on the Sample, with no server)
  shared/        types and logic used by the agent, the cloud and the app
  prompts/       implementer.md, scout.md + scouts.json, reviewer.md (templates with {{vars}})
  docs/specs/    this spec
  .retaskable/     runtime state (gitignored): config.json, machine.json, projects/<id>/state.json, projects/<id>/runs/<itemId>/*.jsonl
```

- A single `npm run dev` starts three processes: the agent (its health check on port 4700, section 8), the local Worker (port 8787) and the app's Expo dev server in `app/` (port 8081, which also serves Expo Go). `npm start` starts the agent alone, with no app build. `npm run check` prints the machine's first-run checks (Node, git, gh, Claude Code and whether it's signed in) and exits 1 if one it needs fails; `npm start` prints the same once it's up ([first-run-check.md](../first-run-check.md) section 3.1).
- **In Docker:** the agent also runs in a Linux container (`docker/agent/`), with its checkout, data and logins in Docker volumes, a credentials file where there's no OS credential store, and `RETASKABLE_MACHINE` for its name ([docker.md](../docker.md)).
- **Below-normal priority:** on startup the agent lowers its own CPU priority (`os.setPriority`, below normal on Windows, nice 10 on macOS and Linux), and every session, build and test run it starts inherits it. Checks can take every core for a minute; this way the computer's own apps, like the browser showing retaskable.com, stay responsive while they run, and the agent still gets all the CPU nobody else wants.
- **Finding Claude:** on Windows the `claude` on PATH is an npm shim, so the server launches the `claude.exe` behind it directly. `RETASKABLE_CLAUDE` overrides the path. Prompts go in on stdin, which avoids the Windows command-line length limit.
- **Config** is `.retaskable/config.json`, written by the agent when retaskable.com's **Link project…** or a Project settings change arrives (section 10; [cloud.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/cloud.md) section 6). Until it exists the orchestrator stays in `setup` status and does nothing.
- **State** is each project's `.retaskable/projects/<id>/state.json`, and the machine's usage readings, auto concurrency and retaskable.com's last answer about its organisations and the organisations' lane slots it holds ([pricing.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/pricing.md) section 3.0.1) are in `.retaskable/machine.json` ([projects.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/projects.md) section 4, [organisations.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/organisations.md) section 3.3). It is written atomically (write to a temp file, then rename) on every transition, and on startup the server reloads it and resumes.
- **Live output:** every Claude session runs with `--output-format stream-json --verbose`. The server tees each line to `.retaskable/projects/<id>/runs/<itemId>/<sessionId>.jsonl` (planner runs go to `runs/_planner/`) and pushes a summarized event to each linked retaskable.com over the cloud link ([cloud.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/cloud.md) section 5), streamed live, never stored there.

### 4.1 Lanes: parallel work without the disk cost

Each work stream is isolated where it matters (its own branch, PR, working files and build output) and shares everything that is safe to share. What takes the disk space is build output, not code: for void-miner a checkout is about 30 MB, `.git` is 33 MB, and `target/` is 3.3 GB. So the orchestrator never makes a fresh worktree per item. It keeps a fixed pool of `lanes` worktrees and reuses them.

- **A lane** is one persistent git worktree, `<worktreesDir>/lane-<k>` (k = 1..`lanes`, the computer's `lanes`, shared by all its projects: a lane another project holds is not free), made once with `git worktree add --detach`. Each lane's gitignored build output (`target/`, `node_modules/`, etc.) stays in it between items, so builds are warm and incremental.
- **Starting an item in a lane:** `git fetch` (skipped when a fetch of the repo began less than 15 seconds ago, since every lane shares the one object store; a merge makes the next lane fetch again regardless), then `git checkout -B retaskable/<id>-<slug>-<slice> origin/<baseBranch>` (a lane already on a branch from before the rename keeps it, [retaskable.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/retaskable.md) section 7.3), `git reset --hard` and `git clean -fd`. That's `-fd` without `-x`, so tracked and untracked files are reset but ignored build output is kept.
- **Nothing outlives its lane's work.** A session can leave a server running in the background (`wrangler dev`, `vite`) after it exits, holding a port and, on Windows, files the clean can't remove. So before a lane is prepared, put back on a branch (Continue), released after a merge or removed, Retaskable stops every process whose program or command line is inside the lane's directory, with its children. The implementer prompt also asks sessions to stop what they start.
- **No half-removed lanes.** On Windows, `git worktree remove` can drop a lane's `.git` and then fail on a locked file or a long path, leaving the folder behind, and a new worktree can't be added there. So after removing a lane, and before adding one, a lane folder without `.git` is deleted (after stopping anything running in it).
- **Shared:** the git object store (every worktree uses the one `.git`), the user-level tool caches (`~/.cargo/registry`, the npm cache), and the toolchains. These are all safe for concurrent use.
- **Not shared:** the branch, the working files, the build output and the Claude session.
- **Disk use is bounded by `lanes`, not by how many items there are.** For void-miner that's about `lanes` × 3.3 GB, plus one light `_planner` worktree with no builds, and one play checkout (`<worktreesDir>/play`, section 4.2) with its own build once an item's build has been played.
- **A lane is held only while something runs in it:** the item's implementer (`implementing`), its checks (`checking`) or its review (`reviewing`), or a Play from the lane it's in. Everything else holds no lane, and neither does a Play of an item's build when the item is in no lane (it runs in the play checkout, section 4.2): `awaiting_ci`, `needs_clarification`, `awaiting_playtest`, `merging`, `awaiting_merge`, `needs_human`, and a long wait such as the usage limit. So `lanes` is how many items can run at once, each with a warm build, and waiting on you never blocks other work. The one exception to first-asked, first-served: the item holding the merge turn, waiting for a lane to be checked again or to check the merge queue together, gets the next free lane, kept from every other item and new work until it takes it (the changes queued behind it wait on it; section 5 `merging`, `mergeLaneWanted`). While it checks the queue it's in `merging`, running, and holds that lane.
- **Letting go:** when an item stops running, Retaskable commits anything left uncommitted ("wip: saved by Retaskable before freeing the lane"), pushes the branch and frees the lane. If the push fails, the item keeps its lane and tries again every few minutes, so no work is ever lost.
- **Picking up again:** an item that needs a lane again takes a free one (its last lane if that's free, since the build there is warm), checks out `origin/<branch>` and carries on, ahead of new items. It skips its fetch the same way as a new item, unless `origin/<branch>` isn't there yet. A Claude session resumes by folder (`claude --resume` looks for `<id>.jsonl` in `~/.claude/projects/<the working directory, every non-alphanumeric character as "-">/`), so Retaskable copies that file into the new lane's project folder and tells the session it's in a different folder on the same branch. If the file can't be found, a fresh session picks up the branch or PR instead.
- **Siblings outside the repo:** repos often depend on a folder next to them (void-miner's `Cargo.toml` has `path = "../void-engine"`). From a lane, that relative path lands next to the lane instead. So whenever a worktree is set up, Retaskable reads the tracked `Cargo.toml` and `package.json` files for dependency paths that climb out of the repo (`path = "../…"`, `"file:../…"`, `"link:../…"`), and adds a directory junction where the lane expects each one, pointing at the real folder. It only creates links under the worktrees root.
- **Every session gets `RETASKABLE_LANE=<k>`** in its environment, so a repo that starts servers or writes to fixed paths can offset by lane. A build played from the play checkout (section 4.2) gets `RETASKABLE_LANE=play`. It's set under its old name too, since a project's own scripts may read that ([retaskable.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/retaskable.md) section 7.3).
- **Lane scaling** (`laneScaling`, optional): all `lanes` take new work only while less than `belowUsedPct` of the 5-hour window is used; above that, only the first `base` lanes do. Work already in a higher lane carries on, and a free one shows why it's waiting. It lets spare capacity early in a window go into more parallel work, then narrows as the window fills.
- **Chore lane** (`choreLane`, optional, a lane number): the other lanes take only roadmap items, and this lane takes a playtest fix first, then the next roadmap item, then a chore when no item can start (chores never run out, so they come last). A playtest fix resumes the session that built the change only if that session ran in the chore lane; otherwise it starts fresh there with the report. It replaces the background-chore rule of section 6.7. Lowering `lanes` doesn't stop work in a higher lane: it finishes there and the lane is then left empty.
- **Changing the pool:** raising `lanes` adds worktrees on demand. Lowering it removes the highest-numbered lanes once they're free (`git worktree remove --force`). The agent reports each lane's disk use to the hub, for the app to show.

#### 4.1.1 How the agent runs git

Starting a process is most of what a git call costs, above all on Windows, where process starts are slow and queue machine-wide (about 25 ms each). So the agent's own git calls (`agent/src/proc.ts` `run`, `gitBin.ts`, `gitCache.ts`) save the ones that check nothing. None of this changes the git its sessions or the person run.

- **The real git.exe on Windows.** Git for Windows puts `cmd\git.exe` on PATH: a launcher that puts its `mingw64\bin` and `usr\bin` first on PATH, sets `MSYSTEM`, then starts the real `mingw64\bin\git.exe` as a second process. When that launcher is the first git on PATH (Git for Windows, or Retaskable's own MinGit), the agent starts the real git.exe itself, with the same PATH and `MSYSTEM` for that call only, so `sh`, `ssh` and the credential helpers (Git Credential Manager, `gh auth git-credential`) are found as before; git itself sets `HOME` when it's missing, as the launcher would. It's looked up once per PATH. Any other git first on PATH, and every other platform, runs plain `git`; `RETASKABLE_PLAIN_GIT=1` turns it off. On a busy machine it takes a call from about 90 ms to 50 ms.
- **No automatic upkeep in the agent's own worktrees.** git runs `maintenance run --auto` (`gc --auto`) after a commit, merge or fetch: one more process each time, to decide there's nothing to do. Git calls the agent makes inside `<worktreesDir>` (its lanes, base checkout, merge, draft and smoke worktrees) pass `-c maintenance.auto=false -c gc.auto=0`. Those worktrees share the project's object store, which keeps its upkeep: the agent's own calls in the project's folder (the minute's `git fetch`, a folder project's versions), sessions' commits and the person's own git all still run it. It's never turned off in the project's repository or in git's config, since a repository only the agent touches would then never be packed.
- **Answers that can't have changed are kept** for the agent's lifetime, so git isn't asked again: which commit a whole commit id names, whether one commit is in another's history (two whole ids: an id fixes its whole history), and whether a commit is an empty start ([code-storage.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/code-storage.md) section 3.2.2). Which commit a shared ref names (`refs/heads/…`, `refs/remotes/…`, `refs/tags/…`, `refs/retaskable/…`, e.g. the base's version that `peerCode` reads) is kept only while the file git reads it from is the same: the loose ref file's id, or, without one, the very same `packed-refs` file. So a commit, fetch, push, merge or reset by anyone, the agent, a session or the person, is seen on the next read. Each repository is told apart by its object store, so one cloned afresh at the same path starts over. Never kept: a failure or a ref that isn't there, `HEAD` and other per-worktree refs, short names (`main`, `origin/main`) and short ids, symbolic refs, history answers in a shallow, grafted or replaced repository, refs in reftable form, and anything when `GIT_DIR` is set or the folder isn't the top of a repository. A stale answer could merge or skip the wrong thing, so anything else is asked every time.
- **The specs are read only when they changed.** The minute's sync sends the specs' new items to the backlog store (which owns the item list and its dependencies) when the default branch's `docs/specs` tree changed ([backlog.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/backlog.md) section 6.4); the tree is checked first, so an unchanged one reads no spec (one git call per spec otherwise: Retaskable's own 130 specs took about 7 seconds every minute).

### 4.2 Sandbox: agents in, game runs out

**Sessions never deploy.** Releasing is the project's CI/CD's, after a merge (section 2), never a session's. On 2026-10-04 a chore checked out `origin/main` in its lane and ran `npm --prefix cloud run deploy:production` with the machine's Cloudflare login, putting main on retaskable.com outside the production branch. So every session, on either engine, gets a Cloudflare token that isn't one (`CLOUDFLARE_API_TOKEN`, set last in its environment, `agent/src/engines/noDeploy.ts`): wrangler takes it over the saved login, so anything that reaches the account (`deploy`, `d1 … --remote`, `secret put`) fails to sign in however it's spelled, while local `wrangler dev` still works. Claude sessions are also refused the deploy and production-push commands by name (`--disallowedTools`: `wrangler deploy`, `npm run deploy…`, `deploy:production`, `git push … production`), and the implementer and chore prompts say never to deploy. The orchestrator's own commands (the checks, the staging smoke) keep the machine's environment.

Two kinds of process run in a lane, and only one of them is sandboxed:

- **Claude sessions** (implementer, scouts, reviewer, planner) run inside Claude Code's own sandbox when `sandbox` is `"auto"` and the platform supports it. The sandbox is built into Claude Code, adds no images or disk, and keeps an agent's shell commands to its lane. Setup checks for support once. The sandbox is turned on through `--settings` (`sandbox.enabled`), and v1 treats it as available on macOS and Linux only. On native Windows, sessions run unsandboxed with `--permission-mode auto`, as before. The sandbox only has to allow what writing code needs: the lane, `gh` and `git` to GitHub, and the package registry (e.g. crates.io). Inside it, an agent runs the cheap, non-game work: `cargo check`, `cargo test` for pure logic, and reading and searching code. If a command fails only because of the sandbox (a window, the GPU, audio), the agent doesn't try to work around it. It leaves that command to the checks.
- **The orchestrator's own commands** run outside any sandbox, as normal child processes in the lane. These are the stage 1 `checks` (section 6.3), which is where the game's headless `--verify` runs happen, and **Play** (below). They are fixed commands from the config, never something an agent chose, so they don't need the sandbox.
- **No automated step ever opens a window.** Checks must be headless (for void-miner, `--verify` always with `--headless`), and no agent launches the game. The only thing that shows a window is Play, which only you start. The windowed picture checks are left to your playtests.

**Play main:** runs `playCommand` on the base branch's latest build, from the planner's worktree (it's fetched and moved to `origin/<baseBranch>` first). That worktree keeps its own build output, so it costs one more build folder on disk (about 3.3 GB for void-miner). A backlog sync waits while the base build is running, so its checkout doesn't move under the game.

**Retaskable building itself.** When the target repo is the very checkout Retaskable runs from (`repoPath` is Retaskable's own folder; State says `selfHosted`), "main" is the Retaskable you're using, and there's no second copy to run: it would fight the running one for its ports and `.retaskable/`. So:
- **After every merge, and after any fetch that finds it behind, the checkout moves forward to `origin/<baseBranch>`**, fast-forward only. The fetch's catch-up tries once for each commit of `origin/<baseBranch>`, so one refused (local changes) isn't tried every minute (2026-10-16: an agent with no work merged nothing for 15 hours and ran that far behind, `catchUp` in `agent/src/selfUpdate.ts`). App and cloud changes show straight away in the app's dev server and `wrangler dev`, which reload them; nothing on the machine serves the app's build, so the update runs no `npm run build` (no-local-ui slice 3). The update's line is "Updated to <base> (<sha>)", plus "; restarting now" when the agent's code changed. Ask Claude's **restart** always restarts after the update, even when it pulled nothing (2026-10-11: a commit made in this checkout left the running agent older than its files, and "restart" did nothing): "Up to date with main; restarting now: what's running picks up again after." (`perform` in `agent/src/assistant.ts`). The restart waits until the ask's answer is saved, and goes after the answer's other actions (`restartSoon`): restarting first left the ask "thinking", so the restarted agent answered it again and restarted again, 51 times on 2026-10-11 until an update refused. Each update's line also goes to `agent.log` ("self-update: Up to date with main."), so one that pulled nothing or failed can be seen there. A changed `package-lock.json` or `app/package-lock.json` runs `npm install` first (which installs the app's packages too). If the agent's code changed (`agent/`, `shared/`, `prompts/`, or `package-lock.json`), it restarts (section 8). A checkout reads `prompts/` once, as it starts, as a bundle inlines it (`promptFile` in `agent/src/prompts.ts`): implementers start while a restart is pending (below), and one started between an update and its restart filled the new template from the old code (2026-10-21, void-miner: "Prompt variable {{codeLimits}} not provided"). **Restarts don't stop the lanes** (2026-10-14, the human: "with 4 lanes we should be ripping through simple changes"; 44 of 61 merges in a day changed the agent, and while each restart waited for every session to end, nothing new started, so on average 0.86 of 4 lanes were building). An implementer on Claude Code runs detached (`agent/src/engines/detached.ts`): started on its own with its prompt from `<session>.prompt.txt`, writing straight to its transcript, which the agent reads as it grows, with `<session>.live.json` beside it saying its process id and where this run's lines start. A restart doesn't wait for these or stop them, and implementers keep starting while one is pending (not before Quit when idle). **A restart is now** (2026-10-19, the human: a restart cancels what's running, and the agent picks it up again after it starts; on a busy agent the wait for every review, chat, draft, check and merge to end went on and on, since new ones kept starting): your own Restart (the website, the chat, the MCP `restart`) and the automatic ones (after a merge that changes the agent, a release install) go on the next tick. The other sessions (reviews, scouts, triage, drafts, chat, release notes, ideas), the checks and their installs, a shoot and a Play on phone build are cut, and each picks up again after it: reviews, checks and triage run again; a draft resumes its session and an ask is asked again; a round of ideas starts again, for the same release; a staging smoke is queued again. The checks', installs' and a shoot's processes are killed as it exits, and anything still running in a lane or the base checkout is killed before its checks run again (`killProcessesIn`). Only these **finish first**, since cutting them part-way isn't safe: a merge (an item `running: "merge"`, which covers bringing it up to date and its push), a plan being merged (a draft in `merging`), an update to main (`updating`, with its `npm install`) and a promote's push, for 2 minutes at most (`FINISH_FIRST_MS` in `agent/src/pool.ts`), then it goes anyway. What a cut merge can leave is put right on start: a merge turn whose item no longer merges, waits for auto-merge or is checked again is dropped, and one left landing a batch has that cleared (`turnAfterRestart` in `agent/src/merge.ts`, so the merges behind it don't wait out 2 hours 15 minutes); a PR whose head moved since it was approved goes to `awaiting_ci` rather than merging a commit CI never ran on; a slice merged here whose merge the shared backlog never heard of is told it, its merge commit looked up, after the next fetch (`retryFinishes` in `agent/src/hostedWork.ts`); a batch's pull request is kept in the state from the moment it's open, so it's closed rather than left open (`agent/src/mergeBatch.ts`); a plan cut while it merged is marked merged if its pull request went in, else approved again (`recoverDrafts`); a rebase onto main cut part-way is aborted before the base checkout is used (`preparePlanner`). The exit waits for a token refresh before the sessions are killed, not after, so it follows the kills at once and a killed session is never recorded as failed (a draft failed, an ask lost); and it lets what was sent in the same tick (an ask's answer, a command's ack) go out first. **Quit when idle** still waits for everything: sessions, checks, merges, a shoot or a Play on phone build. After the restart, the interrupted implementer resumes its session as before, and the runner, finding that session still running, attaches to it instead of starting it again; one that finished while the agent was down answers the result it left in its transcript, and one cut off with no result is resumed. A program behind a shell (a `.cmd` `RETASKABLE_CLAUDE`) runs piped as before, since on Windows a detached process has no console for it. A live file over 12 hours old is never attached to. Quit stops the detached ones too.
- **Play main shows where it stands.** Every fetch (about once a minute) counts how many commits the checkout is behind `origin/<baseBranch>` (State `selfBehind`) and reports the count to the hub. At 0 a playtest session says its changes are already in the Retaskable you're using, to try right there. Behind, the **update to main** command does the same update on demand, and so does Ask Claude's `restart` action. How the app labels and badges it is the app's ([actions-menu.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/actions-menu.md)).
- It refuses, and says why in the button's tooltip and the Ask answer, when the checkout isn't on the base branch, has uncommitted changes to tracked files, or has commits the base branch doesn't. It never merges, stashes or resets your work. A refusal never blocks a merge.
- **Play this build** refuses: playtests happen on main, after the merge.

The play commands are named in the project type's words (a game says **Play main** and **Play**, as below; [project-types.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/project-types.md) section 3); the labels are the app's.

**Play:** each lane can be played by the **Play** command. It runs `playCommand` (for void-miner, `cargo run --release -- --play`) in that lane, in a visible window on your desktop, so you can try a PR's build before it merges. You'll mostly use it from a playtest request (section 6.4), but it works for any lane holding an item. Play is only allowed while no session is building in that lane, and nothing else starts in the lane until the game closes.

**Play this build never takes a lane** (2026-10-19; on void-miner a Play this build failed with "Every lane is busy" while both lanes did real work). An item in a lane plays there, as above. Any other item's build (an `awaiting_playtest` slice, or another computer's from the store's try-out queue, team-state-on-server.md section 7, slice 7) plays from the project's one **play checkout**, `<worktreesDir>/play` (`preparePlay` in `agent/src/git.ts`, `playItem` in `agent/src/lanePlay.ts`): it's added the first time, then each play stops anything still running in it, fetches (as a lane does), checks the branch is there, runs `reset --hard` and `clean -fd`, and checks out the branch's tip, or the try-out row's approved commit, **always detached**, so the branch stays free for a lane that takes the item up (git won't check one branch out in two worktrees). It keeps its own build output between plays, so later plays build incrementally, and holds nothing of the item's: closing the game saves and pushes nothing. The game gets `RETASKABLE_LANE=play`. One build plays there at a time (`playingBuild`, State `playingItem`): **Play this build** on another item closes the one open (and waits up to 15 seconds for it to close, or refuses), the same item twice leaves its game as it is, and **Stop** and a server's **Restart** go by item (`restart_play { itemId }`, [project-types.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/project-types.md) section 3). The item's own steps never wait for it. An Apps Script project's Play this build sends the play checkout's head to the test copy of its Sheet (code-storage.md section 3.7). Unlinking a project removes the play checkout with its lanes.


**Data model: items and drafts.** The agent's `state.json` holds no project data. A draft is never written there, and an item keeps only its run mechanics (a chore keeps its whole record while it runs). Everything else (title, status, notes, questions, decisions, try-out steps, the slice records) is the store's and, for the ones this computer is working on, held in memory, rebuilt from the store at start. An old `state.json` with full `items`/`drafts` arrays still loads; the rest is dropped on the next save. See [last-local-state.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/last-local-state.md) section 3.7.
