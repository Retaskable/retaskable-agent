### 7.5 What a claim and a give-back send

Under runs ([pieces.md](../pieces.md)), the tags go with `run_take` and there is no give-back: a run ends with `run_done` and its why.

- **Tags go with a claim.** `claim_next`'s `agent` record carries this computer's tags (the found ones with the owner's changes, [agent-settings.md](../agent-settings.md) section 3.1; none when it has none), as Retaskable.com's agent sends them. The store matches them against the project's `settings.needs` (computer-tags.md section 3.3). When a needed tag is missing the answer is `{ waitingFor }`, the missing tags and no item: the agent logs them once, stops asking until `work_available` arrives, and starts nothing. (The Rust agent sends them now; see below.)
- **A give-back says why.** Giving an item back (a release the agent chooses: a computer's own failure, an engine's limit before anything was pushed, a lease with no local record, a `waits_on` result) first sends `report { id, token, note }` with one plain sentence, cut at 4,000 characters, then `release { id, token }`. The note lands in the item's history on every computer's board. The item's details are flushed before the release, while the lease still holds. If the store refuses either, the item keeps the note and the lease and tries again after the next fetch, so a lost release never leaves it claimed here. Own-failure handling (section 7.3) uses the same send with its own wording.

**In this Rust agent (as built).** The tags are sent now; what is still missing is below.

- **One tag list, three asks.** `Links.tags` (a `LiveTags` handle in `src/tags.rs`, from `effective_tags`: the found tags, changed by the owner's additions and removals, or replaced whole by `RETASKABLE_TAGS`; read at startup in `src/main.rs`) goes out as `tags` in `ClaimNextAgent` (`claim_next`, `src/orchestrator/driver/project.rs`), `RunTakeAgent` (`run_take`, `src/orchestrator/driver/runs.rs`, with `engines` and `uses` beside it) and the draft claim (`src/orchestrator/driver/drafts.rs`). An empty list is left out of the request, not sent as `[]`. Each ask reads the handle as it asks. `src/main.rs` re-reads the list from `machine.json` each time the settings page saves (the `HelloSettings` signal), logs `Tags: …` again only if it changed, and a changed list ends a project's wait (`hear_work_wake` compares the handle's generation), so a change made on the settings page (agent-settings.md section 3.1) reaches the next ask without a restart. `RETASKABLE_TAGS` still replaces the list whole, so a save can't change it.
- **`{ waitingFor }` is read by `run_take` and `claim_next`.** `RunTakeAnswer::WaitingFor` (`src/backlog/runs.rs`) sets `RunLoop.waiting`, which stops the pass's asking; the `claim` event's `answer` is `{ "waitingFor": [...] }`. `ClaimNextAnswer::WaitingFor` (`Client::claim_next`, read before the `{ item, token }` shape) does the same for the claim path: `ProjectLoop.claim_waiting` is set, nothing starts, no `store_error` is recorded, and `claim` asks nothing while it is set. The `claim` event is added only when the list differs from `claim_logged`, the last list logged; an item or `none` answer resets it. `work_available` on the project's cloud socket (`src/connector/mod.rs` `receive`) calls `WorkSignals::wake` (`src/work_signal.rs`); `ProjectLoop::hear_work_wake` reads it once, in `run_pass` or `claim`, whichever comes first, and clears both `RunLoop.waiting` and `claim_waiting`, so neither path takes the other's wake. A wake alone ends no wait: it is used up, and a wait ends only when the tag list's generation differs from the one read at the ask that got the `{ waitingFor }` (`ProjectLoop.tags_seen`, set at each `claim_next` and `run_take`), so a wake with an unchanged list asks nothing. The signal is a `Notify`, so a wake sent before the loop listens is kept, and several wakes before a pass count as one.
- **A give-back's note is built.** `ProjectLoop::flush_owed` (`src/orchestrator/driver/settle.rs`) sends `report` then `release` for each entry of `unreleased`, in that order. A `stale_lease` from either counts as done; any other refusal is a `store_error` (`op` `report` or `release`) and the entry stays for the next pass, with its note. `flush_owed` also trims the note, cuts it at 4,000 characters (characters, not bytes) and sends `report` only when what is left isn't empty; a blank note sends the `release` alone, for entries saved earlier too. A skip owed for the same item goes only after its release has gone.
- **A stuck release is dropped after 24 hours.** `ProjectLoop.unreleased_since` keeps when each entry was first listed (epoch seconds, `list_unreleased` keeps the first time when an item is listed again; saved as `unreleased_since` beside `unreleased`, and an entry with no saved time, from an older state file, counts as listed when it was loaded). A `report` or `release` refused with a code other than `stale_lease` for an entry listed `STUCK_RELEASE_SECS` (24 hours) or more ago removes it from `unreleased`, with any `unskipped` for the item, and adds one `error` event (`where` `release`, the item set) after the usual `store_error`. A younger entry is kept as before.
- **Re-reading the tag list is built** (`tags-reread-on-save`, #491). `LiveTags::reread` (`src/tags.rs`) re-reads `machine.json` and bumps `generation()` only when the list changed; a list `RETASKABLE_TAGS` replaces whole is left alone (it returns false). A wake that changes nothing asks nothing new; a save that changes the list ends every project's wait with no wake and the next ask carries the new tags.
- **Tests (existing).** `src/backlog/tests.rs` checks the `report` and `release` bodies, the store's refusal code, and that `claim_next` leaves `tags` out when the computer has none and sends them when it has (`claim_next_sends_this_computers_tags_when_it_has_any`). `src/backlog/runs/tests.rs` checks `waitingFor` and the same for `run_take` (`tags` absent when empty, present otherwise). `claim_next` with `{ waitingFor }` and a `work_available` waking the waiting claim path once are tested (`src/orchestrator/driver/tests/claim_waiting.rs`, which also covers a save ending a wait, a wake with no change asking nothing, and a save then several wakes asking once; `a_wake_ends_a_run_wait_only_when_the_tags_changed` and `run_take_carries_the_tags_a_save_changed_to` in `tests/runs.rs`). `src/tags.rs` tests the re-read and its count. `src/orchestrator/driver/tests/note_rules.rs` checks the cut, the blank note and a failed `report` keeping both calls for the next pass.
- **[Proposal] Still open.** The draft claim (`src/orchestrator/driver/drafts.rs`) sends the same list but has no test of its own for an empty list being left out or for a save's new tag reaching it; add both beside the `run_take` ones. Nothing else in this section is left to build for the Rust agent.

- **Completing is one store write (client built, not wired).** `Client::complete` and `Client::details_report` (`src/backlog/complete.rs`) are the store client for Retaskable.com's `complete` (backlog/16-completing-is-one-store-write.md): one idempotent write keyed by the lease token, carrying `built`, `mergeCommit`, `onDefaultBranch`, `remaining` (present, even empty, counts the slice) and `playtest`, answered `{ built, status }`; the same token again answers the same, another token is `stale_lease`, the same token with another commit is `conflict`. `details_report` sends a patch over `baseVersion` (`conflict` when the details moved; its message holds the current record); `report_impl_playtest` is its `{ implPlaytest }` patch. Nothing in the orchestrator calls them yet: the lease path (`claim_next`) has no merge step in this crate (`ItemRun::merge_finished` and `awaiting_merge_finished` in `src/item_lifecycle.rs` are not driven), and a piece's merge ends with `merge_result` (merge queue) or `run_done`, which the store settles itself (`endPieceRun`), with no lease and no `complete`. When the lease path gets its merge step it sends one `complete` (no `report { merged }`), keeps a machine-local outbox of the call for retry, and puts `implPlaytest` up with `details_report` as the change opens. Tests: `src/backlog/complete/tests.rs`, against an in-process store that keeps `completed.lease` and the details version.
