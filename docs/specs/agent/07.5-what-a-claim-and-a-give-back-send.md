### 7.5 What a claim and a give-back send

Under runs ([pieces.md](../pieces.md)), the tags go with `run_take` and there is no give-back: a run ends with `run_done` and its why.

- **Tags go with a claim.** `claim_next`'s `agent` record carries this computer's tags (the found ones with the owner's changes, [agent-settings.md](../agent-settings.md) section 3.1; none when it has none), as Retaskable.com's agent sends them. The store matches them against the project's `settings.needs` (computer-tags.md section 3.3). When a needed tag is missing the answer is `{ waitingFor }`, the missing tags and no item: the agent logs them once, stops asking until `work_available` arrives, and starts nothing. (The Rust agent sends them now; see below.)
- **A give-back says why.** Giving an item back (a release the agent chooses: a computer's own failure, an engine's limit before anything was pushed, a lease with no local record, a `waits_on` result) first sends `report { id, token, note }` with one plain sentence, cut at 4,000 characters, then `release { id, token }`. The note lands in the item's history on every computer's board. The item's details are flushed before the release, while the lease still holds. If the store refuses either, the item keeps the note and the lease and tries again after the next fetch, so a lost release never leaves it claimed here. Own-failure handling (section 7.3) uses the same send with its own wording.

**In this Rust agent (as built).** The tags are sent now; what is still missing is below.

- **One tag list, three asks.** `Links.tags` (a `LiveTags` handle in `src/tags.rs`, from `effective_tags`: the found tags, changed by the owner's additions and removals, or replaced whole by `RETASKABLE_TAGS`; read at startup in `src/main.rs`) goes out as `tags` in `ClaimNextAgent` (`claim_next`, `src/orchestrator/driver/project.rs`), `RunTakeAgent` (`run_take`, `src/orchestrator/driver/runs.rs`, with `engines` and `uses` beside it) and the draft claim (`src/orchestrator/driver/drafts.rs`). An empty list is left out of the request, not sent as `[]`. Each ask reads the handle as it asks. `src/main.rs` re-reads the list from `machine.json` each time the settings page saves (the `HelloSettings` signal), logs `Tags: …` again only if it changed, and a changed list ends a project's wait (`hear_work_wake` compares the handle's generation), so a change made on the settings page (agent-settings.md section 3.1) reaches the next ask without a restart. `RETASKABLE_TAGS` still replaces the list whole, so a save can't change it.
- **`{ waitingFor }` is read by `run_take` and `claim_next`.** `RunTakeAnswer::WaitingFor` (`src/backlog/runs.rs`) sets `RunLoop.waiting`, which stops the pass's asking; the `claim` event's `answer` is `{ "waitingFor": [...] }`. `ClaimNextAnswer::WaitingFor` (`Client::claim_next`, read before the `{ item, token }` shape) does the same for the claim path: `ProjectLoop.claim_waiting` is set, nothing starts, no `store_error` is recorded, and `claim` asks nothing while it is set. The `claim` event is added only when the list differs from `claim_logged`, the last list logged; an item or `none` answer resets it. `work_available` on the project's cloud socket (`src/connector/mod.rs` `receive`) calls `WorkSignals::wake` (`src/work_signal.rs`); `ProjectLoop::hear_work_wake` reads it once, in `run_pass` or `claim`, whichever comes first, and clears both `RunLoop.waiting` and `claim_waiting`, so neither path takes the other's wake. A wake alone ends no wait: it is used up, and a wait ends only when the tag list's generation differs from the one read at the ask that got the `{ waitingFor }` (`ProjectLoop.tags_seen`, set at each `claim_next` and `run_take`), so a wake with an unchanged list asks nothing. The signal is a `Notify`, so a wake sent before the loop listens is kept, and several wakes before a pass count as one.
- **A give-back's note is built.** `ProjectLoop::flush_owed` (`src/orchestrator/driver/settle.rs`) sends `report` then `release` for each entry of `unreleased`, in that order. A `stale_lease` from either counts as done; any other refusal is a `store_error` (`op` `report` or `release`) and the entry stays for the next pass, with its note. `flush_owed` also trims the note, cuts it at 4,000 characters (characters, not bytes) and sends `report` only when what is left isn't empty; a blank note sends the `release` alone, for entries saved earlier too. A skip owed for the same item goes only after its release has gone.
- **A stuck release is dropped after 24 hours.** `ProjectLoop.unreleased_since` keeps when each entry was first listed (epoch seconds, `list_unreleased` keeps the first time when an item is listed again; saved as `unreleased_since` beside `unreleased`, and an entry with no saved time, from an older state file, counts as listed when it was loaded). A `report` or `release` refused with a code other than `stale_lease` for an entry listed `STUCK_RELEASE_SECS` (24 hours) or more ago removes it from `unreleased`, with any `unskipped` for the item, and adds one `error` event (`where` `release`, the item set) after the usual `store_error`. A younger entry is kept as before.
- **The Claude week goes with a claim; a pass-over is read.** `ClaimNextAgent` and `RunTakeAgent` carry `week: { used, resetsAt }` (`src/backlog/week.rs`; `used` 0..1 to whole percent, `resetsAt` in ms) from the project's last weekly reading (`ProjectLoop::week_use`), and `draft_claim_next` carries it in its `agent` too. It is left out with no reading, a status-only one, or a week that has reset, as the TypeScript agent's `weekUse()` does, so the store counts this computer's room unknown (backlog/06.6 section 6.6.5). When another computer has more of its week left the store answers `{ passed: { to, retryMs } }`: `ClaimNextAnswer::Passed` and `RunTakeAnswer::Passed` start nothing and record no `store_error`; the claim logs `left the next item for <to>, which has more of its Claude week left` once per computer named, and `draft_claim_next` reads it as no draft. `retryMs` is read but the loop's own cadence decides when it asks again.

- **Re-reading the tag list is built** (`tags-reread-on-save`, #491). `LiveTags::reread` (`src/tags.rs`) re-reads `machine.json` and bumps `generation()` only when the list changed; a list `RETASKABLE_TAGS` replaces whole is left alone (it returns false). A wake that changes nothing asks nothing new; a save that changes the list ends every project's wait with no wake and the next ask carries the new tags.
- **Tests (existing).** `src/backlog/tests.rs` checks the `report` and `release` bodies, the store's refusal code, and that `claim_next` leaves `tags` out when the computer has none and sends them when it has (`claim_next_sends_this_computers_tags_when_it_has_any`). `src/backlog/runs/tests.rs` checks `waitingFor` and the same for `run_take` (`tags` absent when empty, present otherwise). `claim_next` with `{ waitingFor }` and a `work_available` waking the waiting claim path once are tested (`src/orchestrator/driver/tests/claim_waiting.rs`, which also covers a save ending a wait, a wake with no change asking nothing, and a save then several wakes asking once; `a_wake_ends_a_run_wait_only_when_the_tags_changed` and `run_take_carries_the_tags_a_save_changed_to` in `tests/runs.rs`). `src/tags.rs` tests the re-read and its count. `src/orchestrator/driver/tests/note_rules.rs` checks the cut, the blank note and a failed `report` keeping both calls for the next pass.
- **[Proposal] Still open.** The draft claim (`src/orchestrator/driver/drafts.rs`) sends the same list but has no test of its own for an empty list being left out or for a save's new tag reaching it; add both beside the `run_take` ones. Nothing else in this section is left to build for the Rust agent.

- **Completing is one store write (wired in the two places that finish an item).** `Client::complete` and `Client::details_report` (`src/backlog/complete.rs`) are the store client for Retaskable.com's `complete` (backlog/16-completing-is-one-store-write.md): one idempotent write keyed by the lease token, carrying `built`, `mergeCommit`, `onDefaultBranch`, `remaining` (present, even empty, counts the slice) and `playtest`, answered `{ built, status }`; the same token again answers the same, another token is `stale_lease`, the same token with another commit is `conflict`. `details_report` sends a patch over `baseVersion` (`conflict` when the details moved; its message holds the current record); `report_impl_playtest` is its `{ implPlaytest }` patch. Two paths send it today: a person's Done on an item that needs help (`finish_item`, `built` true at the base branch's head, `driver/finish_steps.rs`) and a person's Merge into main (`merge_item`, `built` false with what the store says is left and the item's `implPlaytest`, `driver/merge_item.rs`). The lease path (`claim_next`) still has no merge step of its own in this crate (`ItemRun::merge_finished` and `awaiting_merge_finished` in `src/item_lifecycle.rs` are not driven), and a piece's merge ends with `merge_result` (merge queue) or `run_done`, which the store settles itself (`endPieceRun`), with no lease and no `complete`. When the lease path gets its merge step it sends through the same outbox, and puts `implPlaytest` up with `details_report` as the change opens. Tests: `src/backlog/complete/tests.rs`, against an in-process store that keeps `completed.lease` and the details version.
- **Decision facts are read from the store item (wired).** `Client::details_get` (`src/backlog/decisions.rs`) reads an item's details record (`{ version, details }`, no lease needed; `None` when the store holds none) and `Decisions::from_details` is the typed view over the 26 decision fields (last-local-state/03.13). `Decisions::diff(old)` builds the `details_report` patch of changed fields only, a field gone as `null`. A field of the wrong shape reads as absent. `failedIn`, `triaged`, `triages`, `reportedBug` and `attempt` are wired (the next two bullets); the rest still sit in the run record until the following slices move each group over and delete the local copy. Tests: `src/backlog/decisions/tests.rs`.
- **An item's decisions are held as `known` and `now` (wired).** `ItemDecisions` (`src/backlog/decisions/sync.rs`) loads the record with `details_get` and keeps what the store last said (`known`, with its version) beside what the loop believes (`now`). `flush` sends `now.diff(known)` as one `details_report` over `known`'s version, with the lease token (none for a parked item's owner). On `conflict` it reads the record again and sends the same patch over the new version, up to three resends, so the fields another writer changed and the fields this side changed both survive. Any other failure leaves `now` ahead of `known`: that difference is kept in memory, nothing on disk, and the next flush sends it again (the loop flushes each leased item once per pass, and before a completion: see the next bullet). `refresh` takes a pushed `details_changed` record the same way (unsent edits stay on top). Tests: `src/backlog/decisions/sync/tests.rs`.
- **A completion the store hasn't taken is an outbox entry on disk (wired).** `ProjectLoop.outbox` (`src/orchestrator/driver/outbox.rs`) holds, per item id, `{ lease, completion, since }` (the lease token the call is made under, the `complete` arguments, and when it was first listed in epoch seconds), saved as `complete_outbox` in the project's state file beside `unreleased` and `unparked`. It holds a call, never a decision, as the TS agent's `ItemRecord.outbox` does. `finish_item` and `merge_item` list the call and save the state file BEFORE sending, then send: first the item's decisions if the loop holds them (a `details_report` flush, the TS `flushDetails`; a flush the store doesn't take keeps the call listed and `complete` waits for it), then `complete`. An entry already listed for the same lease is sent as it is (a second Done never sends another merge commit under one lease); one for another lease is replaced. The store's answer decides the entry: an answer (including a repeat's, which is the first answer again) removes it, and a lease the loop still holds for the item is let go with its run; `stale_lease` and `conflict` are definite refusals (sending the same call again can't change them) and drop the entry with a `store_error` (`op` `complete`) and a log line; unreachable, a 5xx or any other refusal keeps it. Every pass, before anything else is done for the items, the loop sends each listed entry (`send_outbox`, after the decisions are loaded), so a call the store missed goes again on the next pass and after a restart. An entry the store still doesn't take is kept for good, as the TS agent keeps its outbox: only `stale_lease` and `conflict` drop one. While it stays stuck for 24 hours (`STUCK_RELEASE_SECS`) or more, the loop logs it and adds one `error` event (`where` `complete`) per 24 hours, not one per pass (kept in memory, so a restart may say it once more). A refused Done row says so in words, and the entry still goes later; a merge the store didn't hear of answers its row with `Merged #N, but the shared backlog didn't take it` and the call goes on the next pass. Tests: `src/orchestrator/driver/tests/outbox.rs`.
- **The triage group lives on the store item (wired).** `failedIn`, `triaged`, `triages` (`{ slice, n }`) and `reportedBug` (the one signature last sent, as in the TS agent) are no longer in the local run record. Each pass loads the leased items' decisions (`driver/decisions.rs`) before settling, triage reads and edits them in memory, and the changed fields go out as one `details_report` patch after triage (with the lease; a `conflict` is re-read and resent). An item whose decisions couldn't be read is not triaged that pass (fail closed). An old run record that still holds the four fields loads without them.
- **`attempt` lives on the store item too (wired).** The store counts attempts from 1 and an absent `attempt` is the first, as in the TS agent; Start over writes one more through the same patch. Branch names (`-r<n>` above the first) read it from the item's decisions. A session start loads the item's decisions first (an item claimed this pass has none yet) and hands the item back if the store doesn't answer; Start over waits until they were read. The attempt no longer resets when the slice moves (the TS agent doesn't either; the branch name carries the slice). The run record keeps only lane, session, branch, slice, stop reason and look mark.
