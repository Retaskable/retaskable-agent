### 7.5 What a claim and a give-back send

Under runs ([pieces.md](../pieces.md)), the tags go with `run_take` and there is no give-back: a run ends with `run_done` and its why.

- **Tags go with a claim.** `claim_next`'s `agent` record carries this computer's tags (the found ones with the owner's changes, [agent-settings.md](../agent-settings.md) section 3.1; none when it has none), as Retaskable.com's agent sends them. The store matches them against the project's `settings.needs` (computer-tags.md section 3.3). When a needed tag is missing the answer is `{ waitingFor }`, the missing tags and no item: the agent logs them once, stops asking until `work_available` arrives, and starts nothing. Today `ClaimNextAgent` has no tags, so a project with needs would never hand this agent work.
- **A give-back says why.** Giving an item back (a release the agent chooses: a computer's own failure, an engine's limit before anything was pushed, a lease with no local record, a `waits_on` result) first sends `report { id, token, note }` with one plain sentence, cut at 4,000 characters, then `release { id, token }`. The note lands in the item's history on every computer's board. The item's details are flushed before the release, while the lease still holds. If the store refuses either, the item keeps the note and the lease and tries again after the next fetch, so a lost release never leaves it claimed here. Own-failure handling (section 7.3) uses the same send with its own wording.

**In this Rust agent (as built).** The tags are sent now; what is still missing is below.

- **One tag list, three asks.** `Links.tags` (`src/tags.rs`'s `effective_tags`: the found tags, changed by the owner's additions and removals, or replaced whole by `RETASKABLE_TAGS`; read once at startup in `src/main.rs`) goes out as `tags` in `ClaimNextAgent` (`claim_next`, `src/orchestrator/driver/project.rs`), `RunTakeAgent` (`run_take`, `src/orchestrator/driver/runs.rs`, with `engines` and `uses` beside it) and the draft claim (`src/orchestrator/driver/drafts.rs`). An empty list is left out of the request, not sent as `[]`. A change made on the settings page (agent-settings.md section 3.1) reaches the next ask only after a restart, since the list is not re-read.
- **`{ waitingFor }` is read by `run_take` and `claim_next`.** `RunTakeAnswer::WaitingFor` (`src/backlog/runs.rs`) sets `RunLoop.waiting`, which stops the pass's asking; the `claim` event's `answer` is `{ "waitingFor": [...] }`. `ClaimNextAnswer::WaitingFor` (`Client::claim_next`, read before the `{ item, token }` shape) does the same for the claim path, behind the `claim-next-waiting` flag (Off, the answer is a `store_error` with `BadAnswer`, as before): `ProjectLoop.claim_waiting` is set, nothing starts, no `store_error` is recorded, and `claim` asks nothing while it is set. The `claim` event is added only when the list differs from `claim_logged`, the last list logged; an item or `none` answer resets it. `work_available` on the project's cloud socket (`src/connector/mod.rs` `receive`) calls `WorkSignals::wake` (`src/work_signal.rs`); `ProjectLoop::hear_work_wake` reads it once, in `run_pass` or `claim`, whichever comes first, and clears both `RunLoop.waiting` and `claim_waiting`, so neither path takes the other's wake. The signal is a `Notify`, so a wake sent before the loop listens is kept, and several wakes before a pass count as one.
- **A give-back's note is built.** `ProjectLoop::flush_owed` (`src/orchestrator/driver/settle.rs`) sends `report` then `release` for each entry of `unreleased`, in that order. A `stale_lease` from either counts as done; any other refusal is a `store_error` (`op` `report` or `release`) and the entry stays for the next pass, with its note. Behind `give-back-note-rules`, `flush_owed` also trims the note, cuts it at 4,000 characters (characters, not bytes) and sends `report` only when what is left isn't empty; a blank note sends the `release` alone, for entries saved earlier too. A skip owed for the same item goes only after its release has gone.
- **A stuck release is dropped after 24 hours.** `ProjectLoop.unreleased_since` keeps when each entry was first listed (epoch seconds, `list_unreleased` keeps the first time when an item is listed again; saved as `unreleased_since` beside `unreleased`, and an entry with no saved time, from an older state file, counts as listed when it was loaded). Behind `stuck-release-drop` (Off, nothing is dropped), a `report` or `release` refused with a code other than `stale_lease` for an entry listed `STUCK_RELEASE_SECS` (24 hours) or more ago removes it from `unreleased`, with any `unskipped` for the item, and adds one `error` event (`where` `release`, the item set) after the usual `store_error`. A younger entry is kept as before.
