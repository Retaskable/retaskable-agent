### 7.5 What a claim and a give-back send

Under runs ([pieces.md](../pieces.md)), the tags go with `run_take` and there is no give-back: a run ends with `run_done` and its why.

- **Tags go with a claim.** `claim_next`'s `agent` record carries this computer's tags (the found ones with the owner's changes, [agent-settings.md](../agent-settings.md) section 3.1; none when it has none), as Retaskable.com's agent sends them. The store matches them against the project's `settings.needs` (computer-tags.md section 3.3). When a needed tag is missing the answer is `{ waitingFor }`, the missing tags and no item: the agent logs them once, stops asking until `work_available` arrives, and starts nothing. Today `ClaimNextAgent` has no tags, so a project with needs would never hand this agent work.
- **A give-back says why.** Giving an item back (a release the agent chooses: a computer's own failure, an engine's limit before anything was pushed, a lease with no local record, a `waits_on` result) first sends `report { id, token, note }` with one plain sentence, cut at 4,000 characters, then `release { id, token }`. The note lands in the item's history on every computer's board. The item's details are flushed before the release, while the lease still holds. If the store refuses either, the item keeps the note and the lease and tries again after the next fetch, so a lost release never leaves it claimed here. Own-failure handling (section 7.3) uses the same send with its own wording.

**In this Rust agent (as built).** The tags are sent now; what is still missing is below.

- **One tag list, three asks.** `Links.tags` (`src/tags.rs`'s `effective_tags`: the found tags, changed by the owner's additions and removals, or replaced whole by `RETASKABLE_TAGS`; read once at startup in `src/main.rs`) goes out as `tags` in `ClaimNextAgent` (`claim_next`, `src/orchestrator/driver/project.rs`), `RunTakeAgent` (`run_take`, `src/orchestrator/driver/runs.rs`, with `engines` and `uses` beside it) and the draft claim (`src/orchestrator/driver/drafts.rs`). An empty list is left out of the request, not sent as `[]`. A change made on the settings page (agent-settings.md section 3.1) reaches the next ask only after a restart, since the list is not re-read.
- **`{ waitingFor }` is read by `run_take` only.** `RunTakeAnswer::WaitingFor` (`src/backlog/runs.rs`) sets `RunLoop.waiting`, which stops the pass's asking; the `claim` event's `answer` is `{ "waitingFor": [...] }`. `work_available` on the project's cloud socket (`src/connector/mod.rs` `receive`) calls `WorkSignals::wake` (`src/work_signal.rs`), and the next `run_pass` clears `waiting` and asks again. The signal is a `Notify`, so a wake sent before the loop listens is kept, and several wakes before a pass count as one. `claim_next`'s own reader (`Client::claim_next`) knows no `waitingFor`: an answer of that shape fails to read as an item and is a `store_error` with `BadAnswer`, not a wait.
- **A give-back's note is built.** `ProjectLoop::flush_owed` (`src/orchestrator/driver/settle.rs`) sends `report` then `release` for each entry of `unreleased`, in that order. A `stale_lease` from either counts as done; any other refusal is a `store_error` (`op` `report` or `release`) and the entry stays for the next pass, with its note. A skip owed for the same item goes only after its release has gone.
- **[Proposal] What a slice should settle.**
  - `claim_next` reads `{ waitingFor }` the way `run_take` does: the missing tags are logged once (a `claim` event with the `waitingFor` answer, not a `store_error`), the claim path stops asking until `work_available`, and nothing starts. Until then a project with `needs` that this computer lacks shows as a `store_error` every pass, and `repeat_error` (agent-telemetry.md section 4) will report it as a fault when it is only a missing tag.
  - Log the missing tags once per change, not once per ask: the same list asked again after a wake that changed nothing is not logged again.
  - Re-read the tag list when the settings page saves it, so a new tag takes effect on the next ask without a restart. A `work_available` that arrives meanwhile is no reason to ask again unless the list changed.
  - A note is cut at 4,000 characters before it is sent (the cut is not yet in `report`); a note that is empty after trimming is not sent, and the release goes alone.
  - A `release` that keeps failing for a lease the store no longer knows by any code other than `stale_lease` stays listed forever today; after 24 hours the entry is dropped with one `error` event, since the store has expired the lease by then.
- **[Proposal] Slices, in order.** Each is one reviewable pull request.
  1. `claim_next` reads `{ waitingFor }`: `Client::claim_next` returns a wait the way `RunTakeAnswer::WaitingFor` does, the claim path sets its waiting flag, and the missing tags are logged once per change of the list (a `claim` event, no `store_error`).
  2. The tag list is re-read on a settings save (agent-settings.md section 3.1), so the next ask carries it; a wake that changes nothing asks nothing new.
  3. The note rules: cut at 4,000 characters, and an empty note after trimming sends the release alone.
  4. A stuck release is dropped after 24 hours with one `error` event.
  Acceptance: a project whose `needs` this computer lacks shows no `store_error` and no `repeat_error`; a 5,000-character note arrives as 4,000; a blank note sends no `report`; an entry in `unreleased` older than 24 hours is gone after the next pass, with one `error` event.
- **Tests (existing and to add).** `src/backlog/tests.rs` already checks the `report` and `release` bodies and the store's refusal code, and `src/backlog/runs/tests.rs` checks `waitingFor`. To add: `claim_next` with `{ waitingFor: ["gpu"] }`; a `work_available` waking a waiting loop once; an empty tag list leaving `tags` out of the body; a failed `report` keeping both calls for the next pass.
