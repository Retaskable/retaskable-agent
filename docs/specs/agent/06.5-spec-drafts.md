### 6.5 Spec drafts

A plan someone asked for goes ahead on that yes unless the drafter says it's risky (`risk`) or the project's `plans` is `ask`, and a failed plan tries again by itself once ([simple-flow.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/simple-flow.md) sections 2 and 6).

A request to add a spec (the app's **Add spec**, a chat message, gallery feedback) becomes a draft in the store, and the store keeps the drafts and their order ([team-state-on-server.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/team-state-on-server.md) section 3.3). The agent keeps no list of drafts. It asks the store for the next one waiting for a computer (`draft_claim_next`) and turns its description into a spec and its backlog items, as a PR a person reviews before anything is built from it. Spec content never goes to the store: the store has the draft's status, titles, questions and PR link, and the files are read live from the computer when the app asks.

Each piece of a request is first a **fix**, a **tweak** or a **feature** ([chat-specs.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/chat-specs.md) section 13). A fix never creates or changes a spec: the drafter returns it in `fixes`, and the agent adds it to the store itself as a `todo` item "Fix: …" (`addedVia: chat`); when every piece is a fix there is no pull request (`queued_fixes`) and the draft ends done. A tweak only edits the spec(s) already covering it, with no new file and no decided line changed. A feature may add a new spec, as below. A piece the drafter can't classify, or whose kind fails its check against the specs, is put to the person as a question with **Fix**, **Tweak** and **Feature** as the options.

1. The agent makes a small docs-only worktree, `<worktreesDir>/draft-<id>` on branch `retaskable/spec-<id>-<slug>`, from `origin/<baseBranch>`. It has no build output and is removed afterwards.
2. A **drafter** session (on `<midTier>`, Sonnet at best, section 7.1; budget `budget.drafterUsd`, prompt `prompts/drafter.md`) reads the closest specs, and matches their style. If the request is to **write up something already built**, it reads the code and `git log` and brings the existing spec up to date "as built", adding no new item. Otherwise it writes a new spec file (or edits the spec the request extends), with anything it invented marked the way the project marks proposals. The backlog items are the store's: the drafter returns their titles, and the agent reports them to the store (`draft_report`); a spec carries no **Items** header of its own. A chat message is parsed into one spec or several in that same pull request. The cut is the scope that makes each spec clear and buildable on its own, and each title is the short title taken from that piece as it was parsed ([chat-specs.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/chat-specs.md) sections 3 and 4). Each spec is written for the implementer, in the shape the drafter's prompt gives (the opening, decisions, the behavior in slice order, acceptance), and opens with metadata lines (the status line, `Theme:` and `Kind:`; [chat-specs.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/chat-specs.md) sections 10 to 12). A project runs one drafter at a time: the next draft starts when the one ahead of it has ended (its PR is open, it asked questions, or it failed). Which draft is next, and that an answered, sent-back or conflicted draft goes before new prompts, is the store's order ([spec-queue.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/spec-queue.md); `draft_claim_next`, `draft_front`). A restart resumes the draft that was drafting. The drafter commits and returns the PR's title (`Spec: …`) and body; the agent pushes the branch and opens the PR through the code host. It never touches code.
3. The draft is reported to the store with its summary, so the app can show it with its changed files. The files are sent live when the app asks (the `draft_files` command, [cloud.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/cloud.md) section 6), never stored. How the app shows them (rendered SVG, HTML and Markdown, the edit view, the buttons) is the app's. A person can:
   - **Approve and merge.** It follows the project's GitHub workflow ([github-workflow.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/github-workflow.md) section 9), the same landing as a slice, so a draft does not squash-merge straight into the protected branch when the pattern forbids it. When the pattern does merge into `baseBranch`, the agent merges the PR, removes the worktree, and sends the new specs' headers to the store at once (`upsert_from_specs`, even while paused), so the new items appear on the roadmap. If the base branch has moved on and the PR can't merge, the agent rebases it itself when that's clean (then merges, retrying for a few seconds while GitHub catches up). When it conflicts, the drafter resumes to rebase and resolve it, keeping both sides, and the draft merges as soon as it's back, without asking again. After 2 such hand-backs, or on any other merge error, it goes back to waiting for approval with the reason on its timeline. When the pattern only opens the pull request, **Approve** does not merge, and a separate **Merge into main** command squash-merges the finished pull request into the protected branch and deletes the draft branch ([github-workflow.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/github-workflow.md) section 9).
   - **Edit** any of the draft's files by hand. The agent commits and pushes the edit to the same PR, and the file's changes are worked out again from the new branch.
   - **Send back** with notes. The drafter resumes its session and updates the PR.
   - **Discard.** The PR is closed and its branch deleted.

   **Changes, not whole files.** An edited file is listed as its diff against `origin/<baseBranch>` (the same three-dot diff `changedFiles` lists the files from), so a one-line status change to a 40 KB file is one line to read. The agent works it out when it lists the draft's files (after the drafter finishes, after each hand edit, and after a rebase), with `git diff -M -U3 origin/<baseBranch>...HEAD -- <path>` (`changedFiles` in `agent/src/git.ts`), and gives each edited file a `patch`, the unified diff, beside its whole `content`. A file git sees as binary, or a rename (diffed with both its paths, so git pairs them), is listed in full with a line saying why. Parsing the hunks and drawing them are the app's (`shared/diff.ts`), which never diffs anything itself.
4. If the request is too vague, the drafter asks questions first; the agent records them in the store, and the person's answers come back from it (`draft_answer`, `draft_answer_taken`) like an implementer's.

`DRAFTER_RESULT_SCHEMA`: `{ status: "pr_opened | needs_clarification | failed", title?, changeTitle?, changeBody?, itemId?, itemIds?, summary, questions? }`. `itemIds` is every backlog entry it added, in order, and `itemId` the first of them; a drafter that gives only `itemId` is read as a list of one (`entryIds` in `drafts.ts`). Both are reported on the draft, and a revision that names none keeps the earlier ones ([chat-specs.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/chat-specs.md) section 4). A write-up of something already built names none. The drafter's prompt also gets the titles the chat parsed the request into, one per title, each with the theme the chat gave it beside it, or, with none (**Add spec**, gallery feedback, a specs chore), a line telling it to make the cut and the themes itself (`titlesText`). Its `summary` names the new entries' titles under their themes. It may also return a `breakdown`, one line and a size per entry it added and the steps that need people, which the agent checks and reports on the draft ([plan-breakdown.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/plan-breakdown.md) section 3.1).
