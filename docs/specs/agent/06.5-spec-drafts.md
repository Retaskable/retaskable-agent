### 6.5 Spec drafts

A plan someone asked for goes ahead on that yes unless the drafter says it's risky (`risk`) or the project's `plans` is `ask`, and a failed plan tries again by itself once ([simple-flow.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/simple-flow.md) sections 2 and 6).

A request to add a spec (the app's **Add spec**, or a chat message) becomes a draft in the store, and the store keeps the drafts and their order ([team-state-on-server.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/team-state-on-server.md) section 3.3). The agent keeps no list of drafts. It asks the store for the next one waiting for a computer (`draft_claim_next`) and turns its description into a spec and its backlog items, as a PR a person reviews before anything is built from it. Spec content never goes to the store: the store has the draft's status, titles, questions and PR link, and the files are read live from the computer when the app asks.

Each piece of a request is first a **fix**, a **tweak** or a **feature** ([chat-specs.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/chat-specs.md) section 13). A fix never creates or changes a spec: the drafter returns it in `fixes`, and the agent adds it to the store itself as a `todo` item "Fix: …" (`addedVia: chat`); when every piece is a fix there is no pull request (`queued_fixes`) and the draft ends done. A tweak only edits the spec(s) already covering it, with no new file and no decided line changed. A feature may add a new spec, as below. A piece the drafter can't classify, or whose kind fails its check against the specs, is put to the person as a question with **Fix**, **Tweak** and **Feature** as the options. The drafter may list every piece with its `kind` (`pieces`); one with no kind, or a kind other than those three, is that question.

1. The agent makes a small docs-only worktree, `<worktreesDir>/draft-<id>` on branch `retaskable/spec-<id>-<slug>`, from `origin/<baseBranch>`. It has no build output and is removed afterwards.
2. A **drafter** session (on `<midTier>`, Sonnet at best, section 7.1; budget `budget.drafterUsd`, prompt `prompts/drafter.md`) reads the closest specs, and matches their style. If the request is to **write up something already built**, it reads the code and `git log` and brings the existing spec up to date "as built", adding no new item. Otherwise it writes a new spec file (or edits the spec the request extends), with anything it invented marked the way the project marks proposals. The backlog items are the store's: the drafter returns them in `items` (id, title, `dependsOn`, `specRefs`, `kind`, `milestone`, `checking`), the agent keeps them with the plan and adds them to the store when the plan merges ("The plan's items in this Rust agent" below); a spec carries no **Items** header of its own. A chat message is parsed into one spec or several in that same pull request. The cut is the scope that makes each spec clear and buildable on its own, and each title is the short title taken from that piece as it was parsed ([chat-specs.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/chat-specs.md) sections 3 and 4). Each spec is written for the implementer, in the shape the drafter's prompt gives (the opening, decisions, the behavior in slice order, acceptance), and opens with metadata lines (the status line, `Theme:` and `Kind:`; [chat-specs.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/chat-specs.md) sections 10 to 12). A project runs one drafter at a time: the next draft starts when the one ahead of it has ended (its PR is open, it asked questions, or it failed). Which draft is next, and that an answered, sent-back or conflicted draft goes before new prompts, is the store's order ([spec-queue.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/spec-queue.md); `draft_claim_next`, `draft_front`). A restart resumes the draft that was drafting. The drafter commits and returns the PR's title (`Spec: …`) and body; the agent pushes the branch and opens the PR through the code host. It never touches code.
3. The draft is reported to the store with its summary, so the app can show it with its changed files. The files are sent live when the app asks (the `draft_files` command, [cloud.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/cloud.md) section 6), never stored. How the app shows them (rendered SVG, HTML and Markdown, the edit view, the buttons) is the app's. A person can:
   - **Approve and merge.** It follows the project's GitHub workflow ([github-workflow.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/github-workflow.md) section 9), the same landing as a slice, so a draft does not squash-merge straight into the protected branch when the pattern forbids it. When the pattern does merge into `baseBranch`, the agent merges the PR, removes the worktree, sends the new specs' headers to the store at once (`upsert_from_specs`, even while paused, for an older spec that still has one), and adds the plan's own items (below), so the new items appear on the roadmap. If the base branch has moved on and the PR can't merge, the agent rebases it itself when that's clean (then merges, retrying for a few seconds while GitHub catches up). When it conflicts, the drafter resumes to rebase and resolve it, keeping both sides, and the draft merges as soon as it's back, without asking again. After 2 such hand-backs, or on any other merge error, it goes back to waiting for approval with the reason on its timeline. When the pattern only opens the pull request, **Approve** does not merge, and a separate **Merge into main** command squash-merges the finished pull request into the protected branch and deletes the draft branch ([github-workflow.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/github-workflow.md) section 9).
   - **Edit** any of the draft's files by hand. The agent commits and pushes the edit to the same PR, and the file's changes are worked out again from the new branch.
   - **Send back** with notes. The drafter resumes its session and updates the PR.
   - **Discard.** The PR is closed and its branch deleted.

   **Changes, not whole files.** An edited file is listed as its diff against `origin/<baseBranch>` (the same three-dot diff `changedFiles` lists the files from), so a one-line status change to a 40 KB file is one line to read. The agent works it out when it lists the draft's files (after the drafter finishes, after each hand edit, and after a rebase), with `git diff -M -U3 origin/<baseBranch>...HEAD -- <path>` (`changedFiles` in `agent/src/git.ts`), and gives each edited file a `patch`, the unified diff, beside its whole `content`. A file git sees as binary, or a rename (diffed with both its paths, so git pairs them), is listed in full with a line saying why. Parsing the hunks and drawing them are the app's (`shared/diff.ts`), which never diffs anything itself. In this Rust agent, `drafts::files::draft_files(lane_dir, base_branch)` lists them as `DraftFile`s (`path`, `oldPath` for a rename, `isNew` (git status `A`), `content`, `patch`, `deleted`, `note`; empty fields left out of the JSON): a modified file has a `patch`; a new file has content only; a deleted file is `deleted` with no content; a rename (both paths) or a binary file has a `note` saying why it's listed in full and no `patch`. The hub no longer asks a computer for them: the plan's files are the `draft_files` fact this agent keeps in the store (`kept_facts`), so a pushed `draft_files` is answered only when the store holds none for the plan yet (the hub still relays it then, `read_kinds::draft_files`, 09.3: the worktree, else what this computer owes, else the branch with `drafts::files::branch_files`), and `draft_edit` still answers with the files listed again. The audit log holds the command and the answer's size, never the files.
4. If the request is too vague, the drafter asks questions first; the agent records them in the store, and the person's answers come back from it (`draft_answer`, `draft_answer_taken`) like an implementer's.

`DRAFTER_RESULT_SCHEMA`: `{ status: "pr_opened | needs_clarification | failed", title?, changeTitle?, changeBody?, itemId?, itemIds?, items?, summary, questions? }`. `items` is the plan's new backlog items, one per new piece in the order it split them (backlog.md section 5, decided 2026-10-24: no spec holds an `Items:` header); the entries reported on the draft are theirs, and `itemIds` and `itemId` (every entry in order, and the first of them; a drafter that gives only `itemId` is read as a list of one, `entryIds` in `drafts.ts`) are read only when it returned no `items`. Both are reported on the draft, and a revision that names none keeps the earlier ones ([chat-specs.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/chat-specs.md) section 4). A write-up of something already built names none. The drafter's prompt also gets the titles the chat parsed the request into, one per title, each with the theme the chat gave it beside it, or, with none (**Add spec**, a specs chore), a line telling it to make the cut and the themes itself (`titlesText`). Its `summary` names the new entries' titles under their themes. It may also return a `breakdown`, one line and a size per entry it added and the steps that need people, which the agent checks and reports on the draft ([plan-breakdown.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/plan-breakdown.md) section 3.1).

**The plan's items in this Rust agent** (`drafts/items.rs`, `driver/plan_items.rs`, `backlog/plan_items.rs`; Retaskable.com's `agent/src/draftItems.ts`, `drafts.ts`, `hostedBacklog.ts` `sendDraftItems`). Before this the Rust agent read only `itemIds` and learned items from spec headers, so a plan whose specs carry no header (every plan since 2026-10-24) reported entries (`docker-ci-info-line`, drafts 768 and 773, 2026-11-17) that never reached the store, and nothing was built.
- **The drafter returns them.** The prompt (`prompts/drafter.md`, step 5, as the TS one) asks for `items`: `id` (a 2 to 4 word slug, different from every id in the open-items list and from the plan's others), `title`, `kind` (`tweak` or `feature`), `specRefs` (repo paths, the first the file that holds the piece), `dependsOn` (only what the piece can't be built without, looking past its first slice), `checking` (`manual` or `auto`) with `checkingWhy`, and `milestone` when no spec has a `Theme:`. A fresh session is shown the backlog's items not built yet (`list`, then `open_items_text`: `- id: title (depends on …)`, at most 200) after the pieces, to depend on and to keep its ids apart from; a store that can't be asked fails the plan (a first failure goes back to the queue by itself), as for a revision.
- **They are checked in plain code** (`checked_items`, TS `checkedItems`): an id that isn't a readable slug, repeats or is the item the plan revises is dropped, and so is an untitled one; a dependency that isn't a slug or is the item itself is dropped; a spec ref loses a trailing " section 3"; a `kind` other than `tweak` or `feature` is dropped; `checking` stays unset when the drafter gave none, for the tier below. Each item's missing milestone is the first theme of the `Theme:` line of its first spec in the plan's checkout (`with_milestones`; a ref outside the checkout or a file that can't be read leaves it). The checked ids are the entries reported with the plan (`itemIds`) and their `kind`s and `specRefs` are the facts the store decides the tier and the design review from (`itemKinds`, `paths`, each `pieces` entry's `checking`), where a plan with no `items` reads them from its changed specs' headers as before.
- **The tier fills in `checking`.** Once the store has answered the plan's facts, an item with no `checking` takes `manual` with the tier's reasons as `checkingWhy` (at most 200 characters) unless the tier is `routine` (`with_derived_checking`, TS `withDerivedChecking`); a store that sent no tier is read as `needsyou`. The drafter's own call is never changed. A plan with no `items` still keeps `checking: manual` per id in `plan_checking.json` for a header that adds it (`apply_checking`).
- **They are kept with the plan.** Before the plan's report is sent the items are listed in `plan_items.pending.json` in the project's folder, by draft id (written again with the derived `checking` once the store has answered); a plan sent back and written again replaces them, one that returns none keeps the earlier ones, a Discard (or a pull request closed on the code host) drops them, and an entry that never merged on this computer is forgotten after 30 days. The file is the neutral `OwedFile`, since the draft task and the landing task cannot write the state file.
- **They are sent when the plan merges, on every path.** `land.rs`'s `merged` (the Approve on the lease the drafter holds, a person's Approve or Merge into main through `draft_take`, and `settle_landed` for a pull request a person merged on the code host all end there) marks the entry merged, with who asked from the store's draft, before the `merged` report is sent, so a crash right after the merge still sends them. Then on every pass (paused or not, after the headers' `upsert_from_specs`, as TS does after `upsertHeaders`) `send_plan_items` reads which of the plan's ids the store has (`list { ids }`), looks up the dependencies the plan doesn't name (a dependency the store doesn't have is left off), and sends the rest in one `add { via: "draft", items: [{ id, title, dependsOn, specRefs, kind?, milestone?, checking?, checkingWhy?, requestedBy? }] }`: each starts `todo`, and an id already there is left as it is. The agent sends the facts and the store decides the rest.
- **Retries and failures (fail closed).** A store that can't be asked, or a `list` or `add` that fails (unreachable, 5xx, a `conflict` from an id that arrived meanwhile), keeps the entry and tries again on the next pass, also after a restart, with nothing sent without the store's link; a refusal that sending again can't change (`not_found`, `bad_request`, `forbidden`) is dropped with a `store_error`, as a revision's. **Differs from the TypeScript agent**, which keeps the plan's `items` in `state.json` until the store holds them (`itemsSent`) and looks once per run: here the entry is its own file and is sent again every pass. **The same limit as TS:** the items live on the computer that drafted the plan, so a plan another computer merges has none to send from there.
- **A plan that changes no file (`noFiles`)** (`driver/drafts/no_files.rs`; `drafts.ts`). A drafter result with items whose worktree changed no file against the base has nothing to open a pull request for, so its items go straight to the backlog: its items are checked (as for any plan, a `checking` the drafter gave none is a person's), listed and marked merged in `plan_items.pending.json` (so they go to the store by `send_plan_items` as above), the worktree goes, and `draft_report` says `merged` / `merged` with the drafter's title, its summary, the items' ids as the entries and its checked breakdown, no files and no pull request. No plan facts go with it and it never reaches `awaiting_approval`, so the store has nothing to approve, designs or tiers. Like the `merged` of fixes it is kept until the store answers (`draft_owed.rs`, the `plan` of the entry carries the titles, entries and breakdown). A plan whose items all check to none is published as usual. A plan that changed no file and planned no item whose publish fails ends as a failure with "The drafter changed no file and planned no item, so there is nothing to approve.", else with the publish error. A worktree whose changes can't be read counts as having changed files (TS `[{}]`).

**Hand-back in this Rust agent.** The landing task (`driver/land.rs`) does the hand-back itself, counting in memory: when `rebase` reports a conflict it resumes the draft's saved session (`DraftHost::run`, resume prompt `rebase_request`), force-pushes what the drafter did with lease (`git push --force-with-lease`, `DraftHost::push`; the PR already exists), then rebases (clean now) and merges with the usual retries, reporting only `merged`. A third conflict after 2 hand-backs, or a drafter that fails, reports the draft back to waiting for approval with the reason. The draft's files are listed live, so they are the rebased ones.

**In this Rust agent**, `orchestrator::driver::drafts` is the draft step of a project's loop, in `claim` mode with a session starter. Each pass, for a live project that isn't paused (and while the computer isn't stopping), with no draft running and a session slot free, it calls `draft_claim_next`; a draft jumps the item queue (it takes its slot before items are planned) and counts toward `concurrency`. The loop keeps only the running draft's id and session id, in memory, never a list of drafts in `state.json`: a claim that comes back with a `sessionId` resumes that session ("You were interrupted; continue.", or the person's answers, send-back notes or rebase request), so a restart carries on. A `drafting` report (`sessionId`, `branch`) goes out first. The worktree, the drafter session and the PR sit behind `DraftHost` (the real one, `orchestrator::draft_host::ClaudeDrafts`, runs the drafter on its chosen engine (`engines::place`; Cursor on the `top` model); a Cursor chat's id comes back in the result and is reported as the draft's `sessionId`, so a revision's `--resume` is that chat; its sessions register their process trees, and `shutdown.rs` also cuts anything running in a `draft-<id>` worktree). Then `draft_report` carries, as `needs_person` with the holder's state in `detail`: `awaiting_approval` (titles, summary, `prUrl`, `itemIds` when it named any, the checked breakdown), `needs_clarification` (the questions) or `failed` (the reason). Fixes are added with `add` first; when every piece is a fix, no PR is opened, the worktree goes and the draft is reported `merged`. A session cut by a restart or Quit reports nothing. The settings page lists a running draft as a "Drafting specs" session with no lane. **Edit** is the command `draft_edit { id, path, content, branch? }` (`drafts::actions`; nothing on retaskable.com sends it yet, the TypeScript agent's edit being local only; the branch is the one named, else the checkout's only `retaskable/spec-<id>-…`). It makes the draft's worktree again if it was removed, writes the file (a path that isn't inside the draft is a nack), commits it, pushes it to the draft's branch, and acks with `result: { files }`, listed again as above; the same content again commits nothing. **Discard** (`draft_discard { draftId }`) is queued and carried out like Approve: the loop takes the draft (`draft_take`; one that isn't `needs_person` is let go with `draft_release`), closes its pull request by number with `gh pr close <n> --delete-branch` (a failure is ignored, the PR may be closed already), removes the worktree, fetches, and reports `discarded`. **Skip the design** (`draft_skip_design { draftId }`) is the store's own op `draft_skip_design { id }` with no lease, so it works whoever holds the plan; **Try again** and **Change it…** (`board_design_write { draftId, note? }`, note cut to 2000) take the draft, draw its designs (`design_board::draw_design`), keep why not on the plan (`designNote`, at most 500 characters) and let go of it. Both are queued like Approve, run in `claim` and `runs` mode paused or not, in a task of their own (`orchestrator::driver::design_press`), and answer their command when done (`ack`, or `nack` with the reason: a plan not waiting for approval, one with no design to review, why it can't be drawn). **Approve and Merge into main** (`draft_approve { draftId }` and `merge_pr { draftId }`, acked once queued like Continue, in `claim` mode only) are carried out by `orchestrator::driver::land` on every pass, whether or not the project is paused. The loop takes the draft from the store (`draft_take`; one that isn't `needs_person` with `awaiting_approval` or `awaiting_merge`, or has no PR, is let go with `draft_release`). The project's `github` settings decide who merges (`drafts::land::workflow`): with `land` `retaskable` (the default) Approve runs `gh pr merge <n> --squash` (or the settings' `mergeMethod`), adding `--delete-branch` for a `retaskable/…` branch; if that fails it rebases the branch onto `origin/<baseBranch>` in a worktree (`git reset --hard origin/<branch>`, `git rebase`, `git push --force-with-lease`) and, when the rebase is clean, merges again up to 5 times, 2 seconds apart. A rebase that conflicts is handed back to the drafter as below; any other merge error reports `needs_person` / `awaiting_approval` with `summary` "Couldn't merge: <reason>". With any other `land` Approve merges nothing and reports `awaiting_merge` ("Approved. Waiting for you to merge it into <branch>."); **Merge into main** (only for `land` `person` with `baseBranch` the `protectedBranch`) then squash-merges once, with the same error report. A merged draft has its worktree removed, the remote fetched, and is reported `merged`; its `itemIds` and `requestedBy` go with the next `upsert_from_specs` (as `approved` and `askedBy`), which is sent straight away. When the draft's `intake.doNext` is set and it has `itemIds`, the first is then marked do next with the store op `do_next { id, on: true }`, once (a refusal is logged as a store failure, not retried). Send back and answers come with the claim: a claim that carries `notes` (send back) or `answer` resumes the saved session with them and the PR is reported again; for answers the loop sends `draft_answer_taken` once the worktree is ready and before it resumes the session.

**Self-approval and the retry in this Rust agent.** `drafts::approval::approves_itself(plans, requested_by, risk, release, trial)` is `approvesItself`: true when the project's `plans` (`risky`, the default, or `ask`) is `risky`, the draft has a `requestedBy`, the drafter's `risk` (a result field, in `DRAFTER_RESULT_SCHEMA` and `prompts/drafter.md`) is empty, and the draft is neither a release note's (`kind` `release`) nor a trial (`intake.trial`, first-run-check.md). When it holds, right after reporting `awaiting_approval` the draft step queues the same `draft_approve` press a person's would (`DraftCommand::Approve`), and `driver::land` carries it out on its next pass by the project's workflow, so nothing is sent by a command. A draft that fails (the drafter, the worktree or publishing) with no `retried` on it is reported `queued` with `retried: true` and "Trying again by itself", so the store hands it out again; one that fails with `retried` set is reported `needs_person` / `failed` as before.

**Revisions in this Rust agent** (Retaskable.com's card-revisions.md; `agent/src/revisions.ts`). A draft the chat queued with `revises: <item>` (`draft_queue`; a card's own item is what a request on it revises) is a change to that item, not new work.
- **The drafter is told.** A fresh session (not a resume) reads the item (`list { ids: [id] }`) and `drafts::revision::revision_text` puts "The item it revises:" after the pieces in its prompt, in the TS words: the item's state, what is left, its specs, and the three steps (edit its spec in place, return `revision: { id, remaining }`, separate new work stays an entry). A store that can't be asked fails the plan with "couldn't read item <id>, which this plan revises" (a first failure goes back to the queue by itself): a plan never goes ahead blind to its item.
- **`revision` is kept or dropped** (`to_revision`): kept only when it names the item the plan revises and says what is left (cut to 4,000 characters). Then `draft_report` carries `revises: <id>` and `revision: { remaining }` with the rest of the plan's `awaiting_approval` report; otherwise both are sent as `null` and the plan is new work after all. The item is never one of the plan's `itemIds`, and the breakdown may have a `build` line for it.
- **A fix asked on a card reopens its item** (`reopen { id, notes, by }`, once per plan) when the store allows it, and is not added as an item of its own; when it declines, the fix is added as usual. A store that can't be reached fails the plan rather than adding the fix as a separate item. A drafter run again (sent back) that returns the same fix reopens again, where TS remembers the fixes on the draft; the store's `reopen` of an item already reopened is harmless.
- **At merge** (`driver/land.rs`, Approve, Merge into main and the person's merge row alike, in `claim` and `runs` mode): after `merged` is reported, a plan whose store draft has `revises` and `revision.remaining` lists `{ item, remaining, title, by }` in the state file (`revise_owed`, by plan id) and sends `revise { id, remaining, draftId, by?, title }` (`driver/revise.rs`). The store applies it, or keeps it until the slice in hand ends, or answers a repeat; the plan's id makes a second send harmless. **Differs from the TypeScript agent**, which sends once and only notes "Couldn't revise item" on the plan's timeline: here the call is listed before it is sent and sent again every pass, also after a restart, until the store answers. A refusal sending again can't change (`not_found`, `bad_request`, `forbidden`) is dropped with a `store_error`.
- **A plan landed on the code host while it waited (`draftsLanded`)** (`driver/land.rs`, `settle_landed`, Retaskable.com's team-state-on-server section 3.3.4; `agent/src/draftsLanded.ts`). No computer holds a plan waiting for approval, so none watches its pull request, and one merged by a person on GitHub would stay **Plan to approve** for good. So each project's loop, at most every 10 minutes (`LANDED_EVERY`; the first look is on the first pass) and, sooner, whenever a fetch moves `origin/<default>` (a plan merged by hand is on main by then) or the store pushes `drafts_changed` (at least `EARLY_GAP` = 30 seconds after the last look, so the store's pushes for this agent's own reports don't poll the code host; a wanted look waits for it), in `claim` and `runs` mode alike, paused or not, reads the store's `drafts` and looks (`gh pr view <n> --json state`, the host's `pr_state`) at the pull request of each one that is `needs_person` / `awaiting_approval` with no `heldBy`. A **merged** one is taken (`draft_take`, the lock: a plan someone is approving right now is held and left alone, and of two computers looking at once only the first ends it), and then ends as one this agent merged does (`land.rs`, `merged`): its worktree goes, the remote is fetched, `draft_report` says `merged` (the final report, kept until the store answers, also across a restart), its items' headers go with the next `upsert_from_specs` as approved, and a plan that revises an item lists and sends `revise` (`driver/revise.rs`) exactly as above. A **closed** one (closed without merging) is taken and reported `discarded`, with nothing else done to the already closed pull request. A store that can't be asked for the list leaves it for the next pass, so nothing is taken during an outage (07.5); a pull request `gh` can't read is looked at again at the next look. **Differs from the TypeScript agent:** it looks only every 10 minutes (live 2026-11-17: a plan merged by hand at 21:18 was noticed at 21:25), where here the main move and the push ask for a look at once, and its `merged` report carries no summary and a failed take or report is only logged, while here the `merged` report has the summary "Merged <pull request URL>" as an Approve's has, and is kept and sent again until the store answers (`draft_owed.rs`). The plan's revision rides in the kept `merged` entry (`draft_report.pending.json`: `revision`, and `reported` once the store took the report), so a restart at any point, also in an outage after the take, sends `merged` if it is still owed and then the `revise`: the loop, the state file's one writer, lists it in `revise_owed` and only then lets the kept entry go (a crash between the two lists it twice, harmless: the store's `revise` answers `repeat` for a plan it applied, keyed by the plan's id). Agent-made merges (Approve, Merge into main) do the same. A report the store refuses with a code, or gives up after a day, drops its revision with it.
- **Not built here:** the chat's about-the-card prompt block.
- **A feature people will see waits for a design review** (`src/design_board/`, `driver/drafts.rs`, `driver/land.rs`; Retaskable.com's `agent/src/designBoard.ts`, `drafts.ts`, design-view/14). When a new plan is written, `needs_design_of` (plain code: a feature in its specs' `Kind:` lines, a `*.preview.svg` that passes the safety check, not a `Design:` title, not a plan already sent back) decides, and the report that makes it `awaiting_approval` carries `needsDesign: true`, so no press can approve it before its review. Then a read-only Claude session on the scout tier with no shell, run in a scratch directory, is given the idea, the library and the pages' parts and answers one layout; `check_layout` checks it and `place_layout` places it as the chat's own work (`who: "chat"`, so a person's edits are never overwritten, a redraw takes away only the chat's untouched pieces) on the idea's board (`board_ticket`, then `GET /v1/repos/<id>/board?ticket=&board=idea-<draft id>`, one `add` at a time, 60 ms apart, waiting for the hub's acks). A drawing that can't be done (signed out, the session or its check fails, the board doesn't answer) leaves the plan waiting for its review with `designNote` on the draft (`draft_report`), to try again with `board_design_write`. **Approve** on a plan the store says needs its review is dropped (the draft is let go, not merged). **Skip the design** and **Try again / Change it…** are `design_board::skip_design` and `design_board::draw_design`: take the draft, check it waits for approval and for its review, report `needsDesign: false` or `designNote` and let go. Approve design is the app's: it sends the plan back with `planRequest` of the board's pieces. Differs from the TS agent: (1) the review's state is `needsDesign` and `designNote` on the store's draft (TS keeps them on the computer's own draft record, which the store has no field for), so the store must keep and return them; (2) a plan waiting for its design review does not approve itself, where TS's self-approval skips the check; (3) the layout session runs on Claude only, like the classifier, and does not wait on `canPlan`; (4) no "Design skipped" timeline line; (5) a plan is new when its pull request isn't open yet, where TS tests for a summary (a drafter that asked questions has one before it writes).
