### 9.3 What the computer does when a command asks

- **Continue and Start over** on an item that stopped (`needs_human`). Notes work like the triager's `instructions` (section 6.9): Continue with notes sends them as the implementer's next message and puts the item back to `implementing` on its branch; Start over puts them in the new attempt's first prompt. Continue without notes just re-runs the checks. With nothing on a branch to carry on from (no PR, and no session to resume: it stopped before either, say on a prompt it couldn't fill), a person's Continue starts the slice again as Start over would, notes and all, since there's nothing to lose (`continueItem`, `agent/src/orchestratorActions.ts`; the triager's does the same, section 6.9). Notes go into transcripts and the PR's history, so they must not hold secrets.
  - **In this Rust agent**, `continue { id, notes?, pictures? }` is carried out in `claim` mode only (any other mode nacks it). `commands::run` refuses a missing or blank `id`, saves any pictures under `.retaskable/attachments/` (at most 4, 1 MiB each, 4 MiB in all; PNG, JPEG, GIF or WebP; one bad picture nacks the command and saves none) and adds their paths after the notes, then queues the command (`view::ItemCommands`, shared with the orchestrator `Machine` as `view::PauseState` is) and acks. On its next pass the loop drops, and logs, a command for an item that isn't `needs_human` in its runs. For one that is, it waits for a free lane, clears the item's rounds (`resume_from_needs_human`, or `resume_past_slice_limit` at the slice limit) and starts the implementer on its existing branch with the notes as the prompt (lane reused, not reset); with no notes the item goes back to `checking`. With nothing to carry on from (`nothing_to_continue`, and not at the slice limit) it runs Start over below, notes and all.
  - **Start over in this Rust agent** is `retry { id, notes?, pictures? }`: `commands::run` checks, saves pictures and queues it exactly as Continue (`ItemCommand::StartOver`, `claim` mode only). On its next pass the loop drops, and logs, a command for an item that isn't `needs_human`. Otherwise it waits for a free lane, then `SessionStarter::abandon` lets go of the old work: an open PR is closed with `gh pr close` (its branch stays); with no PR the old branch is dropped from `origin` (when pushed) and from the repo; a PR that is merged or already closed is left as it is. If that fails the item stays as it is, nothing started. Then the item's attempt (`RunRecord.attempt`, for its current slice only) goes up by one, its rounds are cleared (`resume_from_needs_human`) and a fresh implementer (a new session id, never the old one) starts in the lane prepared from `origin/<base>` on `retaskable/<id>-<slug>-s<slice>-r<attempt>`, with the notes under "Notes from the last attempt" in its first prompt (`implementer::prompt::Prompt::notes`). The branch name carries the attempt for every later start of that slice too, resumes included.
- **Shoot** runs the gallery's command and keeps the pictures (section 6.8).
  - **In this Rust agent**, `src/commands.rs`'s Shoot finds the gallery by matching the command's `gallery` slug against the project's own `galleries` list (`GalleryConfig::slug`, its name in kebab case), runs `galleries::shoot_refusal`'s blank-command, bad-`outDir`, already-shooting and unknown-gallery checks, then spawns `galleries::shoot` on its own thread and acks at once, once it's started (tray.md section 5.3.3). The base checkout's busy lock (`base_hold::hold_base`) is taken for the shoot and refuses it while Play main holds it; the baseline and a sync don't take that lock yet (docs/specs/agent/06.8-galleries-the-game-photographs-itself.md); the backlog-store upload (item **galleries-in-store**) isn't ported either.
- **Play** and **Play on phone** run the project's own command ([play-on-phone.md](../play-on-phone.md)).
  - **In this Rust agent**, `play { lane: 0 }` and `stop { lane: 0 }` (`src/commands.rs`, `src/play.rs`) are Play main: it refuses a blank `playCommand`, Play main already running, or the base checkout held (`base_hold::hold_base`, shared with Shoot), then moves the base checkout to `origin/<baseBranch>` (`lanes::prepare_base_checkout`) and runs `playCommand` there through the shell, unsandboxed and with a visible window, with `RETASKABLE_LANE=play`, and acks once the process has started. It holds the base checkout until the process ends. `stop` kills the process tree and waits up to 15 s, nacking if it didn't close. `play { lane: k }` and `stop { lane: k }` with `k` from 1 to `lanes` are acked and queued for the orchestrator loop (`view::ItemCommand::Play`/`Stop`, only in `claim` mode; a blank `playCommand` or a lane past `lanes` is nacked), which owns the `LanePool` and decides (`orchestrator/driver/lane_play.rs`). The lane must hold an item that last used it here with no step running, and nothing may hold the lane now; one that's empty, busy building, or already playing is refused and logged (the ack went out already). The game runs `playCommand` in `lanes::lane_path(worktreesDir, k)` (`SessionStarter::play_lane`, `play::start_in_lane`), visible and unsandboxed, with `RETASKABLE_LANE=<k>`. The lane is held as a `lane_pool::Holder::Play` while it runs, so no session or step of the item starts there; it goes back to the item when the process ends or `stop` kills its tree.
- **Pause and Resume.** What stops and what carries on while paused are as in sections 6.6 and 7; a pause stops chat, spec drafts and the planner too. On a shared backlog there are two pauses ([team-state-on-server.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/team-state-on-server.md) section 3.1): the store's, for every computer on the project, which the agent obeys, and this computer's own, which it keeps. The agent reports which is on ("Paused by @james for everyone", "This computer is paused").
  - **In this Rust agent**, `src/commands.rs` runs this computer's own pause only, one command naming `{ computer: true }`; without it the command is refused, since that pause is the shared backlog's, answered by retaskable.com itself without reaching a computer (`agent/src/commands.ts`'s `SITE_ANSWERS`). Pausing sets a reason (`"Paused from retaskable.com by <login>"`) and Resuming clears it, held per project in `view::PauseState` and sent in the project's `pausedReason`, resending the snapshot on either; nothing here yet stops chat, spec drafts or the planner, since none of those run in this agent, and the shared backlog's own pause isn't read, since there's no work loop yet to obey it — still later pieces, not further slices of this item.
- **Restart.** Runs at once (section 4.2: now, finishing a merge first), exiting with code 75 for the supervisor or a release build to start it again (section 8).
  - **The sequence (item `command-handling`; TS: [restart-progress.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/restart-progress.md) section 3.1).** One restart request runs these steps in order, and asking again while one is pending keeps the first request's `why` (`at`, `by`, `reason`).
    1. **Keep the lanes going.** Implementers keep starting and claiming while a restart is pending, since they run detached and work on through it (section 7.4). Only Quit when idle starts nothing new.
    2. **Let only these finish:** a merge, a plan's merge, an update to main, a promote, for 2 minutes at most. Sessions, checks, a shoot and a Play on phone build are not on the list.
    3. **Cancel the rest.** Every other running session, check, shoot and Play on phone build is killed whole and ends `interrupted` (section 7.4), so each item keeps its lease and run record. Detached implementers are not cancelled: they keep running through the restart.
    4. **Restart** by exiting 75, after the same-tick answers are sent and the cloud link flushed (2 seconds at most).
    5. **Pick up again.** After it starts, `readopt` attaches to each detached implementer still running, reads the result of one that finished, and resumes by session id any other with "You were interrupted; continue."
  - The snapshot shows the step (`waiting` with what it still waits on, then `now`), as in restart-progress.md.
  - **In this Rust agent**, a restart is pending, not an immediate exit. `src/commands.rs`'s Restart records the request in `view.restart` (`src/restart.rs`'s `RestartState`: the first request's `why` `{ at, by, reason }`, kept when asked again), then calls the same `exit(75)` the settings page's restart button and a release update use (`restart_handler` in `src/runtime.rs`; those two record `by: "this computer"`, `reason: "asked"` unless a request is already pending). The first call runs the sequence on a thread; later calls start nothing. It logs `restart_asked`, then: runs held by the `runs` loop end first (pieces.md section 3.1); step 1: lanes keep claiming and starting, since `process_tree::stopping()` is set only at the cut; step 2: the finish-first registry (`RestartState::hold(what)` returns a guard, released on drop; a merge, a plan's merge, an update to main and a promote will hold one, and none exist in this agent yet) is waited on for `FINISH_FIRST` (2 minutes) at most, logging `restart_waiting` (what it waited on, `ms`) if anything was held; step 3: `process_tree::cut_all` and `shutdown::stop_other_sessions` end cut sessions as `interrupted`, then the update installs or the release build relaunches; step 4: a flush wait (at most `FLUSH`, 2 seconds; as built, 200 ms for the link to send the same-tick answers, not a check that the link has sent them), `restart_exit` (`drainMs` since the request) and `exit(75)`. The snapshot's `orchestrator.restart` is `{ step: "waiting", waitingOn, at, by, reason }` while it waits, then `{ step: "now", … }`, and a change resends the snapshot. Detached implementers and `readopt` (step 5) aren't in this agent, so nothing runs through the restart and nothing is picked up after it (items `detached-implementers` and `orchestrator-loop`'s readopt).
- **Audit.** Every command checked, run or refused is logged (cloud.md section 6.3).
  - **In this Rust agent**, `src/commands.rs`'s `audit` writes one JSON line per command to `.retaskable/remote.log` (`{ at, id, name, issuedBy, args, outcome: "ack" | "nack", reason? (nacks only), cloud }`), called from `src/connector/mod.rs`'s `receive` right after a command is answered — a replay or an expired or pre-Setup command included, the same as one this agent runs. `answerBytes` and `auditArgs`'s per-command sanitising (`agent/src/commands.ts`) aren't ported, since none of the commands they apply to are; a write that fails is dropped silently, the same as the event log's ([agent-telemetry.md](../agent-telemetry.md) section 3).
- **Release notes.** A read-only **release notes** session (role `writer`, the scouts' tier or the local model when it's free, budget `budget.releaseNotesUsd`, prompt `prompts/release-notes.md`, interactive like an ask) writes the words for the PRs merged in a range, found with `gh pr list --state merged --search merged:…` and `git log --first-parent`, and returns `RELEASE_NOTES_RESULT_SCHEMA`: `{ status, title, summary, highlights: [{ key, headline, text }], entries: [{ key, text }], error? }`. It picks the 3 to 5 highlights and writes the words, but can't add an entry or show a chore. The agent asks the store for what may go in and where the note is kept and published ([release-notes.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/release-notes.md), `releases_get`, `release_set`); it does not decide them.
  - **In this Rust agent**, `src/release_notes/` ports the gathering, grouping, prompt and rendering halves of `agent/src/releaseNotes.ts` and `shared/releaseNote.ts`. `gather` runs `gh pr list --state merged --base <branch> --search merged:<from>..<to>` and `git log --first-parent` over the range and reads each named spec at the base branch. `group` (over a `GroupInput`: the PRs, commits, the store's items and `drafts`, the specs' contents, and the repo and base branch) puts each merged PR under the backlog item that owns it (its `pr_url`, else the longest `retaskable/<id>-` branch prefix): one section per spec, in the order of its first item in the backlog and titled by the spec's first heading without a trailing "— Spec", then **Chores**, then **Other changes** (items with no spec, PRs no item owns, and commits pushed without a PR). An item's entry falls back to its PRs' titles joined with "; ", a chore's to its own title. A merged spec draft's PR (a store draft whose `prUrl` it is) goes under the spec it adds or edits, the first Markdown file it changed (`fill_draft_files` reads only a draft's PR's files, with `gh pr view <n> --json files`, since the store's draft doesn't keep them), as "Specced: <its titles>"; one that changed no Markdown file is another change. Each entry links its specs (`spec_links`): every Markdown file in the item's `spec_refs`, once, at `https://github.com/<repo>/blob/<base branch>/<path>`, labelled with its file name; the store's `specRefs` name whole files, so a link is to the file, not a section. Because this agent's `Item` carries less than the TypeScript one, chores are the `chores` milestone and share one section (no separate playtest-fixes section: the agent's own chores, `fix_playtest` among them, aren't in this crate), an item's spec is its first Markdown `spec_refs` entry, and "done" is its status alone (on main or in production). `for_users` leaves out the **Chores** section and every draft entry, so neither readers nor the model see them. `facts` is the JSON array of sections the prompt is built from, each entry with its item as `<id> <title>` and its status, its PRs' titles and bodies (cut to 600 characters), a commit's subject and its specs' labels (entries past `releaseFullEntries`, 120, are cut to their title, the smallest **Other changes** first), `build_prompt` fills `prompts/release-notes.md`, `release_notes_result_schema()` is `RELEASE_NOTES_RESULT_SCHEMA`, and `markdown` renders the note from the grouping and the model's answer (or, with none, from the facts alone): front matter, the title, then "Nothing new for users between … and …" when nothing is for the readers, else the summary, up to 5 highlights and **Also new** (**What's new** with no highlights). With no answer the highlights are the items that are done, headed by their titles. In **Also new** an item the model wrote no line for is listed by its title, and another change (a PR no item owns, a commit) shows only when the model wrote a line for it. Item ids never reach the note. `note_markdown` can also render a **Fixes** list, which `markdown` leaves empty while there's no playtest-fixes section. `empty_note` is the note for a range with nothing merged. `check_range` refuses a range that isn't two dates, runs backwards, or is in the future (To may be up to two days ahead, being the end of its day) and answers both ends as UTC instants. `write_note` picks the note: `empty_note` for nothing merged, the plain list when only chores merged (no session), and otherwise the read-only, ephemeral `writer` session (`writer_model`: `local` when the scouts' tier is, else `haiku`; `budget.releaseNotesUsd`; the facts' prompt; `RELEASE_NOTES_RESULT_SCHEMA`; the project's sandbox setting) run through the caller's `run_session`. Its answer becomes the note when `status` is `ok`; a session that fails, won't start or answers anything else leaves the plain list, with "Claude hit its $… budget …, so this is the plain list of what's new." (or "couldn't write them: …") as the note's error, and the session's model and cost kept either way. The saved notes are the store's (`release_notes::saved`, ported from `agent/src/storeReleases.ts`): `SavedReleases::list` first offers the store, once, the notes in the repo's `docs/releases` folder on the base branch (`read_release_files`, the last 200 by name; `release_of_file` makes a row of each with `from` and `to` days in its front matter, a file-name id the store takes and a body of at most 128 KB, titled by its first `#` heading and saved at the start of its `to` day) with `releases_offer`, remembered in the project's `releases.offered.json`; a store that can't be reached leaves it to try again at the next read, and one that refuses it (`bad_request`) isn't asked again. Then it answers `releases_get`'s rows without their Markdown, newest first, or none when the store can't give them (never a guessed list), and `get(id)` one note with its Markdown (`not_found` when the store hasn't got it). Saving a note, `release_set`, is the site's as a writer, not this agent's. `backlog::Client::op` is the store call they share with `list` and `drafts`, and a refusal keeps the store's own error code. `context` builds the prompt's inputs from the store: `round_context(live, ideas)` is TS's `context()` shape `{ live, accepted, later, never, waiting, people }` (`live` at most 12, newest first; the store rows' titles by state, Claude's waiting ideas under `waiting` and a person's, `addedBy` set, under `people`); `gather_live` reads the done items (`on_main`, `in_production`) newest first by their PR's merge time from `gh pr list --state merged --base <baseBranch> --json url,mergedAt`, an item whose PR isn't listed last; `profiles_for(audiences)` turns the store's audiences into `Profile`s (`short` as `who`), falling back to `starter_profiles()` when there are none. Nothing calls any of it yet: the command that asks for a note, the note's state while it's written, the scouts' tier and whether the local model is free need the cloud link and the orchestrator loop (milestones 4 and 5 of [11-build-milestones.md](11-build-milestones.md)), and a separate playtest-fixes section and **Fixes** list need the agent's own chores (`fix_playtest` among them) — still later pieces that bring this in, not further slices of this item, the same as `scan`'s and `repo`'s notes in section 9.1.
- **Ideas** ([manual.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/manual.md) section 5.1). After a slice merges (at most once a day), a read-only `writer` session (`itemId` `_ideas`, prompt `prompts/ideas.md`, budget `budget.scoutUsd`, on the scouts' tier) writes up to three ideas from what went live, the questions asked and the owner's past answers. The ideas, their queue and the owner's answers are in the store (`ideas_list`); the agent keeps no copy ([last-local-state.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/last-local-state.md) section 7).
  - **In this Rust agent**, `src/ideas/` ports `agent/src/ideas.ts` and the shared backlog's own copy of the queue, `shared/storeIdeas.ts`, split by responsibility like `src/release_notes/`: `model` is the plain data types and the refill fold, `context` builds the prompt's context and user types from the store, `profiles` is the starter user types and the prompt builder, `store` reads and writes the shared backlog, `write` runs the session and picks the round, and `test_support` holds this module's own shared fixtures. `Idea` and `IdeaSuggestion`/`IdeasResult` (`model`) are the queue's own idea and the session's raw answer (`IDEAS_RESULT_SCHEMA`, `agent/src/schemas.ts`), checked against `shared/storeIdeas.ts`'s `IDEA_LIMITS` (`IDEA_TITLE_MAX`, `IDEA_EXPERIENCE_MAX`, `IDEA_WHY_MAX`, `IDEA_WHY_NOW_MAX`, `IDEA_FOR_MAX`, `IDEA_FEATURE_MAX`, `IDEA_NEW_FEATURE_MAX`); `ideas_result_schema()` is `IDEAS_RESULT_SCHEMA`. `refilled(was, res, profiles, stamp, queue, max_waited)` ports `refilled` exactly: the `Queue` already waiting gets one more refill each (dropped once it's sat through `max_waited`, `ideasMaxWaits`'s default `IDEAS_MAX_WAITS_DEFAULT`), then the session's fresh ideas fill the rest up to `queue` (`ideasQueue`'s default `QUEUE`), skipping a blank title and one already waiting, accepted, or turned down Never, each keeping only the known user types up to `IDEA_FOR_MAX`, once each. `Profile` and `build_prompt` (`profiles`) are trimmed from `shared/audiences.ts`'s `Audience` to the fields the prompt shows; `build_prompt` fills `prompts/ideas.md` (ported byte for byte) with this project's words (`crate::prompt::project_words`), the repo, what prompted the round, how much room is left, the user types and an already-built `context` JSON value, through the same `crate::prompt::render_prompt` the release-notes prompt uses; `starter_profiles()` is a fixed, starter set of eight (`starterAudiences`, shared/audiences.ts) standing in until the real audiences book — one a person can add to and edit — reaches this agent. `Ideas` (`store`) wraps `backlog::Client::op` for `ideas_list`, `ideas_round { ideas, after? }` and `idea_answer { id, answer, draftId? }` (backlog/06.2-operations.md), always sending `for: { via: "command", login? }` since every answer this agent carries out is a person's command; `queue_from_store` folds the store's own rows (`StoreIdeas`, trimmed from `shared/storeIdeas.ts`'s `IdeaList`) into a `Queue`, leaving a person's own waiting ideas (`addedBy` set) out of it, since a round must leave those alone (backlog/06.2-operations.md). `Writer`, `session_spec` and `run_round` (`write`) are the session half (`generate`/`write`, agent/src/ideas.ts): the read-only, ephemeral `writer` session on `budget.scout_usd`, asking for however much room is left in the queue (at least one), run through the caller's `run_session`, its answer folded in with `refilled` when it answers `ok`. A session that fails, won't start, or answers anything else leaves the queue waiting as it was, with "Claude hit its $… budget …" (or "couldn't think of ideas: …") as `Round::error`, the session's model and cost kept either way. Nothing calls any of it yet: the daily chore (needs the orchestrator loop's locks, so two computers don't run a round at once), the command that dispatches Accept/Not now/Never to `Ideas::answer`, and Accept's draft-writing (needs the spec-drafts item) all need pieces that haven't reached this agent yet (milestones 4 and 5 of [11-build-milestones.md](11-build-milestones.md)) — still later pieces, not further slices of this item, the same as `scan`'s and `repo`'s notes in section 9.1.
