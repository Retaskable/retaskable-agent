### 6.8 Galleries: the game photographs itself

A **gallery** is a tab of pictures of everything of one kind in the game, such as every model or every UI screen, so you can look over the art without playing to find it. The work is split in two:

- **The game only takes the pictures.** A gallery's `command` (e.g. `cargo run --release -- --models --shoot`) puts the game into each subject in turn, screenshots it, writes `<outDir>/NN-slug.png`, optionally writes `<outDir>/index.json` (`[{ file, name, group }]`), and exits 0. It needs a window but no input.
- **Retaskable does the rest.** **Shoot** runs the command in the base checkout (the base checkout at `origin/<baseBranch>`, like Play main), in a visible window, with a 30-minute timeout. It empties `outDir` first. `outDir` must be a relative folder inside the repo, not the repo itself (`.` is refused). Setup doesn't check this: the shoot command is refused when the command is empty or `outDir` leaves the repo or is the repo itself, or for an unknown gallery. It then converts each PNG to a JPEG (quality 82, at most 1920 px wide) into `.retaskable/projects/<id>/galleries/<slug>/`, with an `index.json` holding `{ name, shotAt, sha, images: [{ file, title, group? }] }`. The new set replaces the old one only once it's all written. After each shoot, and when the socket to a shared backlog opens, the agent also puts the gallery's set in the backlog store ([last-local-state.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/last-local-state.md) section 3.8, item **galleries-in-store**). Titles come from the game's `index.json` when it has them, and otherwise from the file name (`05-icy-tree-crystal-tree.png` → "Icy tree crystal tree"). Groups travel with each picture; the filter chips and labels are the app's.
- **[Proposal] The pictures move to the store** (last-local-state.md section 3.8; for now the agent only puts a copy there and keeps the folder): once converted, the JPEGs upload to the backlog store by content hash and the local temp copy is deleted; the `gallery_index` and `gallery_image` commands then read the store instead of this computer's disk, so a gallery is visible with this machine offline.
- **The shoot's checkout has its own dependencies.** The base checkout is otherwise a light checkout that nothing but the baseline installs into (section 6.7), so a command such as `npm run shoot:ui` would find no `node_modules` there. (It used to half-work: `vite` started from another checkout's `node_modules/.bin` on PATH, then failed to load `vite.config.ts` with "Cannot find package 'vite'", before any picture was taken.) So:
  - Before running the command, when the checkout has a `package.json` at its root, Retaskable installs its dependencies if `node_modules/` is missing, or `package-lock.json` is newer than `node_modules/.package-lock.json` (the copy npm writes after an install). It runs `npm ci` when there's a `package-lock.json` and `npm install` otherwise, in that checkout, with a 10-minute timeout, as the orchestrator's own command (outside any sandbox, like the checks). The status stays `shooting` meanwhile. If the install fails, the shoot is `failed` with the install's last 40 lines, and the command never runs. The installed `node_modules/` stays in the worktree between shoots and baselines (it's gitignored, so syncs keep it), so later runs skip the install until the lockfile changes. That costs the base checkout one more build folder on disk, as Play main's build output does.
  - The command's environment is Retaskable's own with every PATH entry ending in `node_modules/.bin` (or `node_modules\.bin`) removed, except the checkout's own, which is put first. npm adds its checkout's `.bin` to PATH when Retaskable is started with `npm start`, and without this the shoot would run another checkout's tools against this one. The same goes for the install.
  - Other kinds of project need nothing here: `cargo run` fetches its own crates into the shared cache.
- **A shoot holds the base checkout.** It won't start while a sync, the planner, the baseline or Play main is using the checkout. While it runs, a sync and the baseline wait, Play main is refused, and a sync that was put off runs afterwards. Only one gallery shoots at a time. Its status (`idle`, `shooting`, `converting`, `failed` with the output's last 40 lines) is kept in memory and reported with the computer's state (`State.galleries`) for the app to show.
- **When the game can't take them yet**, the gallery's command is empty and the app offers **Add a way to take these**. That command renders the skill `prompts/shoot-mode.md` for the gallery (what to find, fixed settings, settle frames, file naming, the manifest, exit 0; reuse an existing shoot mode if there is one) and starts a spec draft with it (section 6.5). It then goes through the store's drafts and the pipeline like any feature. Once it's built, you set the command in Setup.
- **Feedback.** The app's feedback boxes (about the whole gallery, or one picture) send what should change. The agent renders `prompts/gallery-feedback.md` (the gallery, the picture's title, group and saved JPEG path for the drafter to look at, and the notes) and starts a spec draft with it (section 6.5): a short sub-spec next to the spec covering those subjects, and a backlog entry under a heading named after the gallery ("Models", "UI", ...), added if the spec has none. These are small fixes, so the box's **Do next once merged** is on by default: the drafter returns the new entry's `itemId`, and once the draft is merged and the store has the item, the agent asks the store to mark it do next (`do_next`), once. A person still approves the draft, and the app says it will jump the queue.
- **In this Rust agent**, `src/galleries.rs` ports the game's-done-the-rest half above: `shoot`, the PNG-to-JPEG conversion, and `gallery_index`/`gallery_image` (tray.md 5.3.2), plus the dependency install and `PATH` scrub (bullets 8-9). Nothing calls any of it from the hub yet: that's the command-dispatch layer, built for no command yet (`src/connector/mod.rs`'s `receive` nacks every command). The backlog-store upload (bullet 2, item **galleries-in-store**) doesn't exist in this agent either — `src/backlog.rs` only reads. The base-checkout lock against the baseline, Play main and a sync (bullet 4) is also still a later piece (`src/lanes.rs`'s `base_checkout_path`): a shoot only holds its own project's status for now. Shoot mode and gallery feedback (the last two bullets) need the drafts pipeline, which isn't ported yet either.
