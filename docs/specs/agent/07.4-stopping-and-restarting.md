### 7.4 Stopping and restarting

Under runs ([pieces.md](../pieces.md)), nothing is kept to resume: what this section says about detached implementers, readopting, resuming by session id and keeping a lease is replaced by pieces.md section 3.1. Killing whole process trees still holds.

These are the Rust agent's rules (items `restart-cuts-sessions` and `detached-implementers`), ported from Retaskable.com's agent.md section 4.2, "Restarts don't stop the lanes". The Restart command's own sequence is in section 9.3.

- **Detached implementers (`detached-implementers`).** An implementer on Claude Code runs detached: started on its own, with its prompt read from `<session>.prompt.txt`, writing straight to its transcript, which the agent reads as it grows. Beside it, `<session>.live.json` holds its process id and where this run's lines start. A program behind a shell (a `.cmd` claude) runs piped, as before, since a detached process has no console for it on Windows. A restart neither waits for these nor stops them, and implementers keep starting while one is pending. Quit stops them too, and Quit when idle waits for everything to end.
- **After the restart, readopt attaches first.** `readopt` (PR #148) resumes an implementing item with `--resume` even when its session is still running. It must instead read the live file. If the process id is alive, the runner attaches to it and does not start it again. If the session finished while the agent was down, it answers the result left in its transcript. Only a session that is gone with no result is resumed with `--resume`. A live file over 12 hours old is never attached to.
- **Every other session is cut (`restart-cuts-sessions`).** A restart cuts reviews, scouts, triage, drafts, chat, release notes and ideas, and also the checks and their installs, a shoot and a Play on phone build. Each is picked up again after. Their process trees are killed as the agent exits, and anything still running in a lane or the base checkout is killed before its checks run again.
- **Process trees die whole.** Each such child starts in a group the agent can kill: on Windows a Job object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, on Linux and macOS a process group of its own. Everything it spawned (a build, a test run, a dev server) is in it. Today `engines/runner.rs`'s `spawn_and_read` kills only the direct child, so on Windows children can outlive the agent. Detached implementers are deliberately outside the group on a restart; on Quit they are stopped too.
- **A graceful stop waits for the kills.** The agent kills each tree, waits until it has gone (5 seconds at most per session, then it reports the one that stayed), and only then exits.
- **A cut session ends as `interrupted`**, not `failed`. A kill the agent asked for in a stop or restart is `interrupted`; a session that died on its own without a result is still the "killed without a result" case above. An interrupted session keeps its lease and run record, the item is not released, and nothing is posted to the store. After the restart it is picked up again as above, resumed by session id with "You were interrupted; continue." Today it surfaces as Failed and is released, which must not happen.
- **Only these finish first**, for 2 minutes at most: merges, plan merges, updates and a promote's push.
