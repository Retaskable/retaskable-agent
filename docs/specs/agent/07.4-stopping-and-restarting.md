### 7.4 Stopping and restarting

Under runs ([pieces.md](../pieces.md)), nothing is kept to resume: what this section says about detached implementers, readopting, resuming by session id and keeping a lease is replaced by pieces.md section 3.1. Killing whole process trees still holds.

These are the Rust agent's rules (items `restart-cuts-sessions` and `detached-implementers`), ported from Retaskable.com's agent.md section 4.2, "Restarts don't stop the lanes". The Restart command's own sequence is in section 9.3.

- **Detached implementers (`detached-implementers`).** An implementer on Claude Code runs detached: started on its own, with its prompt read from `<session>.prompt.txt`, writing straight to its transcript, which the agent reads as it grows. Beside it, `<session>.live.json` holds its process id and where this run's lines start. A program behind a shell (a `.cmd` claude) runs piped, as before, since a detached process has no console for it on Windows. A restart neither waits for these nor stops them, and implementers keep starting while one is pending. Quit stops them too, and Quit when idle waits for everything to end.
- **After the restart, readopt attaches first.** `readopt` (PR #148) resumes an implementing item with `--resume` even when its session is still running. It must instead read the live file. If the process id is alive, the runner attaches to it and does not start it again. If the session finished while the agent was down, it answers the result left in its transcript. Only a session that is gone with no result is resumed with `--resume`. A live file over 12 hours old is never attached to.
- **Every other session is cut (`restart-cuts-sessions`).** A restart cuts reviews, scouts, triage, drafts, chat, release notes, and also the checks and their installs, and a Play on phone build. Each is picked up again after. Their process trees are killed as the agent exits, and anything still running in a lane or the base checkout is killed before its checks run again.
- **Process trees die whole.** `engines/runner.rs`'s `spawn_and_read` starts each such child's session in a group the agent can kill as a whole, via `process_tree.rs`'s `ProcessTree`: on Windows a Job object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, assigned right after spawn; on Linux and macOS a process group of its own, set on the command before spawn. Everything it spawned (a build, a test run, a dev server) is in it, so `spawn_and_read`'s own silence and end-after-result timeouts kill the tree this way rather than walking descendants after the fact, and dropping the tree (the agent exiting) takes a Windows tree down too, by closing its last handle. `lanes.rs`'s `kill_tree` still walks and kills a whole tree the older way (`taskkill /T /F` on Windows, a `ps`-based descendant walk with `SIGTERM` on Linux and macOS) for `shutdown::stop_other_sessions`, which calls it as a restart or Quit happens, scanning each project's main checkout and base checkout for anything still there and waiting up to 5 seconds for it to go — a scan for anything left, not a group closing, so a child that doesn't carry its checkout's path on its own command line is still missed there. Detached implementers are deliberately outside the group on a restart; on Quit they are stopped too.
- **A graceful stop waits for the kills.** As built (`process_tree.rs`): every `ProcessTree` adds itself to a process-wide registry when its child joins it. `process_tree::cut_all()` sets a `stopping` flag, calls `cut()` on every registered tree, then kills and waits for all of them in parallel, `KILL_LIMIT` (5 seconds) at most each, and logs the process id of any tree that stayed. Only then does the agent go on to `shutdown::stop_other_sessions` (the scan above) and exit. Both exits call the same two steps in this order: a Restart (`runtime::cut_every_session_then_exit`, on a thread 200 ms after the answer is sent, then an update install or relaunch if the code is 75 on a release build, then `exit`) and Quit (`main`, after the connectors have stopped, since Quit returns from `main` instead of exiting).
- **Nothing new starts once it is stopping.** The `stopping` flag is read by the orchestrator driver (`orchestrator/driver/machine.rs`'s `stopping()`), which neither starts nor claims work, and by `settle`, so a session cut mid-flight is not settled as a failure.
- **A cut session ends as `interrupted`**, not `failed`. A kill the agent asked for in a stop or restart is `interrupted`; a session that died on its own without a result is still the "killed without a result" case above. `engines/runner.rs`'s `spawn_and_read` checks its `ProcessTree`'s `was_cut()` ahead of the watchdog's own silence check, and its caller (`implementer::run_implementer`) passes the `interrupted` subtype on as a typed `Interrupted` error, the way a watchdog kill already is as `SilenceKilled`. `orchestrator::session::session_result_for_answer` maps that to `orchestrator::driver::settle::SessionResult::Interrupted`, which `settle()` does nothing with: the run stays `implementing`, its lane and lease untouched, nothing posted to the store, and a `session_end` logged with `ok: false` and `subtype: "interrupted"`. After the restart it is picked up again as above, resumed by session id with "You were interrupted; continue." Restart and Quit now call `cut_all`, so this holds end to end for any session whose tree is registered.
- **A run's own cut (`runs/mod.rs`).** Under runs, `Runs::cut_and_end` cuts each of a run's trees (`cut()`, then `kill_and_wait(KILL_LIMIT)`), then ends the run with its lane released and `run_done` queued. It is used for a `stop` verdict from `run_beat` (outcome `interrupted`) and for a run past its kind's ceiling (outcome `failed`, naming the ceiling). A run the agent could not start (no free lane, or its starter refused) ends `interrupted` at once, so the store gives it to another computer. On the next start `runs_drop` ends every run and lock this agent still held as `interrupted`, before any `run_take`.
- **[Proposal] Edge cases a slice should test.**
  - A tree that outlives its 5 seconds: the log names its process id, the agent still exits, and the next start's `runs_drop` is what frees its run in the store. Nothing waits longer.
  - Two cuts at once (a Quit while a Restart's thread is running, or a `stop` verdict during `cut_all`): `cut()` is a flag and `kill_and_wait` on a gone tree returns true, so the second cut does nothing; the run is ended once, since `end` finds no live run the second time.
  - A restart asked for while a session is between `spawn` and `join` (the tree is not yet registered): the tree is missed by `cut_all`. Today nothing closes this gap; the proposal is that `spawn_and_read` checks `stopping()` right after joining and cuts its own tree if it is set, so the child cannot outlive the agent.
  - A cut run's lane is released before `run_done` is sent, and `run_done` is retried a minute later if the store is down; if the agent exits first, `runs_drop` on the next start covers it.
  - On Windows closing the last Job handle kills the tree even if the agent crashes; on Linux and macOS a crash leaves the process group running, so the next start's base-checkout scan is what ends it (a **proposal**: log what it finds there).
- **Only these finish first**, for 2 minutes at most: merges, plan merges, updates and a promote's push.
