### 7.3 Retaskable's own failures

"Needs help" only ever means a person is really needed. A fault of the agent's own goes back to the queue, and the computer that has it restarts itself (2026-10-22: six items went to Needs help with `Error: Prompt variable {{codeLimits}} not provided`, from an agent running older code than its prompts).

- **An error before any work.** A step that throws while starting a slice, before any session ran (`implementing`, no `implSessionId`, no PR: `beforeWork` in `agent/src/steps.ts`), isn't the person's problem (`ownFailure`, from `runStep`'s catch in `orchestrator.ts`). The error itself goes in the item's timeline.
  - The item is given back to the queue (`HostedWork.giveBack`), noted "This computer hit a problem of its own before starting, so it handed the item back.", for a healthy computer to claim.
  - **Then that computer claims nothing new for 30 minutes** (`CLAIM_PAUSE_MS`, `pool.claimPausedUntil`, checked before `claim_next` in `startNext`), so it doesn't take the same item straight back. A restart clears it. Items it already holds carry on.
  - An error once a session has run still goes to `needs_human` with its error, as before: that session's work may need a person.
- **Code that changed under a running agent restarts it.** An agent running from a checkout (not a release build) reads the git trees of `agent/`, `shared/` and `prompts/` at `HEAD` as it starts (`rememberCode`, `agent/src/selfUpdate.ts`). After each fetch (about once a minute) it reads them again (`restartIfCodeChanged`), and if they differ (a `git pull`, a branch switch, a commit, or an update it didn't restart for) it asks for a restart with reason `update`. Changes not yet committed don't count.
- **Claude's sign-in running out is the computer's, not the item's** ([claude-signed-out.md](../claude-signed-out.md), built). A Claude session that ends with Claude Code's own sign-in error (`signedOut`) sets `Pool.claudeSignedOut`: no Claude session starts on that computer, the item waits for the sign-in (`signInWait`, holding no lane) or, with nothing pushed, is given back, and a check once a minute carries everything on once it's signed in again, items left at Needs help for it included.
- **No new work while an update's restart waits.** `canStartSession` refuses new implementer work while an `update` restart is pending, as for Quit when idle, so nothing starts on the old code. Other restarts let an implementer start, as before (section 4.2).
- **Triage never leaves "continue with nothing to continue from".** When the triager decides `continue` but there's no PR and no session's pushed work to carry on from (`nothingToContinue`, `agent/src/triage.ts`), the item starts over instead (`retry`, with the triager's instructions as notes), noted "Started over by Claude: there was nothing to continue from".
- **Every button works from any computer.** An item that needs help and that no session worked on is parked in the shared backlog (`parkFor`), so another computer can take it over. Which computer may press what is the store's and hub's to decide ([claim-while-working.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/claim-while-working.md) section 3.3.4).
- **In this Rust agent (item `own-failure-handling`, only the watchdog kill is built).** Only the bluntest half of this section exists, plus the watchdog kill: any other crash, whenever it happens, becomes a `SessionResult::Failed` (`orchestrator/session.rs`) and that always `hand_back`s the item to the queue, logged `lane_freed` as `queued: <why>` (`orchestrator/driver/settle.rs`'s `settle`/`hand_back`) — a lane-prepare failure, a spawn or crash of the session's own task, and an implementer answer `classify` doesn't recognize all land here the same way. The watchdog's `killed_for_silence` lands here only with the `own-failure-handling` flag Off; On, it is resumed instead (section 7's Watchdog bullet above, and the retry-count bullet below). None of the rest of this section is built, and one of its existing rules is actively wrong for this Rust agent today, not just unbuilt:
  - **An error once a session has run is still "the agent's own fault."** `classify`'s catch-all branch, and a crash mid-session, both produce the same `Failed` as an error before any work ever ran — where this section's own second bullet says that case should go to `needs_human` instead, since that session's work may need a person. **[Proposal]** `settle()` already has the distinction it needs: only a `Failed` for a run still `queued` (no session attempted yet this slice) should `hand_back`; a `Failed` for a run already `Implementing` (a session started, however it ended) should call `run.escalate()` and go to `needs_human` with the error as its reason, the same path `SessionResult::NeedsHuman` already takes a few lines above it.
  - **Claude signing out already produces a distinct message, but nothing acts on it.** `engines/engine.rs`'s `describe_failure` already turns a signed-out session into "found Claude signed out on this computer (…)" (`is_signed_out`/`signed_out_text`, ported from claude-signed-out.md section 3.1), and `implementer/session.rs` already `bail!`s with exactly that text, so the words are right there in the `Failed` reason the item is given back with. But nothing reads it: the next `claim_next` on the same computer tries again at once, fails the same way, and churns until a person notices. **[Proposal]** Match `signed_out_text` against a `Failed`'s reason where `hand_back` is about to send it, and on a match set a per-project flag instead (no new implementer session starts while it's set), clearing it on the next session from this computer that doesn't fail that way — `Pool.claudeSignedOut`/`signInWait` above, with no separate sign-in poll needed since the next wake's own pass already retries.
  - **No claim-pause.** Nothing stops this computer reclaiming the very item it just handed back: `orchestrator/driver.rs`, `steps.rs` and `round_robin.rs` have no equivalent of `CLAIM_PAUSE_MS`. **[Proposal]** A per-project `Instant`, set 30 minutes out on every `hand_back` and checked next to the paused check already in `advance`, kept only in memory (never `state.json`) so a restart clears it exactly as `pool.claimPausedUntil` does.
  - **No retry count** for a crash or an item's other own failures: they requeue with nothing kept, and the triager's own failures have their 3-tries-then-human cap (section 6.9). Two are the exception, behind `own-failure-handling` (Off keeps what's described above). A session whose process won't start (`engines::CouldNotStart`, the `spawn()` error of `runner.rs`, not a missing binary, which `ClaudeStarter` already refuses) answers `SessionResult::NotStarted`: the run keeps its lane and lease, nothing is posted to the store, claiming isn't paused, and about a minute later (the watchdog's `silenced` delay) it is started fresh again, since there's no session to resume. Any other `Failed` still `hand_back`s. Both count in `state.ownFailures` (per item, kept past the lease because a hand-back drops the run record): up to 3 are retried or handed back, and the 4th in a row goes to `needs_human` with its error (`run.escalate()`); a session that starts and answers clears the count. A watchdog kill is the other exception: in this Rust agent, behind `own-failure-handling`, `RunRecord::silence_kills` counts them in a row (saved in state.json, cleared when a session ends with any answer), each is resumed by id a minute later, and the 4th goes to `needs_human` with the kill's reason (section 7's Watchdog bullet).
  - Not found anywhere in the Rust source, and not close to built: `rememberCode`/`restartIfCodeChanged` (this section's "Code that changed under a running agent restarts it" bullet) and `canStartSession`'s pending-update gate (this section's "No new work while an update's restart waits" bullet). Both stay TypeScript-only.
- **In this Rust agent**, the first bullet is ported: `src/orchestrator/driver/settle.rs`'s `hand_back`, the one place every own-failure-before-work goes through (the item unknown here, the starter refusing to start, and a fresh start's lane prep or prompt building failing before `run_implementer` is ever called, in `orchestrator/session.rs`'s `run`), gives the item's lane and lease back as before, logs an `error` event (`where: "start"`) in the local event log standing in for the item's own timeline (the store's `release` takes no note text), and sets `Machine::claim_paused_until` to 30 minutes out (`settle::CLAIM_PAUSE`), checked before `claim` so this computer asks the store for nothing new, on any of its projects, until it passes; a restart clears it (it isn't saved), and items this computer already holds carry on untouched. The last bullet of the first point is ported too, and reaches further than "once a session actually ran": `run`'s own error, `classify`'s fallback for a status this agent doesn't recognize, and (since a resumed session already ran once before the restart that cut it off) a resume's own stopping or lane prep or prompt building failing all answer `SessionResult::NeedsHuman` instead of `Failed` (`ClaudeStarter::start`, gated on the start request's `resume` flag), so they settle exactly like `failed`/`person_steps`/`nothing_left`/`waits_on` above. The `claudeSignedOut` gate is ported too, close to the shape above rather than `signInWait`: `settle`'s `NeedsHuman` arm reads the session's own words for Claude's sign-in error (`engines::signed_out_text`, reused from [claude-signed-out.md](../claude-signed-out.md) against the already-formatted reason text, since by the time it reaches `settle` the raw `SessionResult.signed_out` bool is gone), and if they say so, sets `Machine::claude_signed_out_until` a minute out. Checked alongside `claim_paused_until`, it holds off every new `claim_next` and every new or resumed session start on this computer (`claim`, `apply_starts`, `resume_sessions`), leaving a start `decide` already planned for the next pass to try again rather than parking or giving the item back; the item itself still goes to `needs_human` as any other `NeedsHuman` does, since the session did run and may have left real work behind. No `signInWait` state and no scan of old `needs_human` items for one signed out: without `claim-tags-and-give-back-note`'s give-back note there's nowhere yet to tell "signed out" apart from any other reason once saved, so a wait this short just retries instead. Not yet: restarting on changed code (`selfUpdate.ts` isn't ported, so a checkout running stale code keeps running it — and checkout mode has no relaunch-after-exit path today either, unlike a release build's `restart_handler`, so there is nowhere yet for such a restart to land), refusing new implementer work while an update restart is pending (no restart-on-update exists yet to wait for). `driver/item_commands.rs`'s Continue handling starts the item over (with the triager's or the person's instructions as notes) when `triage::schedule::nothing_to_continue` holds, and with the `own-failure-handling` release flag On its `item_state` note reads "Started over by Claude: there was nothing to continue from" when Claude chose the Continue and "Started over: there was nothing to continue from" when a person did; with the flag Off it stays "<who> chose Start over".
  - **[Proposal] The flag goes.** With `own-failure-handling` Off every failure goes to a person, which is the behavior this section exists to remove. Turn it On for everyone and delete the flag and its Off paths (`settle.rs`, `item_commands.rs`, their tests).
