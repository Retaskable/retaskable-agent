## 11. Build milestones

This list is Retaskable.com's own TypeScript build order; the Rust port follows the same order, one piece at a time ([CLAUDE.md](../../../CLAUDE.md)). **[Proposal]** Each milestone below now carries a line on where this Rust agent stands, named against the backlog ids its own commits use, so it stays a build order for this port and not only a record of the TypeScript one.

1. **Skeleton:** TypeScript, `npm run dev`, config loading, state store.
   - **[Proposal]** In this Rust agent, `cargo run` stands in for `npm run dev`; config loading is `src/config/` (`machine-settings`) and the state store is `src/store/` (`.retaskable/projects/<id>/state.json`, `machine.json`, `local-state-trim`'s compact writes and one-off trim), both built.
2. **Session runner:** spawn `claude -p` with stream-json, parse events, capture structured output, resume. Find where the 5-hour usage limit shows up in the stream and read it into `state.usage`.
   - **[Proposal]** Built for all three engines (`session-runner-claude`, `engine-layer`, `engine-pi`): `src/engines/claude.rs`, `cursor/` and `pi.rs` behind the one `runner.rs`/`engine.rs` interface ([02-the-engine-layer.md](../engines/02-the-engine-layer.md)), each spawning, parsing and resuming its own way; `claude.rs` reads the usage window into `state.usage`.
3. **Orchestrator happy path:** item → lane → implementer → CI (or none) → checks → scouts → Opus review → merge → report to the store, for one slice of one item. `item-lifecycle` and `implementer-session` wire [agent-telemetry.md](../agent-telemetry.md)'s `item_state`, `claim`, `lease`, `session_start`/`session_end`, `step_start`/`step_end`, `ci`, `merged` and `error` events into this, the same way the event log itself was built before anything called it.
   - **[Proposal]** Not started. What it needs is ready (the session runner above, the backlog client's reads in `src/backlog.rs`, the event log in `src/telemetry/events.rs`), but nothing in this crate drives an item through a lane yet, and nothing calls `EventLog::add`. This is `item-lifecycle` and `implementer-session`'s own job, not a further slice of anything already built.
4. **Lanes and loops:** the lane pool and dependency-aware scheduling (the store hands out the work, `claim_next`), slices, clarification, CI failure, requested changes, conflict, `needs_human`, restart recovery. `orchestrator-loop` wires [agent-telemetry.md](../agent-telemetry.md)'s `lane_taken`/`lane_freed`, `tick` and `restart_*` events into this. The base checkout this moves to the base branch (installing dependencies, Capacitor, the Windows environment fix, concurrency gating) is also what [play-on-phone.md](../play-on-phone.md) section 5 builds and installs on, so that section's port lands here.
   - **[Proposal]** Partly built. `lane-worktree-pool` ported the pool's own mechanics (`src/lanes.rs`: `ensure`, `prepare`, `kill_processes_in`, sibling links) and `engine-choice-settings` ported the per-lane engine lookup (`src/engines/choose.rs`), but nothing yet owns a session's lifecycle, polls a free lane on a tick, or asks the store for the next item: there is no `Pool` and no orchestrator loop. `claude-signed-out-hold` ported its own sign-out detector the same standalone way; it has nothing to pause yet, because the loop this milestone builds is what would hold a lane for it.
5. **Cloud link and snapshot:** the outbound link to retaskable.com, the snapshot and the live session events, and the commands the site may send ([cloud.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/cloud.md) section 6). The port serves only `/api/health` and the settings page (section 8). This milestone also carries the rest of [first-run-check.md](../first-run-check.md) section 3.1: `hello`'s optional `checks` field and `SetupCheckRunner`'s 10-minute re-check go with the connector; the read-only `setup_check` command goes with the command handling that lands alongside it. [play-on-phone.md](../play-on-phone.md) section 6 (phone status up, `phone_play`/`phone_stop` down) ports along with this.
   - **[Proposal]** Not started past `GET /api/health` (`src/api.rs`). There is no connector, no `hello` and no command handling yet, so every "lands with this milestone" note elsewhere in this folder is still waiting on it.
6. **Dogfood on void-miner:** point it at `C:/Users/mail/working/Personal/Games/void-miner`. It's a good test because its items are whole systems (so it needs slices), it has no CI (so the local `cargo test` and `--verify --headless` runs are the gate), and its specs mark some choices as **[Decided]** (which should produce clarification questions, not guesses). Start with `lanes: 2, concurrency: 1` and watch the first few slices. Then try `concurrency: 2` on two independent items, and check that the second lane's build is warm by its second item.
   - **[Proposal]** Blocked on milestones 3 and 4: nothing to dogfood until the orchestrator can run a slice end to end.

The first planner, the Setup screen and the Web UI (milestones 3 and 7 of the first version) are retired: the list of work is the shared backlog, and the screen is the Expo app.
