## 11. Build milestones

1. **Skeleton:** TypeScript, `npm run dev`, config loading, state store.
2. **Session runner:** spawn `claude -p` with stream-json, parse events, capture structured output, resume. Find where the 5-hour usage limit shows up in the stream and read it into `state.usage`.
3. **Orchestrator happy path:** item → lane → implementer → CI (or none) → checks → scouts → Opus review → merge → report to the store, for one slice of one item.
4. **Lanes and loops:** the lane pool and dependency-aware scheduling (the store hands out the work, `claim_next`), slices, clarification, CI failure, requested changes, conflict, `needs_human`, restart recovery.
5. **Cloud link and snapshot:** the outbound link to retaskable.com, the snapshot and the live session events, and the commands the site may send ([cloud.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/cloud.md) section 6). The port serves only `/api/health` and the settings page (section 8). This milestone also carries the rest of [first-run-check.md](../first-run-check.md) section 3.1: `hello`'s optional `checks` field and `SetupCheckRunner`'s 10-minute re-check go with the connector; the read-only `setup_check` command goes with the command handling that lands alongside it.
6. **Dogfood on void-miner:** point it at `C:/Users/mail/working/Personal/Games/void-miner`. It's a good test because its items are whole systems (so it needs slices), it has no CI (so the local `cargo test` and `--verify --headless` runs are the gate), and its specs mark some choices as **[Decided]** (which should produce clarification questions, not guesses). Start with `lanes: 2, concurrency: 1` and watch the first few slices. Then try `concurrency: 2` on two independent items, and check that the second lane's build is warm by its second item.
