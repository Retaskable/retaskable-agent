### 6.6 Ask Claude

The app has a chat box on every screen. A message in it reaches the agent as an `ask` command ([cloud.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/cloud.md) section 6), and the chat's conversations are kept by the store (`asks_list`, `ask_report`; [team-state-on-server.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/team-state-on-server.md) section 3.3), not by the agent. A message is, by default, a request to write specifications: the agent turns it into specs written for the implementer, with metadata, grouped by theme, and into backlog items, and after the draft is approved those items are queued ([chat-specs.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/chat-specs.md)). A message that is clearly a question ("why is step 5 stuck?") or clearly one of the other actions ("launch the web app", "pause") is still just that. While it thinks, the agent reports how long it's been and what it's reading, live, for the app to show.

- It runs one **assistant** session (the implementer's tier, budget `budget.askUsd`, prompt `prompts/assistant.md`), read-only, in the base checkout of the base branch. The prompt gives it a summary of the current state (items, lanes, drafts, status, spend), read from the store and the agent's own run state, and the last five exchanges.
- **It can only act through a fixed list**, each one a command a person could send themselves: `play` / `stop` (lane 0 = the base build, or an item's lane), `pause`, `resume`, `retry` / `skip` an item, and `draft_spec` (a new draft for the store's queue, section 6.5; [spec-queue.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/spec-queue.md)). It returns `{ answer, actions: [...] }`. The orchestrator validates each action (unknown or malformed ones are dropped and reported) and runs it through the same code, with the same checks, as the command. The result of each goes back with the answer.
- **The default is `draft_spec`.** The assistant's prompt says so ([chat-specs.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/chat-specs.md) section 3): anything that isn't clearly a question or clearly one of the other actions is a spec request, passed on whole, as one draft. Parsing it yields one backlog entry or several, by the scope that makes each spec clear and buildable on its own, and the answer names those titles under their themes (section 6.5, [chat-specs.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/chat-specs.md) sections 4 and 12). The titles go out on the action as `draft_spec`'s `titles`, and each one's theme beside it in `themes` (`toAction` keeps the non-empty strings, in order, drops anything else, and keeps the themes only when there is one per title), and both go to the store with the draft (`draft_queue`) for the drafter. Images on the message stay on the draft: `perform` adds the ask's "Attached images…" block to the request when the model's `request` left it out. The orchestrator still only runs actions from this list.
- **Who it's for** ([chat-asks-who.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/chat-asks-who.md)). The company's audiences list is the store's, not the agent's: the agent asks the store for it (`facts_get`, kind `audiences`) and puts it in the prompt (`{{audiences}}`), and a `draft_spec` may carry `audience`, an id on that list or `null`, only when the message makes it plain. The agent passes it to the store with the draft (`draft_queue`); guessing an audience, and asking **Who is this for?** when there is none, are the store's and the app's (`item_assign`, `draft_assign`).
- **Changes stay on their card** ([card-revisions.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/card-revisions.md)). A question asked on a card's or a plan's page carries `about`; the prompt's state then starts with that item, and a `draft_spec` may carry `revises`, the id of the backlog item it changes (`null` for separate work asked on a card). `perform` keeps it only for an item the store knows and plans the change as a revision of that item; approving the plan sends the store a `revise`, which puts the item back in the queue with the plan's remaining work and adds no item.
- The assistant is told not to launch anything, edit files or change git itself: that's what the actions are for. It's told the project type, and the actions are described in its words ([project-types.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/project-types.md) section 4). A `stop` waits (up to 15 seconds) for the process to close, so a `stop` then a `play` of the same lane is a restart.
- **Reply** under an answer asks a follow-up in place (the `ask` command with `replyTo`). A reply's prompt has the thread it continues (the answer it replies to and what that replied to, up to five exchanges) instead of the last five, so it keeps its context even when other asks came in between. How the app lays conversations and replies out is the app's ([chat-windows.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/chat-windows.md)).
- **Retaskable's own messages** ([chat-follow-up.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/chat-follow-up.md)): a spec draft a person asked for posts a message into the chat when it's written, asking "Do you want to approve it?", or when the drafter has questions. Once approved, the same conversation hears how it moves on: approved and merged (or waiting for a merge on GitHub), each item it added started, needing a person, merged in part or built, skipped, and the staging link once staging serves it (or that there's no staging link). It goes into the conversation that asked for it (a new one for **Add spec** and feedback), as an ask with `from: "retaskable"` and the draft's `draftId`, written in code, never by a model, and recorded in the store (`ask_report`). The assistant sees it as "Retaskable: <text>" in its context.
- **Clearing** finished asks is the store's (`asks_clear`); cleared asks still count as the last five exchanges.

 **Retaskable's own messages after approval** (`ask::follow_up`, `orchestrator::driver::land` and `driver::follow`): the agent posts each message itself (`ask_post`, `from: "retaskable"`, the draft's `draftId`). `land` posts "Approved and merged. N items are queued: titles." (titles when the chat parsed one per item), or "Approved. It's waiting for someone to merge it on GitHub." Every pass over a live project's items, `follow` goes through those that carry the backlog `Item`'s `draftId` and, for a draft that already has a message of Retaskable's own, posts: "Started building <title>." (first state past `todo`), "<title> needs you. See its card.", "<title>: a part of it was merged. More to come." (back in the queue with `slice` above 0), "<title> is built and merged.", "<title> was skipped.". Once every item is built or skipped (and one built), with a staging `url` on the base branch it takes `origin/<base>`'s head and looks at `<url><versionPath>` every 30 seconds until the served commit is or contains it, then posts "It's on staging: <url>"; after 20 minutes it posts "It's merged, but staging hasn't picked it up yet." and looks every 5 minutes, for a day. With no staging url, or staging on another branch, it posts "There's no staging link set up for this project." instead. Each message is posted once: before posting, the conversation (`asks_list`) is read, and a message of Retaskable's own with the same `draftId` and text is not sent again, so a restart repeats nothing and no local record is kept. A message goes into the conversation of the draft's latest message, else of the ask that wanted the draft (`askId`), else a new one (**Add spec**, feedback). A draft with no message of Retaskable's own is not followed.

**Interactive sessions:** asks and drafts have a human waiting on them, so they don't queue behind `concurrency` (they still count toward it while they run). A further chat prompt in the same project waits for that project's drafter to finish, which is the spec queue and not a session slot ([spec-queue.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/spec-queue.md)). They don't start while paused, either pause (this computer's or the project's, which the agent reads from the store: [team-state-on-server.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/team-state-on-server.md) section 3.1), over the daily budget or at the usage limit; a question asked while paused waits, "Paused: I'll answer when someone resumes", and is answered on resume.

**In this Rust agent**, an `ask { askId, text, replyTo?, about?, images? }` command (`commands::ask`) is checked (an `askId` and non-empty `text`, `replyTo` and `about` text if given, `images` saved as a message's pictures are, at most 4 and 1 MiB each) and acked once queued, in `claim` mode only. `orchestrator::driver::asks` takes the queue on every pass of a live project. It is not queued behind `concurrency`: it starts at once, takes a slot while it runs and the slots the items and drafts then see are fewer by the asks running. The `AskHost` (the real one, `orchestrator::ask_host::ClaudeAsks`, Claude only) says whether the store blocks new asks (`facts_get { kind: "project" }`: the project's `paused`, or `spentTodayUsd` at the machine's `budget.dailyUsd`), and runs one: it reads `asks_list`, the audiences, the items, the drafts and the project facts, builds the prompt from them and the loop's lanes and runs, runs the assistant read-only in the base checkout, and carries out the actions with `ask::perform`. The loop sends `ask_report` with the `answer` and each action's result (`actions`, `status` `answered`). While this computer is paused, the store blocks asks, the engine is at its usage limit or Claude is signed out, an ask is reported once as `status` `waiting` with `waiting` "Paused: I'll answer when someone resumes" and answered on the first pass after. While the session runs, the host sends its summarized events (`Engine::summarize` over the transcript it tails) to the loop, which reports `progress` on a timer (every 3 seconds, not per event): "Thinking for 12s, reading src/lib.rs" (the latest `Read` tool's file, or what it is searching for or using). Each report is sent before the next step, so the answer always follows the last progress report. A store that fails (the gate's read, the host's reads or the report) leaves the ask in the queue to be tried again, and nothing is answered locally.
