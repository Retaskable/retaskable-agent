### 6.6 Ask Claude

The app has a chat box on every screen. A message in it reaches the agent as an `ask` command ([cloud.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/cloud.md) section 6), and the chat's conversations are kept by the store (`asks_list`, `ask_report`; [team-state-on-server.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/team-state-on-server.md) section 3.3), not by the agent. A message is, by default, a request to write specifications: the agent turns it into specs written for the implementer, with metadata, grouped by theme, and into backlog items, and after the draft is approved those items are queued ([chat-specs.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/chat-specs.md)). A message that is clearly a question ("why is step 5 stuck?") or clearly one of the other actions ("launch the web app", "pause") is still just that. While it thinks, the agent reports how long it's been and what it's reading, live, for the app to show.

- It runs one **assistant** session (the implementer's tier, budget `budget.askUsd`, prompt `prompts/assistant.md`), read-only, in the base checkout of the base branch. The prompt gives it a summary of the current state (items, lanes, drafts, status, spend), read from the store and the agent's own run state, and the last five exchanges.
- **It can only act through a fixed list**, each one a command a person could send themselves: `play` / `stop` (lane 0 = the base build, or an item's lane), `pause`, `resume`, `retry` / `skip` an item, and `draft_spec` (a new draft for the store's queue, section 6.5; [spec-queue.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/spec-queue.md)). It returns `{ answer, actions: [...] }`. The orchestrator validates each action (unknown or malformed ones are dropped and reported) and runs it through the same code, with the same checks, as the command. The result of each goes back with the answer.
- **The default is `draft_spec`.** The assistant's prompt says so ([chat-specs.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/chat-specs.md) section 3): anything that isn't clearly a question or clearly one of the other actions is a spec request, passed on whole, as one draft. Parsing it yields one backlog entry or several, by the scope that makes each spec clear and buildable on its own, and the answer names those titles under their themes (section 6.5, [chat-specs.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/chat-specs.md) sections 4 and 12). The titles go out on the action as `draft_spec`'s `titles`, and each one's theme beside it in `themes` (`toAction` keeps the non-empty strings, in order, drops anything else, and keeps the themes only when there is one per title), and both go to the store with the draft (`draft_queue`) for the drafter. Images on the message stay on the draft: `perform` adds the ask's "Attached images…" block to the request when the model's `request` left it out. The orchestrator still only runs actions from this list.
- **Who it's for** ([chat-asks-who.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/chat-asks-who.md)). The company's audiences list is the store's, not the agent's: the agent asks the store for it (`facts_get`, kind `audiences`) and puts it in the prompt (`{{audiences}}`), and a `draft_spec` may carry `audience`, an id on that list or `null`, only when the message makes it plain. The agent passes it to the store with the draft (`draft_queue`); guessing an audience, and asking **Who is this for?** when there is none, are the store's and the app's (`item_assign`, `draft_assign`).
- **Changes stay on their card** ([card-revisions.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/card-revisions.md)). A question asked on a card's or a plan's page carries `about`; the prompt's state then starts with that item, and a `draft_spec` may carry `revises`, the id of the backlog item it changes (`null` for separate work asked on a card). `perform` keeps it only for an item the store knows and plans the change as a revision of that item; approving the plan sends the store a `revise`, which puts the item back in the queue with the plan's remaining work and adds no item.
- The assistant is told not to launch anything, edit files or change git itself: that's what the actions are for. It's told the project type, and the actions are described in its words ([project-types.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/project-types.md) section 4). A `stop` waits (up to 15 seconds) for the process to close, so a `stop` then a `play` of the same lane is a restart.
- **Reply** under an answer asks a follow-up in place (the `ask` command with `replyTo`). A reply's prompt has the thread it continues (the answer it replies to and what that replied to, up to five exchanges) instead of the last five, so it keeps its context even when other asks came in between. How the app lays conversations and replies out is the app's ([chat-windows.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/chat-windows.md)).
- **Retaskable's own messages** ([chat-follow-up.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/chat-follow-up.md)): a spec draft a person asked for posts a message into the chat when it's written, asking "Do you want to approve it?", or when the drafter has questions. Once approved, the same conversation hears how it moves on: approved and merged (or waiting for a merge on GitHub), each item it added started, needing a person, merged in part or built, skipped, and the staging link once staging serves it (or that there's no staging link). It goes into the conversation that asked for it (a new one for **Add spec** and feedback), as an ask with `from: "retaskable"` and the draft's `draftId`, written in code, never by a model, and recorded in the store (`ask_report`). The assistant sees it as "Retaskable: <text>" in its context. (This Rust agent doesn't post them yet: see the end of this section.)
- **Clearing** finished asks is the store's (`asks_clear`); cleared asks still count as the last five exchanges.

**Interactive sessions:** asks and drafts have a human waiting on them, so they don't queue behind `concurrency` (they still count toward it while they run). A further chat prompt in the same project waits for that project's drafter to finish, which is the spec queue and not a session slot ([spec-queue.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/spec-queue.md)). They don't start while paused, either pause (this computer's or the project's, which the agent reads from the store: [team-state-on-server.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/team-state-on-server.md) section 3.1), over the daily budget or at the usage limit; a question asked while paused waits, "Paused: I'll answer when someone resumes", and is answered on resume.

**In this Rust agent**, a chat message reaches the computer as an `ask` intent row, not as a command: the `ask` command is gone and the agent answers only the rows it pulls ([intent-rows.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/intent-rows.md)). `intents` is the puller: each pass of a live project it lists the open rows of the kinds it has a handler for (`intent_list { kinds }`), claims one it may run (`intent_claim { id, machine, can: true }`, answered `{ won, blocked }`; a lost or blocked claim is skipped and tried again next pass), beats it every 60 seconds while the handler runs (`intent_beat { id }`, the first at once), and ends it with `intent_finish { id, status, result?, why? }` (`done`, `refused` or `failed`; `result` at most 4 KB, `why` at most 280 characters; a finish the store doesn't take is tried 3 times, then logged as a store error for the row). A row that was claimed is never run twice by this process, and a handler that is cut by a restart (`Abandoned`) sends nothing: the store opens the row again once its claim has gone stale (3 minutes). Adding a kind is one `Handler` registered on the puller (its `kind`, whether it `takes` a row, and its `run`); `ask`, `take_over_requested`, `finish_requested`, `merge_requested` (an item or a spec draft), `main_pr_requested`, `sync_requested` and `draft_wanted` are registered so far. A kind that must never run twice (`merge_requested`, `main_pr_requested` and `sync_requested`, the TS agent's `NOT_TWICE`) is `failed` (`This computer restarted before it finished; check, then ask again`) when this computer held its row before a restart, not run again; a handler that ends `done` with no result sends no `result`.

**`take_over_requested`** (`args.itemId`): a person asks this computer to carry on an item whose owner's computer has gone quiet and that is waiting for help. A claimed item is pulled every 60 seconds by a project loop in `claim` mode, not by the lane that runs sessions, because it needs no lane and no slot. The handler refuses `It's on this computer already.` without a store call when the loop holds the item (or has just taken it), and otherwise sends the ordinary `claim { id, agent, because: "person", did: "took_over" }`, answered `{ item, token, wasWaiting, wasOwner }`. The store refuses with `conflict` and `why { reason: "held", login, machine }` when another computer is working on it (`@login's computer (machine) is working on this right now. It'll come back to you if it needs you.`), or `held_by_owner` when the owner's computer was online in the last 2 hours (`machine has been online in the last 2 hours, so it's still theirs. Carry it on, or ask @login.`); any other refusal reads `It can't be taken over in the shared backlog: <message>`. Only an item that was waiting for `help` is taken: a claim whose `wasWaiting` is anything else is given straight back with `release { id, token }` and the row is `refused` (`It isn't waiting for help on another computer, so there's nothing to take over.`), so no lease is left behind. A taken item is handed to the loop, which holds its lease and records it as `needs_human` with no lane and no session, the same state as one that was waiting for help here; the row ends `done` with `{ itemId }`. Taking over the other waits (`ci`, `answer`, `tryout`, `merge`) is not built yet.

**`finish_requested`** (`args.itemId`): a person presses Done on an item that needs help on this computer. The handler writes nothing itself: it hands the item id to the project's loop and ends the row with the loop's answer on its next pass (`done` with `{ itemId, sha }`, or `refused` in words; a loop cut by a restart sends nothing, so the store opens the row again). The loop checks the item is a run of its own in `needs_human` (`It isn't on this computer.` / `It isn't waiting for a person on this computer.`), that nothing is on a branch (no pull request, no branch: `This item isn't waiting for a person's steps, and has work on its branch.`) and that it holds the lease, then reads the base branch's head from the remote (`git ls-remote origin refs/heads/<base>`; unreadable is `Nothing left to build, but <base>'s head couldn't be read.`) and sends the one `complete { id, token, built: true, mergeCommit: <head>, onDefaultBranch, remaining: "" }` ([07.5](07.5-what-a-claim-and-a-give-back-send.md)); a refusal of it ends the row `refused` and the item stays. When the store takes it, the run, its record and its lease go. Not built yet, refused rather than guessed: an item waiting for a person's steps (this agent never records that stop) and a change the reviewer found right, which the TS agent merges as an approval would; and so no change is ever closed from here.

**`merge_requested`** (`args.itemId`, `args.draftId` or `args.ship`): a person presses **Merge into main** on an item whose finished pull request waits for them, on a spec draft, or (`ship: true`) on the team branch's pull request into main (below). A row naming none or more than one is `refused` (`Name one item, one draft, or the pull request into main to merge.`). The handler hands the item id to the project's loop, which answers on its next pass; a paused project still merges and no slot is used. Only a project whose workflow has the person merge into the protected branch (`github.land` is `person` and the base branch is the protected one) has it: otherwise, and when this computer holds the item with no step running, the row is `refused` (`It isn't waiting for you to merge it.`), or with a step running (`A step is running for this item; try again in a moment.`). The loop claims by name (`claim { id, agent, because: "person", did: "merged" }`, a store refusal in the words of `take_over_requested`); a claim that wasn't waiting for a `merge`, or an item with no pull request, is put back as it was and refused the same: `park { id, token, for: <what it waited for> }`, because `release` would send the item back to `todo` (a finished change requeued, a help or CI wait lost). Only a claim that wasn't waiting at all is `release`d, as the TS agent does. The pull request number is read from the item's `prUrl`, else the open pull request for its branch (`gh pr list --head`); with none the item is parked again and the row refused (`Lost track of this pull request: no PR number on record, and none found open for its branch.`). Before the merge, the item's playtest is read from the store (`details_get`, asked twice); with no answer the item is parked again and the row `refused` (`Couldn't read this item's playtest from the shared backlog, so nothing was merged: …`), since the merge can't be undone (the TS agent merges first). Then `gh pr view <n> --json headRefOid` and `gh pr merge <n> --squash --match-head-commit <that head>`, with `--delete-branch` only when the head is the slice's own (`retaskable/…`); a push since the read is `refused` as `Couldn't merge #<n>: The pull request changed since it was checked; look again, then merge.` (the TS agent's `mergeForPerson`, `merge.ts:318`, matches no head, and the draft press below reads its head the same way). A `gh pr list` that fails is `refused` with gh's reason (`Couldn't look for this pull request: …`), not as a lost pull request. **It merges directly like the TS agent, not through the store's merge queue (`merge_enqueue`) as Retaskable.com's intent-rows.md words it.** A merge GitHub refuses is `refused` as `Couldn't merge #<n>: <reason>` (gh's GraphQL prefix stripped, at most 300 characters) and the item is parked back for its merge wait (`park … for: "merge"`), since this agent has no stop in which to hold an item waiting for a person's merge (the TS agent leaves it held as waiting); a refused merge leaves the item as it was. On success the loop sends `complete { id, token, built: false, remaining }` with the item's `remaining` and its `implPlaytest` detail (the TS agent's `implDone` is local to its record, so a taken-over item reports the slice merged and the store decides whether it is built or queued again) and the row ends `done` with no result. If that `complete` is refused the row is `refused` with the merge noted, and the claim stays with this computer. A row naming a `draftId` is the same press as the pushed `merge_pr { draftId }`: the loop queues it for the draft landing ([06.5-spec-drafts.md](06.5-spec-drafts.md) step 3), which takes the draft by name and, when it is `needs_person` waiting for approval or for the merge and the project's workflow has the person merge into the protected branch, runs `gh pr merge <n> --squash` whatever the project's merge method is, deleting the head only when it is the draft's own (`retaskable/…`), whatever the delete setting says (the TS agent's `forPerson`; the pushed `merge_pr` is squashed the same way). The row ends `done` with no result once the draft is `merged`. A draft that isn't waiting (or a project where the person doesn't merge) is let go and the row is `refused` (`Draft <id> isn't waiting for you to merge it.`); a merge GitHub refuses is `refused` as `Couldn't merge #<n>: <reason>` (as for an item) and the draft is reported back to waiting for approval with the note `Couldn't merge into <into>: <reason>`; a draft the store won't hand over is `refused` as `Couldn't take draft <id>: <why>`. A press dropped before it was answered (the loop stopping) leaves the row for the store to open again. **`{ ship: true }`** is the merge control into main (the TS agent's `shipToMain`, merge pattern only; no local-only project, no check that main takes writes), for a project working on a team branch: the loop answers the way `main_pr_requested` does (no team branch is `refused` with the same words; the branch is read afresh after a fetch) and applies `shipRefusal`'s words in order (`No pull request from <base> into <main> is open.`, `Wait for <main> to finish coming into <base> first.`, `It conflicts with <main>: bring <main> into <base> first.`, `A slice is going into <base>; try again in a moment.`). It then asks `gh pr view <n> --repo <R> --json state,headRefOid`; not `OPEN` is `refused` (`PR #<n> isn't open any more.`). `gh pr merge <n> --repo <R> --squash --match-head-commit <head the refusal check read>` follows, never `--delete-branch`, so nothing that landed since goes in and the long-lived dev branch stays; a merge GitHub refuses is `refused` as `GitHub didn't merge PR #<n>: <reason>`. A second `gh pr view` must say `MERGED`: `gh pr merge` also exits 0 when it only queued the pull request, and then `<base>` is left as it is. Merged, the dev branch starts again from main: `git fetch origin <main>`, `git ls-remote --heads origin refs/heads/<base>`, and, when origin's copy is gone (create) or still at the merged head (reset), `git push --force-with-lease=refs/heads/<base>:<sha it showed, empty to create> origin refs/remotes/origin/<main>:refs/heads/<base>`, each call under 120 seconds. Origin's copy at any other sha has new work, so nothing is pushed. The push names the base branch only, never main and never a bare `--force`. **Divergence from the TS agent:** its warning only reaches the strip's HTTP answer, and the Rust agent has no strip; here a warning goes into the row's result, so the row ends `done` with `{ says: <warning> }` when it merged but the dev branch wasn't started again (`<base> has new work since its pull request was read, so it wasn't started again from <main>.`, `Couldn't fetch <main> to start <base> again: …`, `Couldn't read <base> on GitHub to start it again from <main>: …`, `Couldn't start <base> again from <main>: …`) or the merge was only queued (`PR #<n> didn't go in straight away (GitHub may have queued it), so <base> was left as it is.`), and `done` with no result when all went well. A look that breaks ends it `failed` in plain words. A second small difference: the merge is matched to the head the refusal check read, where the TS agent matches the head its own later `view` read (used only when the list gave none). **Divergences from the TS agent, made for runs mode (where a landing slice or a main sync is no store item).** (1) Before it reads anything the ship takes the store's `sync_main-<base>` lock (`lock_take`, dropped when the ship ends, beaten with the runs' locks meanwhile): a main sync running in this loop, or the lock held by anyone (another computer's sync, or its ship), is `refused` (`Wait for <main> to finish coming into <base> first.`), and so is any merge turn this loop holds or has not yet reported (`A slice is going into <base>; try again in a moment.`); the TS agent looks only at the items in its store (`teamBranchActions.ts:88`). A lock the store won't answer for fails the row in plain words. A piece merging into the dev branch from another computer is held off by the store's own merge turn (4); `--match-head-commit` (a head that moved is refused) and the restart's exact lease (a dev branch that moved since is left alone with a warning) stay as the last check. (2) The look after the merge is asked twice before the pull request reads as not merged (`teamBranchActions.ts:101` asks once). (3) A restart a stop or a git failure left undone is finished: on each main-sync look (once a minute, when the base is ahead of main), if the newest pull request from the base into main is `MERGED` with a head equal to origin's `<base>`, the loop takes the same lock and runs the restart above (lease-guarded, so safe to repeat), logging it; a base already restarted asks `gh` nothing. The TS agent keeps its restart only in memory (`restartNote`). (4) **The store's merge turn for the dev branch** (closes Retaskable/Retaskable.com#3852 for the Rust agent; the TS agent is still to follow): no store change is needed, because a chore entry is a turn. With the sync lock held and the pull request read (a first read that refuses ends the row before the store is asked), the ship sends `merge_withdraw { item: "ship-<base>" }` (clears a leftover), `merge_enqueue { item: "ship-<base>", chore: true, holdsBranch: true, base: <dev branch>, head: <the pull request's head>, pr: { number, url }, land: "retaskable" }` (`holdsBranch` makes this computer the owner, so the entry is never handed to another computer) and `merge_next { base }` without `piece: true` (with it the store answers `waiting`). Only `{ turn }` goes on. `{ waiting: { place, ahead } }` or null is withdrawn at once and `refused`, never waited for (a line-holder with no piece at the front would hold every piece's merge up): `A piece is being merged into <base> (waiting on <ahead>). Try again when it has landed.` (no parenthesis when the store names none) and, for null, `The project is paused, so the merge turn can't be taken.`. With the turn it sends `merge_beat { token, phase: "updating" }`, reads the branch again (fetch, read, `shipRefusal`, view), sends `merge_beat { token, phase: "merging" }` right before `gh pr merge`, and then merges and restarts as above; a beat that answers `held: false` is `refused` (`The merge turn was lost, so nothing was merged.`) with no merge, and one the store can't answer fails the row. The turn is given back on every path: `merge_result { token, outcome: "merged", mergeCommit }` (the squash commit `gh pr view --json mergeCommit` names after the merge) when GitHub reports it merged, else `merge_result { token, outcome: "closed" }` (a merge only queued, a refusal, a failure, a commit that can't be read; never `released`, which would requeue the chore), and then `merge_withdraw { item }` again as a backstop. A store that can't be reached for any of this fails the row closed, with nothing merged. After a restart the first pass withdraws `ship-<base>` once, a `merge_open` or `merge_next` that hands the loop a turn whose item starts `ship-` has it withdrawn (never released), and no piece's `merge_next` is asked for while a ship's turn is held. The store's rollout repair freeze (`mayMerge`) lets a chore through, so a repair doesn't block a ship; the agent id is one per computer, and the project loops run one after another, so two projects on one repo and base never hold the ship's turn at once.

**`draft_wanted`** (`args.idea`, or `{ request, audience?, trial?, pictures }`): what the website writes for a person's **Build this** on an idea (`{ idea }`, what the `idea_accept` command did) and for a drafted request (`draft_spec`). A row with `idea` is handed to the project's loop, which queues the idea as a draft in the shared backlog and answers the idea, as `idea_accept` does ([09.3.1-ideas.md](09.3.1-ideas.md)); the row ends `done` with no result, or `refused` with the reason in plain words (the idea gone, already answered or already being planned, the backlog out of reach). A row without `idea` is a `draft_spec`, which this agent can't start yet: it is `refused` (`This computer can't start a draft from a request yet. Ask again from a computer that can.`), never `failed`. The kind starts work and runs a session, so a paused project or a computer signed out of Claude leaves the row open for another computer, and no more than two such rows run at once. It is taken in both `claim` and `runs` modes. There is no `release_wanted` kind.

**`main_pr_requested`** (no arguments): a person presses **Open PR to main** on a project whose base branch isn't the repo's default branch (its team branch). The handler hands the request to the project's loop, which answers on its next pass; no session and no slot, and a paused project still opens it (the TS agent's `STARTS_WORK` leaves it out). The loop refuses in the TS agent's order, with its words: no team branch (the base is the default branch, or `gh` can't say it: `This project works on the repo's default branch, so there's no dev branch to send to it.`), a pull request from the base into main already open (`PR #<n> from <base> into <main> is already open.`), a main sync in flight while the base is behind (`Sync <main> first: its sync is in flight.`), nothing ahead of main (`<base> has nothing <main> doesn't.`), and then a pull request found open when `gh pr list --repo <R> --base <main> --head <base> --state open --limit 1` is asked once more. It reads the branch afresh for each request (fetch, `rev-list --left-right --count origin/<main>...origin/<base>`, the open pull request, and the store's items for an open `sync_main`) where the TS agent keeps what the last fetch showed. The pull request is titled `<base>: <n> slice(s)`, and its body names the slice pull requests merged into the base since the last pull request from the base into main merged (`gh pr list --state merged`, 20 into main and 200 into the base), oldest first, without the `retaskable/sync-main-*` branches, then `gh pr create --repo <R> --base <main> --head <base> --title … --body-file -`; the row ends `done` with `{ url }`. A read, `gh` or store call that breaks ends it `failed` in plain words, not guessed at. A main sync running in this loop or holding the store's `sync_main-<base>` lock counts as in flight too, though it isn't an item yet (the opening takes that lock for its duration, as the merge control does above). A kind that must never run twice, like `merge_requested`. Merge pattern only: the integration pattern's rebase isn't built, and neither is a local-only project.


**`sync_requested`** (`args.dev`): a person presses **Sync now**. With `dev` true it is the team branch's main sync (the TS agent's `team_sync`); without it the TS agent pushes an Apps Script project's code (`sync_push`), which this agent has no storage for, so the row is `refused` (`This project's code isn't synced anywhere else.`) and the loop is never asked. The handler hands the request to the project's loop, which answers on its next pass; no session and no slot, and a paused project still syncs (the TS agent's `STARTS_WORK` leaves it out). It is handled where a main sync exists, in `runs` mode with a runner. The loop refuses in the TS agent's order, with its words: no team branch (`This project works on the repo's default branch, so there's no dev branch to send to it.`), a sync already in flight (`A sync of <main> into <base> is already in flight.`: this loop's own sync running, an open `sync_main` item in the store, or another computer holding the `sync_main-<base>` lock), and `<base> already has all of <main>.` (after a fetch). Then it starts the same sync the minute's look would, now: the `sync_main-<base>` lock, the merge in the sync worktree and the `sync_main` item's add, past the minute's gate, the last handled commit and `syncMain: off` (a sync by hand works with it off, as the TS agent's `chore_trigger` does); the row ends `done` with `{ id }`, the id of the chore item (`chore-sync-main-<sha>`) the sync adds when its merge is in, not an item that exists yet. A store call that breaks is `failed` (`Couldn't ask the store to sync <main> into <base>: …`); a `sync_main` item already made for main's latest commit, whatever became of it (even skipped), is `refused` (`A sync of <main> into <base> was already made for <main>'s latest commit.`), since the store keeps one per commit. Not ported: there is no planner worktree here to be busy (the sync has its own), so the TS agent's `The planner's worktree is busy; try again in a moment.` has no counterpart, no `The project is <skipped>, so nothing was started.` since no store op decides it, and the integration pattern's rebase. A kind that must never run twice, like `merge_requested`.

**Which modes take which rows** ([pieces.md](../pieces.md) section 3.1). `ask`, `sync_requested`, `fix_requested`, `main_pr_requested` and `merge_requested` with a `draftId` or `ship: true` are taken in `claim` mode and in `runs` mode with a runner, by the same passes; the commands for experts, `idea_accept` and the draft presses are taken in both too. The kinds that need an item held on this computer are `claim` mode's alone, and `runs` mode leaves their rows unclaimed and `requested`, so the TS agent or a computer in `claim` mode can take them: `take_over_requested`, `finish_requested` and `merge_requested` with an `itemId` (its handler's `takes` is false for any row naming an item, so such a row is never claimed there, even to be refused). Lane play, stop and restart, Continue, Start over, Skip and a playtest answer stay `claim` mode's.

**Rows that start work** (the TS agent's `STARTS_WORK`, `RUNS_SESSION` and `MAX_WORK_ROWS` in `intentPuller.ts`): a handler says so with `starts_work()` and `runs_session()` (both default false; `ask` has its own gate and says neither). The loop gives the puller what it knows (`Gates`), and the puller leaves such a row open, unclaimed, so another computer can take it, while the project is paused (this computer's pause or the store's) or, for a kind that runs a session, while Claude Code is found signed out here, or while this computer is already running two rows that start work (`Work`, one count for every project and kind; a row counts from its claim until its handler ends). A kind that starts no work is taken whatever the gates say.

**`fix_requested`** (`args.pr`, `args.sha`; the TS `ci_fix`): the owner's **Fix** on a red pull request. It starts work and runs a session. Only the computer the store names as the project's rollout runner takes it (`Runners`, the flag the CI watcher uses): any other leaves the row open without listing it, where the TS agent claims it and refuses, and a project loop asks at most once a minute. Arguments that aren't a positive whole `pr` and a 7 to 64 character hex `sha` are `refused`. The handler asks the CI watcher to press ([ci-watch-through-store.md](../ci-watch-through-store.md) item 5): it checks, in the TS agent's order and words, that no fix is running on that head, that this computer is the runner and that the pull request is open at exactly that head, then asks the store. The row ends `done` with `{ says: "Trying a fix for pull request #N." }` at once and the fix goes on in the background, its attempt on the pull request's log, not on the row; a computer with no watcher is `refused` (`This computer isn't watching pull requests.`). A refusal ends the row `refused` in its words (the TS agent throws a plain `Error` there, which its puller ends as `failed`; the spec says it refuses). A pull request in a fork is refused before the store is asked (see the CI watch spec). Not a not-twice kind: a row held from before a restart is run again, and the press's own head hold and the store's attempt count keep a second fix from running.

The `ask` handler takes only code questions (`args.codeQuestion`; `ask::code_answer::question_of`). `orchestrator::driver::asks` runs it on every pass of a live project, at most once a minute (the poll interval): it does not look at the store while this computer or the project is paused, over the daily budget (`facts_get { kind: "project" }`: `paused`, or `spentTodayUsd` at `budget.dailyUsd`), the engine is at its usage limit, Claude is signed out or the agent is stopping; the row waits and the store times it out after 5 minutes unclaimed. A store that can't be read takes nothing. A question is not queued behind `concurrency`: it starts at once, takes a slot while it runs, and the slots the items and drafts then see are fewer by the questions running. The `AskHost` (`orchestrator::ask_host::ClaudeAsks`) reads the audiences, the items, the drafts and the project facts, builds the prompt, runs the assistant read-only in the base checkout and returns the row's outcome: `done` with `{ answer }` (cut to 3500 characters), `failed` with a plain reason (at most 280 characters) for a session that can't start, fails or is over `budget.askUsd`, and nothing if a restart cut it. The row's `args.pictureIds` (each a 36-character id and `png`, `jpg`, `gif` or `webp`; anything else is dropped) are fetched from the store (`GET /v1/repos/{id}/pictures/{picture}` with the link's token) into the computer's temp folder `retaskable-pictures`, listed for the session in an "Attached images (look at each with your Read tool before acting on this)" block, and removed when the question is done; a picture the store won't give fails the row with "Couldn't read the attached pictures." and no session runs.

Not built yet: the conversation's other messages (actions, spec drafts from chat, progress, Retaskable's own follow-up messages) and the store's chat-write op. The answer is finished as the row's `{ answer }`, which the Coding Agent does for code questions in the TypeScript agent; writing it into the chat through a chat-write op and finishing with `{ messageId }` waits for that op. The old `asks_list`, `ask_report` and `ask_post` mirroring is removed, and `ask::perform` has no caller.
