### 7.1 Model tiers

Before every `claude -p` call (new or resumed), the orchestrator picks the model from the share of the 5-hour usage limit still left. `local` is the local model (section 7.2), which scouts and chores also use whenever its slot is free; with it off or its server down, the choice in brackets applies:

| 5-hour limit left | Implementer (`<tier>`) | Scouts (`<scoutTier>`) | Drafter, triager (`<midTier>`) | Planner, final reviewer (`<topTier>`) |
|---|---|---|---|---|
| ≥ `models.opusAbovePct` (default 50%) | `opus` | `sonnet` | `sonnet` | `opus` |
| ≥ `models.sonnetAbovePct` (default 20%) | `sonnet` | `sonnet` | `sonnet` | `opus` |
| ≥ `models.pauseBelowPct` (default 5%) | `local` (`sonnet`) | `local` (`sonnet`) | `local` (`sonnet`) | `opus` |
| below `models.pauseBelowPct`, or `rejected` | `local` (wait for the reset) | `local` (wait) | `local` (wait) | `local` (wait) |

`<midTier>` is `<tier>` but never Opus (`midTier` in `agent/src/tiers.ts`, 2026-10-22): the drafter and the triager write and read, and Opus is kept for the planner and the final review.

A role on Cursor is not held by that wait: its sessions keep starting, and the Waiting for limit tooltip says "Cursor roles carry on" when any role is on Cursor ([engines.md](../engines.md) section 3.2). Cursor's own usage limit retries after 30 minutes instead, and asks a human after 3 in a row.

**First tries are written on Sonnet** (2026-10-22, `implementerModel` in `agent/src/orchestratorHelpers.ts`): where the table says `opus`, a roadmap item's implementer runs on `sonnet` on its first try. A retry (`attempt` over 1), an item a try-out reopened, or one of size L or XL keeps `opus`, and a tier already below Opus is kept. The final review stays on Opus, so a change written on Sonnet is still read by Opus before it merges. Until then only a fix, a tweak or a size S started on Sonnet, and Opus implementers were about two thirds of October's tokens.

Scouts never run on Opus: their job is to do the reading cheaply so Opus doesn't have to. Near the limit the planner and final reviewer stay on Opus; at the limit they run locally, or wait for the reset without the fallback. Asks use the implementer's tier.

Haiku isn't a tier: Claude Code runs Haiku sessions in `default` permission mode even when asked for `auto` (seen with Claude Code 2.1.283, and again 2026-10-22), and in `claude -p` that refuses edits and most commands. So it runs only read-only sessions that write text from what they're given: release notes, ideas and vetting suggestions (`writerModel` in `agent/src/orchestratorHelpers.ts`), on `haiku` at any tier but `local` (which keeps the local model). Haiku has no slot cap of its own (`modelConcurrency` has no `haiku`), only `concurrency`, and a Cursor role maps it to its model as it does `sonnet`. Subagents a session starts run on `sonnet` (`haiku` in a Haiku session): `CLAUDE_CODE_SUBAGENT_MODEL`, section 6.2.

**Auto concurrency** (`autoConcurrency`, on by default) makes the most of the subscription. Every 5 minutes it compares the recent burn rate of the 5-hour window (the change in its `utilization` over the last half hour, within the current window) with the rate that would reach `targetPct` (default 75%; 95% until 2026-10-22, which left no room for the people using the same subscription by hand) exactly at the reset:

- **Behind pace** (below 85% of the needed rate) and work is waiting for a slot: allow one more session, up to `max` (default 8).
- **Ahead of pace** (above 115%): allow one fewer, down to `min` (default 1).
- **The week comes first:** if the weekly limit is more than 10% (`weekMarginPct`) ahead of an even pace through the week, allow one fewer, whatever the window says, but never fewer than 2 (`weekFloor`; or `max`, if lower). Ahead on the week it throttles rather than stalls.
- **A new window** (the reading's `resetsAt` has moved on since the last pace) goes straight back to `concurrency` (within `min` and `max`), without waiting for the 5-minute step, rather than climbing back one session at a time from where the last window ended. The usual pacing then lowers it if that burns too fast.
- With no burn rate yet (a fresh window), it leans in one step at a time while work is waiting. Once the target is reached it drops to `min`.

The per-model caps (`modelConcurrency`) still apply on top, and the snapshot carries the reason for the current number.

- **Where the number comes from:** every session's stream-json output starts with a `rate_limit_event`: `{"rate_limit_info": {"status": "allowed", "resetsAt": <epoch s>, "rateLimitType": "five_hour", ...}}`. The latest one is kept in `state.usage`. If there's no reading yet, or the window has reset since the last one, the window is treated as full (`opus`).
- **Newer Claude Code builds** also report every window under `rate_limit_info.unifiedWindows` (`five_hour` and `seven_day`, each with `utilization` 0–1 and `resetsAt`). When they're there, the 5-hour percentage drives the tiers and the weekly one is reported in the snapshot. Claude Code 2.1.126 doesn't send them. When the weekly limit is what turned a session away (`status: rejected` on `seven_day`), the usage record's reset time is the week's, so nothing is retried at the 5-hour reset into the same wall. A session ended by the limit sends its item back to the shared backlog's queue (shown queued, not building) when nothing was pushed for it; an item with a PR waits, shown paused until the reset. At 95% (`weekCutoffPct`) of the weekly limit used, nothing new starts (a hard cutoff, whatever the 5-hour window says) until the week resets.
- **It doesn't always carry a percentage.** When it has one (`utilization`), the thresholds above apply. When it only has a status, the tiers go by the status:

  | Status | Implementer | Scouts |
  |---|---|---|
  | `allowed` | `opus` | `sonnet` |
  | `allowed_warning` | `sonnet` | `local` (`sonnet`) |
  | `rejected` | as below `pauseBelowPct` | |
- **Waiting near the limit** (without the local fallback) is its own status, `waiting_for_limit`, separate from a manual pause. It resumes by itself at the window's reset time. Running sessions are left to finish.
- A session that hits the limit mid-run and exits is treated like an interrupted session: the orchestrator resumes it once the window resets (and never sooner than 10 minutes, in case it was a different limit), on the tier picked then. It doesn't move to the local fallback. If a scout hits the limit, the whole review re-runs after the reset, rather than Opus approving without that scout.
- The tier is picked when a session actually starts (after it gets its slot), not when it's queued. A reading with no reset time expires after 5 hours.
- **A resumed session stays on the backend it started on** (the model in its transcript's first line). An Anthropic session whose tier is now `local` resumes on `sonnet`, or at the limit waits for the reset; a local session stays local while local is on and up, and otherwise resumes on its Anthropic tier (a local conversation fits there easily, and Claude Code resumes it fine). An Anthropic conversation won't fit the local context.
- Each session records the model it ran on. It's in the snapshot and the transcript.

- **Drafts, triage, asks, looks and the planner on the ladder (Rust agent).** Behind the `local-tier-ladder` flag these roles pass `LocalModel::ladder()` (flag On and the model up) as `local_available` only when the session runs on Claude: the drafter (`drafter_tier`: `mid_tier` of the implementer's tier, a `[Lighthouse]` draft on the chore tier), the triager (`mid_tier`), asks (the implementer's tier) and looks (`mid_tier`, no usage reading) so they are `local` exactly in the implementer's low rows, and the triager's second look (`top_tier`) at the floor; the planner is on `top_tier` (no usage reading, so `opus`) instead of the chore tier only with the flag On (Off, it stays on the chore tier), with `Roster::begin` offering the tier the ladder. A `local` tier waits for the model's one slot with `LocalModel::claim` (held until the session ends), runs `--model sonnet` (`claude_model`) against `LocalModel::target()` as the spec's `local`, and a role above the limit never takes the free slot, since its tier isn't `local`. Off, or with the model down or the role on another engine, the bracketed tier applies. A drafter or ask whose engine is the local model places as Claude Code, like `place`.
- **Review scouts and the final reviewer on the ladder (Rust agent).** Behind the same flag, `piece_review.rs`'s `review_models` gives scouts `scout_tier` and the final reviewer `top_tier`, with `local_available` true only when the model is up and that session is placed on Claude (a scout also takes a free slot at once with `try_take()`, section 7.2). Off, scouts are `sonnet` and the reviewer `opus`.
- **In this Rust agent**, `src/tiers.rs` builds both tables of this section as pure functions taking `local_available`: `implementer_tier`, `scout_tier` and `top_tier` (`opus` down to `pauseBelowPct`, then `local` when available, else `opus`) read the usage and `mid_tier` is the implementer's tier but never Opus; the `local` rows come back only when `local_available` is true, else `sonnet` (`opus` for the top tier). Of those, `implementer_tier` picks the implementer's own model from the usage shapes in "Where the number comes from" above: once `unifiedWindows.five_hour` exists it decides alone — its own `resetsAt` at or before now makes it a full window (`opus`) whatever the top-level `status` says, and otherwise its own `utilization` (normalized like `frac` above: a whole number over 1 is read as a percentage, not clamped to a full window) against `models.opusAbovePct`; failing that, the older flat `utilization` next to the top-level `resetsAt`, read the same way; and failing that, the top-level `status` alone (`allowed` is `opus`, `allowed_warning`/`rejected` is `sonnet`). No reading yet, or one whose `resetsAt` has passed with neither a percentage nor `unifiedWindows.five_hour` to fall back on, is `opus`, same as the table says for a full window. Where that gives `opus`, `implementer_model` then applies "First tries are written on Sonnet" above: the claimed item's `reopened` (backlog/06.1-an-item.md) keeps `opus`, and, behind the `implementer-step-up` flag, so do a retry (`attempt` over 0: this agent counts Start over from 0, the branch's `-r<attempt>`; `ClaudeStarter` passes the job's, the trial and a piece run pass 0) and an item whose `size` (`Item.size`, any case) is `L` or `XL`; with the flag Off only `reopened` does. Anything else `implementer_tier` gave below `opus` is returned as it was. `src/orchestrator/session.rs`'s `ClaudeStarter` calls both when a session actually starts, against the project's `state.usage` (`src/store/project.rs`'s `usage`/`set_usage`), kept up to date from each session's own `rate_limit_info` (`src/engines/engine.rs`'s `SessionResult.usage`) once it settles (`src/orchestrator/driver/settle.rs`) — but only when it is, or carries, the 5-hour window, or (behind the `weekly-limit-reading` flag) is a lone `rateLimitType: "seven_day"` reading whose `status` is `rejected` (`src/tiers.rs`'s `is_usage_reading`): a build that reports one window per event and happens to send a later, unrelated one doesn't overwrite a usable 5-hour reading with one no tier can be read from. A kept weekly rejection still reads as `sonnet` in `implementer_tier` (its `status` is `rejected`), and `src/engines/engine.rs`'s `resets_in(usage, weekly)` gives the time to the week's reset when the weekly window is what rejected (a top-level `seven_day` rejection's own `resetsAt`, or `unifiedWindows.seven_day` rejected or full, the later of its `resetsAt` and the top-level one), so `record_session_end` limits Claude until then rather than for the 5-hour reset or `LIMIT_PAUSE`; with the flag Off both behave as before. Behind the same flag, `src/tiers.rs`'s `week_cutoff_until(usage, now, models)` reads whether the week is cut off now: the weekly percentage used (`unifiedWindows.seven_day.utilization`, or a lone `seven_day` reading's own, normalized like `frac`) at or over `models.weekCutoffPct` (95, `ModelsConfig::week_cutoff_pct`), or that window `rejected`, with the week's `resetsAt` still ahead, and returns that reset. `ProjectLoop::cut_off_for_week` (`src/orchestrator/driver/settle.rs`) calls it with the default `ModelsConfig` (the configured value isn't passed to it yet) and then marks Claude limited on this computer until then through `EngineLimits::hit`, so the start gate lets no new Claude session start while running ones finish, whatever the 5-hour window says. It reads each session's own reading as it settles (before the 5-hour filter, so a lone weekly reading counts) and the saved `state.usage` and `state.weekUsage` once, on the project's first poll or pass (when the flag can be asked), so a restart keeps the cutoff (`state.weekUsage`, `src/store/project.rs`'s `week_usage`/`set_week_usage`, is the last reading that carried the week, `unifiedWindows.seven_day` or `rateLimitType: "seven_day"`, saved by `settle.rs` whatever `is_usage_reading` decides for `state.usage`, so a lone non-rejected `seven_day` reading survives a restart without touching the tier; only with a weekly flag On, or with auto concurrency on and the `auto-concurrency-week` flag On, so the pacer's week survives a restart; that alone never turns the weekly cutoff on); `EngineLimits::hit` keeps the later of the recorded and the new time, so a shorter 5-hour limit never shortens the cutoff, and logs one line when applied. Behind the `weekly-cutoff` flag the same cutoff is also applied with `weekly-limit-reading` Off (either flag turns the weekly window on), and extends to every role: `EngineLimits::cut_off_for_week` (`src/orchestrator/fresh_start.rs`) is what both call, `record_session_end` (`src/orchestrator/live/sessions.rs`) calls it for each Claude session that ends with a usage reading (the machine keeps `EngineLimits::set_week_cutoff` fresh from the flag), and a `seven_day` rejection is held until the week's reset rather than `resets_in`/`LIMIT_PAUSE`. Because `engine_limits` only holds implementer claims while `engine-start-rules` is On, `ProjectLoop::claim` (`src/orchestrator/driver/project.rs`) also claims nothing while that gate is Off and Claude is week-cut-off (`EngineLimits::week_cut_off`); with the gate On a Cursor lane or role still starts. Running sessions finish. With the flag Off nothing changes. The weekly percentage in the snapshot is still not yet. Auto concurrency is behind the `auto-concurrency` flag (any live project's flags, `autoConcurrency.enabled` also true), pacing claim-mode sessions: `src/pace.rs`'s `Pacer` keeps the 5-hour samples from Claude Code readings only (a lone `seven_day` reading is never a sample) and reads the week from `unifiedWindows.seven_day` and, behind the `auto-concurrency-week` flag, also from a lone `rateLimitType: "seven_day"` reading (`src/tiers.rs`'s `week_reading`, shared with `week_cutoff_until`; a reading with no utilization leaves the last weekly value as it was; with the flag Off only `unifiedWindows.seven_day`), and `pace(now, current, concurrency, work_waiting, cfg)` applies the bullets above in order — a new window, target reached, the week, then the burn rate against the needed rate, with `due(now)` for the 5-minute step; `autoConcurrency` also reads `targetPct`, `weekMarginPct` and `weekFloor`. One `Pacer` serves the whole computer (`src/orchestrator/driver/auto.rs`, held by `Machine`, which `SpawnArgs.auto_concurrency` configures). `Machine::effective_concurrency()` replaces `concurrency` in every `room` and `slots` of `schedule`: the pacer's number with auto concurrency on (before its first step, `concurrency` clamped to `min`..`max`), else `concurrency` exactly as before. At the start of each `schedule` pass, after the sessions that ended are settled, the pacer takes the readings of Claude implementer sessions as they settled (`ProjectLoop::pace_readings`, filled in `settle.rs`; a Cursor, pi or Codex session's reading is left out) and, on a project's first pass, its saved `state.usage` and `state.weekUsage`; when `due` it steps with `work_waiting` = the last pass ended with no slot left while one more slot would have started something (`round_robin::plan` for one slot over the live, unpaused projects: a start, or asking the store with a lane free). A change of the number logs one `auto_concurrency` line with the reason. The pacer's state is kept in `.retaskable/machine.json` under `autoConcurrency` (`MachineStore::auto_concurrency`/`set_auto_concurrency`, `pace.rs`'s `PacerState`): the number, the reason, the `resetsAt` of the window it was paced in, the time of the last step and the latest samples (12 at most). It is written after a step only when the number or the window changed, and a missing value or one that doesn't fit loads as none. With the flag On and `autoConcurrency.enabled`, the first pass restores it (`Machine::with_machine_dir`): a window that hasn't reached its `resetsAt` keeps its number and the 5-minute clock, and one that has starts from `concurrency` as a new window. With the flag Off nothing is read or written. Running sessions are never stopped; only starts are held. Asks, drafts and do-next keep their own slot rules, and `runs` mode has no session cap. Not yet: the store doesn't send an item's `size` yet (sizing came from the TypeScript agent's own now-removed planner, estimates.md section 3.2), so every item reads as below size L until it does; a reading with no `resetsAt` anywhere is read as already expired rather than kept for 5 hours from when it arrived; the wait-for-reset floor (below `models.pauseBelowPct`, or `rejected`, the implementer and scouts stay on `sonnet` when the local model isn't available, since no wait state exists in this agent — section 7.2's own note), and any caller but the implementer's (`attempt`, a piece run and the trial pass the local model's `available()` behind the `local-tier-ladder` flag, section 7.2's "In this Rust agent"; every other caller passes `false`); the per-model caps are built, behind the `model-concurrency-caps` flag: `src/engines/model_slots.rs`'s `ModelSlots`, built once from `modelConcurrency`, holds a Claude session to its model's `opus` or `sonnet` slot in `run_session_tracked` until it ends, a session waiting for its slot still counting toward `concurrency`; so the loop doesn't claim work the cap can't start, `ModelSlots::has_room(model)` is a non-blocking look at a slot, `SessionStarter::implementer_may_start(usage)` (`ClaudeStarter` answers from `session.rs`'s `model_has_room`) says whether a fresh implementer may start — the claimed item isn't known yet, so on the `opus` tier it needs room on both `opus` (a reopened item, and with `implementer-step-up` a retry or L/XL item, keeps it) and `sonnet` (a first try runs there, `implementer_model`), and on any other tier on that tier's own model — counting the Claude implementer starts this pass has already made (`pending`), over every project since the slots are shared by the computer, which haven't taken their slot yet (a start from an earlier pass still setting up its lane isn't counted, so a pass right after may claim one more); with the flag On, `schedule`'s claim and start steps skip every lane whose fresh implementer would run on Claude while that answer is no, asking again after each start, so a capped, full model claims nothing new for Claude lanes; Cursor, pi and Codex lanes, asks, resumes and the other roles go on; `haiku`, `local` and Cursor, pi and Codex sessions never wait); Cursor's own usage handling; the other roles' tiers (the scout, drafter, triager, planner and final-reviewer sessions all exist now, `src/scouts/`, `src/drafts/`, `src/triage/`, `orchestrator/plan_run.rs` and `src/reviewer/`, but `src/tiers.rs` has `implementer_tier`, `scout_tier`, `mid_tier`, `chore_tier` and `top_tier`, with no per-role usage rule beyond those); a resumed session keeping its tier; and the model recorded in the snapshot or transcript.
