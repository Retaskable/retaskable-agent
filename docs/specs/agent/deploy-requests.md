# Deploy requests — what the computer does

Status: v0.1, draft (2026-11-14). Copies the agent's part of Retaskable.com's [deploy-requests-on-server.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/deploy-requests-on-server.md) (v0.1, backlog item `deploy-requests-claimable`, sections 3.1 and 3.2) and the TypeScript agent's `agent/src/deployRequests.ts`. The store's row and ops (`shared/backlogDeployOps.ts`) are the server's: this file keeps only what the computer sends and runs. Builds on [agent/09.3-what-the-computer-does-when-a-command-asks.md](09.3-what-the-computer-does-when-a-command-asks.md) (the pushed commands these replace), [../rollout-on-server.md](../rollout-on-server.md) (the same shape: the store owns the record, the computer runs and reports) and [../testflight-restart-wait.md](../testflight-restart-wait.md).

Theme: Orchestration

Kind: change

## 1. What it is

The website's TestFlight build, promote, hosting read and go-live prepare are not pushed to one computer. Each is a **deploy request**, a row in the store (`deploy_requests`) that any computer may claim, but only one that can run it. A computer that holds the signing keys or the cloud credentials claims it; the others skip it. The keys stay on the computer and never reach the store: a request holds the command's own arguments and its result only what the code answered.

## 2. What the computer does

- **List** (`deploy_list`): every project's loop reads the open requests every 5 seconds (the store has no push to this computer yet). A request whose status is not `requested` is not touched; a claim that went 10 minutes without a beat already shows `requested` again. A store that can't be reached or read means nothing is claimed (fail closed), and the loop says so once per change.
- **Claim by capability** (`deploy_claim { id, machine, can: true }`): the computer checks its own keys and setup first (`Deps::can`), and calls `deploy_claim` only for a request it can run. It never claims in order to decline on the site's behalf, and the store refuses a claim whose `can` is not `true`. Two computers able to run it: the first claim wins and the other is told so and does nothing. A request whose `args.prefer` names another computer is left to it for 5 seconds from `at`, then taken like any other.
- **Capability per kind** (the code is `deploy_requests::Live::can`):
  - `testflight_build` needs `release.testflight` on and a Mac with the committed Xcode project and `testflight-ios.sh`; the build is Xcode, never EAS. It is claimed only by the computer whose code-host login is the issuer's (case-insensitive) unless `release.testflightAnyMember` is on; a computer that can't say who it is signed in as leaves it to the build's own admin check.
  - `promote` needs the project to have staging and production branches (`environmentsOf`: both `deploy.<env>.branch` set) and not merge straight to production (`deploy.mergesTo` is not `production`).
  - `hosting` and `go_live_prepare` need only the project (its repo and its GitHub name) and a link to the store (the computer holds the backlog token); a paused project still takes them.
  - A paused project (paused here or in the store) claims no `testflight_build` or `promote`.
- **Run**: a claimed request is beaten (`deploy_beat { id }`) at once, which marks it `running`, and every minute while it runs, then run with the code the pushed command ran. A beat that fails is ignored; the store reopens a claim that goes stale.
- **Finish** (`deploy_finish { id, status, result? }`): `done`; `refused` when the code refuses in its own words (the reason is `result.why`, at most 500 characters); `failed` for any other error with the same `why`; a TestFlight build that does not end `submitted` is `failed` with `{ sha, buildNumber, result }`. A result over 4 KB, or with a top-level key that names a secret (`/token|secret|password|credential|api[_-]?key|private/i`, the store's own check, top level only: a nested key passes), is not sent: the request is `failed` with a short `why` instead. A finish from a claim that expired answers `{ ok: false }` and is dropped; the computer says so in its log and does nothing else.
- Several requests run at once, each on its own task, and a request this computer already runs is never claimed twice.

## 2.1 The hosting read

`hosting` is a read: it writes nothing (no store row but its own finish, no file, no git). `src/hosting/` ports `detectHosting` (`agent/src/setup.ts`: the root `package.json` and its npm workspaces' dependencies, a Worker's `main` in `wrangler.toml` or `wrangler.jsonc`, a Dockerfile `EXPOSE`, `flask|django|fastapi` in `requirements.txt`, and the folders `api`, `server`, `functions`, `netlify/functions`, `pages/api`, `app/api`, `src/pages/api`, `src/app/api`, found by path components; Electron, Tauri or `src-tauri` is a desktop app, Expo or React Native a phone app), `gh repo view <repo> --json visibility` (`gh.repoPrivate`: public only when GitHub says `PUBLIC`; `gh` that can't say is not public) and `pickHosting`'s choice (go-live.md section 2).

The result is `{ project, pick }`:

```json
{ "project": { "type": "web", "public": true, "backEnd": false, "app": null },
  "pick": { "shape": "static", "default": "github-pages", "alternatives": ["cloudflare-pages", "netlify"], "database": null } }
```

`pick` names the chosen providers by **id only**: where the TypeScript agent sends each provider's whole object (name, limits, steps, pictures), this sends `default`, `alternatives` and `database` (`{ default, alternatives }` or `null`) as the ids of `shared/hosting.ts`'s `HOSTING` table. The site looks the providers up from its own table ([Retaskable.com#3858](https://github.com/Retaskable/Retaskable.com/issues/3858)), so the agent keeps the ids and the choosing and none of the display text. The result is under 300 bytes for every project, far inside the 4 KB cap. A project with no `projectType` does not exist here (the config's default is `game`), so the TypeScript's "undefined type reads as a static site" has no case.

## 2.2 The go-live prepare

`go_live_prepare { provider }` adds the one backlog item that prepares the repo for the provider chosen (`add { via: "site", items: [item] }`, through the store, as Use this does). Neither deploys: the provider builds from the GitHub repo itself, and no token, password or secret is asked for or written. The item is `{ id: "go-live-<provider id>", title: "Get <repo name> ready for <provider name>", remaining }`, and its text is the TypeScript's `prepareItem` word for word (`src/hosting/prepare_golden.json` is that function's output for every provider and the test holds this one to it); the repo name is what follows the last `/` of `owner/name`.

- A provider that isn't one of the thirteen ids (or none given) is the code's own refusal: `refused`, "There's no hosting provider \"<id>\"." (`undefined` when none), and the store is not asked.
- The store's `conflict` (the item is already on the list: chosen before) is `done` with `already: true`, so the walkthrough carries on.
- Any other refusal by the store is `refused` with its message. A store that can't be reached is `failed`: nothing said no.
- The result is `{ id, title, already }`, about 100 bytes.

## 2.3 The promote

`promote { sha }` is the website's Deploy to production: the same push as the machine's Promote, after the website's own checks. `src/promote/` ports `agent/src/promote.ts` (`siteChecks`, `promote`, `pushRefusal`, `environmentsOf`); `src/deploy_requests/promote.rs` is `deployRun`'s `promote` case. Plain code, no model. The only ref it ever names is `refs/heads/<production>`, and it never forces.

- **Run order:** a project whose merges go straight to production is refused, "This project's merges go straight to production: there's nothing to promote." (first); a request with no `sha` is refused, "Name a commit."; then `siteChecks`, then the promote. The result is `{ sha }`, the commit as the request named it.
- **`siteChecks`** (the first failing one refuses; anything that can't be read refuses): staging has an address ("Staging has no address to check: deploy it from the machine."); it answers `GET <url><versionPath>` (default `/version.json`, `cache-control: no-cache`, 15 seconds) with `{ "sha": "<7 to 40 hex>" }` ("Staging doesn't say which commit it serves at <url>: deploy it from the machine."); that sha starts with the requested one, case-insensitively ("Staging serves <7>, not <7>: check again."); the issuer matches `/^[a-z\d][a-z\d-]{0,38}$/i` ("Only the repo's admins can deploy from the website."); and `gh api repos/<repo>/collaborators/<issuer>/permission --jq .permission` says `admin` ("Only the repo's admins can deploy from the website (@x has write)." with `no access` for `none` or nothing; a `gh` that can't say refuses with "Couldn't ask GitHub whether @x is an admin of <repo>: <gh's words>").
- **`promote`**: the sha must be 7 to 40 hex ("Promote needs the commit to push."); one promote per repo at a time, a second is refused, not queued ("A promote is already being pushed."); `git fetch --prune origin`; `git rev-parse --verify --quiet <sha>^{commit}` ("<7> isn't a commit in this repo"); on `origin/<staging>` ("<7> isn't on <staging>"), not already on `origin/<production>` ("Up to date"), and production has nothing staging doesn't ("Production has commits staging doesn't: fix that by hand"); then the machine's own admin check, `gh api repos/<repo> --jq .permissions` ("Only the repo's admins can promote (you have write access)", "Only the repo's admins can promote", or "Couldn't ask GitHub whether you're an admin of <repo>: <words>"); then `git push origin <full sha>:refs/heads/<production>` with a 5-minute limit, never `--force` and never a `+` refspec, so git itself refuses anything but a fast-forward; then `git fetch --prune origin` again. A refused push is "GitHub refused the push: <reason>", the reason being git's output without `hint:`, `To ` and `Everything up-to-date` lines and without the `remote:` prefix, cut to 500 characters. The work runs on a task of its own, so a rollout that loses its runner mid-push never leaves a push done and its row unwritten.
- **The deploy log row** (`log_add { kind: "deploy", entry }`) is written for a push that got to GitHub, pushed or refused, never for a refusal before the push: `{ at, login, environment: "production", from, to, outcome: "pushed" | "refused", reason?, via? }`. `from` is `origin/<production>` before, `to` the full sha, `login` the issuer from the website (`via: "site"`) or this computer's `gh api user --jq .login` (`via: "auto"` for the rollout's promote, none otherwise).
- **The log outbox** (`src/promote/log.rs`, last-local-state.md section 3.4 of the TypeScript spec): the row is put in a queue and on disk BEFORE anything is sent, in `<data>/projects/<id>/logs.pending.json` (`[{ kind, at, entry }]`, oldest first, the TypeScript agent's own file). It is its own file, not a key of `state.json`, because `state.json` is the orchestrator's and written by its task alone, while a promote runs on the deploy request loop's and the rollout's tasks. One queue per file in a process, shared by both. The queue is sent in order right after a promote and on every pass of the deploy request loop (also when the list can't be read), and after a send the store didn't take, not before 30 seconds later. A row leaves the queue and the file only when the store has answered it: taken, or refused as `bad_request` (the row itself is wrong; dropped with a warning, as the TypeScript's). Anything else, an unreachable store above all, keeps every row, and the rows behind a kept one wait for it. A restart reads the file back; a file that isn't a queue is moved aside as `.bad`, never written over. A row the store has already taken but whose reply was lost is sent again (the store keeps both), as the TypeScript's.
- **Rollout**: the store's `promote` instruction (rollout-on-server.md section 3, step 4) runs this same code with `via: "auto"`, or, when it carries `by`, the website's own (`siteChecks` then the push, logged `via: "site"` under `by`). Under Production only it does nothing and succeeds. A refusal is the instruction's `why`, whole, cut to 300 characters.
- **Not ported**: the Environments panel's reads (`environments`, `productionOnlyEnvironments`, GitHub's rules on production), the `offer` path (`via: "offer"`), and a restart waiting for a push in flight (`promoting()`).

## 2.4 The TestFlight build

`testflight_build { sha, environment }` builds Retaskable's own iOS app and uploads it to TestFlight, in a throwaway checkout of the commit the environment serves (production, or staging when asked). `src/testflight/` ports `agent/src/testflight.ts` and `src/deploy_requests/testflight.rs` is `deployCan` and `deployRun`'s `testflight_build` case. Plain code, no model; Xcode, never EAS. `release.testflight` and `release.testflightAnyMember` (`ReleaseConfig`) are on only for the boolean `true`.

- **Claimed** (`deployCan`): only a Mac (`cfg!(target_os = "macos")`) with the setting on, `<repo>/app/ios/Retaskable.xcodeproj/project.pbxproj` and `<repo>/app/scripts/testflight-ios.sh`, not paused, and (unless `testflightAnyMember`) whose `gh api user` login equals the issuer's, case-insensitively; a `gh` that can't say leaves it to the admin check below. A Windows or Linux computer never claims it.
- **Run order:** a request with no `sha` is refused, "Name a commit."; then the refusals, the first failing one refusing with nothing run (`checkRefusals`): the setting is off ("TestFlight builds are off on this computer: turn them on in its settings."); not a Mac ("TestFlight builds need a Mac: Xcode archives the app.") or no project or script ("This project has no app/ios Xcode project and app/scripts/testflight-ios.sh."); the issuer isn't a login ("Only the repo's admins can build for TestFlight."); `gh api repos/<repo>/collaborators/<issuer>/permission` can't say ("Couldn't ask GitHub whether @x is an admin of <repo>: <words>") or isn't `admin` ("... (@x has write)", `no access` for `none` or nothing); staging asked under Production only ("This project's merges go straight to production: build production."); the environment has no address ("<Production|Staging> has no address to check: set it in Settings → Project settings."); its version address, read up to 5 times (the first read starting with the sha wins, else the commit answered most, the last of a tie), says nothing ("<Name> doesn't say which commit it serves at <url>.") or another commit ("<Name> serves <7>, not <7>: build that one."); `xcodebuild -version` fails ("Xcode isn't ready on this computer: install it and open it once to accept its license."). Then one build at a time per repo: a second is refused, "A TestFlight build is already running: wait for it.", never queued. A restart waits for a running build (`testflight::Running`, [../testflight-restart-wait.md](../testflight-restart-wait.md)).
- **The build** (all in `<project folder>/testflight-build.log`, emptied first, each command shown as `$ <command>`): `git fetch --prune origin` in the checkout, then, with the build number `YYMMDDHHmm` (UTC, from the clock) and `<dir>` = `<worktreesDir>/testflight-<number>`:
  1. `git worktree add --detach <dir> <full sha>` (in the repo);
  2. `npm ci` (in `<dir>/app`, 10 minutes);
  3. every `CURRENT_PROJECT_VERSION = ...;` in `<dir>/app/ios/Retaskable.xcodeproj/project.pbxproj` is rewritten to the build number (App Store Connect refuses a number it has seen), then `bash scripts/testflight-ios.sh` (in `<dir>/app`, 60 minutes) with `RETASKABLE_BUILD_NUMBER=<number>` and, for staging, `RETASKABLE_CLOUD_ORIGIN=<staging url without trailing slashes>`.
  A timeout, or a restart or quit, kills the step's whole process tree (the agent's process tree registration), not just `npm` or `bash`. On every path the checkout is removed: `git worktree remove --force <dir>`, then, if the folder is still there, the folder itself and `git worktree prune`.
- **How it ends:** `submitted` (every step exited 0), `failed` (a step exited non-zero, timed out, the pin couldn't be written, or the fetch failed; the error is the last 5 lines, or "`npm` timed out.", cut to 500 characters) or `cancelled` (cut by a restart or quit). The result is `{ sha, buildNumber, result }`, `sha` the full commit the environment serves; the request is `done` only when `submitted`, else `failed`. Refusals are `refused` with their words.
- **The log line**, written when the build ends: `{ at, sha, buildNumber, login, via: "site", environment, result, error? }` is appended to `<project folder>/testflight.log` first (a crash keeps it), then queued in the on-disk outbox of section 2.3 as a `testflight` row (`log_add { kind: "testflight", entry }`), sent at once and on every pass. The row leaves `testflight.log` when the store has answered it (taken, or refused as `bad_request`); a file left empty is removed.
- **Differs from the TypeScript:** a failure writing the build number, which the TypeScript reported as `submitted` (it set the result before the steps), is `failed`, and the script is never run unpinned; `cancelled` is a command cut from outside, not a guess from an empty exit code and error text; a command's output goes straight to the build log, not into memory; a half-made checkout is removed from disk too; a project with no `worktreesDir` builds under the system's temp folder.
- **Not testable in CI:** the real `npm ci`, the Xcode archive and upload, Apple signing and `xcodebuild -version` need a Mac with Xcode and the project's certificates. Everything before and around them is tested with a fake runner (section 4); the real runner's own process handling is tested with `sh` on Unix.

## 3. What is not here

- The pushed commands are gone from the site; the agent has no case for them in its command handler and no `testflight_report`.
- The `rollout` store log, pruning of `deploys.log` and `rollouts.log`, and `nativeApp` reading the store's `testflight` rows (`logs_get`) are the TypeScript spec's section 3.4; only the `deploy` and `testflight` kinds' outbox is ported (sections 2.3 and 2.4), with `testflight.log` pruned as the store answers.
- The row, the ops, who may request what and the website are the server's.

## 4. Tests

- `src/backlog/deploy/tests.rs`: the ops' wire shapes (a claim always says `can: true`; `finish` sends a result only when there is one; a refusal keeps the store's code; a result over 4 KB is caught before sending; an unknown kind is a bad answer, not a guess).
- `src/deploy_requests/tests.rs`: a request the computer can't run is left unclaimed; one it can run is claimed, run and finished with the derived result; a refusal is `refused` with its reason and any other error `failed`; a result over 4 KB or a reason over 500 characters is cut; losing the claim runs nothing; only `requested` rows are claimed; `prefer` waits 5 seconds for the other computer; a request being run is not claimed twice and a long run beats every minute; an unreadable store claims nothing; no store link means no op is sent; every pass flushes the deploy log, also when the list can't be read.
- `src/deploy_requests/promote_tests.rs` (real temp repos, a bare origin, a fake `gh`, a fake staging site and store): a promote is claimable only with both branches, merges to staging, not paused and linked; "Name a commit." and the straight-to-production refusal; a push answers `{ sha }` and the store then holds one `log_add` and the file is gone; a store that is down keeps the row on disk and the request still ends `done`; a refused check pushes and logs nothing.
- `src/promote/tests/`: never a force (the argv, and git's own refusal of a push that isn't a fast-forward), production's reflog shows one fast-forward from c1 to the commit named; a commit not on staging, "Up to date", production ahead, a non-admin machine login, a push the remote refuses (logged `refused`), a second promote of the repo while one pushes, two at once push once; every `siteChecks` refusal in its words (the wrong sha, staging that can't say, a bad login, `write`, `read`, `none`, `gh` that can't say); `pushRefusal`'s cutting; the log outbox (the row is on disk when the store is asked, kept when it is down and sent in order 30 seconds later, a restart reads it back, a bad request is dropped, a file that isn't a queue is kept aside).
- `src/rollout/tests.rs`: the `promote` instruction runs the promote once, keeps its result for the next poll, passes `by`, fails with the refusal's whole words cut to 300, and is never run for a bad sha or under Production only.

- `src/testflight/tests.rs` (a fake runner: no Xcode, no npm, no network): the refusals one by one in order, nothing run and nothing logged before they pass; the served commit's 5 reads and vote; the steps in order with their working folders, timeouts and environment (`RETASKABLE_BUILD_NUMBER`, plus `RETASKABLE_CLOUD_ORIGIN` for staging only); the build number pinned in the checkout's pbxproj (a fixture) and never in the repo, a failed pin failing the build; the checkout removed on success, a failed step, a timeout, a cut, a failed checkout and one git can't remove; failure words; one build at a time; the line in `testflight.log` and the outbox on disk when the build returns, before anything is sent.
- `src/testflight/real_tests.rs` (Unix): the real runner on `sh`: output appended whole and read back, the environment, a command that can't start, a timeout killing a grandchild, a cut.
- `src/deploy_requests/testflight_tests.rs`: a non-Mac never claims; the setting, the files, the owner's login (any case, any member, a login that can't be said); "Name a commit." first; a refusal is `refused`; `submitted` is `done` and the rest `failed` with `{ sha, buildNumber, result }`.
- `src/promote/tests/log.rs`: a `testflight` row leaves `testflight.log` only once the store has answered it.

## 5. Slices

1. **This slice (done):** the store ops and the claim, beat and finish loop, with the capability gate, and nothing ported yet to run: the loop starts for a project only once a kind is in `deploy_requests::PORTED`, so today this computer claims nothing and the website's request waits for a computer that can (the TypeScript agent).
2. **`hosting` (done):** the picker's read (section 2.1), in `PORTED`.
2b. **`go_live_prepare` (done):** the item that prepares the repo (`add { via: "site" }`), in `PORTED` (section 2.2).
3. **`promote` (done):** the staging-to-production fast-forward push with its checks (git, the admin check; not the code host's rules, which only the Environments panel shows) and the deploy log row with its on-disk outbox (section 2.3), in `PORTED` and in the rollout's `promote` instruction.
4. **`testflight_build` (done):** the Xcode build and upload (section 2.4), the `testflight` log kind in the outbox, in `PORTED`; the claim holds to a Mac. Not yet: `nativeApp` reading the store's `testflight` rows.
5. A push from the store (`facts_changed` naming `deploy_requests`), when the Rust agent has a store link, to replace the 5-second read.
