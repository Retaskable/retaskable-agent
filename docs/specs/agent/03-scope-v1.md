## 3. Scope (v1)

- One agent runs several projects, each a repo and its backlog with its own lanes, run by the one process and sharing the sessions, the daily budget and the usage limit ([projects.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/projects.md)). A project is linked, and its settings changed, by the commands retaskable.com sends ([cloud.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/cloud.md) section 6), which the agent writes to `.retaskable/config.json`. The config, the state and the loop hold several projects. Switching between projects, and the bell that covers all of them, are the app's.
- The backlog is the shared store ([backlog.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/backlog.md)). The agent asks it for the next item and for what a project's items wait on; the roadmap's order and its milestones are the store's.
- An item can be bigger than one PR. It is worked in **slices**, one PR each, until the store says it is done.
- CI is optional. If the repo has none, the implementer's local test run is the gate (section 6.2).
- Several items can be in flight at once, each on its own branch, PR and worktree, in a fixed pool of reusable **lanes** (section 4.1). No Docker or VMs.
- Runs locally on Windows, macOS and Linux. Requirements: `claude`, the code host's CLI (`gh` authenticated, or `glab`) and `git`.

Out of scope for v1: GitHub Issues/Linear/Jira as a backlog, and any UI of the agent's own (its port answers only its health check and the computer's settings page, on localhost; section 8). Watching and steering agents remotely is retaskable.com's job: see [cloud.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/cloud.md).

### 3.1 Working as a team

Every developer runs their own Retaskable agent, on their own machine, next to their own checkout. Linked to retaskable.com, the web and phone app show each developer's agents.

How branches and pull requests work is the project's GitHub workflow pattern ([github-workflow.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/github-workflow.md)). A new setup defaults to GitHub Flow: slices are pull requests into the protected default branch, and that branch moves only when GitHub merges one. Retaskable does not push it, and it does not squash-merge a slice onto it. A project already running with `baseBranch` on the default branch keeps squash-merge until someone picks a pattern in the project's settings.

- **Integration branch** is the team model: each developer's Retaskable agent has its own base branch (`baseBranch`, e.g. `dev/<github login>`, branched from the team's default branch). Its slices merge there, so a playtest, which happens after the merge by default (section 6.4), plays that branch: all of that developer's changes, and nobody else's. Getting that branch into the team's default branch is a pull request. Opening it, and rebasing it when the default branch moves, is a setting of this pattern ([github-workflow.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/github-workflow.md) section 4.2), not a separate question (section 12).
- **Squash into the base branch** is the previous behaviour, kept as a pattern and labelled not recommended: `baseBranch` is the default branch and Retaskable squash-merges into it. It is not what a new setup selects.
- **Getting a developer's branch into the team's `main` is the team's review:** a normal PR, reviewed and merged however the team reviews. When asked (the **Open PR to main** command, [team-branch.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/team-branch.md) section 5), the agent opens that PR through the code host and reports how far ahead and behind the branch is and the PR's checks, review and mergeability; on **Add it in** it squashes the PR into `main` and starts the branch again from `main` ([github-workflow.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/github-workflow.md) section 4.2).
- **Keeping the branch up to date with `main`** ([team-branch.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/team-branch.md) section 4): when `main` moves, the agent merges it into the base branch through a PR (merged with a merge commit, never squashed), and a conflict goes to a `sync_main` chore, as a red main goes to a fix-main chore. Open slice PRs that then conflict are sent back to rebase.
- **CI on the base branch** ([team-branch.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/team-branch.md) section 3): the repo's CI has to run for PRs into the dev branch (a workflow with `pull_request: branches: [main, 'dev/**']`). The agent reads the base branch's workflow triggers after each fetch; when none can run for a PR into it, `awaiting_ci` doesn't wait for checks that will never come, and it reports that to the store so the app can warn.
- **Recommended environments** (local, optional preview, staging, production) are the project's own CI/CD's, not Retaskable's: [cloud.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/cloud.md) section 9 and [environments.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/environments.md) describe them, and promoting staging to production from the app is the site's command.
- **Setup** (the GitHub workflow field of a project's settings): branch names follow the pattern. On save, an integration branch or Git Flow's `develop` is created from the default branch when the pattern says to create it and origin does not have it yet. The login comes from `gh api user`, and a missing `dev/<login>` is pushed from `origin/<default branch>`. With a saved `github`, its **Create this branch on save** flag (`createIntegrationBranch`) covers any name: the branch is pushed from `origin/<protected branch>` when origin does not have it. A project saved without `github` keeps the `dev/<login>`-only rule. After the config is saved, the agent also writes the pattern's merge settings and the `retaskable` ruleset on GitHub ([github-workflow.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/github-workflow.md) section 10), for an admin and never for a fork; what GitHub won't take comes back as `warnings` beside `ok` (or the new project's `id`) in the command's answer, for the app to show.
