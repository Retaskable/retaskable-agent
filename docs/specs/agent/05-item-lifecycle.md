## 5. Item lifecycle

```
queued ─▶ implementing ─▶ awaiting_ci ─▶ checking ─▶ reviewing ─▶ merging ─▶ merged ─▶ done
   ▲         ▲   │  ▲          │             │            │           │          │
   │         │   ▼  │          │ CI red      │ check red  │ changes   │ conflict │ store says
   │         │ needs_clarification           │            │ requested │          │ not done yet
   │         │   (answered in the app)            │            │           │          │
   │         └───────────────────────────────┴────────────┴───────────┘          │
   └─────────────────────────────────────────────────────────────────────────────┘  (next slice)
reviewing ─▶ awaiting_playtest ─▶ merging   (only when the reviewer asks for a playtest; a failed one goes back to implementing)
reviewing ─▶ awaiting_merge ─▶ merged   (the GitHub workflow leaves the merge to GitHub or a person; github-workflow.md)
any state ─▶ needs_human   (budget hit, max rounds, max slices, reviewer escalates, error)
```

| State | Owner | What happens |
|---|---|---|
| `queued` | orchestrator | The store handed the item out (`claim_next`, or `claim` for one a person pressed Process on here) and it has no active run. Which items are ready, in what order, and which wait for a person's **Process** (the store's `held` items, including a GitHub-synced first slice, [confirm-github.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/confirm-github.md)) are the store's ([backlog.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/backlog.md) section 6.6); the agent decides none of it. |
| `implementing` | implementer session | Claude codes the next slice in the worktree (a whole one: the next slice or step the spec plans, all of it in one PR, a PR of 500 to 2,000 changed lines being a good size, split further only when it can't be finished or left working in one go, `prompts/implementer.md` rule 1; 2026-10-21, after one item went out as 41 PRs of 150 to 400 lines against the 5 slices its spec planned; and in as little code as it needs: the project's own helpers first, no unrequested abstraction or "for later" code, a bug fixed once at its root, never cutting validation, error handling or security, after the ponytail skill's rules), runs tests, updates the backlog file and commits; the agent then pushes the branch and opens or updates the PR through the code host. An item that comes back here with the `ci-ready` label on (CI red, a conflict, a playtest problem, Continue) has it taken off before the session starts, so its pushes run no CI until it's ready again, as it next goes to `checking` ([ci-when-ready.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/ci-when-ready.md)). The agent reports what it's doing here to the store as `doing`: `paused` with `until` while `resumeAfter` is ahead (the usage limit or a retry), `slot` while its implementer waits for a session slot (`SessionRunner.waitingForSlot`), `session` while it runs, and `preparing` before that, while its lane is set up. How a card words it is the app's ([new-ui.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/new-ui.md) section 5.6). |
| `needs_clarification` | human | The session exited with questions, which the agent records in the store; the app shows them, and the answer that comes back resumes the same session. The answers are also kept on the item for good (`decisions`, `agent/src/decisions.ts`) and noted in the shared backlog: every implementer session on it, fresh or resumed, gets them as "Already decided by a person", and a question asked again goes back to the session with its answer instead of to the person, at most twice before the item needs a human; only questions nobody has answered are put to the person (2026-10-07: github-workflow asked the same three questions three times). |
| `awaiting_ci` | orchestrator | If `requireCi` is off, it goes straight to `checking`. With `ciWhenReady` on (section 10, [ci-when-ready.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/ci-when-ready.md)) it's where an approved change waits for the CI run that started beside its checks and review, when `checking` put the `ci-ready` label on (`ciReadyAt` on the item; the grace (10 minutes) and the pending limit (2 hours) count from then, not from the approval, so a run that already finished is read at once). If the label isn't on yet (adding it beside the checks failed, or a main sync, which comes here straight from `implementing`), it adds it first and the wait counts from then; an item here that isn't approved and isn't a main sync (the setting just turned on) goes to `checking` instead, which puts the label on. A CI failure that finished minutes before it's read here counts as quick or not by when the failed check finished (`completedAt`, ciHealth.ts), not when it was read. Otherwise it polls `gh pr checks <pr>` until every check passes or one fails. When every check passes on the commit the review already approved (`approvedSha` is the PR's head, as after `merging` brings an approved PR up to date with the base), it goes straight to `merging`: its checks and review were done, so it takes no lane, runs no local checks and isn't reviewed again. Otherwise a pass carries on to `checking`, or, with `ciCoversChecks` on (section 10), where CI runs the same checks, straight to `reviewing`: no lane is claimed to run them again, and the reviewer is told which CI checks passed (section 6.3, stage 1). A failure goes back to `implementing` with the failed checks' names and links, and counts as a check round (`checkRounds`, capped by `maxCheckRounds`, default 3; more go to `needs_human`). If no checks show up within the grace (`ciGraceMinutes`, default 10 minutes), it carries on to `checking`. When the base branch's workflows can't run for a PR into it (`ciCoverage` `not_covered` or `none`, [team-branch.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/team-branch.md) sections 3.2 and 3.3), it carries on at once; either way the item's `ciNote` says why, and the card and drawer show a "no CI" chip. If CI is still pending after the limit (`ciMaxMinutes`, default 2 hours; both are project `tuning`, so the notes name the set value), the item goes to `needs_human`; the reason says which pending checks never started (queued with no runner) or started but never finished, from `gh pr checks --json` where `gh` has it. A `gh` error (no answer from GitHub, not a failed check) waits a minute and tries again, here, in `merging` and in `awaiting_merge`; only 5 in a row go to `needs_human`, and any answer starts the count again. It reads `gh pr checks`' plain output, so it works on older `gh` versions without `--json`. A check that was skipped (`skipping`) is left out; when every check was skipped, with `ciWhenReady` on that's the run from before the label and it keeps waiting, and with it off it reads as a pass, as it always has. With `ciWhenReady` on, `ciCoversChecks` doesn't apply, and when it carries on with no CI (none showed up, or none runs for the base) an item approved at the PR's head goes to `merging` rather than back to review. |
| `checking` | orchestrator | Runs the repo's deterministic checks in the lane (section 6.3, stage 1), after installing its dependencies when it needs that. Skipped when CI passed and `ciCoversChecks` is on. With `ciWhenReady` on, an implementer that finishes comes here straight from `implementing` (a main sync still goes to `awaiting_ci`), keeping its lane, and the `ci-ready` label goes on before the checks start, so CI runs beside the checks and the review (best effort: if the code host doesn't answer, the checks go on and `awaiting_ci` adds it after the approval). A blocking failure goes back to `implementing` with the output and counts as a check round, the same `checkRounds` as a CI failure, so a slice that can't pass its checks ends at `needs_human` (past `maxCheckRounds`) rather than looping. Check rounds don't use up review rounds. No model reads the diff. |
| `reviewing` | scouts, then the Opus reviewer | Cheap scouts look for one kind of issue each, then Opus makes the final call from their findings (section 6.3, stages 2 and 3). |
| `awaiting_playtest` | human | The approved slice waits for you to play it (section 6.4). It holds no lane: **Play this build** checks its branch out, detached, into the project's play checkout (section 4.2), never a lane, so it can be tried while every lane is busy; on a shared backlog another computer can play it too, from the store's try-out queue, without taking it over (team-state-on-server.md section 7, slice 7). Pass moves it to `merging`. Fail resumes the implementer with your notes, increments `reviewRound` and drops the approval (`approvedSha`), so the slice is reviewed again rather than merged unchanged. |
| `merging` | orchestrator | **One item merges at a time per project.** A free merge turn goes to the item in `merging` queued longest (earliest `mergeQueued`; one that hasn't waited yet comes after every one that has, and one waiting out a `resumeAfter` isn't in line; until 2026-10-20 the first to tick took it, so a new slice could merge ahead of changes queued long before it, github-workflow.md section 4.4) (kept in the project's state as `mergeTurn`, so a restart keeps it: until 2026-10-18 it was in memory only, and a self-update restarting the agent while the holder was checked again after being brought up to date handed the turn to the next item in `merging`, whose merge then sent the holder round again); the others stay in `merging`, holding no lane, with one timeline note "Waiting for <id> to merge first", and try again each tick. The turn is given up when the item leaves `merging` (merged, handed to GitHub or a person in `awaiting_merge`, sent back, `needs_human`, skipped), when it goes to `awaiting_ci` after an update that did not keep its approval, or after 45 minutes; an item brought up to date with its approval kept (below) keeps the turn while it's checked again (`awaiting_ci`, `checking`, `reviewing`), since passing brings it straight back, and one handed to GitHub's auto-merge up to date keeps it through `awaiting_merge` until GitHub merges it; those two last at most 2 hours 15 minutes (CI's own limit and 15 minutes, `MERGE_HOLD_MS`). While the item holding the turn waits for a lane (checked again with none, or checking the queue in a lane, below), the next free lane is kept for it: no other item and no new work takes it (`mergeLaneWanted`, section 4.1). The step that gives it up changes the item's state, so the loop ticks at once and the next item takes it. On a shared backlog the team's merge lock goes with the turn (`releaseMergeQueue`, each tick). For the merge queue and the patterns a person lands, the turn covers the update and the hand-off only, not the wait in `awaiting_merge`. Then it checks the PR is mergeable. On a conflict it first brings the PR up to date itself (a team branch's main sync, [team-branch.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/team-branch.md) section 4.3, is left to its implementer: it goes straight back with the "merge again" instruction), with no session: in a throwaway worktree (`<worktreesDir>/merge-<id>`, always removed) it merges `origin/<base>` into the PR's branch (a merge, not a rebase: PRs squash-merge, so no force-push is needed). A conflict there, or any failure, pushes nothing and goes back to `implementing` with a "merge origin/<base> into your branch" instruction and the item's `rebasing` flag set, so its status reads **rebasing**; the flag clears as soon as it leaves `implementing`. Conflicts don't count as review rounds (parallel lanes cause them: other items can merge while an updated one is re-checked and re-reviewed), so they have their own cap, `maxConflictRounds` (default 5), counting both kinds of update; more than that go to `needs_human`. **Continue** on one resets the count, so it's brought up to date again rather than coming straight back. **When the base moved since its checks ran, it is brought up to date and checked again before it merges** (2026-10-12, [github-workflow.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/github-workflow.md) section 4.4), so a PR goes in tested on top of the last merge: on a shared backlog it first takes the team's merge lock (`merge-<base>`, `agent/src/mergeQueue.ts`; others wait here "Queued to merge", `mergeQueued`, with "Waiting for the merge lock (held by <login> for <item> on <machine>)"). Then, for the patterns Retaskable or GitHub's auto-merge lands, after a fetch (skipped if one began in the last 15 seconds; a merge marks it stale), `git merge-base --is-ancestor origin/<base> <PR head>` says whether the base has commits the PR's head lacks (GitHub only reports `BEHIND` when branch protection requires up-to-date branches, so it isn't used). The checks ran on the PR's head, so a head that contains the base's head was checked with it, and nothing more is recorded. If it is behind and other changes of the project wait in `merging` behind it, where Retaskable lands them and CI is the whole recheck (`ciWhenReady` or `ciCoversChecks`), they're **checked together** instead: the base and their approved heads merged in a throwaway worktree, pushed to `retaskable/merge-batch-<id>` and opened as a pull request of its own that CI runs on; the item waits in `merging`, holding the turn, and CI passing there merges each of them in turn with no run of its own, while CI failing closes it and each goes the one-at-a-time way below ([github-workflow.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/github-workflow.md) section 4.4, `agent/src/mergeBatch.ts`). Where the lane's checks are the whole recheck instead (no CI: `requireCi` off, or no CI runs for the base), with checks configured and Retaskable or auto-merge landing them, they're checked together in a lane: the item takes the next free lane (kept for it), merges the base and their approved heads there, detached, with nothing pushed, and runs the checks once; passing, on a base that hasn't moved, Retaskable merges each in turn itself (auto-merge too: they were just checked on that base), and failing gives it up the same way. Otherwise, if it is behind, the same throwaway-worktree update runs, with the note "origin/<base> moved since its checks ran; merging it into the branch and checking it again before it merges", and goes on: "Brought up to date with <base>; checking it again before it merges" to `awaiting_ci`, and if the slice's own changes read the same as at `approvedSha` (the section 6.3 comparison), the new head becomes `approvedSha` and it keeps its merge turn while it's checked again: CI passing merges it with no review, after the lane's checks run again too where CI doesn't run them (`requireCi` without `ciCoversChecks` or `ciWhenReady`: `recheck` on the item sends it from `awaiting_ci` to `checking`, and review finds it approved at its head); with `requireCi` off, `awaiting_ci` goes to the lane's checks as always. A check that fails goes back to the implementer with its output, as any failed check does. If the merge doesn't go through mechanically, it goes back to `implementing` with the "merge origin/<base> into your branch" instruction. It counts against `maxConflictRounds` too; once the count is reached, a PR that is only behind merges as it is. A main sync is never updated this way. If it can't tell (the fetch failed, or the PR's head isn't there), it merges as it is and GitHub's mergeability decides. Otherwise it lands the PR the way the project's GitHub workflow says ([github-workflow.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/github-workflow.md)): `gh pr merge --squash --delete-branch` only for the pattern that still squash-merges into the base branch. It never git-pushes the protected branch. GitHub Flow enables auto-merge and waits in `awaiting_merge`; it does not squash-merge onto that branch itself. Auto-merge is only turned on once the PR is up to date (above), and if the base moves while it waits (someone merged around the queue), it is turned off again (`gh pr merge --disable-auto`) and the item goes back to `merging` to be brought up to date and checked again. A finished pull request waiting on a person is squash-merged from the merge control instead (github-workflow.md section 8.1), the same `gh pr merge --squash --delete-branch` into the protected branch. The orchestrator does not press it. |
| `awaiting_merge` | orchestrator | The PR is open and the review has passed, and GitHub or a person has not merged it yet (github-workflow.md section 8). It holds no lane. When a person is the one who lands it, the merge control in section 8.1 of that spec is how it gets merged. A merged PR continues as a successful merge. A PR closed without merging goes to `needs_human`. |
| `merged` | orchestrator | Frees the lane (its worktree and build output stay for the next item) and increments `slice`. The item's backlog (the store, [backlog.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/backlog.md) sections 7 and 8) is told at once, from the implementer's `itemDone` and `remaining`: done, the item is `done` here; otherwise it stays `merged` here and is back in the backlog's queue for its next slice. (Until 2026-10-04 a planner session reread the backlog file after each merge to settle it, backlog.md section 11.) |
| `done` | — | Its backlog says nothing in it is left (above). |
| `needs_human` | triage, then human | Records why in state, comments on the PR if there is one, frees the lane and skips the item. Claude looks into it first and may continue, start over or skip it itself (section 6.9); what it leaves is reported to the store, and the app's **Needs you** and bell show it. **Carry on** (Continue) picks the PR's branch up in the next free lane and re-runs the checks, keeping the PR (with notes, the implementer's session resumes there with them). Either way its review, check and conflict rounds start again. Without a PR but with a session, it resumes the session from its pushed branch. **Start this slice over** starts the slice over on a new branch (`…-s<slice>-r<attempt>`) and closes the old PR (or drops the old branch); merged slices are never touched. With nothing in flight (e.g. it hit the slice limit) the same action is labelled **Carry on** too (it was Keep going; board-attention.md section 2.9): it queues the next slice and, at the limit, raises the item's own `sliceLimit` by another `maxSlicesPerItem`. |


**Slice records** (one per started slice: state, PR, open questions, merged PR) are the store's ([slices-as-cards.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/slices-as-cards.md)). The agent reports each slice's state and PR with its `report` and `complete` calls and keeps no copy.
