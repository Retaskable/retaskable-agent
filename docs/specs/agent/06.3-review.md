### 6.3 Review

Review is layered so that Opus never reads the whole diff line by line. Each stage is cheaper than the next and filters what reaches it. A new round starts from stage 1, and every session is fresh, so it has no memory of writing the code.

**Stage 1: deterministic checks** (`checking`, orchestrator code, no model). First, when the lane has a `package.json` and needs an install (the same rule as the base checkout's, section 6.8: `node_modules/` missing, or `package-lock.json` newer than `node_modules/.package-lock.json`), it runs `npm ci` (or `npm install` without a lockfile) there with a 10-minute timeout, as that lane. A failed install counts as a failed blocking check named after the command, with its output, and the checks don't run. Then the orchestrator runs each command in `checks` (section 10) in the lane, outside the sandbox (section 4.2), with a timeout, and keeps the exit code and the last ~200 lines of output. It also collects `git diff --stat origin/<baseBranch>...HEAD`, the list of changed files, and whether the backlog file changed. If a `blocking` check fails, the item goes straight back to `implementing` with that output, and no model is spent reviewing it. Results from non-blocking checks (e.g. lint on a repo that isn't lint-clean yet) are passed on to the later stages as evidence.

**CI only once a change is ready** (`ciWhenReady`, with `requireCi`, [ci-when-ready.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/ci-when-ready.md)): a change is ready once its implementer's work is pushed. As it goes to `checking` the `ci-ready` label goes on, so CI runs beside the lane's checks and the review (since 2026-10-14; before, only after the approval). Wherever an approved item would go to `merging` (the review approved it, its playtest passed or was deferred, it was already approved at this commit) it goes to `awaiting_ci` instead, and CI passing on the approved commit merges it: the lane's blocking checks, the review and CI, all on the same head. The item acts on CI only there, so a change the review sends back while its CI failed is sent back once, with both in the message (`ciFailedSoFar`), and CI's own failure only sends back an approved change. The repo's workflow has to skip pull requests without the label (this repo's `ci.yml` does, for `retaskable/` branches).

**When CI covers the checks** (`ciCoversChecks`, with `requireCi`, not with `ciWhenReady`): the PR's CI already ran the same commands, so after CI passes stage 1 isn't run again in a lane. The item goes from `awaiting_ci` straight to `reviewing`, and the scouts' and the reviewer's check results (`{{checks}}`) read "Run by CI: " and the names of the CI checks that passed (from `gh pr checks`), as does the review comment's **Checks**. A CI failure goes back to the implementer as before.

**Stage 2: scouts** (`reviewing`, cheap sessions in parallel). Each scout is a read-only session with one concern, on the scout model (section 7.1):

| Scout | Looks for |
|---|---|
| `correctness` | Logic bugs, broken edge cases, error handling, and regressions in the code the diff touches; also committed secrets, unsafe input handling and risky commands |
| `tests` | Missing or weak tests, only where a real bug could ship unnoticed without them (not trivial code, wiring or layout) |
| `spec` | Whether the diff does what the `specRefs` say, whether it changes anything marked decided, and whether the specs describe what was built (the diff adds no **Items** header or list of items to a spec, since the backlog keeps them) |

- There's no separate security scout: in its first 61 runs it found nothing, so its checklist is part of `correctness`.
- Each scout reads only its share of the diff (`git diff origin/<baseBranch>...HEAD -- <files>`). If the diff is larger than `review.maxScoutDiffLines` (default 4000), the orchestrator splits the `correctness` scout by file into several scouts, each under the limit.
- **Most diffs get no scouts.** Below `review.minScoutDiffLines` (default 2000, raised from 1000 on 2026-10-21 as slices became whole planned slices) lines, no scouts run and the final reviewer is told to read the diff itself, line by line, for all of the scouts' concerns. Scouts are for very large diffs only: measured over a week they cost about 8 times the Opus review they fed (41% of all usage against 5%), because each starts cold and re-reads the code around its share, and Opus re-checks what they find anyway.
- **A re-review only scouts what changed.** Each review records the commit it saw (`reviewedSha`) and, if it requested changes, what it asked for. The next review of the same slice scouts only the slice's files that changed since that commit, with their changes since then (`git diff <reviewedSha> HEAD`), and the small-diff rule applies to that. The final reviewer is told it's a re-review and gets its earlier requests to check. Files changed outside the slice (a merge from the base branch) are left out. If the recorded commit is no longer behind `HEAD` (a rebase), the review covers the whole diff again. Both are cleared when a new slice starts.
- **A rebase after approval isn't reviewed again if the code is the same.** An approving review records `approvedSha`. When the slice comes back to review after a rebase, the slice's changes from where it branched off to `approvedSha` are compared with those to `HEAD` (`git diff -U0`, leaving out the backlog file, with index and hunk-header lines dropped so moved line numbers don't count). If they're the same, the item goes straight to `merging`: only the backlog file, where parallel slices conflict, was touched. The checks still run after the rebase as usual. A slice that reaches review at `approvedSha` itself (Continue after a stop, or a mechanical update with `requireCi` off) merges without another review. When `merging` brings the PR up to date itself, the comparison is made there and CI passing is enough (section 5, `awaiting_ci`). Any other difference, or a commit git can't find, gets the full review. Measured over a week, 20 of 21 merge conflicts had led to a full re-review, about 30% of all review time.
- **A plain conflict merge keeps the approval** (2026-10-14: 16 changes in a day were sent back to merge the base branch in, each a full round). When an approved item is sent back only to merge the base in (`merging` found a conflict it couldn't settle), the approved commit is kept on it (`conflictOf`); going back to work for anything else since (checks or CI red, a review, Continue, answers) clears it. If, back in review, the slice's changes before and after differ only by a resolution, it isn't reviewed again: the two patches above, file by file, may differ by at most `RESOLUTION_MAX_LINES` (12) changed lines (`patchDrift` in `agent/src/git.ts`: the base's new version of a line both sides changed, and the merged line), touching the same files the same way, with no binary file. Its checks ran again on the merge and CI runs on it, so it goes on to `awaiting_ci` (or `merging`) approved at the new head. More than that, a file added or dropped, or any doubt, is reviewed as above.
- **Reviews go first for a session slot.** Scouts and the final reviewer queue ahead of implementers waiting for a slot (in order among themselves), so finished work is reviewed and merged before more is written.
- **A review that can't start yet waits unannounced.** While no session may start (the usage limit, a restart finishing a merge first, `sessionMayStart`), the review step leaves the item in `reviewing` as it is and tries again on a later tick; its "Review round N" note is written only once it can start. Before (2026-10-14), it noted the round and then waited for a slot; Restart when idle then restarted the agent and the step began again, so the round showed twice, 3 to 22 minutes apart, with one review run.
- All scouts share `prompts/scout.md`, and each one's focus and instructions come from `prompts/scouts.json`. Every finding must cite a file and line and quote the code as evidence, and scouts are told not to report style.
- Scouts run in parallel, but they count toward `concurrency` like any other session.

```
claude -p "<rendered prompts/scout.md>" \
  --model <scoutTier> \
  --permission-mode auto \
  --disallowedTools "Edit Write NotebookEdit" \
  --output-format stream-json --verbose \
  --json-schema '<SCOUT_RESULT_SCHEMA>' \
  --max-budget-usd <budget.scoutUsd>
```

`SCOUT_RESULT_SCHEMA`:
```json
{
  "findings": [{
    "severity": "blocker | major | minor",
    "file": "string",
    "line": "number",
    "evidence": "string",
    "body": "string"
  }],
  "notes": "string"
}
```

**Stage 3: final review** (`reviewing`, one Opus session). This session gets:
- the item, its `specRefs` and the implementer's `sliceDescription`
- the stage 1 results and the diff stat
- every scout's findings
- the User Manual versions the product owner has signed off (the store's `manualApprovals`, which the agent asks for again just before the review: [last-local-state.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/last-local-state.md) section 3.1; as "<version>, approved <date> by <login>" lines, or "(none)"). If the diff adds or changes a revision in `app/src/manual/manual.ts` whose id isn't in that list, it says in `summary` that the product owner hasn't signed off that experience yet. That is a note only: never a reason to request changes or ask for a human, and the result schema doesn't change

It is told to **verify, not re-review**. It confirms or throws out each finding by reading only the cited lines and the code around them. It also spot-checks what the scouts can't see: whether the slice as a whole makes sense, and whether it fits the rest of the codebase. It reads the full diff only if the findings contradict each other or a whole file needs judging. It decides the verdict.

```
claude -p "<rendered prompts/reviewer.md>" \
  --model opus \
  --permission-mode auto \
  --disallowedTools "Edit Write NotebookEdit" \
  --output-format stream-json --verbose \
  --json-schema '<REVIEWER_RESULT_SCHEMA>' \
  --max-budget-usd <budget.reviewerUsd>
```

`REVIEWER_RESULT_SCHEMA`:
```json
{
  "verdict": "approve | request_changes | needs_human | person_steps",
  "personSteps": ["string"],
  "summary": "string",
  "comments": [{ "file": "string?", "line": "number?", "body": "string" }],
  "dismissedFindings": [{ "scout": "string", "file": "string", "line": "number", "reason": "string" }],
  "playtest": { "what": "string", "steps": ["string"] }
}
```

The orchestrator posts the review to the PR as one comment through `gh pr comment`, because GitHub won't let you approve your own PR. The comment includes the check results, the confirmed findings and the dismissed ones, so the reasoning is on record.
- `approve` moves the item to `awaiting_playtest` if the reviewer's result has a `playtest`, and to `merging` if it doesn't. The reviewer is shown the implementer's suggested `playtest`. It keeps it, sharpens the steps, drops it, or adds one the implementer missed, and its answer is final.
- `request_changes` resumes the implementer with the comments and increments `reviewRound`.
- `person_steps` (2026-10-12, [board-attention.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/board-attention.md) section 2.1): the slice is right, but only a person can do what's left before it merges (an account, a secret, a setting in production). The item waits for `personSteps` as the implementer's `person_steps` do (section 6.2, `waitForSteps`), its PR kept and the steps in the review comment; **Done: finish it** then merges the reviewed commit as an approval would (`approvedSha` set to it, then `merging`, or `awaiting_ci` with `ciWhenReady`). With no steps it's `needs_human`.
- `needs_human`, or `reviewRound > maxReviewRounds`, moves the item to `needs_human`. `reviewRound` counts review and playtest send-backs only; failed CI and checks count `checkRounds` against `maxCheckRounds` (section 5), so a flaky check doesn't use up the review's rounds.

**After the merge: the staging smoke** (`agent/src/smoke.ts`). With a `deploy.staging.smoke` command (section 10) whose staging branch is the base branch, every merge (a chore's too) is checked once staging is running it:

- **Wait for the deploy.** It fetches and takes `origin/<baseBranch>`'s head as the merged commit, then asks `<deploy.staging.url><versionPath>` (default `/version.json`, which answers `{ "sha": "<commit>" }`; [cloud.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/cloud.md) section 9 for retaskable.com) every 30 seconds until staging serves that commit or one after it (`git merge-base --is-ancestor <merged> <deployed>` in the repo, fetching first when the deployed commit isn't known yet).
- **One at a time per project, newest only.** A merge while one is waiting or running replaces the commit to smoke next; older merges aren't smoked on their own, since the newer deploy has their changes.
- **Run it** in its own worktree, `<worktreesDir>/smoke`, detached at the merged commit (added once, then reused: `checkout --detach` and `clean -fd` under the same lock as the lanes, so its `node_modules` stays), after the same dependency install the baseline uses (section 6.7), with a 15-minute timeout. It never touches the planner's worktree, so the planner sync, the baseline, Play main and shoots don't wait for it. Removing the project's worktrees removes it too.
- **Status**: `State.smoke` is `{ sha, status: waiting | running | passed | failed | timeout, at, url, tail? }`, kept in the project's state and reported to the hub as a derived result (status and a failure's last lines), which the app shows as one line. A smoke cut off by a restart starts again.
- **A failure** queues a `fix_main` chore (section 6.7) whose report is staging's URL, the commit and the command's last lines; its session gets that report instead of main's checks. While one such fix is open, another failure doesn't add a second.
- **No deploy within 20 minutes** is only a status (`timeout`): nothing is queued.
