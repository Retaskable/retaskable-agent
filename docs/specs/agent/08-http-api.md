## 8. HTTP API

The agent's HTTP port has the health check and, since 2026-10-22, the computer's own settings page ([agent-settings.md](../agent-settings.md) section 4, tray.md decision 8). `createApi(version, settings)` (`agent/src/api.ts`, the page's routes in `agent/src/settingsServer.ts`) listens on `127.0.0.1`, or on the local network only when the person at the computer turns network access on and sets a password, at `PORT` (the env, else the config's `port`, else 4700, or 4701 in a Staging release build, [installers.md](../installers.md) section 8.1). It never listens on a public port: the cloud link is outbound only.

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/health` | `{ ok: true, version }`, `version` the agent's package version, so a script or a person can ask whether the agent is running |
| GET | `/settings` | the settings page (`agent/settings.html`), plain HTML and a little JS |
| POST | `/api/settings/session` | signs in: `{ token }` from the tray's link, or `{ password }` with network access on |
| GET / POST | `/api/settings` | the computer's own settings, read and changed (agent-settings.md section 3) |
| POST | `/api/settings/restart` | restarts the agent, for a new port or network access |

Every other path answers 404 `{ error: "Not found" }`, and none of them runs a command. The port serves no app build, no snapshot (`/api/state`) and no event stream (`/api/events`): retaskable.com is the only screen.

A request that fails one of section 4.3's checks on the TypeScript agent gets a 403 naming which check failed (a bad Host, a bad Origin, or a bad CSRF token). This Rust agent instead answers a bad Host or Origin with the same blanket 404 as an unknown path, a deliberate difference: it would rather not confirm to a caller that the settings page exists at all. A bad or missing CSRF token still gets its own response, 401 rather than the TypeScript agent's 403, with its own wording.

Everything else the agent does for a person comes over the outbound cloud link, as one of the commands the website can send ([cloud.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/cloud.md) section 6), each of which the agent checks itself. The site reads the snapshot and the live session events over the same link. The agent has no route for any of them.

- **Commands that run something on the machine** (Play, Promote, Go live, Restart, linking and unlinking a project) are on the same list, and the agent checks each one before it runs ([cloud.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/cloud.md) section 6.1; the tray's own allow step, [tray.md](../tray.md) section 5.1).
- **A shared project's own commands** (checks, Play, CI, the staging smoke) are no request since 2026-10-22: a new version of them waits in the snapshot (`commandsWaiting`) until the computer's owner approves it on the site, freshly signed in (`approve_commands`, cloud.md section 6.1, [project-settings-on-server.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/project-settings-on-server.md) section 3.3), and until then the agent runs the ones it ran (`agent/src/allowedCommands.ts`).
- The tray helper speaks JSON over stdin and stdout, and the tray, the console and `npm run link` call the orchestrator in process. Without a desktop (`--no-tray`, no `DISPLAY` on Linux) and with a terminal on stdin and stdout, or with `--tui` / `RETASKABLE_TUI=1`, the tray's menu is drawn in the terminal instead, full screen, with the console's last lines under it ([tray.md](../tray.md) section 4.7).
- A restart exits with code 75 (section 4.2: now, finishing a merge first), and `agent/scripts/supervise.mjs` (what `npm run dev` and `npm start` run) starts it again with the current code; a release build, which has no supervisor, starts its next copy itself ([installers.md](../installers.md) section 3.8). This Rust agent exits with the same code for the same restart request, but nothing yet relaunches it afterwards: it has no supervisor script and doesn't start its own next copy, so a restart from its settings page currently just stops the process until something outside it (a person, a service manager) starts it again.
- The commands that send text to Claude can carry `pictures`, which the agent saves in `.retaskable/attachments/` (`agent/src/attachments.ts`) and whose paths it adds after the text, under "Attached images (look at each with your Read tool before acting on this)".
- **[Proposal] The approval gate in this Rust agent .** `src/allowed_commands.rs` ports `agent/src/allowedCommands.ts`. For a shared project, the commands in the store's project settings (`checks`, `playCommand`, CI, the staging smoke and the deploy; the exact list is `allowedCommands.ts`'s) are not run as read. The agent keeps, per project, the set it **has allowed** — the last version the computer's owner approved, kept in the project's own state so a restart does not lose it. A version read from the store that differs from the allowed one is **waiting**: the snapshot's project carries `commandsWaiting` (which commands, and the new text for the site to show) and everything that runs a command (a lane's checks, Play, CI, the smoke, a promote) uses the allowed version. The first read of a project with nothing allowed yet allows nothing: a project's commands do not run until they are approved, and the checks that need them wait or are skipped as with an empty command. `approve_commands { project }` marks the waiting version allowed; the hub only sends it after the owner has signed in freshly, and the agent nacks it from anyone else (`issuedBy` is not the computer's owner), when nothing is waiting, or when the version has changed since the site showed it (it carries the version it showed; **[Proposal]** a hash of the waiting commands). A change to the store's commands while one is waiting replaces what waits. A project that is not on a shared backlog has none of this (there is no such project: every project has a shared backlog). Tested: a changed command waits and the old one still runs, `approve_commands` makes it run, a stale approval is a nack, and a restart keeps what was allowed.

- **The approval gate's wiring (per project).** Each project's loop reads `settings_get` on every pass that reads the backlog and gives the record to its `CommandAllowing` (`src/command_gate.rs`, one per project, loaded from `allowed-commands.json` and reachable through `AgentView.item_commands.gates()`). A failed read changes nothing. Until the first read answers, nothing is allowed. Everything that runs a command takes its `ProjectConfig` from `ItemCommands::allowed_config` (the loop's own project, the CI loop's config) or `allowed_view` (Play main, a lane's Play in `commands.rs`), which lay `allowed_commands::with_allowed` over config.json's. The snapshot's `state.commandsWaiting` is `{ version, text, by }` from the project's `CommandAllowing::waiting()` while a version waits, and absent otherwise; a change in what waits (starts, is replaced, is approved) sends the snapshot again over the open connection. `approve_commands { version }` (`commands.rs`) calls the project's `CommandAllowing::approve(version)`: it acks once the allowed file is saved and wakes the project's loop, and nacks when `version` is missing or not a number, when `issuedBy` is not the login of this computer's `gh` (`repo::github_login`, read once and kept on `AgentView`; unknown is a nack), or when nothing waits or `version` is not the waiting one (`NOT_WAITING`). The version is the store's `commandsVersion`; the hash of the waiting commands is not built.
- **[Proposal] The agent has no rollout of its own (catch-up piece P8, TypeScript #3349 and #3209).** The server does the rolling out of a release, so the agent drops what it kept for one. `src/allowed_commands.rs` keeps `deploy.production.rollout` among the commands to approve, with its `machine` left out; the owner's approval text is just `traffic <cmd>, health <cmd>` (no minutes, and a saved `site` is not shown): the `traffic` and `health` commands the store's rollout has this computer run are approved on the site like the other commands, then laid over `deploy.production.rollout` of the project's config (`with_allowed`; with a store record and nothing allowed they are empty, so nothing runs). The per-computer rollout runner is not in this Rust agent and is not to be added; what the computer does for the store's rollout (report, poll, run `promote`, `traffic` and `health`) is [rollout-on-server.md](../rollout-on-server.md). Orphan items, orphan drafts and the merge batch are not in it either: the orphan offers went with the offers (agent/09.3, catch-up piece P7), and a merge is one change at a time (`src/merge_update.rs`, `src/orchestrator/merge_run.rs`), which stays as it is. Tested: `rollout/tests.rs` (the loop against fakes) and `allowed_commands/tests.rs`. Ends with `cargo fmt`, `cargo clippy --all-targets -- -D warnings` and `cargo test`.
