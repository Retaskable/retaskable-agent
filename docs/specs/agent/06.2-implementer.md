### 6.2 Implementer

The orchestrator does this first, outside Claude: it takes a free lane and resets it onto a new branch (section 4.1).

Invocation (with the lane's worktree as cwd):

```
claude -p "<rendered prompts/implementer.md>" \
  --model <tier> \
  --permission-mode auto \
  --output-format stream-json --verbose \
  --json-schema '<IMPLEMENTER_RESULT_SCHEMA>' \
  --max-budget-usd <budget.implementerUsd> \
  --max-turns <maxTurns> \
  --strict-mcp-config [--mcp-config <cwd>/.mcp.json] \
  --session-id <uuid>
```

Every Claude session runs with `--strict-mcp-config`, and with the project's own `.mcp.json` passed back in when it has one, so a session loads only the project's MCP servers, never ones from the user's own Claude Code config ([engines.md](../engines.md) section 3.4). Every Anthropic session's environment also has `ENABLE_CLAUDEAI_MCP_SERVERS=false` (no claude.ai connectors), `CLAUDE_CODE_AUTO_COMPACT_WINDOW=200000` (Claude Code compacts the conversation once it reaches 200k tokens, even on a 1M-token model) and `CLAUDE_CODE_SUBAGENT_MODEL` (`sonnet`, or `haiku` in a Haiku session; `sessionEnv` in `agent/src/engines/claude.ts`).

The prompt includes the item's title, `remaining` and `specRefs`, the slice number, and the repo's CLAUDE.md conventions. A fresh session's prompt ends with **Where to start** (`agent/src/startFiles.ts`). It lists, at most 15 in all, the item's spec files, then the files its earlier slices changed (commits on `origin/<baseBranch>` titled `<item id>:`), then the code its specs name, with the ask to read the ones it needs together, several Read calls in one message, before searching.
- **The code its specs name:** the backticked paths in the sections the item's spec links in the backlog store point at (`Specs: section 5.6; [b.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/b.md) section 3.3`, a bare "section" being the line's own spec; a section runs to the next heading at its level or above). When the line names no section, or the spec has no line for the item, the whole spec's paths, but only if it names 15 or fewer. Only files that exist, from the repo root or the spec's folder.
- **Changed since its specs last did:** under its own heading, at most 10 commits on that code since each spec last changed, newest first, so the spec check (below) starts from them instead of searching the log.
- **Why:** on 2026-10-16 sessions took a median 24 reads and searches, 3.7 minutes, before their first edit, each a round trip to the model. On 2026-10-20 (`npm run start-report`, 20 sessions) it was a median 19 turns of 54 and 36% of the session's cost before the first edit, with 92% of those turns making a single call, most of them looking for where something lives.
  - **In this Rust agent**, `src/implementer/start_files.rs` ports this "Where to start" build. `item_spec_files` keeps the item's existing `spec_refs` that are markdown, resolved from the repo root, each once. `named_code_paths` reads a spec's backticked paths; because this agent's `Item` carries no section data for its spec links, every spec is the "names no section" case, so it's the whole spec's paths, only when there are 15 or fewer, resolved from the repo root or the spec's folder. `slice_changed_files` runs `git log --name-only` on `origin/<baseBranch>` for commits titled `<item id>:` and lists their files once each. `changed_since_spec` reads a spec's own last-changed date (`git log -1 --format=%cI` on the spec path) and then, at most `MAX_CHANGED_COMMITS` (10), the commits since that date that touch its named code. `build` runs all three against a `git_bin` and caps the combined file list at `MAX_FILES` (15); `render` writes them as the "Where to start" and "Changed since its specs last did" markdown sections. Nothing calls it yet: the prompt template, `IMPLEMENTER_RESULT_SCHEMA`, and the session that runs with them are later slices.

**Its first job, every time, is to bring the spec up to date.** Work often lands without a spec update, so before planning anything the implementer checks the item's backlog entry and linked specs against the code. It uses `git log` since each spec last changed, and searches for the things listed as remaining. It corrects anything stale "as built" as the first commit on its branch. Then it plans its slice from the corrected picture. If nothing is left, the PR is just the spec update, with the item marked done. It reports `specWasStale` and `specNotes`, which go in the item's timeline, and the spec scout flags any spec that's still stale after the PR.

Then these rules:
- Pick the next coherent, reviewable slice of the item's remaining work, in the order the specs suggest. If the whole item fits in one PR, do it all.
- Work only in this worktree and branch. Never push to the base branch, and never push to the protected branch when the GitHub workflow names a different one ([github-workflow.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/github-workflow.md)).
- Before committing the slice, run whatever tests work in your environment (e.g. `cargo check`, `cargo test`). The orchestrator's checks run the full suite outside the sandbox once you return, including the game's headless `--verify` runs, and send any failures back to you. Never launch the game in a window yourself (the prompt says the project type's noun, [project-types.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/project-types.md) section 4): if a change can only be judged by playing, say so in `playtest`. The PR body lists what you ran and the results. Since 2026-10-16 the session runs only the tests closest to its change and a quick type check, never the full suite: the checks that follow run it (`prompts/implementer.md` rule 3).
- In the same PR, update any spec the slice changes to describe what is now built. Mark the item done only if nothing in it is left. The prompt names no backlog file ([backlog.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/backlog.md) section 7), for every item whether or not it holds a lease: the implementer updates only the specs and returns `itemDone` (nothing is left) or `remaining`, which the agent reports to the store when the slice merges.
- If the slice changes something a player can see or feel (new behaviour, visuals, controls, feel, balance), fill in `playtest`: `what` to look at, in a sentence, and the `steps` to get there from launch (e.g. "Start `--play`, walk to the crash site, press G"). Leave it out for refactors, docs, and anything the checks already fully prove.
- Commit on the branch and return `changeTitle` (with the item id and title in it) and `changeBody`; never push or open the PR. The agent pushes the branch and opens its PR through the project's code host, or finds the one already open for the branch and has just pushed to it (`publishChange` in `agent/src/codeHost/index.ts`, [code-storage.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/code-storage.md) section 3.1). Every follow-up (CI, checks, review, a conflict, a playtest) likewise says "commit, and return the result again", and the agent pushes after each.
- If the task is ambiguous, or it would change something the specs mark as decided, don't guess. Stop and return `needs_clarification` with specific questions, each with 2–4 suggested options where possible.

`IMPLEMENTER_RESULT_SCHEMA`:
```json
{
  "status": "pr_opened | needs_clarification | failed | nothing_left | person_steps | waits_on",
  "personSteps": ["string"],
  "waitsOn": ["string"],
  "changeTitle": "string?",
  "changeBody": "string?",
  "summary": "string",
  "sliceDescription": "string",
  "specWasStale": "boolean?",
  "specNotes": "string?",
  "itemDone": "boolean?",
  "remaining": "string?",
  "playtest": { "what": "string", "steps": ["string"] },
  "questions": [{ "header": "string?", "question": "string", "options": ["string"] }]
}
```

**Nothing left** (`nothing_left`, 2026-10-11, the human: "if there is a clear recommendation why isn't it doing it automatically"): on a shared backlog, when the specs on the base branch already describe the whole item as built, or name the later item that now has the rest, there's nothing to change and no PR to open. Before this the implementer could only say `failed` ("nothing to implement"), which stopped the item for a person. Now the orchestrator, in plain code (`nothingLeft` in `agent/src/steps.ts`), closes any pull request still open for the item, unmerged, with a comment saying why, frees its lane, and completes it in the store as built at the base branch's head, as a merged slice would (`HostedWork.sliceMerged`). A chore is dropped. An item this agent holds no claim on in the store stops for a person, saying so. Setup only a person can do isn't nothing left: that's still `failed`, naming what they must do. The prompt's `{{nothingToChange}}` asks for it, and not to ask a question the specs already answer. Tested in `agent/src/ciWhenReady.test.ts`.

**Waiting for a person's steps** (`person_steps`, 2026-10-12, the human: "This is really confusing and annoying, why does it get stuck like this?" and "i have done all the steps so thats why its confusing"): when all of an item's code is on the base branch and only steps a person can do are left (an account, a secret, a setting in production, an invitation), the implementer opens no PR and returns them, one short sentence each. Before, it could only say `failed`, so the item showed "Implementer gave up" with Carry on and Start this part again, which ran it again to the same end, and nothing to say the steps were done. Now the item stops (`waitForSteps` in `agent/src/steps.ts`) with the steps in its `needsHumanReason`, in the one shape `shared/personSteps.ts` writes and reads (so the store needs no new field), and isn't triaged. The app shows **Waiting for your steps**, the steps numbered, and **Done: finish it** in place of the reason and its buttons. That sends `finish_steps` (cloud.md section 6.1): the agent takes the item over if another computer holds it, checks it is waiting for steps (or needs help with nothing on a branch, `canFinish`, [board-attention.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/board-attention.md) section 2.1), and completes it in the store as built at the base branch's head, as nothing left does; steps the reviewer left on a PR (section 6.3) merge it instead. A note saying the steps are done (Carry on) is believed: the implementer says so in the spec and finishes the item. Tested in `agent/src/ciWhenReady.test.ts` and `shared/personSteps.test.ts`.

**Waits on another item** (`waits_on`, `waitOn` and `waitableText` in `agent/src/steps.ts`): when the item can't be built until **another item in the backlog** is built first (it needs code or infrastructure that item brings, which isn't on the base branch yet, so building it here would mean doing that item's work), the implementer opens no PR and returns `status: "waits_on"` with `waitsOn`, the ids of those items — only ones a fresh session's prompt named under **Items not built yet** (the backlog's other items not yet built, for this purpose), never one this item could do itself — and `summary` saying what it needs from each. The orchestrator then tells the store the item depends on them (`depends`) and gives its lease back, unclaimed, until they're built; without a lease to give back (a change is already open, or it's a chore), or when the store refuses the ids, a person decides instead (`needsHuman`). Tested in `agent/src/steps.test.ts`.

**Code gates before the push** (2026-10-20, the human: "an automatic 1000 line file size checker ... and also the dedupe ... built into Retaskable and run before a PR"). On `pr_opened`, before the agent pushes, plain code (`agent/src/codeGates.ts`, `codeGates(cfg, laneDir)`) checks the lane's committed change against the base branch (`git diff -U0 <base>...HEAD`). It runs on every round, so no later round can grow a file or copy code in, and on every chore except a main sync, which only merges main in.
- **Which files count.** Only source files count (`isSource`: code extensions, not `node_modules/`, `vendor/`, `dist/`, `build/`, `.min.`, `.d.ts` or `.generated.`). Markdown, JSON and other assets never do, except specs for the spec size check below.
- **Size.** Every source file the change touches must be at most `codeGates.maxFileLines` lines (default 1,000). That includes files that were already over it before the change: touching one means splitting it.
  - The message names each file with its line count.
  - For the first three split points it names a top-level declaration near equal parts, as the place it could split.
- **Copies.** Runs of `codeGates.dupLines` (default 8) consecutive meaningful lines that the change added must not already be somewhere in the project's tracked source files. That covers an existing file, elsewhere in the same file, or a second new copy.
  - Meaningful lines are trimmed with their whitespace collapsed. Lines with fewer than three word characters, comments, imports and re-exports are left out.
  - Tests are left out on both sides, as their setup repeats on purpose, and so are files over 1 MB.
  - Overlapping runs merge into one range (`new.ts:4-13 repeats old.ts:2-11`), at most five are listed, and a copy where both sides are new is listed once.
  - Code that was moved rather than copied passes, since the old place no longer has it.
- **Spec size** (2026-10-22). Every spec the change touches (`isSpec`: `specs/<name>.md`, or a split spec's section file `specs/<name>/<file>.md`) must be at most `codeGates.maxSpecChars` characters (default 40,000), counted with line endings as one character so it's the same on every computer. A big spec is split as section 6.10 says.
  - The message names each spec with its size, and up to three `##` headings (`###` in a section file) near equal parts, as the places it could split.
  - It says how: break it into a folder `docs/specs/<name>/` with one file per top-level section (`NN-<slug>.md`), keep `<name>.md` as a short index listing each section's number, title and link so "<name>.md section 7" still resolves, move text only, and split a section file still over the limit the same way at its `###` headings (`NN.M-<slug>.md`).
- **What a finding does.** It sends the session back (`sendBack`, kind `checks`) with the findings and "Fix them, commit, and return the result again". It counts against `maxCheckRounds` like failed checks, and nothing is pushed. The timeline says "Code gates: 1 file over 1000 lines (src/big.ts) and 2 copied blocks".
- **If the gates can't run** (a git error), that's noted and the push goes ahead.
- **The prompts say so up front.** The implementer's and chore's "Stay in your lane" rules carry the limits (`{{codeLimits}}`, `gateRule`), so a session doesn't spend a round finding out.

**Follow-ups** (answers, CI failures, review feedback, rebase) all use
`claude -p "<follow-up>" --resume <sessionId> ...same flags...` in the same worktree, so the implementer keeps its context. `<tier>` is picked fresh for each follow-up (section 7.1), so a resumed session can step down or back up a model. A Cursor implementer resumes with `cursor-agent --resume` on the chat it started (saved before the process is spawned, so a restart resumes it), and starts a fresh chat when the item has moved to another lane ([engines.md](../engines.md) section 3.3). A spec draft keeps its chat id the same way.

**A session that's grown starts fresh** (2026-10-22: every turn re-reads the whole conversation, so a resumed session that had grown to a few hundred thousand tokens cost that much again on each turn of every follow-up). Each Claude implementer session's size, its last main-thread turn's input plus cached tokens (`contextTokens` from the reader; a subagent's turns don't count), is kept on the item as `implContextTokens`. A follow-up for a session over `maxResumeContextTokens` (default 150,000) starts a fresh session on the same branch instead of resuming. Its prompt opens **You're picking up an existing PR** (or **earlier work**, before a PR): the branch already has commits, so read the diff with `git diff --stat <base>...HEAD` first and then only the files that matter, then the follow-up itself. The timeline says "Its session had grown to N tokens; starting a fresh one". The size is cleared whenever the session is.

**At most `maxTurns` turns** (default 300, `--max-turns`): a session that loops ends with `error_max_turns` rather than running up its budget. Its session id is kept, and the item's follow-up is set to "An earlier session ran out of turns before it finished. Check `git status` and `git diff --stat` for its uncommitted work, then carry on with the slice." So the next step (after a restart too) starts a fresh session with the picking-up prompt in the same lane, keeping any uncommitted work. A fresh session that also runs out of turns goes to `needs_human` ("Implementer ran out of turns (300) twice in a row").

**Fresh-start rules on resume (this Rust agent, item `resume-fresh-start-rules`).** A follow-up resumes the item's session by id. It starts a fresh session on the same branch instead, with the picking-up prompt and a line in the item's history saying why, when any of these holds. The first is built (`No conversation found`, from PR #148); the rest are to build, with the TS rules (`steps.ts`, `startFresh`) as the reference.
- **Claude Code has no such conversation** ("No conversation found with session ID"): the session was stopped before Claude Code saved it. A fresh session picks up the branch if there is a PR, and starts the slice over if there is not.
- **The transcript is too big.** The item keeps `implContextTokens`, the last main-thread turn's input plus cached tokens. A follow-up for a session past `maxResumeContextTokens` (default 150,000) starts fresh. The timeline says "Its session had grown to N tokens; starting a fresh one". The size is cleared with the session.
- **It ran out of turns.** A session that ends `error_max_turns` keeps its id, and the follow-up becomes "An earlier session ran out of turns before it finished. Check `git status` and `git diff --stat` for its uncommitted work, then carry on with the slice." The next step starts fresh in the same lane, keeping uncommitted work. A fresh session that also runs out goes to `needs_human` ("Implementer ran out of turns (300) twice in a row").
- **The engine changed since the session started.** The session's engine is kept with its id. A session resumes only on the engine it started on. It starts fresh when the lane now has an engine of its own that differs, when the engine it started on is at its usage limit and another can take it, and always for pi and Codex, which cannot resume (engines.md sections 13 and 14). Each has its own line in the history.
- Starting fresh clears `implSessionId`, `implContextTokens` and the resume marker. A follow-up that was not just "interrupted" is kept. These need the machine's `maxResumeContextTokens` and `maxTurns` settings in the config.

**Results the orchestrator acts on (this Rust agent, item `item-waits-and-finishes`).** The schema and parsing of `waits_on` and `nothing_left` are built (`implementer/model.rs`). Acting on them is not.
- **`waits_on`.** The orchestrator checks that every id in `waitsOn` is an item the store has that was named under "Items not built yet" in the prompt. It sends `depends { id, add: [ids] }` and then gives the item back (section 7.5), noted with the result's `summary`, so it is not claimed again until those items are built. If the item has no lease to give back (a change is already open, or it is a chore), or the store refuses any id, the item goes to `needs_human` instead.
- **`nothing_left`.** The orchestrator closes any pull request still open for the item, unmerged, with a comment saying why, frees the lane, and completes the item in the store as built at the base branch's head, as a merged slice would. A chore is dropped. An item this agent holds no lease on stops for a person, saying so. `person_steps` is not part of this item.
