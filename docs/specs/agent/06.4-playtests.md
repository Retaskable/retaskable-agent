### 6.4 Playtests

A playtest is how Retaskable asks you to test the game: only when a slice is actually testable by playing, and only after the checks and the review have passed, so your time goes on feel and correctness a test can't judge. **By default (`playtests: "after_merge"`) what you playtest is on `main`:** an approved slice merges first, and you play the base build. `playtests: "on"` is the opt-in alternative that asks before merging, on the PR's branch.

- The agent records the playtest in the store with what to look at, the steps and the PR link, and a **Play** command (section 4.2) is ready for it. How it is shown (the bell, **Needs you**, the counts and the page title) is the app's.
- You answer **Looks good**, or **Problem** with notes. A problem resumes the implementer with the notes and the steps, the same as review feedback, and the slice goes through checks and review again before it comes back to you.
- A playtest never times out, and it has no model cost while it waits. It holds no lane (section 4.1), not even while you play it (the play checkout, section 4.2), so other work keeps flowing however many pile up.
- `playtests: "off"` in the config skips them entirely (every approved slice merges straight away), for repos with nothing to play or a product owner who doesn't want to try each one. Switching to it releases anything already waiting for a playtest: it merges with no playtest asked for, now or later (`releasePlaytests`).
- `playtests: "after_merge"` defers them instead: an approved slice merges straight away, and its playtest waits in the store's try-out queue, played with **Play main** (the base build now has the change). **Looks good** clears it. **Problem reopens the item itself** (`agent/src/reopen.ts`): the agent sends the store a `reopen` (backlog.md section 6.2) with the try-out's notes, and the store puts the item back in the queue, first, with its next slice's `remaining` made from the person's words and the try-out's, and records `reopened { notes, at, by }` on it, so its history and chat stay one card; what the card then shows and how release notes count the fix are the store's and the app's. The computer that built it takes it in the same operation (`reopen` with `agent`) and resumes the session that built it on a new branch (below). The fix's merge clears `reopened`. An item that can't be reopened (it's being built: claimed, in review, merging or waiting for a person), a chore's own try-out, and a store that doesn't know `reopen` queue a **playtest fix** chore with the notes and steps instead, which unlike other chores can ask the human questions; so the person's report is never lost. Switching to this mode releases anything already waiting for a playtest.
- **Grouped into sessions.** Once 4 or more are waiting, a small read-only Sonnet session (prompt `prompts/playtest-groups.md`) sorts them into themed sessions of about 3–6 checks each, by where in the game they happen, ordered to flow in one play-through. Every playtest lands in exactly one group (anything left out goes to "Other"). It regroups when the queue changes, at most every 30 minutes. The agent sends the grouping to the store (`tryout_groups`); how the app shows it is the app's.
- **On a shared backlog the queue is the team's** ([team-state-on-server.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/team-state-on-server.md) section 3.2): each computer sends its after-merge playtests to the store (`tryout_add`), an answer goes to the store (`tryout_result`), and the grouping runs on one computer at a time under the store's `tryout-groups` lock. A problem comes back to the computer that built the slice (`tryout_problem`), which takes it, reopens the item and resumes its session as below; with that computer offline the store reopens the item itself, first in the queue for any agent to claim (a fix item "Fix: <title>" only when the item is being built). With `playtests: "on"`, a slice waiting in `awaiting_playtest` goes in the store's queue too, marked `onBranch` (its branch and approved commit); it's still answered on the item, and the answer is recorded on its row.
- **A problem goes back to whoever built it.** When a slice merges, Retaskable records its implementer session and lane with the deferred playtest. A reopened item resumes that session once, on its new branch, told the item is reopened and this slice is the fix (`resumeForReopen`), its PR titled "<id>: Fix: …"; a later slice starts its own session. A playtest fix chore waits for that lane (a session resumes only from its own folder), resets it onto a new branch from the base, and resumes the original session with the report. If the lane stays busy for 10 minutes, or the session can't be resumed, it starts a fresh session with the report instead.

**In this Rust agent.** When config.json's `playtests` (not a settings overlay) is `"off"` and the value the project last saw was something else, the agent owes the store a `release_playtests` for the project, so every item in `awaiting_playtest` and every try-out in the store's queue is let go and merges with no playtest asked for. The last value seen and the debt are kept in memory only, not in the state file; the send is made from `flush_owed`, cleared when the store takes it, and sent again on the next pass when it fails. Every pass records the value, so Off → On → Off sends twice. A first run with nothing remembered and `"off"` already set sends nothing.


**The grouping round, as built in this Rust agent** (2026-11-13; `src/playtest_groups.rs`, `src/orchestrator/driver/playtest_round.rs`; the numbers are the TypeScript agent's `agent/src/playtestGroups.ts`).

- **When it runs.** Once a minute, right after the loop's pass (`Machine::playtest_rounds`), for every project that is live (or in `runs` mode), not paused, ticked this pass, and whose `playtests` isn't `"off"`. A round still running for a project makes the next minute's skip it, so there is never a second one on top.
- **What it reads.** `tryouts_list` from the store. Only the entries with no `onBranch` are grouped (a `playtests: "on"` slice waits on its own branch and is answered on its item). A project with no repo id, no backlog link, or an unreachable store skips the round and tries again next minute; a failed read is logged, never raised.
- **The gate** (`should_group`). Fewer than `MIN_TO_GROUP` = 4 waiting: nothing. Nothing sent yet: group. Otherwise the waiting keys' **signature** (every key, sorted, joined with `|`) must differ from the last grouping's, **and** `REGROUP_EVERY_MS` = 30 minutes must have passed since it. An unchanged signature never regroups, however long ago the last round was, so a long quiet queue costs no session.
- **The lock.** The round takes the store's `tryout-groups` lock first, so one computer groups at a time: `chore_lock` in `claim` mode; in `runs` mode a `lock_take` held with the project's other locks and beaten with them. A lock held by another computer ends the round quietly. The lock is dropped once `tryout_groups` has been sent or the round gave up. A `runs`-mode lock that was lost mid-session (its beat failed) means nothing is sent, so a stale grouping never overwrites a newer one.
- **The session.** One ephemeral, read-only session on the `planner` role (the chosen engine, model `sonnet`, `budget.plannerUsd`, the engine's own sandbox) in the project's checkout, with `prompts/playtest-groups.md` filled with the project's words and one block per waiting playtest (key, item id and title, what to check, its steps joined with " / "). It is listed on the settings page's Now tab while it runs. A planner engine whose binary can't be found skips the round without failing it.
- **What's trusted.** The answer is read through a schema (`groups: [{ title, why, keys }]`) and then **cleaned** (`clean_groups`): a key the session didn't get, or already used by an earlier group, is dropped; a group left with no keys is dropped; a blank title becomes "Playtests"; anything left over lands in a final group "Other" ("Not grouped with the others."). So every playtest is in exactly one group however the model answered. A session that fails, runs out of budget or gives no usable grouping sends nothing and logs why; the same signature is retried on the next minute's gate, since nothing was recorded.
- **What goes up.** `tryout_groups` with the signature of the keys that were read and the cleaned groups, in order. How the app shows them is the app's.

**A person's answer, as built.** An answer to a try-out in the store's queue (the item isn't one this computer runs) is kept owed in the project's state (`unanswered`) and sent with `tryout_result` (`passed` or `problem`, with notes), looked up by the try-out's key or its item id. An answer whose try-out is no longer waiting is dropped and logged; one the store refuses or can't be reached for stays owed and is sent again on a later pass, so a person's answer is never lost. What follows a **Problem** is the store's: it forwards `tryout_problem` to the computer that built the slice, or reopens the item itself.

**Not built in this Rust agent yet** (the code's own notes say the same): sending `tryout_add` when a slice merges, since this agent's loop doesn't merge items yet, so nothing of its own is in the queue; and acting on a `tryout_problem`: `src/reopen.rs` holds the pre-filter (`may_reopen`: never for a chore's own try-out, and the store has the final say) and the message a resumed session gets (`resume_for_reopen`), but nothing calls the store's `reopen` or resumes the session, and the playtest-fix chore fallback isn't ported.
