### 9.1 What the computer works out for a project's settings

Setting a project up is the site's project settings ([project-settings-on-server.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/project-settings-on-server.md)); the computer supplies what only it can see:

- **The repo.** A local folder, or one of the person's (and their GitHub organisations') repos from `gh repo list`, with the checkout found or cloned. `githubRepo` comes from the `origin` remote with `gh repo view --json nameWithOwner`. It reports why a folder won't do: not a git repo, no GitHub remote, `gh` not authenticated, the integration branch (`dev/<login>`, `develop`) couldn't be created, a backlog file that isn't on `origin/<baseBranch>`. Saving creates the integration branch when the pattern says to and it isn't on origin yet ([github-workflow.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/github-workflow.md)).
  - **In this Rust agent**, `src/repo.rs` ports GitLab and plain-remote detection (`code_host`, `remote_repo`) and the plain-GitHub half of `agent/src/setup.ts`'s `repoInfo`/`githubLogin`/`devBranch`/`createBranchIfMissing` and `agent/src/github.ts`'s `listOwners`/`listRepos`/`remoteRepo`: a local-only project and the full `GithubPicker`'s caching and clone-serialising lock aren't ported, since this agent's trimmed spec doesn't reach them yet. `repo_info(repo_path)` reads `origin` (`origin_url`, `code_host`) and, on GitHub, runs `gh repo view --json nameWithOwner,defaultBranchRef,isFork,parent`, with a fork's upstream read the same way `repoInfo`/`upstreamOf` do; on GitLab (`src/repo_gitlab.rs`) it runs `glab repo view --output json` and fills `repo` (`path_with_namespace`), the default branch and a fork's `forked_from_project` upstream with its own default branch. A plain remote is handled with git alone: `repo_info` runs no `gh`/`glab` and has no `repo` or `github_repo`, reading the default branch from `git ls-remote --symref origin HEAD`; `remote_reachable(repo_path)` is `git ls-remote origin`; `clone_remote(url, dest)` is `git clone`; `find_checkout` matches a plain-remote sibling by its `origin` URL with a trailing `/` and `.git` dropped; and there is no owner list (`list_owners`/`list_repos`/`clone_repo` refuse it). `RepoInfo.repo` is the project on either host and `github_repo` is it on GitHub only. `glab_login()` and `glab_authenticated()` read `glab api user`/`glab auth status`; GitLab `list_owners(CodeHost::Gitlab)` is the login then the groups from `glab api groups --paginate`, `list_repos` is `glab repo list` (`--mine` for the login, `--group` for a group) and `clone_repo` is `glab repo clone`. `github_login()` and `gh_authenticated()` read `gh api user`/`gh auth status`; `list_owners(CodeHost::Github)` adds the person's GitHub organisations from `gh api user/memberships/orgs`, and `list_repos(CodeHost::Github, owner)` is `gh repo list`. `find_checkout(search_dir, github_repo)` looks for an already-cloned sibling by its `origin` remote (`remote_repo`, pure, parses a GitHub or GitLab HTTPS or SSH URL, keeping every GitLab group segment, and is `None` for a plain remote)., and `clone_repo(host, repo, dest)` is `gh repo clone` on GitHub when none is found. `code_host(url)` tells GitHub (github.com), GitLab (gitlab.com or any host containing `gitlab`) and a plain remote (any other host, a path, `file://`) apart; `RepoCheck` carries it as `code_host` (`None` without an origin) and `host_cli_authenticated` (`gh` or `glab`, ignored for a plain remote). `repo_problems` says `glab isn't authenticated. Run \`glab auth login\`.` on GitLab, and a plain remote is accepted with no problem (work merges with plain git, no pull requests). `create_branch_if_missing(repo_path, branch, from)` ports `createBranchIfMissing` exactly: `git ls-remote` to check, `git fetch` plus `git push origin/<from>:refs/heads/<branch>` to create it, left alone if it already exists. `backlog_on_origin(repo_path, base_branch, backlog_path)` is this bullet's own "backlog file that isn't on `origin/<baseBranch>`" check (no separate function in the TypeScript agent to port it from): `git cat-file -e origin/<baseBranch>:<backlogPath>`. `repo_problems` turns an already-gathered `RepoCheck` into this bullet's own wording. Nothing in this crate calls `repo` yet, the same as `scan`'s own note below: picking it up for an actual new project needs the cloud link and the orchestrator loop (milestones 4 and 5 of [11-build-milestones.md](11-build-milestones.md)) to reach this agent at all, and the GitHub-repo-listing and checkout UI itself is the Expo app's Setup screen — still a later piece, not a further slice of this item, the same as the pool/orchestrator's job in [07.2-local-model.md](07.2-local-model.md) section 7.2.
  - **[Proposal] Slices for the rest of project setup**, in order:
    1. *GitLab and a plain git remote.* `repo_info`, `remote_repo`, `list_owners`/`list_repos` and `clone_repo` learn `glab` (the code host's CLI, `glab repo view`, `glab repo list`, `glab repo clone`) and a plain git remote (any other `origin` URL: `git ls-remote` and `git clone`, no pull requests, no owner list). `remote_repo` parses GitLab HTTPS and SSH URLs. A plain remote has no `githubRepo`; `repo_problems` says so in its own words instead of "no GitHub remote".
    2. *A local-only project.* A folder with no `origin` at all is accepted for what the TypeScript agent allows it, with the work staying on the computer; `repo_problems` stops listing a missing remote as a problem for it. It still has the shared backlog (the store is reached or setup fails closed).
    3. *The picker's caching and the clone lock.* `list_owners` and `list_repos` are cached for a short time (60 seconds) and refreshed on demand; two clones at once of the same repo are serialised by a lock so the second finds the first's checkout instead of cloning again (`GithubPicker`).
    Acceptance: a GitLab repo and a plain remote each give `repo_info`, a checkout and the right `repo_problems`; a folder with no remote is accepted as local-only; the second of two simultaneous clones does not run `clone`.
- **The scan.** A guess at the project type (Game, Web app, Server / API, CLI / library or Other — `game`, `web`, `server`, `cli`, `other` in the config, [project-types.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/project-types.md)), the suggested checks (tests blocking; lint and format non-blocking, because a repo that isn't clean yet would otherwise block every PR), a suggested `playCommand` (for npm a `launch` script ahead of `start`), whether `.github/workflows` exists, and, with team-branch, whether the picked base branch is covered by the workflows' `pull_request` triggers ([team-branch.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/team-branch.md) section 3.4). The scan only reads files already on disk at the branch it checks out (the manifests, lockfiles and workflow YAML; never a sibling folder outside the repo, section 4.1); it runs no script and starts no build, since nothing has been approved yet. **[Proposal]** It runs once, from whatever checkout Setup already has (the local folder, or a fresh clone when the repo came from `gh repo list`) — never in a lane, since a project's lanes don't exist until its config does (section 4). A later **Link project** re-send, or the person pressing a "look again" action on the Setup screen, re-runs the same scan on the base branch's current tip; nothing re-scans on its own.
  - **In this Rust agent**, `src/scan.rs` ports `detectProjectType` and `detectChecks` (`agent/src/setup.ts`) above the type and the checks/play-command halves of the scan. `detect_project_type(repo)` reads the repo's own `Cargo.toml`, `package.json` (and its npm workspaces', root first), `project.godot`/`ProjectSettings`, `wrangler.toml`/`wrangler.jsonc` and `Dockerfile`, first match wins: a game crate (`bevy`, `macroquad`, `ggez`, `piston`) or a Godot project file is Game; a web dependency (`vite`, `next`, `react`, `vue`, `svelte`, `@angular/core`) is Web app; a server dependency (`express`, `fastify`, `koa`, `hono`), a Wrangler config or a Dockerfile with an `EXPOSE` is Server / API; a `package.json` `bin` field or a `Cargo.toml` `[[bin]]` is CLI / library; anything else is Other. `detect_checks(repo)` suggests `cargo test` (blocking), `cargo clippy --all-targets` and `cargo fmt --check` (both non-blocking) and `cargo run --release` to play for a Cargo project; for an npm one, a check per `typecheck`/`test`/`lint` script the root `package.json` has (typecheck and test blocking, lint not) and `npm run launch` ahead of `npm start` to play. `scan::has_workflows(repo)` is `suggest`'s `hasWorkflows`: whether the checkout has any `.yml`/`.yaml` file under `.github/workflows`. Whether the *picked* base branch's workflows actually cover it ([team-branch.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/team-branch.md) section 3.2) is `crate::ci_coverage` instead, ported from `ciCoverage`/`readOn` in `agent/src/ciCoverage.ts`: `ci_coverage(workflows, base_branch)` is the pure covered/not_covered/none/unknown table over workflow files already read, and `read_workflows(repo, git_ref)` reads them from a git ref with `git ls-tree`/`git show` (so it can read `origin/<branch>` once that remote exists, not only the checkout). `ci_warning(coverage, base_branch)` is Setup's warning text (section 3.4) for `not_covered`. Only the GitHub-workflows half is ported: Woodpecker and GitLab CI, which the TypeScript `ciCoverage` also answers `covered` for, aren't, since this agent doesn't support those code hosts yet. Nothing in this crate calls `scan` or `ci_coverage` yet: picking them up for an actual new project needs the cloud link and the orchestrator loop (milestones 4 and 5 of [11-build-milestones.md](11-build-milestones.md)) to reach this agent at all — still a later piece, not a further slice of this item, the same as the pool/orchestrator's job in [07.2-local-model.md](07.2-local-model.md) section 7.2.
  - **[Proposal]** The project type is the first of these that matches, read from whichever manifests sit at the repo's root (not a sub-folder's): a game engine named in `Cargo.toml` (`bevy`, `macroquad`, `ggez`) or `package.json` (`phaser`, `three`, `pixi.js`, `@godot`) or a `project.godot` file → **Game**; failing that, a browser-facing framework in `package.json` (`react`, `vue`, `next`, `expo`, `vite`) or a root `index.html` with no server framework alongside it → **Web app**; failing that, a server framework in `Cargo.toml` (`axum`, `actix-web`, `warp`, `tonic`) or `package.json` (`express`, `fastify`, `koa`) → **Server / API**; failing that, a `[[bin]]` in `Cargo.toml`, a `src/main.rs` with no web or server dependency, or a `bin` field in `package.json` → **CLI / library**; nothing above matching → **Other**. Two manifests at the root that would each name a different type (say a Rust binary beside a Node web app) still pick the first rule that matches, top to bottom. It is only ever a suggestion: Setup (the app's own screen) shows it filled in but changeable, and saving a different one never re-runs the scan.
  - **[Proposal]** Suggested checks come from the same manifests, one suggestion per toolchain found, never merged into one: a declared test command (`cargo test`, a `package.json` `test` script, `pytest` from a `pytest.ini`/`pyproject.toml`, `go test ./...` from a `go.mod`) is suggested blocking, except npm's own placeholder script (`echo "Error: no test specified" && exit 1`) counts as no script at all; a declared lint or format command (`cargo clippy -- -D warnings`, `cargo fmt --check`, an `eslint` or `prettier --check` script) is suggested non-blocking, same reasoning as today (a repo that isn't clean yet shouldn't block every PR on it). A repo with both a `Cargo.toml` and a `package.json` at its root (a Rust game with a web-based editor, say) gets both toolchains' suggestions, and the person on Setup keeps, drops or edits each on its own.
  - **[Proposal]** The suggested `playCommand` tries, per toolchain, in order, the first that exists: for npm, a `launch` script, then `start`, then `dev`; for Cargo, a binary named `play` (`cargo run --release --bin play`), else the crate's own default binary (`cargo run --release`) when `[[bin]]` or `src/main.rs` is there. Nothing found leaves `playCommand` blank for the person to fill in; it's never guessed for a project typed **CLI / library**, where "play" doesn't apply.
- **The sandbox.** Whether Claude Code's sandbox is available here. `auto` uses it when it is. **[Proposal]** Checked once, by what the platform is: available on macOS and Linux, never on native Windows (04-architecture.md section 4.2) — no command is run to probe for it, since whether it's offered at all doesn't depend on this repo.
- **A repo's existing backlog file.** Read once; the agent sends its rows to the shared store ([backlog.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/backlog.md) section 8.3). A project's work then comes only from the store: the agent fails closed when it can't reach it.
- **Galleries.** Each has a tab name, a command and an output folder (section 6.8). A gallery's slug (its name in kebab case) names its tab, its folder and its routes, so a name that makes the slug of **Releases**, the same slug as another gallery's, or an empty one is refused (`galleryErrors` in `shared/galleries.ts`).
- **Checks and Play.** The commands are the project's own, held on the server and approved by the computer's owner before they run (section 8). Run Lighthouse daily is [daily-lighthouse.md](../daily-lighthouse.md).

**[Proposal]** Everything in the scan is a suggestion, never a decision: the computer sends its guesses once, alongside what it's certain of (the repo, whether `.github/workflows` exists), and Setup is free to show, pre-fill and let the person override every one of them before saving. A scan that finds nothing for a field (no `playCommand`, an **Other** project type) sends it empty or as **Other** rather than guessing past what the files say.

The settings themselves, who may change them and what the screens show are the site's and the app's.
