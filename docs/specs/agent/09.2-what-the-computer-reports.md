### 9.2 What the computer reports

Most of it goes into the snapshot over the cloud link; the app draws it. Two bullets below are local-only routes instead, read by the settings page and the tray, never sent to the cloud.

- **Sessions.** Per active session: the role (planner, implementer, scout, reviewer or writer), the model, the lane, the item, the elapsed time, the cost so far, and the last ~20 streamed events as readable lines (`Bash: cargo test`, `Edit: src/foo.rs`, assistant text). A Cursor session reports no cost ([engines.md](../engines.md) section 7). The live events of a session the site is watching go out over the same link, and a session's transcript is never stored in the cloud.
- **Usage.** The 5-hour and weekly windows as section 7.1 reads them, the reset times, "local down" while the local server isn't answering, and the reason for the current concurrency when auto concurrency is on.
- **The orchestrator.** Setup, running, paused (and why: by hand, the daily budget reached, or a new setup not yet resumed), or waiting for the limit with its reset time; the staging smoke's one line when the project has one (section 6.3).
- **What looks wrong** ([agent-telemetry.md](../agent-telemetry.md) section 4.1). The watchdog's warning lines, each with since when, and the one that names an item.
- **A gallery.** Its picture count, when and from which commit it was taken, the command, and a failed shoot's last output.
- **Restart progress** ([restart-progress.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/restart-progress.md)). Who asked and when, what it finishes first ("finishing a merge first"), and for 10 minutes after it is back, when it restarted.
- **Rust (this agent).** `src/link/` links in the terminal (`retaskable link [production|staging|local]`, the device flow of `agent/src/link.ts`) and keeps one access token per cloud, the refresh token in the OS credential store or, with none, `credentials.json` in the data folder. `src/connector/` connects to each of the three environments' clouds and a custom `cloud.url`, one socket per project (the agent's own hub before Setup), and sends hello, a snapshot and `alive`. Its snapshot holds the machine, a real `galleries` list ([`galleries::info`], tray.md section 5.3.1), the orchestrator block, the lanes list and the trial plan, and is otherwise a stub: `src/view.rs` hard-codes `usage: {}` apart from (with `snapshot-reporting` On) the windows below, `localDown` and, once auto concurrency has stepped, `autoConcurrency: { allowed, reason }` (section 7.1), `sessions: []`, `drafts: []` and `asks: []`, and, with the `snapshot-reporting` release flag Off or for a project whose loop isn't running (orchestrator mode off), a project's status is paused with the reason "This computer's agent doesn't run work yet." (`NO_WORK_YET`) unless a person's pause set another. With the flag On (`HelloSettings::snapshot_reporting_on`, read from the last answer), `AgentView` holds the loop's `LiveHandle` and the orchestrator block (`src/view/orchestrator.rs`) reports `running`, `paused` with the person's reason (`PauseState`), or `waiting_for_limit` with `resetsAt` when the loop can't start work because Claude is at its usage limit or the weekly cutoff (`ProjectLive.limit_resets_at`, set by the machine's pass from `EngineLimits`), plus `concurrency`, the number the shared pool allows (auto concurrency's once it has stepped). A change in those fields (`LiveHandle::subscribe`) sends the snapshot again over an open connection, waiting a few seconds so a burst of changes sends one; a pass that changes none sends nothing. Filling these from what the loop holds is the existing item `snapshot-reporting` (with `live-sessions-reporting` for `sessions`); until then the site sees an idle computer. `src/commands.rs` checks every command the hub sends in the order section 6.2 of cloud.md gives (replay, expiry, Setup done), then runs it if it's Restart, Pause, Resume or Shoot (section 9.3) and refuses it with a `nack` otherwise. With `snapshot-reporting` On, each lane a project's loop holds (`ProjectLive.held`: lane, item id, branch from the item's run record, and whether its game runs) gives the lanes list its `itemId`, `branch` and `playing`, a lane held past `lanes` after it was lowered is listed until it finishes, and `mainPlaying` is true while Play main runs (`play::running`); a change in the held lanes, or Play main starting or stopping from a command, sends the snapshot again. With the flag Off the lanes list has no work and `mainPlaying` is false. With `snapshot-reporting` On, `items` lists the items the project's loop holds a lease on (`ProjectLive.items`, copied each pass from the backlog read: id, title, state, lane, branch, `prUrl`, attempt, `chore`), an item given back leaves on the next pass, and `milestones` is `[{ id: "chores", title: "Chores" }]` while a chore is held and empty otherwise; with the flag Off both are empty, and a change in the held items sends the snapshot again. With `snapshot-reporting` On, `src/view/cursor.rs` adds `usage.cursor` to the snapshot: `{ todayTokens, weekInputTokens, weekOutputTokens, limitHitAt? }` from `MachineStore` (`cursor_today_tokens`, `cursor_week_tokens` over the rolling 7 local days, today included, input and output apart, and `cursor_limit_at` as an ISO time), absent until a Cursor session has reported tokens; the machine file keeps 7 local days of each. With `snapshot-reporting` On, the snapshot's `smoke` is the project's `State.smoke` (`AgentView::smoke_json`): `{ sha, status, at, url }`, plus `tail` only for a failure or timeout, and left out when the project has none; saving a state that holds a smoke (`Store::save`, signalled by `subscribe_smoke_changes`) sends the snapshot again.
- **The computer's link state — local only.** Whether it is linked to retaskable.com and to the shared backlog, as the tray's menu and the Profile dialog show it ([tray.md](../tray.md) section 4): `GET /api/link` (`LinkView`) and `GET /api/backlog/link`. It's a plain route, not in the State: it is never sent to the cloud (not in the snapshot, no command carries it).
  - **In this Rust agent**, `GET /api/link` behind the settings page's session (section 8) is `settings_server::link_view`: the three environments of `src/link::ENVIRONMENTS` plus a custom `cloud.url` when one is set (`link::cloud_urls`), each with its `environment_name` and whether this machine already holds a stored refresh token for it (`keychain.get(url)`, the same `TokenStore` `src/link/` keeps). The in-progress "Waiting: code" state isn't here: only the `retaskable link` terminal command tracks it, in a process that exits once it's done, so there's nothing for a running agent to read it from. `GET /api/backlog/link` isn't ported: the shared backlog's own device-link flow (`shared-backlog-auto-link`, `BacklogLink.autoLink()`) isn't built in this agent yet, so there's no link state for that route to report.
  - **[Proposal] Slice for `GET /api/backlog/link`.** The route behind the settings page's session returns the shared backlog's link state: `{ linked, url, waiting }` (whether the keychain holds a token for `backlog::url`, the store's address, and whether a device-link code is waiting, with its approval URL while one is). `backlog::unlinked_on_site()` is the in-memory `unlinkedOnSite` flag (`BacklogStore.unlinkedOnSite()`): set when a store call with the backlog's own token answers `invalid_grant`, cleared by a link (`auto_link` approved, or `retaskable link backlog`), never saved, and `auto_link` does not start the flow while it is set. Like `GET /api/link`, it is never sent to the cloud. Acceptance: unlinked, the route says `linked: false`; with a code waiting it gives the approval URL; after linking it says `linked: true`; a test covers `invalid_grant` setting the flag.
- **Who the agent works as — local only.** There is no sign-in of its own: it works as whoever `gh` is signed in as on this machine (section 3.1), read with `gh api user` (`login`, `name`, `avatar_url`, kept only if `https://`) behind `GET /api/profile`, asked again on a fresh read (`?fresh=1`) so a `gh auth switch` shows up without a restart. A failed read says why ("gh isn't signed in: run `gh auth login`"). Like the link state above, it's a plain route: never sent to the cloud (not in the snapshot, no command carries it).
  - **In this Rust agent**, `src/profile.rs` ports this bullet's `gh api user` read: `profile::read()` calls it fresh every time and parses `login`, `name` and an `avatar_url` kept only when it's `https://`, or [`profile::NOT_SIGNED_IN`] when `gh` can't answer. `GET /api/profile` behind the settings page's session wraps it as `{ signedIn, login, name, avatarUrl }` or `{ signedIn: false, error }`. There's no cache here for `?fresh=1` to bypass, so the query string changes nothing and the route doesn't inspect it.

- **Sessions count (this Rust agent, item `live-sessions-reporting`).** The cloud tick's `sessions` field is the number of sessions running now across every project, as the TS tick sends it. It is still always 0. It is the same number the settings page's Now tab lists ([agent-settings.md](../agent-settings.md) section 4.5).

- **Today's spend (this Rust agent, behind the `snapshot-reporting` flag).** When a session ends with a `cost_usd` above 0 (Claude, Codex or pi; Cursor reports none), `record_session_end` (`src/orchestrator/live/sessions.rs`) adds it to that project's total for the local day in machine.json under `spend` (`MachineStore::add_spend`, `{ project: { "Y-M-D": usd } }`, the last 7 days kept), under the same write lock as the token counts and whether or not `engine-limit-records` is On. With `snapshot-reporting` On the snapshot's orchestrator block carries `spendTodayUsd` (the project's today on this computer) and `dailyUsd` (the machine's `budget.dailyUsd`); Off, neither. This only reports: it adds no daily-budget stop.
