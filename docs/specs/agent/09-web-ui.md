## 9. What the app and site ask of the computer

The agent has no UI. The only screen is the Expo app in `app/` ([expo.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/expo.md)): retaskable.com serves its web build, phones run it in Expo Go, and nothing on this computer serves it (no-local-ui, [tray.md](../tray.md) section 6.1). The app's screens, where each lives and the words on them (the everyday words of [plain-language.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/plain-language.md) section 5) are the app's own specs, not this one. The agent's port serves only `GET /api/health` and the computer's own settings page (section 8).

This section is what the computer still does for those screens: what it works out and reports, and the work it runs when a command from the site asks. Each of the old dashboard's tabs, menus and dialogs (the Roadmap board, the Inbox and its filters, the bell, the chat window, the usage meters, the Profile dialog, the Flow view, the Releases tab's editor, the header and its chips) now belongs to the app and the hub, and is not described here.

**Words a model writes for the person** follow the same plain-language rule: `prompts/drafter.md`, `implementer.md`, `reviewer.md` and `assistant.md` each end with a short closing rule, so a draft's summary, a question, a try-out's what and steps, and a chat answer are short everyday words, while the spec files the drafter writes stay precise ([plain-language.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/plain-language.md) section 7).

**Images.** Every command that sends text to Claude (Ask Claude, Add spec, Send back, question answers, playtest problems, Continue and Start over notes, gallery feedback) can carry images. The agent saves them under `.retaskable/attachments/` and adds their paths after the text (section 8).

### 9.1 What the computer works out for a project's settings

Setting a project up is the site's project settings ([project-settings-on-server.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/project-settings-on-server.md)); the computer supplies what only it can see:

- **The repo.** A local folder, or one of the person's (and their GitHub organisations') repos from `gh repo list`, with the checkout found or cloned. `githubRepo` comes from the `origin` remote with `gh repo view --json nameWithOwner`. It reports why a folder won't do: not a git repo, no GitHub remote, `gh` not authenticated, the integration branch (`dev/<login>`, `develop`) couldn't be created, a backlog file that isn't on `origin/<baseBranch>`. Saving creates the integration branch when the pattern says to and it isn't on origin yet ([github-workflow.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/github-workflow.md)).
  - **In this Rust agent**, `src/repo.rs` ports the plain-GitHub half of `agent/src/setup.ts`'s `repoInfo`/`githubLogin`/`devBranch`/`createBranchIfMissing` and `agent/src/github.ts`'s `listOwners`/`listRepos`/`remoteRepo`: GitLab, a plain git remote, a local-only project and the full `GithubPicker`'s caching and clone-serialising lock aren't ported, since this agent's trimmed spec doesn't reach them yet. `repo_info(repo_path)` is `gh repo view --json nameWithOwner,defaultBranchRef,isFork,parent` over `origin`, with a fork's upstream read the same way `repoInfo`/`upstreamOf` do. `github_login()` and `gh_authenticated()` read `gh api user`/`gh auth status`; `list_owners()` adds the person's GitHub organisations from `gh api user/memberships/orgs`, and `list_repos(owner)` is `gh repo list`. `find_checkout(search_dir, github_repo)` looks for an already-cloned sibling by its `origin` remote (`remote_repo`, pure, parses a GitHub HTTPS or SSH URL), and `clone_repo` is `gh repo clone` when none is found. `create_branch_if_missing(repo_path, branch, from)` ports `createBranchIfMissing` exactly: `git ls-remote` to check, `git fetch` plus `git push origin/<from>:refs/heads/<branch>` to create it, left alone if it already exists. `backlog_on_origin(repo_path, base_branch, backlog_path)` is this bullet's own "backlog file that isn't on `origin/<baseBranch>`" check (no separate function in the TypeScript agent to port it from): `git cat-file -e origin/<baseBranch>:<backlogPath>`. `repo_problems` turns an already-gathered `RepoCheck` into this bullet's own wording. Nothing in this crate calls `repo` yet, the same as `scan`'s own note below: picking it up for an actual new project needs the cloud link and the orchestrator loop (milestones 4 and 5 of [11-build-milestones.md](11-build-milestones.md)) to reach this agent at all, and the GitHub-repo-listing and checkout UI itself is the Expo app's Setup screen — still a later piece, not a further slice of this item, the same as the pool/orchestrator's job in [07-orchestrator-loop.md](07-orchestrator-loop.md) section 7.2.
- **The scan.** A guess at the project type (Game, Web app, Server / API, CLI / library or Other, [project-types.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/project-types.md)), the suggested checks (tests blocking; lint and format non-blocking, because a repo that isn't clean yet would otherwise block every PR), a suggested `playCommand` (for npm a `launch` script ahead of `start`), whether `.github/workflows` exists, and, with team-branch, whether the picked base branch is covered by the workflows' `pull_request` triggers ([team-branch.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/team-branch.md) section 3.4).
  - **In this Rust agent**, `src/scan.rs` ports `detectProjectType` and `detectChecks` (`agent/src/setup.ts`) above the type and the checks/play-command halves of the scan. `detect_project_type(repo)` reads the repo's own `Cargo.toml`, `package.json` (and its npm workspaces', root first), `project.godot`/`ProjectSettings`, `wrangler.toml`/`wrangler.jsonc` and `Dockerfile`, first match wins: a game crate (`bevy`, `macroquad`, `ggez`, `piston`) or a Godot project file is Game; a web dependency (`vite`, `next`, `react`, `vue`, `svelte`, `@angular/core`) is Web app; a server dependency (`express`, `fastify`, `koa`, `hono`), a Wrangler config or a Dockerfile with an `EXPOSE` is Server / API; a `package.json` `bin` field or a `Cargo.toml` `[[bin]]` is CLI / library; anything else is Other. `detect_checks(repo)` suggests `cargo test` (blocking), `cargo clippy --all-targets` and `cargo fmt --check` (both non-blocking) and `cargo run --release` to play for a Cargo project; for an npm one, a check per `typecheck`/`test`/`lint` script the root `package.json` has (typecheck and test blocking, lint not) and `npm run launch` ahead of `npm start` to play. `scan::has_workflows(repo)` is `suggest`'s `hasWorkflows`: whether the checkout has any `.yml`/`.yaml` file under `.github/workflows`. Whether the *picked* base branch's workflows actually cover it ([team-branch.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/team-branch.md) section 3.2) is `crate::ci_coverage` instead, ported from `ciCoverage`/`readOn` in `agent/src/ciCoverage.ts`: `ci_coverage(workflows, base_branch)` is the pure covered/not_covered/none/unknown table over workflow files already read, and `read_workflows(repo, git_ref)` reads them from a git ref with `git ls-tree`/`git show` (so it can read `origin/<branch>` once that remote exists, not only the checkout). `ci_warning(coverage, base_branch)` is Setup's warning text (section 3.4) for `not_covered`. Only the GitHub-workflows half is ported: Woodpecker and GitLab CI, which the TypeScript `ciCoverage` also answers `covered` for, aren't, since this agent doesn't support those code hosts yet. Nothing in this crate calls `scan` or `ci_coverage` yet: picking them up for an actual new project needs the cloud link and the orchestrator loop (milestones 4 and 5 of [11-build-milestones.md](11-build-milestones.md)) to reach this agent at all — still a later piece, not a further slice of this item, the same as the pool/orchestrator's job in [07-orchestrator-loop.md](07-orchestrator-loop.md) section 7.2.
- **The sandbox.** Whether Claude Code's sandbox is available here. `auto` uses it when it is.
- **A repo's existing backlog file.** Read once; the agent sends its rows to the shared store ([backlog.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/backlog.md) section 8.3). A project's work then comes only from the store: the agent fails closed when it can't reach it.
- **Galleries.** Each has a tab name, a command and an output folder (section 6.8). A gallery's slug (its name in kebab case) names its tab, its folder and its routes, so a name that makes the slug of **Releases**, the same slug as another gallery's, or an empty one is refused (`galleryErrors` in `shared/galleries.ts`).
- **Checks and Play.** The commands are the project's own, held on the server and approved by the computer's owner before they run (section 8). Run Lighthouse daily is [daily-lighthouse.md](../daily-lighthouse.md).

The settings themselves, who may change them and what the screens show are the site's and the app's.

### 9.2 What the computer reports

All of it goes into the snapshot over the cloud link; the app draws it.

- **Sessions.** Per active session: the role (planner, implementer, scout, reviewer or writer), the model, the lane, the item, the elapsed time, the cost so far, and the last ~20 streamed events as readable lines (`Bash: cargo test`, `Edit: src/foo.rs`, assistant text). A Cursor session reports no cost ([engines.md](../engines.md) section 7). The live events of a session the site is watching go out over the same link, and a session's transcript is never stored in the cloud.
- **Usage.** The 5-hour and weekly windows as section 7.1 reads them, the reset times, "local down" while the local server isn't answering, and the reason for the current concurrency when auto concurrency is on.
- **The orchestrator.** Setup, running, paused (and why: by hand, the daily budget reached, or a new setup not yet resumed), or waiting for the limit with its reset time; the staging smoke's one line when the project has one (section 6.3).
- **What looks wrong** ([agent-telemetry.md](../agent-telemetry.md) section 4.1). The watchdog's warning lines, each with since when, and the one that names an item.
- **A gallery.** Its picture count, when and from which commit it was taken, the command, and a failed shoot's last output.
- **Restart progress** ([restart-progress.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/restart-progress.md)). Who asked and when, what it finishes first ("finishing a merge first"), and for 10 minutes after it is back, when it restarted.
- **The computer's link state.** Whether it is linked to retaskable.com and to the shared backlog, as the tray's menu shows it ([tray.md](../tray.md) section 4).
- **Rust (this agent).** `src/link/` links in the terminal (`retaskable link [production|staging|local]`, the device flow of `agent/src/link.ts`) and keeps one access token per cloud, the refresh token in the OS credential store or, with none, `credentials.json` in the data folder. `src/connector/` connects to each of the three environments' clouds and a custom `cloud.url`, one socket per project (the agent's own hub before Setup), and sends hello, a snapshot and `alive`. Its snapshot holds the machine and empty lists, with the orchestrator in Setup before the first project and paused after, since this agent runs no work yet. It refuses every command with a `nack`.
- **Who the agent works as.** There is no sign-in of its own: it works as whoever `gh` is signed in as on this machine (section 3.1), read with `gh api user` (`login`, `name`, `avatar_url`, kept only if `https://`) and asked again on a fresh read so a `gh auth switch` shows up without a restart. A failed read says why ("gh isn't signed in: run `gh auth login`").

### 9.3 What the computer does when a command asks

- **Continue and Start over** on an item that stopped (`needs_human`). Notes work like the triager's `instructions` (section 6.9): Continue with notes sends them as the implementer's next message and puts the item back to `implementing` on its branch; Start over puts them in the new attempt's first prompt. Continue without notes just re-runs the checks. With nothing on a branch to carry on from (no PR, and no session to resume: it stopped before either, say on a prompt it couldn't fill), a person's Continue starts the slice again as Start over would, notes and all, since there's nothing to lose (`continueItem`, `agent/src/orchestratorActions.ts`; the triager's does the same, section 6.9). Notes go into transcripts and the PR's history, so they must not hold secrets.
- **Shoot** runs the gallery's command and keeps the pictures (section 6.8). **Play** and **Play on phone** run the project's own command ([play-on-phone.md](../play-on-phone.md)).
- **Pause and Resume.** What stops and what carries on while paused are as in sections 6.6 and 7; a pause stops chat, spec drafts and the planner too. On a shared backlog there are two pauses ([team-state-on-server.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/team-state-on-server.md) section 3.1): the store's, for every computer on the project, which the agent obeys, and this computer's own, which it keeps. The agent reports which is on ("Paused by @james for everyone", "This computer is paused").
- **Restart.** Runs at once (section 4.2: now, finishing a merge first), exiting with code 75 for the supervisor or a release build to start it again (section 8).
- **Release notes.** A read-only **release notes** session (role `writer`, the scouts' tier or the local model when it's free, budget `budget.releaseNotesUsd`, prompt `prompts/release-notes.md`, interactive like an ask) writes the words for the PRs merged in a range, found with `gh pr list --state merged --search merged:…` and `git log --first-parent`, and returns `RELEASE_NOTES_RESULT_SCHEMA`: `{ status, title, summary, highlights: [{ key, headline, text }], entries: [{ key, text }], error? }`. It picks the 3 to 5 highlights and writes the words, but can't add an entry or show a chore. The agent asks the store for what may go in and where the note is kept and published ([release-notes.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/release-notes.md), `releases_get`, `release_set`); it does not decide them.
- **Ideas** ([manual.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/manual.md) section 5.1). After a slice merges (at most once a day), a read-only `writer` session (`itemId` `_ideas`, prompt `prompts/ideas.md`, budget `budget.scoutUsd`, on the scouts' tier) writes up to three ideas from what went live, the questions asked and the owner's past answers. The ideas, their queue and the owner's answers are in the store (`ideas_list`); the agent keeps no copy ([last-local-state.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/last-local-state.md) section 7).
