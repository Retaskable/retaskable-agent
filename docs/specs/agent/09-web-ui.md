## 9. What the app and site ask of the computer

The agent has no UI. The only screen is the Expo app in `app/` ([expo.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/expo.md)): retaskable.com serves its web build, phones run it in Expo Go, and nothing on this computer serves it (no-local-ui, [tray.md](../tray.md) section 6.1). The app's screens, where each lives and the words on them (the everyday words of [plain-language.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/plain-language.md) section 5) are the app's own specs, not this one. The agent's port serves only `GET /api/health` and the computer's own settings page (section 8).

This section is what the computer still does for those screens: what it works out and reports, and the work it runs when a command from the site asks. Each of the old dashboard's tabs, menus and dialogs (the Roadmap board, the Inbox and its filters, the bell, the chat window, the usage meters, the Profile dialog, the Flow view, the Releases tab's editor, the header and its chips) now belongs to the app and the hub, and is not described here.

**Words a model writes for the person** follow the same plain-language rule: `prompts/drafter.md`, `implementer.md`, `reviewer.md` and `assistant.md` each end with a short closing rule, so a draft's summary, a question, a try-out's what and steps, and a chat answer are short everyday words, while the spec files the drafter writes stay precise ([plain-language.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/plain-language.md) section 7).

**Images.** Every command that sends text to Claude (Ask Claude, Add spec, Send back, question answers, playtest problems, Continue and Start over notes, gallery feedback) can carry images. The agent saves them under `.retaskable/attachments/` and adds their paths after the text (section 8).

### 9.1 What the computer works out for a project's settings

Setting a project up is the site's project settings ([project-settings-on-server.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/project-settings-on-server.md)); the computer supplies what only it can see:

- **The repo.** A local folder, or one of the person's (and their GitHub organisations') repos from `gh repo list`, with the checkout found or cloned. `githubRepo` comes from the `origin` remote with `gh repo view --json nameWithOwner`. It reports why a folder won't do: not a git repo, no GitHub remote, `gh` not authenticated, the integration branch (`dev/<login>`, `develop`) couldn't be created, a backlog file that isn't on `origin/<baseBranch>`. Saving creates the integration branch when the pattern says to and it isn't on origin yet ([github-workflow.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/github-workflow.md)).
  - **In this Rust agent**, `src/repo.rs` ports the plain-GitHub half of `agent/src/setup.ts`'s `repoInfo`/`githubLogin`/`devBranch`/`createBranchIfMissing` and `agent/src/github.ts`'s `listOwners`/`listRepos`/`remoteRepo`: GitLab, a plain git remote, a local-only project and the full `GithubPicker`'s caching and clone-serialising lock aren't ported, since this agent's trimmed spec doesn't reach them yet. `repo_info(repo_path)` is `gh repo view --json nameWithOwner,defaultBranchRef,isFork,parent` over `origin`, with a fork's upstream read the same way `repoInfo`/`upstreamOf` do. `github_login()` and `gh_authenticated()` read `gh api user`/`gh auth status`; `list_owners()` adds the person's GitHub organisations from `gh api user/memberships/orgs`, and `list_repos(owner)` is `gh repo list`. `find_checkout(search_dir, github_repo)` looks for an already-cloned sibling by its `origin` remote (`remote_repo`, pure, parses a GitHub HTTPS or SSH URL), and `clone_repo` is `gh repo clone` when none is found. `create_branch_if_missing(repo_path, branch, from)` ports `createBranchIfMissing` exactly: `git ls-remote` to check, `git fetch` plus `git push origin/<from>:refs/heads/<branch>` to create it, left alone if it already exists. `backlog_on_origin(repo_path, base_branch, backlog_path)` is this bullet's own "backlog file that isn't on `origin/<baseBranch>`" check (no separate function in the TypeScript agent to port it from): `git cat-file -e origin/<baseBranch>:<backlogPath>`. `repo_problems` turns an already-gathered `RepoCheck` into this bullet's own wording. Nothing in this crate calls `repo` yet, the same as `scan`'s own note below: picking it up for an actual new project needs the cloud link and the orchestrator loop (milestones 4 and 5 of [11-build-milestones.md](11-build-milestones.md)) to reach this agent at all, and the GitHub-repo-listing and checkout UI itself is the Expo app's Setup screen — still a later piece, not a further slice of this item, the same as the pool/orchestrator's job in [07-orchestrator-loop.md](07-orchestrator-loop.md) section 7.2.
- **The scan.** A guess at the project type (Game, Web app, Server / API, CLI / library or Other — `game`, `web`, `server`, `cli`, `other` in the config, [project-types.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/project-types.md)), the suggested checks (tests blocking; lint and format non-blocking, because a repo that isn't clean yet would otherwise block every PR), a suggested `playCommand` (for npm a `launch` script ahead of `start`), whether `.github/workflows` exists, and, with team-branch, whether the picked base branch is covered by the workflows' `pull_request` triggers ([team-branch.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/team-branch.md) section 3.4). The scan only reads files already on disk at the branch it checks out (the manifests, lockfiles and workflow YAML; never a sibling folder outside the repo, section 4.1); it runs no script and starts no build, since nothing has been approved yet. **[Proposal]** It runs once, from whatever checkout Setup already has (the local folder, or a fresh clone when the repo came from `gh repo list`) — never in a lane, since a project's lanes don't exist until its config does (section 4). A later **Link project** re-send, or the person pressing a "look again" action on the Setup screen, re-runs the same scan on the base branch's current tip; nothing re-scans on its own.
  - **In this Rust agent**, `src/scan.rs` ports `detectProjectType` and `detectChecks` (`agent/src/setup.ts`) above the type and the checks/play-command halves of the scan. `detect_project_type(repo)` reads the repo's own `Cargo.toml`, `package.json` (and its npm workspaces', root first), `project.godot`/`ProjectSettings`, `wrangler.toml`/`wrangler.jsonc` and `Dockerfile`, first match wins: a game crate (`bevy`, `macroquad`, `ggez`, `piston`) or a Godot project file is Game; a web dependency (`vite`, `next`, `react`, `vue`, `svelte`, `@angular/core`) is Web app; a server dependency (`express`, `fastify`, `koa`, `hono`), a Wrangler config or a Dockerfile with an `EXPOSE` is Server / API; a `package.json` `bin` field or a `Cargo.toml` `[[bin]]` is CLI / library; anything else is Other. `detect_checks(repo)` suggests `cargo test` (blocking), `cargo clippy --all-targets` and `cargo fmt --check` (both non-blocking) and `cargo run --release` to play for a Cargo project; for an npm one, a check per `typecheck`/`test`/`lint` script the root `package.json` has (typecheck and test blocking, lint not) and `npm run launch` ahead of `npm start` to play. `scan::has_workflows(repo)` is `suggest`'s `hasWorkflows`: whether the checkout has any `.yml`/`.yaml` file under `.github/workflows`. Whether the *picked* base branch's workflows actually cover it ([team-branch.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/team-branch.md) section 3.2) is `crate::ci_coverage` instead, ported from `ciCoverage`/`readOn` in `agent/src/ciCoverage.ts`: `ci_coverage(workflows, base_branch)` is the pure covered/not_covered/none/unknown table over workflow files already read, and `read_workflows(repo, git_ref)` reads them from a git ref with `git ls-tree`/`git show` (so it can read `origin/<branch>` once that remote exists, not only the checkout). `ci_warning(coverage, base_branch)` is Setup's warning text (section 3.4) for `not_covered`. Only the GitHub-workflows half is ported: Woodpecker and GitLab CI, which the TypeScript `ciCoverage` also answers `covered` for, aren't, since this agent doesn't support those code hosts yet. Nothing in this crate calls `scan` or `ci_coverage` yet: picking them up for an actual new project needs the cloud link and the orchestrator loop (milestones 4 and 5 of [11-build-milestones.md](11-build-milestones.md)) to reach this agent at all — still a later piece, not a further slice of this item, the same as the pool/orchestrator's job in [07-orchestrator-loop.md](07-orchestrator-loop.md) section 7.2.
  - **[Proposal]** The project type is the first of these that matches, read from whichever manifests sit at the repo's root (not a sub-folder's): a game engine named in `Cargo.toml` (`bevy`, `macroquad`, `ggez`) or `package.json` (`phaser`, `three`, `pixi.js`, `@godot`) or a `project.godot` file → **Game**; failing that, a browser-facing framework in `package.json` (`react`, `vue`, `next`, `expo`, `vite`) or a root `index.html` with no server framework alongside it → **Web app**; failing that, a server framework in `Cargo.toml` (`axum`, `actix-web`, `warp`, `tonic`) or `package.json` (`express`, `fastify`, `koa`) → **Server / API**; failing that, a `[[bin]]` in `Cargo.toml`, a `src/main.rs` with no web or server dependency, or a `bin` field in `package.json` → **CLI / library**; nothing above matching → **Other**. Two manifests at the root that would each name a different type (say a Rust binary beside a Node web app) still pick the first rule that matches, top to bottom. It is only ever a suggestion: Setup (the app's own screen) shows it filled in but changeable, and saving a different one never re-runs the scan.
  - **[Proposal]** Suggested checks come from the same manifests, one suggestion per toolchain found, never merged into one: a declared test command (`cargo test`, a `package.json` `test` script, `pytest` from a `pytest.ini`/`pyproject.toml`, `go test ./...` from a `go.mod`) is suggested blocking, except npm's own placeholder script (`echo "Error: no test specified" && exit 1`) counts as no script at all; a declared lint or format command (`cargo clippy -- -D warnings`, `cargo fmt --check`, an `eslint` or `prettier --check` script) is suggested non-blocking, same reasoning as today (a repo that isn't clean yet shouldn't block every PR on it). A repo with both a `Cargo.toml` and a `package.json` at its root (a Rust game with a web-based editor, say) gets both toolchains' suggestions, and the person on Setup keeps, drops or edits each on its own.
  - **[Proposal]** The suggested `playCommand` tries, per toolchain, in order, the first that exists: for npm, a `launch` script, then `start`, then `dev`; for Cargo, a binary named `play` (`cargo run --release --bin play`), else the crate's own default binary (`cargo run --release`) when `[[bin]]` or `src/main.rs` is there. Nothing found leaves `playCommand` blank for the person to fill in; it's never guessed for a project typed **CLI / library**, where "play" doesn't apply.
- **The sandbox.** Whether Claude Code's sandbox is available here. `auto` uses it when it is. **[Proposal]** Checked once, by what the platform is: available on macOS and Linux, never on native Windows (04-architecture.md section 4.2) — no command is run to probe for it, since whether it's offered at all doesn't depend on this repo.
- **A repo's existing backlog file.** Read once; the agent sends its rows to the shared store ([backlog.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/backlog.md) section 8.3). A project's work then comes only from the store: the agent fails closed when it can't reach it.
- **Galleries.** Each has a tab name, a command and an output folder (section 6.8). A gallery's slug (its name in kebab case) names its tab, its folder and its routes, so a name that makes the slug of **Releases**, the same slug as another gallery's, or an empty one is refused (`galleryErrors` in `shared/galleries.ts`).
- **Checks and Play.** The commands are the project's own, held on the server and approved by the computer's owner before they run (section 8). Run Lighthouse daily is [daily-lighthouse.md](../daily-lighthouse.md).

**[Proposal]** Everything in the scan is a suggestion, never a decision: the computer sends its guesses once, alongside what it's certain of (the repo, whether `.github/workflows` exists), and Setup is free to show, pre-fill and let the person override every one of them before saving. A scan that finds nothing for a field (no `playCommand`, an **Other** project type) sends it empty or as **Other** rather than guessing past what the files say.

The settings themselves, who may change them and what the screens show are the site's and the app's.

### 9.2 What the computer reports

Most of it goes into the snapshot over the cloud link; the app draws it. Two bullets below are local-only routes instead, read by the settings page and the tray, never sent to the cloud.

- **Sessions.** Per active session: the role (planner, implementer, scout, reviewer or writer), the model, the lane, the item, the elapsed time, the cost so far, and the last ~20 streamed events as readable lines (`Bash: cargo test`, `Edit: src/foo.rs`, assistant text). A Cursor session reports no cost ([engines.md](../engines.md) section 7). The live events of a session the site is watching go out over the same link, and a session's transcript is never stored in the cloud.
- **Usage.** The 5-hour and weekly windows as section 7.1 reads them, the reset times, "local down" while the local server isn't answering, and the reason for the current concurrency when auto concurrency is on.
- **The orchestrator.** Setup, running, paused (and why: by hand, the daily budget reached, or a new setup not yet resumed), or waiting for the limit with its reset time; the staging smoke's one line when the project has one (section 6.3).
- **What looks wrong** ([agent-telemetry.md](../agent-telemetry.md) section 4.1). The watchdog's warning lines, each with since when, and the one that names an item.
- **A gallery.** Its picture count, when and from which commit it was taken, the command, and a failed shoot's last output.
- **Restart progress** ([restart-progress.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/restart-progress.md)). Who asked and when, what it finishes first ("finishing a merge first"), and for 10 minutes after it is back, when it restarted.
- **Rust (this agent).** `src/link/` links in the terminal (`retaskable link [production|staging|local]`, the device flow of `agent/src/link.ts`) and keeps one access token per cloud, the refresh token in the OS credential store or, with none, `credentials.json` in the data folder. `src/connector/` connects to each of the three environments' clouds and a custom `cloud.url`, one socket per project (the agent's own hub before Setup), and sends hello, a snapshot and `alive`. Its snapshot holds the machine, a real `galleries` list ([`galleries::info`], tray.md section 5.3.1) and otherwise empty lists, with the orchestrator in Setup before the first project and paused after, since this agent runs no work yet besides a shoot. `src/commands.rs` checks every command the hub sends in the order section 6.2 of cloud.md gives (replay, expiry, Setup done), then runs it if it's Restart, Pause, Resume or Shoot (section 9.3) and refuses it with a `nack` otherwise.
- **The computer's link state — local only.** Whether it is linked to retaskable.com and to the shared backlog, as the tray's menu and the Profile dialog show it ([tray.md](../tray.md) section 4): `GET /api/link` (`LinkView`) and `GET /api/backlog/link`. It's a plain route, not in the State: it is never sent to the cloud (not in the snapshot, no command carries it).
  - **In this Rust agent**, `GET /api/link` behind the settings page's session (section 8) is `settings_server::link_view`: the three environments of `src/link::ENVIRONMENTS` plus a custom `cloud.url` when one is set (`link::cloud_urls`), each with its `environment_name` and whether this machine already holds a stored refresh token for it (`keychain.get(url)`, the same `TokenStore` `src/link/` keeps). The in-progress "Waiting: code" state isn't here: only the `retaskable link` terminal command tracks it, in a process that exits once it's done, so there's nothing for a running agent to read it from. `GET /api/backlog/link` isn't ported: the shared backlog's own device-link flow (`shared-backlog-auto-link`, `BacklogLink.autoLink()`) isn't built in this agent yet, so there's no link state for that route to report.
- **Who the agent works as — local only.** There is no sign-in of its own: it works as whoever `gh` is signed in as on this machine (section 3.1), read with `gh api user` (`login`, `name`, `avatar_url`, kept only if `https://`) behind `GET /api/profile`, asked again on a fresh read (`?fresh=1`) so a `gh auth switch` shows up without a restart. A failed read says why ("gh isn't signed in: run `gh auth login`"). Like the link state above, it's a plain route: never sent to the cloud (not in the snapshot, no command carries it).
  - **In this Rust agent**, `src/profile.rs` ports this bullet's `gh api user` read: `profile::read()` calls it fresh every time and parses `login`, `name` and an `avatar_url` kept only when it's `https://`, or [`profile::NOT_SIGNED_IN`] when `gh` can't answer. `GET /api/profile` behind the settings page's session wraps it as `{ signedIn, login, name, avatarUrl }` or `{ signedIn: false, error }`. There's no cache here for `?fresh=1` to bypass, so the query string changes nothing and the route doesn't inspect it.

- **Sessions count (this Rust agent, item `live-sessions-reporting`).** The cloud tick's `sessions` field is the number of sessions running now across every project, as the TS tick sends it. It is still always 0. It is the same number the settings page's Now tab lists ([agent-settings.md](../agent-settings.md) section 4.5).

### 9.3 What the computer does when a command asks

- **Continue and Start over** on an item that stopped (`needs_human`). Notes work like the triager's `instructions` (section 6.9): Continue with notes sends them as the implementer's next message and puts the item back to `implementing` on its branch; Start over puts them in the new attempt's first prompt. Continue without notes just re-runs the checks. With nothing on a branch to carry on from (no PR, and no session to resume: it stopped before either, say on a prompt it couldn't fill), a person's Continue starts the slice again as Start over would, notes and all, since there's nothing to lose (`continueItem`, `agent/src/orchestratorActions.ts`; the triager's does the same, section 6.9). Notes go into transcripts and the PR's history, so they must not hold secrets.
- **Shoot** runs the gallery's command and keeps the pictures (section 6.8).
  - **In this Rust agent**, `src/commands.rs`'s Shoot finds the gallery by matching the command's `gallery` slug against the project's own `galleries` list (`GalleryConfig::slug`, its name in kebab case), runs `galleries::shoot_refusal`'s blank-command, bad-`outDir`, already-shooting and unknown-gallery checks, then spawns `galleries::shoot` on its own thread and acks at once, once it's started (tray.md section 5.3.3). The base checkout's own busy lock against the baseline, Play main or a sync isn't checked yet, since that lock doesn't exist in this agent (`src/lanes.rs`'s `base_checkout_path`; docs/specs/agent/06.8-galleries-the-game-photographs-itself.md); the backlog-store upload (item **galleries-in-store**) isn't ported either.
- **Play** and **Play on phone** run the project's own command ([play-on-phone.md](../play-on-phone.md)).
- **Pause and Resume.** What stops and what carries on while paused are as in sections 6.6 and 7; a pause stops chat, spec drafts and the planner too. On a shared backlog there are two pauses ([team-state-on-server.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/team-state-on-server.md) section 3.1): the store's, for every computer on the project, which the agent obeys, and this computer's own, which it keeps. The agent reports which is on ("Paused by @james for everyone", "This computer is paused").
  - **In this Rust agent**, `src/commands.rs` runs this computer's own pause only, one command naming `{ computer: true }`; without it the command is refused, since that pause is the shared backlog's, answered by retaskable.com itself without reaching a computer (`agent/src/commands.ts`'s `SITE_ANSWERS`). Pausing sets a reason (`"Paused from retaskable.com by <login>"`) and Resuming clears it, held per project in `view::PauseState` and sent in the project's `pausedReason`, resending the snapshot on either; nothing here yet stops chat, spec drafts or the planner, since none of those run in this agent, and the shared backlog's own pause isn't read, since there's no work loop yet to obey it — still later pieces, not further slices of this item.
- **Restart.** Runs at once (section 4.2: now, finishing a merge first), exiting with code 75 for the supervisor or a release build to start it again (section 8).
  - **The sequence (item `command-handling`; TS: [restart-progress.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/restart-progress.md) section 3.1).** One restart request runs these steps in order, and asking again while one is pending keeps the first request's `why` (`at`, `by`, `reason`).
    1. **Stop claiming new work.** Ticks start nothing new, and no `claim_next` is sent.
    2. **Let only these finish:** a merge, a plan's merge, an update to main, a promote, for 2 minutes at most. Sessions, checks, a shoot and a Play on phone build are not on the list.
    3. **Cancel the rest.** Every running session's tree is killed and ends `interrupted` (section 7.4), so each item keeps its lease and run record.
    4. **Restart** by exiting 75, after the same-tick answers are sent and the cloud link flushed (2 seconds at most).
    5. **Resume by session id.** After it starts, `readopt` resumes each interrupted session with "You were interrupted; continue."
  - The snapshot shows the step (`waiting` with what it still waits on, then `now`), as in restart-progress.md.
  - **In this Rust agent**, `src/commands.rs`'s Restart calls the same `exit(75)` the settings page's own restart button uses (`restart_handler` in `src/runtime.rs`), so it finishes an install and relaunch the same way.
- **Audit.** Every command checked, run or refused is logged (cloud.md section 6.3).
  - **In this Rust agent**, `src/commands.rs`'s `audit` writes one JSON line per command to `.retaskable/remote.log` (`{ at, id, name, issuedBy, args, outcome: "ack" | "nack", reason? (nacks only), cloud }`), called from `src/connector/mod.rs`'s `receive` right after a command is answered — a replay or an expired or pre-Setup command included, the same as one this agent runs. `answerBytes` and `auditArgs`'s per-command sanitising (`agent/src/commands.ts`) aren't ported, since none of the commands they apply to are; a write that fails is dropped silently, the same as the event log's ([agent-telemetry.md](../agent-telemetry.md) section 3).
- **Release notes.** A read-only **release notes** session (role `writer`, the scouts' tier or the local model when it's free, budget `budget.releaseNotesUsd`, prompt `prompts/release-notes.md`, interactive like an ask) writes the words for the PRs merged in a range, found with `gh pr list --state merged --search merged:…` and `git log --first-parent`, and returns `RELEASE_NOTES_RESULT_SCHEMA`: `{ status, title, summary, highlights: [{ key, headline, text }], entries: [{ key, text }], error? }`. It picks the 3 to 5 highlights and writes the words, but can't add an entry or show a chore. The agent asks the store for what may go in and where the note is kept and published ([release-notes.md](https://github.com/Retaskable/Retaskable.com/blob/main/docs/specs/release-notes.md), `releases_get`, `release_set`); it does not decide them.
  - **In this Rust agent**, `src/release_notes/` ports the gathering, grouping, prompt and rendering halves of `agent/src/releaseNotes.ts` and `shared/releaseNote.ts`. `gather` runs `gh pr list --state merged --base <branch> --search merged:<from>..<to>` and `git log --first-parent` over the range and reads each named spec at the base branch. `group` (over a `GroupInput`: the PRs, commits, the store's items and `drafts`, the specs' contents, and the repo and base branch) puts each merged PR under the backlog item that owns it (its `pr_url`, else the longest `retaskable/<id>-` branch prefix): one section per spec, in the order of its first item in the backlog and titled by the spec's first heading without a trailing "— Spec", then **Chores**, then **Other changes** (items with no spec, PRs no item owns, and commits pushed without a PR). An item's entry falls back to its PRs' titles joined with "; ", a chore's to its own title. A merged spec draft's PR (a store draft whose `prUrl` it is) goes under the spec it adds or edits, the first Markdown file it changed (`fill_draft_files` reads only a draft's PR's files, with `gh pr view <n> --json files`, since the store's draft doesn't keep them), as "Specced: <its titles>"; one that changed no Markdown file is another change. Each entry links its specs (`spec_links`): every Markdown file in the item's `spec_refs`, once, at `https://github.com/<repo>/blob/<base branch>/<path>`, labelled with its file name; the store's `specRefs` name whole files, so a link is to the file, not a section. Because this agent's `Item` carries less than the TypeScript one, chores are the `chores` milestone and share one section (no separate playtest-fixes section: the agent's own chores, `fix_playtest` among them, aren't in this crate), an item's spec is its first Markdown `spec_refs` entry, and "done" is its status alone (on main or in production). `for_users` leaves out the **Chores** section and every draft entry, so neither readers nor the model see them. `facts` is the JSON array of sections the prompt is built from, each entry with its item as `<id> <title>` and its status, its PRs' titles and bodies (cut to 600 characters), a commit's subject and its specs' labels (entries past `releaseFullEntries`, 120, are cut to their title, the smallest **Other changes** first), `build_prompt` fills `prompts/release-notes.md`, `release_notes_result_schema()` is `RELEASE_NOTES_RESULT_SCHEMA`, and `markdown` renders the note from the grouping and the model's answer (or, with none, from the facts alone): front matter, the title, then "Nothing new for users between … and …" when nothing is for the readers, else the summary, up to 5 highlights and **Also new** (**What's new** with no highlights). With no answer the highlights are the items that are done, headed by their titles. In **Also new** an item the model wrote no line for is listed by its title, and another change (a PR no item owns, a commit) shows only when the model wrote a line for it. Item ids never reach the note. `note_markdown` can also render a **Fixes** list, which `markdown` leaves empty while there's no playtest-fixes section. `empty_note` is the note for a range with nothing merged. `check_range` refuses a range that isn't two dates, runs backwards, or is in the future (To may be up to two days ahead, being the end of its day) and answers both ends as UTC instants. `write_note` picks the note: `empty_note` for nothing merged, the plain list when only chores merged (no session), and otherwise the read-only, ephemeral `writer` session (`writer_model`: `local` when the scouts' tier is, else `haiku`; `budget.releaseNotesUsd`; the facts' prompt; `RELEASE_NOTES_RESULT_SCHEMA`; the project's sandbox setting) run through the caller's `run_session`. Its answer becomes the note when `status` is `ok`; a session that fails, won't start or answers anything else leaves the plain list, with "Claude hit its $… budget …, so this is the plain list of what's new." (or "couldn't write them: …") as the note's error, and the session's model and cost kept either way.
